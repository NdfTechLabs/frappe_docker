# NDF Product Image Repositories and Tagging

## Scope

This document defines the registry naming and release-tag contract for NDF product images built from this repository. It is the M3.1 foundation; publishing automation and registry credentials are implemented in subsequent M3 work packages.

## Product repositories

Each independently released product has its own GHCR package:

- `dhanaerp-master-v16`: `ghcr.io/ndftechlabs/dhanaerp-master`
- `dalali-v16`: `ghcr.io/ndftechlabs/dalali`
- `vincowoods-v16`: `ghcr.io/ndftechlabs/vincowoods`

The image ID identifies the build definition and Frappe compatibility line. The repository identifies the independently distributed product. Do not add the framework major to the package name; it belongs in the image tags.

## Tag contract

The framework major is included in every release tag so multiple Frappe compatibility lines can coexist in one product package.

- **Stable latest — `v16-latest`:** Latest approved stable release for Frappe 16. Updated only by a product release.
- **Product semantic version — `v16-1.2.0`:** Immutable product release. Semantic versioning is independent for each product.
- **Source commit — `v16-<full-git-sha>`:** Immutable traceability tag for the exact source commit used to build the image.
- **CI validation — `ci-<run-id>-<attempt>`:** Temporary validation tag; never a release alias.

Examples:

- `ghcr.io/ndftechlabs/dalali:v16-1.2.0`
- `ghcr.io/ndftechlabs/dalali:v16-latest`
- `ghcr.io/ndftechlabs/dalali:v16-<full-git-sha>`

## Release rules

1. Product semantic versions are independent. Releasing Dalali does not require releasing DhanaERP Master or Vincowoods.
2. A product release is initiated by a product-specific Git tag, using `<product>-v<major>.<minor>.<patch>`, for example `dalali-v1.2.0`.
3. The release workflow checks out the exact tagged source, resolves and verifies the committed manifest lock, builds the image once, and publishes all release aliases from that same image digest.
4. The semantic-version tag, `v16-latest`, and full Git-SHA tag must resolve to the same manifest digest for a given release.
5. Existing semantic-version and full Git-SHA tags must never be overwritten. A release must fail if either tag already exists.
6. `v16-latest` is mutable by design and is advanced only when a newer stable product release is successfully published.
7. CI validation builds must not update release aliases or publish to production product repositories.
8. Production deployments should pin an image digest (`@sha256:...`) when reproducibility is required. Tags are discovery and release references, not a substitute for digest pinning.

## Publishing boundaries

- Pull requests: build and validate only; no GHCR publishing.
- Main branch validation: build and validate only until the M3 publishing workflow is explicitly introduced.
- Product release tags: publish only the selected product package after all release checks pass.
- No workflow may publish to upstream Frappe Docker namespaces or repositories.

## Required image traceability

Published images must retain the OCI and NDF labels already generated by the build tooling, including product/image ID, source repository, manifest checksum, lock checksum, Frappe framework reference, and immutable application commit references.

The release workflow must additionally attach or expose the source Git commit and release version. Registry digest and provenance/SBOM verification are part of later M3 publishing validation.

## Implementation status

This document defines the intended contract. It does not itself enable registry authentication, create GHCR packages, or publish images. Those are subsequent M3 work packages.

## Build output modes

The NDF build command supports local validation and explicit registry publishing through Docker Buildx.

Local builds are the default and load the result into the local Docker image store:

```bash
python images/ndf/scripts/build_image.py \
  --image dalali-v16 \
  --tag local-test \
  --platform linux/amd64
```

Registry publishing requires the explicit `--push` flag. Multiple tags are applied to the same build result:

```bash
python images/ndf/scripts/build_image.py \
  --image dalali-v16 \
  --tag v16-1.2.0 \
  --tag v16-latest \
  --tag v16-<full-git-sha> \
  --platform linux/amd64,linux/arm64 \
  --push
```

The command writes the Buildx metadata to `buildx-metadata.json` and a build summary to `build-result.json` in the selected build output directory. When Buildx provides it, the summary records the resulting image digest. Registry authentication is intentionally external to this command; the caller must authenticate before using `--push`.

Local `--load` builds are limited to one platform. Multi-platform builds require registry output via `--push`.
