## 1. Purpose and ownership

This package defines how an accepted PDD and its exact supporting evidence are published as a durable OCI artifact, how a consumer resolves the immutable artifact reference, and what DT Master must verify before accepting it.

Ownership remains separated:

- **NDF Frappe Docker** owns the PDD schema, generation, validation, evidence/image binding, publication format and publication workflow.
- **DT Master** owns acquisition of the publication receipt/reference, artifact retrieval, independent PDD validation, product/candidate compatibility decisions, trust policy, environment allocations and deployment authorization.
- **DT Tenant** is not a PDD consumer.
- This package does not implement the DT Master consumer, Bench Environment DocTypes, candidate-driven build workflow, signing/attestation or runtime orchestration.

The read-only audit in `M4.2.6.1-CONSUMER-CONTRACT-AUDIT.md` found no PDD consumer implementation on the inspected `dt_master@develop` tree. The target design in `NdfTechLabs/dt_master/docs/migrations/M4_BENCH_ENVIRONMENT_SCHEMA_AND_IMPLEMENTATION.md` Section 8 remains an architectural consumer contract, not evidence of implemented behavior.

## 2. Publication transport and layout

### 2.1 OCI artifact in the image repository

The PDD is published as a standalone OCI artifact in the **same GHCR repository as the image it describes**. For example:

- Subject image repository: `ghcr.io/ndftechlabs/dalali`
- Subject image digest: `sha256:<64-hex>`
- PDD artifact type: `application/vnd.ndf.product-deployment-descriptor.v1`
- PDD layer media type: `application/vnd.ndf.product-deployment-descriptor.v1+json`

The OCI artifact carries the PDD, the M4.2.6.5 binding report, all eleven PDD evidence files and the sidecars required to re-run the binding verifier. Files are separate OCI layers, with stable relative file names. The logical PDD lock path `lock-v2.json` is transported as the physical build artifact `<image-id>.lock-v2.json`, exactly as the M4.2.6.5 verifier expects.

The publication contains **16 unique files**:

- `product-deployment.json`;
- `binding-verification.json`;
- the eleven evidence files referenced by the PDD (including the physical image-specific lock-v2 file);
- the additional sidecars `build-result.json`, `image-validation.json` and `image-verification-evidence.json`.

`build-metadata.json` and `buildx-metadata.json` are already members of the eleven-file evidence set and are not duplicated.

The publisher verifies the PDD independently, reruns the full M4.2.6.5 evidence and registry binding verifier, compares the saved binding report with the fresh result, pushes the files, fetches the artifact by digest, pulls it back and compares the exact file inventory and bytes before writing a publication receipt.

### 2.2 Deterministic locator versus immutable reference

The publisher assigns a deterministic discovery tag:

```text
pdd-v1-<platform>-<subject-image-digest-hex>
```

Example shape:

```text
ghcr.io/ndftechlabs/dalali:pdd-v1-linux-amd64-<64-hex>
```

This tag is a **locator only**. OCI tags are mutable registry names and must not be treated as immutable identity. After publication, the authoritative artifact reference is:

```text
ghcr.io/ndftechlabs/dalali@sha256:<artifact-manifest-digest>
```

The publication receipt records this full digest-pinned reference. DT Master must persist and use that exact reference. It must not resolve the locator tag during deployment or silently substitute a later tag target.

The publisher uses create-once/idempotent semantics for the deterministic locator:

- if the locator is absent, publish the artifact and verify the result by digest;
- if it already exists, require the artifact type, all NDF annotations, descriptor identity and every published file byte to match the requested publication; otherwise fail closed;
- never overwrite a different descriptor or evidence bundle at an existing locator.

GHCR package write access must be restricted to the authorized NDF publication workflow/operators. The digest-pinned reference is the retrieval identity; the tag is not an authorization or trust boundary.

### 2.3 No dependency on OCI Referrers discovery

This contract deliberately does not require `oras discover` or the OCI Referrers API. The PDD artifact is directly addressable by its own manifest digest, and its manifest annotations bind it to the subject image digest and descriptor identity. This avoids making consumer correctness depend on referrer-discovery behavior or registry-specific support.

ORAS documents GHCR as an OCI-artifact-compatible registry and documents digest-addressed references, push/pull and artifact manifest metadata. See the [ORAS compatible registry list](https://oras.land/docs/compatible_oci_registries/), [ORAS push/pull guide](https://oras.land/docs/how_to_guides/pushing_and_pulling/) and [ORAS CLI documentation](https://oras.land/docs/commands/use_oras_cli/).

## 3. OCI artifact metadata

The artifact manifest uses:

- `artifactType`: `application/vnd.ndf.product-deployment-descriptor.v1`;
- PDD layer media type: `application/vnd.ndf.product-deployment-descriptor.v1+json`;
- evidence and binding-report layer media type: `application/vnd.ndf.pdd.evidence.v1+json`;
- manifest annotations:
  - `io.ndf.pdd.descriptor-id`;
  - `io.ndf.pdd.content-sha256`;
  - `io.ndf.pdd.subject-image-digest`;
  - `io.ndf.pdd.schema-version`;
  - `org.opencontainers.image.title`.

The subject image repository is the artifact repository. The subject image digest is the exact digest already verified by M4.2.6.5. Consumers must compare these annotations with both the publication receipt and the retrieved PDD.

## 4. Publication receipt

The workflow emits `pdd-publication-record.json`, validated against `schemas/pdd-publication-record-v1.schema.json`. The receipt is a small durable handoff record containing:

- publication record schema/type version;
- descriptor ID, PDD schema version and PDD content SHA-256;
- subject image repository, digest and platform;
- OCI artifact type, repository, locator tag, artifact manifest digest and immutable reference;
- evidence count, binding-report SHA-256 and published file count;
- publication timestamp.

The receipt is also uploaded as a GitHub Actions artifact for workflow traceability. That workflow artifact has 90-day retention and is **not** the durable publication store. The OCI artifact in GHCR is the durable content store.

The receipt itself is not embedded in the OCI artifact because it contains the artifact manifest digest, which is only known after the artifact has been pushed.

A consumer must obtain the receipt from the authorized publication record channel, validate its schema, and retain the digest-pinned reference and descriptor identity with the relevant candidate/build record. Signing and attestation of the receipt/artifact are M4.2.8, not .6.

## 5. Publication workflow

The manual workflow is:

```text
.github/workflows/ndf-publish-product-deployment-descriptor.yml
```

Inputs:

- `build_run_id`: successful `NDF / Publish Product Images` source run;
- `build_artifact_name`: exact original build evidence artifact;
- `verification_run_id`: successful `NDF / Verify Product Deployment Binding` run;
- `verification_artifact_name`: exact descriptor/report artifact from that verification run.

Before publication, the workflow verifies that both runs completed successfully and came from the expected workflow files, and that the named artifacts belong to the supplied runs/attempts and are not expired. The PDD and binding report are taken from the successful .5 verification artifact; the original evidence bundle is downloaded from the source build run.

The workflow is restricted to dispatches from `main` and requires the .5 verification run to have completed on `main`. It serializes publication runs to prevent concurrent writes to deterministic locators. It uses ORAS CLI **1.3.6**, installed through `oras-project/setup-oras@v2.0.3`, authenticates to GHCR with the workflow token and `packages: write`, and runs `scripts/publish_product_deployment_descriptor.py`. The GHCR image package must grant this repository's Actions workflow package write access; repository token permissions alone do not override package-level access settings.

The publisher:

1. independently validates the PDD;
2. reruns exact M4.2.6.5 evidence-byte and OCI registry-manifest verification;
3. requires the saved binding report to match the fresh verifier output;
4. checks the complete publication file inventory and safe in-root regular-file paths;
5. publishes or verifies the deterministic locator;
6. retrieves the resulting artifact by immutable digest and compares all 16 files byte-for-byte;
7. writes the schema-validated publication receipt atomically.

A registry write, manifest fetch, pull-back, file inventory or byte comparison failure prevents successful publication.

## 6. Consumer retrieval and verification

Reference implementation:

```text
images/ndf/scripts/fetch_product_deployment_descriptor.py
```

Invocation:

```bash
python images/ndf/scripts/fetch_product_deployment_descriptor.py \
  --publication-record /path/to/pdd-publication-record.json \
  --output-dir /path/to/retrieved-pdd
```

The default mode performs full image/evidence binding verification. The consumer must have ORAS authenticated to GHCR and Docker/Buildx access to the subject image repository.

Retrieval sequence:

1. validate the publication receipt against the publication-record schema;
2. require a digest-pinned artifact reference whose repository and digest agree with the receipt;
3. fetch the OCI manifest by digest and verify manifest digest, artifact type, PDD layer media type and NDF annotations;
4. pull the artifact by digest into a fresh temporary directory;
5. require the expected file count and verify the exact binding-report SHA-256 from the receipt;
6. independently validate the PDD schema, canonical content integrity, descriptor identity, image digest and schema version against the receipt;
7. by default, rerun the M4.2.6.5 verifier against the retrieved evidence bundle, including a fresh registry OCI manifest digest check;
8. copy the verified artifact contents to the caller's previously empty output directory and emit a machine-readable result.

`--skip-image-binding` is available for constrained inspection workflows. It still validates the receipt, OCI artifact digest/type/annotations, PDD schema and PDD integrity, but the result is `descriptor_verified`, not `verified`. It must not be treated as deployment authorization or as a replacement for the full verification mode.

Consumers must reject:

- mutable tag references or malformed digest references;
- unsupported artifact type, schema version or PDD media type;
- artifact manifest digest mismatch;
- missing, duplicate, unexpected or unsafe artifact content;
- publication receipt/PDD/OCI annotation identity disagreement;
- PDD canonical integrity or schema failure;
- image repository, digest or platform mismatch;
- failed evidence or registry binding verification.

## 7. DT Master handoff mapping

The current PDD v1 schema is evidence-backed and intentionally does not mirror every aspirational top-level section in the DT Master M4.1 target specification. The consumer must map the actual NDF v1 fields rather than assume that the target shape already exists.

| DT Master target area                                                            | Current PDD v1 source                                                                                              | Consumer handling                                                                                                                                                  |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Schema                                                                           | `schema_version`, `descriptor_type`                                                                                | Require supported schema major; validate with the NDF-published schema contract.                                                                                   |
| Identity                                                                         | `product.id`, optional `product.release`, `composition.lock.sha256`                                                | Compare product and composition against the candidate. Do not infer a release from tags.                                                                           |
| Build                                                                            | `build.source_repository`, `source_commit`, `workflow_run_id`, `workflow_run_url`, `built_at`                      | Preserve source/build provenance separately from application commits.                                                                                              |
| Image                                                                            | `artifact.repository`, `artifact.digest`, `artifact.platform`, optional immutable reference and informational tags | Require exact repository/digest/platform; ignore tags for identity.                                                                                                |
| Framework/applications                                                           | `composition.applications`, `runtime_inventory.framework`, composition verification evidence                       | Compare exact app names/repositories/actual commits and framework identity with candidate composition.                                                             |
| Runtime                                                                          | `runtime_inventory` including explicit `scope`                                                                     | Respect `builder_stage` versus `final_runtime_image`; never represent builder inventory as final runtime.                                                          |
| Dependencies                                                                     | Build inventory and lock-v2 evidence references                                                                    | Interpret only the measured evidence scope; do not claim a complete final-runtime transitive closure unless proven.                                                |
| Services/external requirements                                                   | `composition.services`, `composition.external_requirements`, `requirements.services`                               | Identity/dependency declarations only; do not infer a complete runnable Compose topology.                                                                          |
| Storage, networking, configuration, health/readiness, operations, infrastructure | Corresponding `requirements.*` domains                                                                             | Respect `not_declared`, `declared` and `verified`. A required domain that is not adequately declared/verified is a deployment blocker, not an invitation to guess. |
| Integrity/provenance                                                             | `integrity`, `composition.lock`, `evidence`, `build` and the publication receipt                                   | Verify descriptor hash, evidence hashes/sizes, image digest and publication artifact digest independently.                                                         |

### 7.1 Requirement-state decision

- `not_declared` means unknown/not specified; it does not mean no requirement exists.
- `declared` means an authoritative declaration exists but is not independently verified.
- `verified` means declarations and verification evidence exist, with explicit scope.

The current Dalali v16 descriptor does not establish every service execution, storage, networking, configuration, health/readiness, operations or infrastructure fact described in the M4.1 target. DT Master must not deploy a product when its own policy or the product's deployment profile requires a domain that remains `not_declared` or insufficiently verified.

### 7.2 Immutable facts and environment allocations

NDF product facts include image digest, product identity, Bench application composition, immutable app commits, measured runtime facts, service/external requirement identities and descriptor/evidence integrity.

DT Master supplies environment-specific bindings such as Node, resource allocation, concrete volumes, host ports, ingress, external endpoints and secret-manager references. It must reject overrides that mutate image identity, application composition, immutable service artifacts or other descriptor-owned facts.

No credentials, secret values, tenant FQDNs, customer data, Node-specific paths/ports or arbitrary shell commands are accepted from the PDD.

## 8. Failure and trust model

- Registry read/write authorization is explicit. A successful login alone is not evidence that the artifact exists or is retrievable.
- The publication workflow's token receives only `actions: read`, `contents: read` and `packages: write`.
- The consumer needs registry read access to both the PDD artifact and subject image if it runs the full image-binding check.
- The digest-pinned artifact reference and receipt are integrity identifiers, not cryptographic publisher authentication. M4.2.8 adds signing/attestation and trust-policy verification.
- A GitHub Actions run artifact or locator tag is not the authoritative long-term content store.
- Missing/expired workflow artifacts prevent publication, but do not invalidate an already published OCI artifact.
- A missing/invalid receipt, registry object, PDD, evidence file or digest match is a fail-closed condition.
- A successful .5 binding does not prove undeclared deployment requirements, official product-tag promotion or successful deployment on any Node.

## 9. Acceptance criteria

M4.2.6.6 is complete when:

1. The publication artifact type, media types, annotations, locator and digest-reference rules are documented and versioned.
2. Publication includes the exact PDD and its complete eleven-file evidence set plus binding report and required sidecars.
3. A publication receipt schema defines the descriptor/image/artifact/evidence identities.
4. Publisher refuses unverified or mismatched inputs, handles existing locators idempotently and verifies the pushed artifact by digest and exact bytes.
5. Consumer retrieval validates the receipt, manifest, PDD and all identity relationships and can re-run the full .5 binding.
6. A manual GitHub Actions workflow validates provenance of both input runs/artifacts and publishes to GHCR with least-privilege package permissions.
7. Tests cover deterministic locators, file inventory, unsafe paths, receipt schema, fail-closed mismatches, idempotent publication and consumer retrieval.
8. DT Master handoff mapping and unresolved requirement-state behavior are documented without modifying the DT Master repository.
9. Documentation and implementation tracker reflect the actual implementation and operational evidence.

**Operational acceptance remains pending** until the user runs the publication workflow against the accepted M4.2.6.5 Dalali v16 AMD64 descriptor and the published artifact is fetched and independently verified by digest.

## 10. Explicit exclusions

- DT Master code changes or live consumer implementation;
- DT Tenant changes;
- candidate-driven workflow integration (M4.2.7);
- signing, attestations, key management and trust-policy enforcement (M4.2.8);
- end-to-end M4 acceptance beyond descriptor publication/consumption (M4.2.9);
- Docker/Compose deployment orchestration (M4.3+);
- inventing service execution topology, storage, networking, health, operations or infrastructure facts that are not declared and evidenced.
