## M4.2.5.1 source-tree fingerprint contract

Algorithm identifier: ndf-source-tree-sha256-v1.

The root SHA-256 is calculated over a deterministic stream. The stream begins with the domain separator NDF-SOURCE-TREE, followed by a NUL byte, the algorithm identifier, and a final NUL byte. Each filesystem entry becomes canonical UTF-8 JSON (sorted keys, compact separators, no ASCII escaping), preceded by its unsigned 8-byte big-endian length. Entries are globally sorted by slash-separated relative path. The root directory is not an entry.

| Entry                   | Fingerprinted representation                                                      |
| ----------------------- | --------------------------------------------------------------------------------- |
| Directory               | Relative path and type; empty directories included                                |
| Regular file            | Relative path, byte size, executable-bit boolean and SHA-256 of complete contents |
| Symbolic link           | Relative path and literal link target; never followed                             |
| Any .git entry          | Excluded at any depth                                                             |
| Other filesystem object | Rejected (FIFO, socket, device, etc.)                                             |

No other path is excluded. Caches, virtual environments, node_modules, generated files, hidden files and ignored files are included when present. Ownership, timestamps and non-executable permission bits are not hashed, so image-layer permission normalization does not alter the fingerprint. Paths and link targets must be strict UTF-8. Files are checked for replacement or mutation while being read. Unsupported inputs fail closed.

The output contains algorithm, root SHA-256 and diagnostic entry/file/directory/symlink counts. Tests pin a golden vector to prevent silent changes to the v1 algorithm.

### Git provenance boundary

A matching filesystem fingerprint proves equality between snapshots; it does not prove that a snapshot corresponds to a Git commit. M4.2.5.2 must additionally verify canonical credential-free repository identity, actual Git HEAD and tracked working-tree content against that HEAD. Untracked, ignored, generated and installation-modified files must be explicitly classified, not silently attributed to the commit.

The same tree fingerprint is then compared after .git cleanup and in the final runtime image. This detects changes to retained files across those stages.

## A10 acceptance

For Frappe and every expected Bench app, verification must establish repository identity, actual acquired HEAD, tracked content correspondence, explicit classification of untracked/generated content, matching pre-cleanup/post-cleanup/final-image fingerprints, and binding to the exact image digest. A Git SHA or build-time pass report alone is insufficient.

## A11 acceptance

Expected composition comes from authoritative lock-v2 and product composition inputs, not image labels alone. Actual image and runtime configuration are inspected. Missing or unexpected Bench apps and independent services fail closed. Explicit optional capabilities must match. External requirements remain a separate category and are checked against their declared contract, not treated as image-installed services.

The independent-service inspection contract must be confirmed from the existing product deployment model before implementation. This document does not assume Redis or MariaDB is bundled in every product image.
