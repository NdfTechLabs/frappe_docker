## M4.2.5.1 source-tree fingerprint contract

Algorithm identifier: ndf-source-tree-sha256-v1.

The root SHA-256 is calculated over a deterministic stream. The stream begins with the domain separator NDF-SOURCE-TREE, followed by a NUL byte, the algorithm identifier, and a final NUL byte. Each filesystem entry becomes canonical UTF-8 JSON (sorted keys, compact separators, no ASCII escaping), preceded by its unsigned 8-byte big-endian length. Entries are globally sorted by slash-separated relative path. The root directory is not an entry.

| Entry                   | Fingerprinted representation                                                      |
| ----------------------- | --------------------------------------------------------------------------------- |
| Directory               | Relative path and type; empty directories included                                |
| Regular file            | Relative path, byte size, executable-bit boolean and SHA-256 of complete contents |
| Symbolic link           | Relative path and literal link target; never followed                             |
| Any .git entry          | Excluded at any depth                                                             |
| Other filesystem object | Rejected (FIFO, socket, device, etc.)                                             |

No other path is excluded. Caches, virtual environments, node_modules, generated files, hidden files and ignored files are included when present. Ownership, timestamps and non-executable permission bits are not hashed, so image-layer permission normalization does not alter the fingerprint. Paths and link targets must be strict UTF-8. Files are checked for replacement or mutation while being read. Unsupported inputs fail closed.

The output contains algorithm, root SHA-256 and diagnostic entry/file/directory/symlink counts. Tests pin a golden vector to prevent silent changes to the v1 algorithm.

### Git provenance boundary

A matching filesystem fingerprint proves equality between snapshots; it does not prove that a snapshot corresponds to a Git commit. M4.2.5.2 now captures canonical credential-free repository identity, actual Git HEAD and HEAD tree, tracked working-tree changes, untracked/ignored paths and the complete pre-cleanup source-tree fingerprint. This is build-time provenance evidence. M4.2.5.3 separately verifies complete source-tree snapshot equality after .git cleanup and inside the final runtime image. Independent correspondence checks between Git provenance and authoritative lock-v2 are assigned to M4.2.5.4.

The same tree fingerprint is compared after .git cleanup and in the final runtime image. M4.2.5.3 is accepted for Dalali v16 AMD64; its evidence is recorded below.

## M4.2.5.2 capture design baseline

The capture point remains immediately after `bench init --apps_path` completes and before the Containerfile removes application `.git` metadata. The existing build-inventory capture already records canonical repository identity, requested ref, resolver commit and actual Git HEAD; M4.2.5.2 adds evidence that distinguishes the Git commit's tracked tree from post-clone build/install changes.

### Upstream Bench lifecycle inspected

The upstream Bench source at tag `v5.31.1` was inspected:

- `bench init` creates the Bench environment, obtains Frappe, processes `--apps_path`, and runs `build_assets` unless `--skip-assets` is supplied.
- `App.get()` clones application repositories with Git remote name `upstream`; capture must not assume the remote is named `origin`.
- `install_app()` installs each app in editable mode using uv or pip, runs `yarn install --check-files` when an app has `package.json`, and invokes asset building unless skipped.
- The current Containerfile does not pass `--skip-assets`, so the final `bench build` occurs before source evidence capture.

This confirms that the capture point observes source trees after Bench acquisition, editable Python installation, per-app Node dependency installation and asset building. It does not prove that any particular app currently has tracked files modified; that must be measured rather than assumed.

### Required per-repository evidence

For Frappe and each locked Bench application, the source-provenance record must bind to the lock SHA-256 and record:

1. Canonical credential-free repository identity, requested ref, resolver-time commit, actual Git HEAD and HEAD tree object. The requested ref/resolver-time commit are cross-checked against lock-v2; actual HEAD is checked against captured provenance but is not required to equal the resolver-time SHA because M4.2.4 intentionally preserves rolling refs for Bench acquisition.
2. Whether tracked working-tree content still matches HEAD. If not, record changed tracked paths and a SHA-256 of the binary Git diff against HEAD; classify these as post-clone build/install modifications, not as content supplied by the commit.
3. Untracked and ignored paths, classified separately as post-clone content. A fresh Bench clone begins from Git-tracked content, so these entries must not be attributed to the source commit.
4. The `ndf-source-tree-sha256-v1` fingerprint of the complete app directory, including tracked, untracked, ignored and generated/installed files, while excluding only `.git`.
5. Explicit submodule handling. Materialized submodules are checked against parent gitlink SHAs and declared repository identities, with recursive capture. Uninitialized submodules are recorded as metadata-only; no actual HEAD or child fingerprint is claimed. Unexpected content and inconsistent Git metadata fail closed.

The source-provenance document will be a separate versioned build-evidence artifact, linked to the existing lock and repository records. This avoids changing the existing M4.2.4 build-inventory contract merely to add M4.2.5 verification evidence. It will be written under the existing Bench `build-evidence` directory so it is retained with the runtime image for subsequent M4.2.5.3 comparison.

No generated-path allowlist will be invented. The capture will classify Git-tracked modifications, untracked paths and ignored paths from Git's own index/status view; the complete filesystem fingerprint covers their contents. Any unsupported or ambiguous Git state must fail closed.

## M4.2.5.4 — Independent Source Verification

### Objective and trust boundary

Independently establish that each source repository acquired by Bench corresponds to the repository identity and resolved revision declared by generated lock-v2, and that captured provenance accurately represents the pre-cleanup Git/source state.

This is separate from provenance capture and M4.2.5.3 filesystem snapshot equality. The verifier must not import Git-inspection/canonicalization helpers from capture_source_provenance.py or treat its report as self-authenticating.

### Inputs and authority

- Generated lock-v2: authority for expected Bench app composition, repository identities, requested refs and resolver-time commit observations.
- source-provenance.json: evidence to verify; schema validity is necessary but not sufficient.
- Live Git repositories: independent source for repository identity, HEAD/tree, tracked modifications, generated paths and submodule state before .git cleanup.
- Existing source-provenance and source-tree-verification schemas: structural contracts, not proof of truth.

Verification must execute after Bench acquisition and provenance capture but before the Containerfile removes application .git metadata.

### Required independent checks

1. **Lock/evidence identity:** independently hash exact lock-v2 bytes; compare version/digest with provenance; require exact one-to-one repository composition; reject missing, duplicate and unexpected records.
2. **Repository identity:** independently inspect repository roots and configured remotes; independently canonicalize credential-free identities; compare with lock-v2 and provenance; reject unsupported or ambiguous remotes and unsafe paths.
3. **Commit/tree identity:** independently inspect HEAD and HEAD^{tree}; compare them with actual_commit/head_tree in provenance. Cross-check requested_ref and resolver_commit against lock-v2 target_ref and resolution-time ref. Do not require actual_commit to equal the resolver-time SHA: M4.2.4 intentionally preserves rolling refs for Bench acquisition, and a ref may move between resolution and acquisition.
4. **Tracked content:** independently inspect index/worktree state; recompute modified tracked paths and binary diff SHA-256; compare matches_head, installation_modified_paths and installation_diff_sha256; preserve distinction between commit-supplied source and post-clone Bench/build/install changes.
5. **Generated/ignored content:** independently enumerate untracked and ignored path roots; compare with provenance; reject ambiguous states. Path lists are classification evidence, not content-integrity proof.
6. **Submodules:** independently inspect committed .gitmodules declarations and index gitlinks. Verify materialized submodules recursively against declared identity, expected gitlink, actual HEAD/tree and tracked/generated state. Require uninitialized submodules to remain metadata-only with null actual commit/tree/tracked/generated/source-tree fields and no child records.
7. **Report:** emit a versioned source-provenance-verification-v1 report containing verifier identity/version, lock and provenance digests, per-repository/submodule outcomes and overall result. Missing, malformed, inconsistent, ambiguous or unsupported evidence fails closed.

### Proposed implementation files

- Verifier: images/ndf/scripts/verify_source_provenance.py
- Report schema: images/ndf/schemas/source-provenance-verification-v1.schema.json
- Tests: images/ndf/tests/test_verify_source_provenance.py
- Evidence: build-evidence/source-provenance-verification.json

### Scope boundaries

Included: independent lock/provenance binding, repository identity and commit/tree checks, tracked/generated classification checks, recursive submodule checks, versioned report, negative tests and builder-stage integration before .git cleanup.

Excluded: whole-tree snapshot comparison (.3); independent application/service composition (.5); exact image-digest evidence binding (.6); candidate publication gating (.7); changes to lock-v2 or build-inventory contracts without a separately justified requirement.

## M4.2.5.5 — Independent Application and Service Composition Verification

### Objective

Independently prove that the final Frappe product image contains exactly the Bench applications required by the generated lock-v2 composition, while independently validating the selected capability, container-service and external-requirement inventories. Preserve the M4.2.3 boundary: only Bench applications enter the Bench installation; independent container services and external requirements remain separate artifacts.

### Authoritative inputs

- Generated lock-v2: expected application, capability, service and external-requirement composition.
- Product and included capability manifests plus their recorded checksums: source declarations used to validate selected capability and service descriptor identity.
- Service descriptors under `images/ndf/descriptors/services/`: authority for service kind, immutable image reference or external provider requirement, dependency edges and descriptor checksum.
- Final runtime image: actual Bench application directories and `sites/apps.txt`; it must not contain missing or unexpected Bench applications or misclassify service/external identities as Bench apps.

### Required independent checks

1. Reconcile the exact Bench application set across lock-v2, `apps.json`, build metadata, build inventory, runtime `apps/` directories and `sites/apps.txt`. Reject missing, duplicate, unexpected or cross-category identities.
2. Validate capability selections from lock-v2 against the product manifest graph and recorded manifest checksums. An optional capability is included only when explicitly selected; required capabilities remain selected by contract.
3. Reconstruct container-service and external-requirement inventories from the selected manifest graph and canonical service descriptors. Verify exact identity, kind, descriptor path/checksum, immutable container image digest, provider metadata and transitive dependency closure/order.
4. Prove that container services and external requirements are not passed to Bench as apps and do not appear in the Bench application inventory or runtime app directories.
5. Reject overlap between application, container-service and external-requirement identities; reject undeclared or missing transitive dependencies, duplicate service IDs, descriptor tampering and service-kind substitution.
6. Emit a versioned independent composition-verification report that records expected and observed inventories, capability selections, checks performed and fail-closed result. The report must bind to the exact lock-v2 bytes and source manifest/descriptor checksums.
7. Keep service deployment and service-image build orchestration outside this work package. M4.2.5.5 verifies the product image's composition contract and separation; M4.2.6/M4.2.7 own consumer deployment descriptor and candidate workflow integration.

### Scope boundary

This package must not duplicate the resolver or introduce another package resolver. It independently validates the generated composition and the final image against existing M4.2.3 descriptor/lock contracts. It does not implement final image-digest binding (M4.2.5.6) or publication gating (M4.2.5.7).

### Initial implementation sequence

1. Inspect lock-v2 capability/service records, selected manifest graph and canonical service descriptor catalogue.
2. Define the independent composition report schema and trust boundary.
3. Add positive fixtures for no optional capabilities, selected/unselected capabilities, container services, external requirements and transitive service dependencies.
4. Add negative fixtures for missing/extra Bench apps, app/service leakage, duplicate/cross-category identities, altered descriptor checksums, mutable image refs, missing dependencies and capability-selection tampering.
5. Integrate the independent verifier with final-image inspection without making product image builds automatic.
6. Run focused tests and the full NDF regression locally; run a real product Buildx build only when required to prove the new runtime-image inspection path.
