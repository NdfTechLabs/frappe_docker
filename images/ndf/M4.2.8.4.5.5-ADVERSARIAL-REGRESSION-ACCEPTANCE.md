# M4.2.8.4.5.5 — Adversarial and Regression Acceptance

**Branch:** `feat/M4.2.8.4.5.5-adversarial-regression-acceptance`
**Base:** `feat/M4.2.8.4.5.3-consumer-fetch-orchestration`
**Scope:** independent PDD consumer verification and the read-only GitHub Actions fetch workflow.

## Objective

Demonstrate that the consumer remains fail-closed when registry evidence, trust-result documents, signer metadata, source provenance, cross-artifact relationships or workflow outcomes are malformed or contradictory. Preserve retrieved evidence for diagnosis even when a later verification stage rejects it.

This work package does not change signer identities, identity-policy status, trust roots, publication permissions, production promotion or deployment authorization. The live staging exercise remains M4.2.8.4.5.6.

## Findings addressed

### A1 — Preserve retrieved evidence before verification

The fetcher previously copied the ORAS pull directory into the output directory only after descriptor validation, evidence binding, PDD trust, image trust and provenance correlation had all completed. A failure during any of those checks caused the temporary directory to be deleted before the workflow's `if: always()` upload could retain the retrieved PDD and evidence.

The fetcher now calls `_preserve_pulled_bundle()` immediately after a successful ORAS pull and before checking the returned reference or validating the bundle. The helper scans the complete pulled tree and rejects symlinks before copying the files and directory structure into the initially empty output directory. Later verification continues against the temporary working copy; the preserved copy is retained as diagnostic evidence.

### A2 — Adversarial trust-result coverage

Additional tests mutate trust-result fields to exercise rejection of:

- unverified signatures;
- mismatched OIDC issuer/signer identity;
- incomplete transparency verification;
- unexpected predicate types;
- multiple attestations where exactly one is required; and
- a trusted decision under the provisional identity policy.

Existing tests continue to cover wrong artifact digests, wrong certificate identity, missing Rekor verification, duplicate JSON keys, symlinked trust-result files and mutable image references.

### A3 — Correlate image provenance to the PDD build identity

The consumer extracted the image provenance `source_commit` and PDD binding publication `source_commit`, but did not explicitly compare the image provenance identity to the PDD descriptor's original image-build identity before setting `correlation.image_source_sha_verified` to true.

The consumer now requires both:

- image provenance `ndf_build.workflow.source_commit` equals descriptor `build.source_commit`; and
- image provenance `ndf_build.workflow.run_id` equals descriptor `build.workflow_run_id`.

The PDD binding workflow's own `source_commit` is intentionally distinct: it identifies the publication workflow revision, not the original product-image build revision. The implementation does not incorrectly compare those two different workflow identities.

### A4 — Workflow contract coverage

Static workflow contract tests now assert that:

- both artifact decisions must agree with the top-level decision and exit-code policy;
- the exact provisional reason is required for both artifacts under provisional policy;
- deployment authorization remains `not_granted`; and
- the retrieved bundle is preserved before binding and independent trust verification.
