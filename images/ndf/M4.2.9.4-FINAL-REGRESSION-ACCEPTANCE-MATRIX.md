## 1. Purpose and acceptance rule

This matrix consolidates the approved A01–A20 criteria from `M4.2-IMPLEMENTATION-PLAN.md` against the evidence recorded by M4.2.1–M4.2.9.3.

A criterion is not marked passed merely because a related test exists. The disposition distinguishes:

- **Satisfied — scoped evidence:** the required NDF implementation and its defined evidence exist.
- **Partial:** some NDF-local evidence exists, but an explicit criterion or required integration fact remains unresolved.
- **Pending live evidence:** local tests pass, but a fresh artifact/workflow observation is still required.
- **Deferred:** owned by a later milestone or external producer/consumer and cannot be claimed by NDF-local tests.

Historical run IDs remain useful evidence for their original commit and inputs; they are not proof that a later code change has been exercised.

## 5. Release workflow negative test — separate authorization gate

The release workflow `.github/workflows/ndf-release-product.yml` is materially different from the build workflow. Its successful path promotes an immutable source digest to semantic and stable release tags.

A negative trust-gate exercise may be considered only after explicit dispatch authorization. If authorized, it must use an existing published source image whose signer identity is still rejected by the provisional policy, use a valid semantic version and source commit SHA, and verify that:

- the independent trust-verification job fails closed;
- the `release` job is skipped;
- no semantic or stable release tag is created or changed.

Do not dispatch this workflow as part of the routine Buildx check. No release, official promotion, production trust or deployment authorization is granted by this matrix.
