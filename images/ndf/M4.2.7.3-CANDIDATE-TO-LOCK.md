# M4.2.7.3 — Candidate-to-Lock Composition Adapter

**Repository:** `NdfTechLabs/frappe_docker`  
**Branch:** `feat/M4.2.7`  
**Status:** Implementation checkpoint; user-run verification pending  
**Implementation:** `scripts/adapt_candidate_to_lock.py`

## 1. Purpose

Translate an intake-validated Deployment Candidate into the existing NDF lock-v2, Bench `apps.json` and build metadata inputs.

The adapter does not introduce a second resolver or application manifest. The selected NDF product manifest remains authoritative for:
- product/image identity;
- the complete allowed application set;
- application repository identity;
- dependency topology and install order;
- compatibility disposition and effective resolution policy;
- included manifests, services and external requirements.

Candidate records supply the selected immutable Git commit for each application and preserve the requested release/ref assertion. The adapter verifies each supplied commit against its declared repository, then pins that commit into the lock and Bench build input. It does not resolve a moving branch or tag to choose a build commit.

## 2. CLI

```bash
python images/ndf/scripts/adapt_candidate_to_lock.py \
  --candidate .ndf-candidate/deployment-candidate.json \
  --candidate-artifact-ref \
    ghcr.io/ndftechlabs/dt-master-deployment-candidates@sha256:<manifest-digest> \
  --payload-sha256 <sha256-of-exact-candidate-json-bytes> \
  --output-dir .ndf-build/candidate-<run-id>
```

The adapter independently checks the candidate schema and exact payload SHA-256. It also enforces the candidate package reference allowlist. The candidate file is expected to be the exact file emitted by the intake stage.

## 3. Composition mapping

1. Resolve `product.id` to exactly one image definition.
2. Load the corresponding product manifest through `ManifestLoader`.
3. Apply selected optional capabilities only where the product manifest uses v2 capability selection. Candidate selections are canonical manifest-relative paths such as `capabilities/ai-automation-v16.json`. A v1 product manifest cannot consume candidate capability overrides; a non-empty selection is rejected rather than ignored.
4. Compose the complete required application graph using the existing resolver.
5. Map candidate `app_id` to the resolver's descriptor `_app_id`; for legacy embedded manifest entries, the Bench application name is the identity key.
6. Require exact set equality between candidate applications and the NDF-resolved composition. Missing and unexpected apps fail closed.
7. Require the candidate repository to equal the NDF-authorized repository and require `app_source_type=git`. Preserve `is_required` and `change_action` as candidate metadata; presence in the complete candidate application set, together with capability selection, determines the requested build composition.
8. For descriptor-backed applications, compare the candidate app name and release version with the locally registered Marketplace App Descriptor.
9. Require a full 40-character commit SHA and verify that exact commit is fetchable from the declared repository.
10. Preserve the candidate's requested version as metadata, but set lock `target_ref` and `ref` to the immutable commit. The lock records `reference_kind=commit` and the exact commit as `resolved_ref`. Bench `apps.json` therefore consumes immutable commit pins, not rolling refs.

The resolver's dependency order is retained. The adapter does not use candidate array order as installation order.

## 4. Runtime and build policy

Current supported boundary:
- target platform: exactly `linux/amd64`;
- Python runtime family: CPython 3.14;
- Node.js runtime family: 24.x;
- build profile: `production`;
- build options: only `assets=true` is accepted; other candidate build options fail because the existing NDF build pipeline has no approved mapping for them.

This package does not broaden the accepted runtime matrix or implement arbitrary candidate-supplied build arguments.

## 5. Buildx handoff

The existing `build_image.py` previously regenerated a product lock unconditionally. That would discard candidate pins. It now accepts `--prepared-inputs-dir` to consume the adapter output without calling `prepare_build` again. Before Buildx starts, it verifies the candidate artifact reference and payload hash, lock-v2 identity, product/image mapping, exact lock SHA-256, candidate metadata equality, target platform, immutable commit pins and exact `apps.json` equivalence to the lock. The normal `--output-dir` path remains unchanged for manual product builds; the two modes cannot be combined.

## 6. Outputs

The attempt output directory contains:
- `candidate-<candidate-id-hash>.lock-v2.json` — existing NDF lock-v2 structure, with immutable candidate commits and candidate correlation metadata;
- `apps.json` — existing Bench app input, with non-Frappe applications pinned to the candidate commits;
- `build-metadata.json` — existing build metadata plus candidate correlation;
- `candidate-composition.json` — safe mapping evidence including candidate/artifact identity, composition hash, lock hash and application pins.

The candidate ID is hashed for the lock filename; untrusted candidate text is never used as a path component. Existing output files are not overwritten. Each workflow attempt must use a fresh output directory.

The lock contains the candidate ID, immutable candidate artifact reference/digest, payload hash, supplied composition hash, selected capability paths and target platforms. The original requested version and candidate descriptor references/digests are retained on each locked application.

## 7. Integrity and limits

- The adapter verifies the candidate payload hash against the exact candidate file bytes.
- It verifies candidate application membership, repository identity and immutable commit availability against the current NDF manifest graph.
- It validates the generated lock using the existing lock-v2 validator. The resolver's source-manifest composition equality check is bypassed only for this final validation because candidate commit pins replace manifest rolling refs; the adapter performs the candidate-to-manifest composition comparison before constructing the lock.
- The supplied `composition_hash` is preserved but not recomputed. The cross-repository contract does not yet define a canonical serialization algorithm for independently recomputing that hash. The generated lock SHA-256 is computed over the exact generated lock bytes.
- For legacy embedded manifest applications that have no registered local Marketplace App Descriptor, `release_version` and external descriptor artifact identity are retained but cannot be independently compared with local descriptor content. For descriptor-backed apps, app name and release version are compared with the local descriptor.
- The adapter does not fetch candidate descriptor OCI artifacts. Descriptor artifact content verification remains an explicit integration limitation and must be resolved before claiming full descriptor provenance verification.
- A real DT Master-published candidate artifact remains a separate cross-repository acceptance gate. Synthetic candidates and mocked ORAS intake tests do not close it.

## 8. Tests

`tests/test_adapt_candidate_to_lock.py` builds a candidate from the current Dalali manifest composition and covers:
- deterministic lock-v2 output for identical candidate bytes;
- immutable commit pins in the lock and Bench `apps.json`;
- commit verification without resolving rolling refs;
- missing/unexpected application rejection;
- source repository and source-type mismatch;
- malformed commit pins;
- product/framework and platform mismatch;
- unsupported optional capability paths and v1 capability overrides;
- unsupported build profile/options;
- payload hash and candidate artifact repository mismatch;
- no overwrite of existing attempt outputs;
- Buildx prepared-input handoff, lock hash validation and lock/apps.json mismatch rejection.

User-run focused/full tests, compilation, pre-commit and diff checks are pending. This checkpoint makes no acceptance claim.
