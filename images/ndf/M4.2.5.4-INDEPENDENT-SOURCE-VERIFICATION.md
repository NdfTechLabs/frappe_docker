# M4.2.5.4 — Independent Source Verification

**Status:** Complete — accepted 2026-11-14.
**Parent work package:** M4.2.5 — Image Verification.
**Implementation branch:** `feat/m4.2.5.4-independent-source-verification` (merged into the M4.2.5 integration line)
**Baseline commit:** 6e927a7ed2508d7d54d1bf20191cd3c4f8ed0e7d
**Scope:** Independent verification of Git/source provenance against generated lock-v2 before .git cleanup.

## 1. Objective

Independently establish that each source repository acquired by Bench corresponds to the repository identity and resolved revision declared by generated lock-v2, and that captured provenance accurately represents the source state observed before Git metadata is removed.

This is a separate trust boundary from provenance capture and whole-tree fingerprint comparison. A schema-valid capture report or matching filesystem fingerprints do not independently prove Git-to-lock correspondence.

## 2. Inputs and authority

| Input | Role |
|---|---|
| Generated lock-v2 | Authority for expected Bench application composition, repository identities, requested refs and resolver-time commit observations |
| source-provenance.json | Evidence to verify; schema validity is necessary but not sufficient |
| Live Git repositories | Independent source of repository identity, HEAD/tree, tracked modifications, generated paths and submodule state before cleanup |
| source-provenance-v1 schema | Structural contract for captured evidence |
| source-tree-verification-v1 reports | M4.2.5.3 snapshot-equality evidence; not proof of Git-to-lock correspondence |

Verification must run after Bench acquisition and provenance capture but before the Containerfile removes application .git metadata.

## 3. Proposed implementation

- Verifier: images/ndf/scripts/verify_source_provenance.py
- Report schema: images/ndf/schemas/source-provenance-verification-v1.schema.json
- Tests: images/ndf/tests/test_verify_source_provenance.py
- Builder integration: images/layered/Containerfile (runs after provenance capture and before .git cleanup)
- Report location: build-evidence/source-provenance-verification.json\n- Final image validation extracts, schema-validates and binds this report to the exact captured provenance bytes; CI exports it as standalone evidence.

The verifier must implement independent Git inspection and repository canonicalization. It must not import Git-inspection/canonicalization helpers from capture_source_provenance.py. Shared low-level standard-library utilities may be considered only if they do not carry the capture implementation's conclusions into verification.

## 4. Required checks

### 4.1 Lock and evidence identity

- Validate lock-v2 and calculate SHA-256 from the exact generated lock bytes.
- Require provenance lock version and digest to match.
- Require an exact one-to-one mapping between expected Bench apps and provenance repositories.
- Reject missing, duplicate and unexpected repository records.

### 4.2 Repository identity

- Independently inspect each repository root and configured remotes.
- Independently canonicalize credential-free remote identities.
- Compare actual identity with both lock-v2 and captured provenance.
- Reject unsupported remote forms, ambiguous identities and unsafe path resolution.

### 4.3 Commit and tree identity

- Independently inspect actual HEAD and HEAD^{tree} from each live repository.
- Compare actual HEAD and tree values with captured actual_commit and head_tree.
- Cross-check provenance requested_ref against lock-v2 target_ref, and provenance resolver_commit against the lock-v2 resolution-time ref.
- Do **not** require actual_commit to equal the lock-v2 resolution-time ref. M4.2.4 intentionally passes rolling requested refs to upstream Bench; a branch or tag may move between resolution and acquisition. The resolver SHA is a resolution-time observation, not proof of the commit Bench acquired.
- The independently observed live HEAD/tree, compared with the captured actual_commit/head_tree, establishes what Bench actually acquired at the verification point. Do not infer equality or equivalence from branch names.

### 4.4 Tracked content

- Independently inspect Git index/worktree state.
- Recompute tracked modifications against HEAD, including changed path sets and binary diff SHA-256 where applicable.
- Compare matches_head, installation_modified_paths and installation_diff_sha256 with provenance.
- Preserve the distinction between content supplied by the Git commit and post-clone Bench/build/install modifications.

### 4.5 Generated and ignored content

- Independently enumerate untracked and ignored path roots.
- Compare them with generated_content.untracked_paths and ignored_paths.
- Reject ambiguous or inconsistent Git states.
- Do not treat path lists as content-integrity proof; complete content equality remains the source-tree fingerprint contract.

### 4.6 Submodules

- Independently inspect committed .gitmodules declarations and Git index gitlinks.
- Materialized submodules: verify declared identity, expected gitlink SHA, actual HEAD/tree, tracked/generated state and nested submodules recursively.
- Uninitialized submodules: require metadata-only representation, with null actual commit/tree/tracked/generated/source-tree fields and no child records.
- Reject inconsistent declarations, unsafe paths, unexpected files and mismatched materialization state.

### 4.7 Verification report

Produce a versioned source-provenance-verification-v1 report containing verifier identity/version, lock-v2 SHA-256, source-provenance SHA-256, per-repository and recursive submodule outcomes, checks performed, metadata-only submodule status and overall result.

Missing, malformed, inconsistent, ambiguous or unsupported evidence must fail closed. The report must not claim checks that could not be performed.

## 5. Scope boundaries

Included: independent lock/provenance binding, repository identity and Git commit/tree checks, tracked/generated-content classification, recursive submodule checks, versioned report, negative tests and builder-stage integration before .git cleanup.

Excluded:
- Whole-tree snapshot comparison already implemented in M4.2.5.3.
- Independent application/service composition verification (M4.2.5.5).
- Final verification-evidence/image-digest binding (M4.2.5.6).
- Candidate publication gating (M4.2.5.7).
- Changes to lock-v2 or build-inventory contracts without a demonstrated, separately approved requirement.

## 7. Required negative fixtures

Tests must demonstrate rejection of:
1. Lock digest or version mismatch.
2. Missing, duplicate or unexpected repository records.
3. Incorrect or ambiguous remote identity.
4. Altered actual HEAD or HEAD tree.
5. Modified tracked content or altered modified-path/diff evidence.
6. Changed untracked or ignored path sets.
7. Materialized submodule identity or gitlink/HEAD mismatch.
8. Uninitialized submodule falsely claiming materialized metadata.
9. Malformed report/provenance structures.
10. Unsafe paths, ambiguous Git state and unsupported repository metadata.

## 8. Implementation sequence

1. Inspect capture implementation and schema against the accepted .3 baseline.
2. Define independent Git command contracts and canonicalization rules without reusing capture conclusions.
3. Implement verifier and report schema.
4. Add focused fixtures for clean, post-clone-modified, generated-content and submodule cases.
5. Add adversarial negative fixtures for each acceptance dimension.
6. Integrate verification into the builder before .git cleanup.
7. Run focused tests, full NDF regression, pre-commit and git diff --check.
8. Run a real Buildx product build and inspect generated verification evidence.
9. Update the design, verification document, plan and tracker with exact commit/run/test evidence.
