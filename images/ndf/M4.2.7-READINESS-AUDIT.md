## 1. Purpose and authority

This document records the M4.2.7 readiness audit across the NDF workflow/artifact pipeline and the accepted cross-repository contracts documented by DT Master and DT Tenant.

**Only NDF Frappe Docker is in scope for changes.** DT Master and DT Tenant were inspected on their `develop` branches solely as read-only sources of requirements. No files in either repository are to be edited as part of M4.2.7.

The accepted architecture in DT Master's `docs/migrations/M4_BENCH_ENVIRONMENT_SCHEMA_AND_IMPLEMENTATION.md`, especially Sections 15 and 16, is the requirements authority for candidate, build, operation, authorization and result contracts. DT Tenant's `README.md` is a reference for the tenant request/status boundary. These repositories have not yet implemented all prescribed DocTypes and operations. Their documentation describes the target contract; the absence of implementation must not be interpreted as permission for NDF to invent or take ownership of those functions.

This audit does not authorize implementation or create a new implementation branch.

## 3. A.1 — NDF workflow and artifact-flow audit

### 3.1 Existing NDF capabilities

| Component                                                         | Existing responsibility                                                    | M4.2.7 disposition               |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------- |
| `.github/workflows/ndf-build-product.yml`                         | Manually selected product build and validation                             | Extend/reuse                     |
| `.github/workflows/ndf-publish-product.yml`                       | Product build, validation and GHCR publication                             | Extend/reuse                     |
| `.github/workflows/ndf-release-product.yml`                       | Promotion of an already published immutable image                          | Preserve; not candidate intake   |
| `.github/workflows/ndf-publish-product-deployment-descriptor.yml` | PDD publication as an OCI artifact                                         | Reuse                            |
| `.github/workflows/ndf-fetch-product-deployment-descriptor.yml`   | Independent PDD retrieval and verification                                 | Reuse as consumer verification   |
| Existing resolver, preparation, build and validation scripts      | Composition resolution, lock generation, image construction and validation | Preserve as the build foundation |

M4.2.6 publication and independent retrieval are operationally verified. The PDD contract and immutable OCI artifact model remain authoritative.

### 3.2 Gaps against the accepted candidate contract

1. Existing product build/publish workflows are product-list/manual-dispatch oriented; they do not accept the documented Deployment Candidate identity and immutable candidate artifact reference.
2. No candidate artifact retrieval and schema-validation entry path was identified.
3. No complete candidate validation gate was identified for candidate identity, composition, registered app identities, immutable release descriptors, runtime constraints and approved build parameters.
4. Existing build and PDD workflows do not return one structured result bound to a DT Master candidate and build attempt.
5. Existing PDD publication is a separate workflow operation; candidate orchestration must connect image publication and PDD publication without bypassing either verification boundary.
6. No candidate-driven orchestration path was identified that correlates workflow run, image digest, PDD reference/digest, composition hash, lock hash and provenance.
7. Existing workflows and permissions must be reviewed as a single least-privilege chain before dispatch and publication are enabled.

### 3.3 A.1 conclusion

NDF has reusable build, image verification, immutable publication and PDD machinery. M4.2.7 should add the candidate intake/orchestration/result layer around those components. It must not create a competing resolver, image builder, image validator or PDD schema.

Candidate content is untrusted input. It must be schema-validated and semantically validated before any value is used in shell commands, workflow expressions, paths, build arguments or privileged operations. Candidate data must never supply arbitrary commands or secrets. GHCR write credentials remain exclusively in NDF.

## 4. A.2 — DT Master candidate and operation requirements audit

### 4.1 Documentation authority

Read-only reference: `NdfTechLabs/dt_master`, branch `develop`, file:

`docs/migrations/M4_BENCH_ENVIRONMENT_SCHEMA_AND_IMPLEMENTATION.md`

Relevant sections include the logical schema and migration design, Section 15 (cross-repository security and authorization contract), Section 16 (NDF integration contract), and particularly Sections 16.4–16.7.

### 4.2 Prescribed DT Master records

The documentation prescribes the following records and responsibilities. They are requirements for DT Master implementation, not NDF-owned DocTypes.

| Prescribed DocType                        | Documented purpose                                               | NDF relationship                                                                          |
| ----------------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Deployment Candidate                      | Complete desired Bench composition and approved build parameters | NDF consumes an immutable candidate artifact                                              |
| Deployment Candidate Application          | Application entries in the complete desired composition          | NDF validates and resolves the submitted composition                                      |
| Deployment Build                          | One asynchronous NDF build attempt and its result references     | NDF returns the result data used to update this record                                    |
| Bench Environment                         | Runtime ownership and target Bench context                       | NDF consumes only supported product/runtime inputs; it does not provision the environment |
| Bench Deployment / Bench Deployment Stage | Deployment lifecycle and ordered deployment-stage history        | Outside NDF image-build execution                                                         |

### 4.3 Candidate input contract

The accepted documentation requires the immutable build input to identify:

- Candidate ID and request/schema version.
- Target product and complete product composition.
- Selected `app_id`, release and descriptor digests.
- Requested optional capabilities.
- Supported runtime constraints or an explicitly selected runtime profile.
- Approved build parameters and platform targets.
- Composition hash and source/provenance references.

The documented candidate fields include candidate identity/code, Bench Environment relationship, candidate type, product/release, framework version, base deployment, composition hash, candidate artifact reference/digest, optional capabilities, runtime profile/constraints, target platforms, approved build parameters, provenance references, status and request audit metadata.

The documented child application rows include stable app identity, app name, release version, immutable descriptor reference/digest, source classification/reference, immutable commit, required/optional status and requested change action.

**NDF must validate the received artifact against the accepted contract. NDF must not create a competing candidate schema or become the system of record for candidate lifecycle.**

The candidate must exclude tenant credentials, database passwords, API secrets, customer data, arbitrary shell commands, site FQDNs, Node-specific ports, TLS private keys and live tenant configuration.

### 4.4 Build result contract

The documented Deployment Build record includes:

- Candidate relationship.
- Provider and workflow identity.
- GitHub workflow run ID and URL.
- Immutable source commit.
- Candidate artifact reference and digest.
- Composition hash and resolved lock hash.
- Build status.
- Image repository and immutable image digest.
- PDD reference and descriptor hash.
- Build provenance reference.
- Safe failure code and summary.
- Start and completion timestamps.

A retry creates a new Deployment Build record; a terminal build attempt is not reset or reused.

## 5. A.3 — DT Tenant request/status requirements audit

### 5.1 Documentation authority

Read-only reference: `NdfTechLabs/dt_tenant`, branch `develop`, `README.md`, together with the DT Master cross-repository contract in Section 15.

### 5.2 Prescribed responsibility boundary

DT Tenant owns the tenant-facing request and status experience and its authoritative records for tenant-originated requests and tenant-side operations. DT Master independently validates the authenticated tenant service identity, tenant binding, scope, subscription eligibility and platform resource ownership. DT Master owns platform/deployment operation records. NDF owns build execution and build artifacts.

DT Tenant must not call NDF directly and must not receive unrestricted build execution or registry publishing authority.

### 5.3 Existing implementation observations

The inspected DT Tenant source contains marketplace listing and application request methods, capability synchronization and a Capability Sync Log. The current Master marketplace implementation queues direct SSH-based site app execution through the tenant installed-app executor.

Those existing methods do not implement the accepted candidate/build/replacement-Bench architecture. The existing capability synchronization record is not a substitute for an application request or build-operation record.

The audit did not identify a complete implementation of the documented durable request identity, cross-repository correlation, authenticated callback, idempotency and validated status synchronization contract.

### 5.4 A.3 conclusion

These are future DT Tenant/DT Master implementation requirements. They are recorded here only to define the NDF boundary. M4.2.7 must not edit DT Tenant, implement tenant-facing request records, add tenant callbacks, or create platform operation records.

## 6. A.4 — Cross-repository contract reconciliation

| Contract                                                   | Authority                                   | Required NDF behavior                                                                                         |
| ---------------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Tenant user authorization                                  | DT Tenant                                   | Not implemented by NDF                                                                                        |
| Tenant/site/subscription authorization and tenant binding  | DT Master                                   | NDF accepts dispatch only from the authorized workflow invocation boundary; it does not infer tenant identity |
| Deployment Candidate lifecycle and record                  | DT Master                                   | Consume immutable candidate input; do not own candidate lifecycle                                             |
| Deployment Build lifecycle and record                      | DT Master                                   | Return candidate-correlated build result data; do not create a competing Master record                        |
| Candidate validation and composition resolution            | NDF                                         | Validate candidate input and resolve exact build lock                                                         |
| Image construction and validation                          | NDF                                         | Build and independently verify requested composition                                                          |
| Image and PDD publication                                  | NDF                                         | Publish immutable artifacts and provide digest-pinned references                                              |
| Build result production                                    | NDF                                         | Produce structured, traceable, safe result tied to candidate and workflow run                                 |
| Build-result verification and candidate readiness decision | DT Master                                   | Not an NDF deployment authorization decision                                                                  |
| Tenant-facing status                                       | DT Tenant, based on authorized Master state | No direct NDF-to-tenant notification                                                                          |

### 6.1 Required asynchronous sequence

1. DT Master creates and validates a Deployment Candidate.
2. DT Master submits candidate ID and immutable candidate artifact reference to an authorized NDF GitHub Actions workflow.
3. NDF validates candidate identity, composition, runtime compatibility, dependencies and source provenance.
4. NDF resolves the exact build lock, builds the image, validates installed commit identities and product smoke requirements, and publishes the image.
5. NDF generates and publishes the PDD associated with the image digest.
6. NDF returns candidate/request ID, workflow run ID, status, image repository/digest, descriptor reference/digest, composition hash, lock hash, build provenance and safe failure code/summary.
7. DT Master independently retrieves/verifies the descriptor and relevant artifact evidence before marking the candidate ready or proceeding to deployment.
8. DT Tenant displays authorized tenant-facing status from DT Master.

NDF does not deploy the Bench, move tenant sites, authorize tenant requests or mark a candidate deployment-complete.

### 6.2 Security and operation requirements

The accepted DT Master contract requires:

- Authenticated principal and explicit authorization before dispatch.
- Durable operation identity before asynchronous work is queued.
- Separate business and execution lifecycles.
- Shared correlation ID while each repository retains its own authoritative operation record.
- Idempotency and replay-safe result processing.
- Explicit retry semantics; a retry is a distinct build attempt.
- Safe, sanitized result/failure information.
- No secrets in candidate artifacts, descriptors, workflow outputs, logs or callbacks.
- NDF-only GHCR write credentials.
- No unrestricted candidate-supplied shell commands or executable build instructions.

For NDF, these translate into strict input validation, narrowly scoped GitHub Actions permissions, protected publication credentials, immutable artifact references, deterministic result records and safe failure summaries.

## 7. Audit conclusions and boundaries

1. M4.2.7 is an NDF-only implementation package.
2. DT Master and DT Tenant documentation are the requirements baseline, not implementation targets in this work package.
3. The documented DT Master Candidate and Build records must be implemented by DT Master in its own milestone. NDF must not invent or implement replacement DocTypes.
4. DT Tenant's request and status responsibilities remain with DT Tenant and DT Master.
5. NDF should extend the existing resolver/build/validation/image publication/PDD workflow machinery.
6. M4.2.7 must not implement signing/attestation assigned to M4.2.8.
7. M4.2.7 must not implement runtime orchestration, Bench deployment, tenant application execution, callbacks to tenant sites or DT Master DocTypes/APIs.
8. The M4.2.7 implementation branch is not created by this audit.
