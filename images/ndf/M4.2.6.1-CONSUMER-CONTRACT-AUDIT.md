## 1. Executive conclusion

DT Master `develop` contains the architectural consumer contract for an NDF Product Deployment Descriptor (PDD), but it does not yet contain an implemented PDD consumer, Bench Environment DocType, Deployment Candidate, Deployment Build or Bench Deployment DocType. The actual runtime code remains primarily Host/SSH and Git-reference based.

The NDF repository already produces substantial authoritative evidence for image identity, Bench application composition, source provenance, runtime/package inventory and verification. This evidence is sufficient to ground important PDD sections, but it does not currently prove every item in the broader M4.1 consumer-side descriptor requirements. In particular, complete service execution topology, storage/network allocation requirements, health semantics, operational capabilities and infrastructure minimums must not be invented from the current application/service descriptors or inferred from the legacy Host scripts.

**Decision for M4.2.6.2:** define the PDD as a truthful, evidence-derived contract. Make evidence-backed product facts mandatory where available and required for deployability; represent unsupported/optional sections explicitly with typed declarations and evidence references, or defer them until NDF has an authoritative source. Do not fabricate values to satisfy the aspirational consumer document. Any unresolved mandatory deployability field is a recorded gap, not permission to guess.

## 3. Consumer-side target contract

The current architectural consumer specification is `docs/migrations/M4_BENCH_ENVIRONMENT_SCHEMA_AND_IMPLEMENTATION.md`, Section 8, on `dt_master@develop`. It expects NDF to own the formal JSON Schema and generator. Its required top-level areas are:

- `schema`: descriptor name and semantic version;
- `identity`: product, product release and composition hash;
- `build`: build ID, workflow run, source commit and timestamp;
- `image`: repository, immutable digest, platform and labels;
- `framework`: Frappe/ERPNext versions and compatibility;
- `applications`: complete resolved app inventory;
- `runtime`: exact Python, Node, Yarn and other runtime versions;
- `dependencies`: resolved Python, Node and OS dependency inventory/lock references;
- `services`: Compose definition reference and complete service definitions;
- `storage`: storage roles, mount targets and persistence requirements;
- `networking`: networks, ports, routing and ingress requirements;
- `infrastructure`: architecture, Docker/Compose requirements and minimum capacity;
- `secrets`: required secret names/types/references, never secret values;
- `health`: readiness and health checks;
- `operations`: initialization, migration, backup, restore and recovery capabilities;
- `integrity`: manifest, lock, composition and descriptor hashes;
- `provenance`: source repository/commit, workflow and build provenance.

The same consumer specification requires exact OCI digest identity, immutable app commits, complete dependency closure, compatibility checks, service dependency/readiness/health data, storage/network references and an explicit override allowlist. Environment-specific allocations belong to DT Master, not NDF.

These are consumer expectations recorded in architecture documentation, not implemented DT Master runtime behavior.

## 6. Contract decisions for M4.2.6.2

1. NDF remains the sole authority for PDD schema, generation, validation and publication semantics.
2. DT Master architecture documentation is the consumer requirements source; its future implementation must independently validate PDD and evidence.
3. A PDD must be bound to one exact OCI digest and the matching lock-v2 and M4.2.5 verification evidence.
4. Bench applications, independently distributed container services and external requirements remain distinct typed inventories. They must never be flattened into a single app list.
5. Actual app commits come from verified post-acquisition source evidence, not from resolver SHA fields or mutable Extension Version source refs.
6. Runtime versions must identify their evidence stage (builder vs final runtime); do not report builder-only tools as present in the deployed image.
7. Service descriptors currently do not prove a complete runnable service topology. Do not fabricate commands, health checks, storage, networks, resource requirements or override semantics.
8. Storage, networking, infrastructure capacity, health and operational capability gaps remain explicit. If these are mandatory for a deployable product, implementation must pause at the affected contract field and add the missing authoritative source rather than emit guessed values.
9. PDD immutable product facts remain separate from DT Master environment-specific overrides.
10. Signing and attestations remain M4.2.8; candidate workflow integration remains M4.2.7; DT Master implementation remains M4.3+.
