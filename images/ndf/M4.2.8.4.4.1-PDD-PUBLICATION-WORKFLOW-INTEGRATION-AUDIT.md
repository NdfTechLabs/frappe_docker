## 1. Objective

Audit the existing PDD publication workflow and its upstream evidence handoffs before adding keyless PDD signing. This step is read-only: it defines the integration contract and identifies required changes but does not modify workflow behavior.

## 3. Current publication flow

The existing `ndf-publish-product-deployment-descriptor.yml` is a manually dispatched workflow with four required inputs:

- source image build run ID;
- exact source build evidence artifact name;
- PDD binding-verification run ID;
- exact verified descriptor/report artifact name.

Its single `publish` job:

1. Checks out the publication workflow ref and installs Python validation dependencies, ORAS and Buildx.
2. Confirms the source build and binding-verification runs completed successfully and validates their workflow paths, run IDs, artifact names, run attempts and artifact availability.
3. Downloads the original build evidence and verified descriptor/report.
4. Authenticates to GHCR and publishes the PDD plus evidence bundle.
5. Writes the digest-pinned publication receipt to `$RUNNER_TEMP/pdd-publication-record.json`.
6. Uploads the receipt as `ndf-pdd-publication-${build_run_id}-${github.run_attempt}`.

The publication script already emits an immutable `repository@sha256:digest` reference in the receipt. The receipt schema binds the PDD descriptor identity/content hash, subject image repository/digest/platform, PDD OCI repository/digest, locator tag and evidence counts.

The current workflow has no job outputs, no PDD binding statement generation, no PDD Cosign signing/verification and no dedicated signing job. Its top-level permissions include `packages: write`, which would be inherited by all jobs unless permissions are moved to job scope.

## 4. Missing upstream source-image trust handoff

The deterministic PDD binding generator requires four authoritative inputs:

- validated PDD descriptor;
- PDD publication receipt;
- source-image trust verification result;
- source-image SLSA provenance predicate.

The current PDD publication workflow downloads the first two but does not download or validate the source-image trust result.

The source-image publishing workflow produces the missing trust evidence in a separate `sign-trust` job. For a single staging product on `main`, that job uploads:

`ndf-cosign-live-${image_id}-${run_id}-${run_attempt}`

The artifact contains the source `image-provenance-predicate.json`, `cosign-live-verification-result.json` and Cosign verification evidence. The original `ndf-publish-${image_id}-${run_id}-${run_attempt}` build artifact also contains the build-time provenance predicate and supporting build evidence.

The source `sign-trust` job is conditional: it runs only when the source image workflow is on `main`, a single product is selected, and official publication is disabled. Therefore PDD publication must fail closed if the exact attempt-scoped trust artifact is missing, expired, mismatched or not produced by a successful trust job. A build artifact alone is not sufficient evidence of verified source-image trust.

### Required source artifact correlation

Derive the expected image ID and attempt from the already-required build artifact name:

`ndf-publish-<image_id>-<build_run_id>-<run_attempt>`

Then derive the exact trust artifact name:

`ndf-cosign-live-<image_id>-<build_run_id>-<run_attempt>`

The publication workflow must:

1. Query the source build run's jobs as well as its artifacts.
2. Require the exact source run to be completed successfully and originate from `ndf-publish-product.yml` on `main`.
3. Require the exact `Live Cosign trust check for <image_id>` job to have completed successfully.
4. Require the derived trust artifact to exist, be unexpired and belong to the same source run/attempt.
5. Download the trust result and predicate from that exact artifact.
6. Compare the trust-artifact predicate with the build-artifact predicate before binding generation; reject disagreement.
7. Let the generator validate the source trust result, exact image digest, SLSA predicate type and canonical `predicate_sha256`.

No new manually supplied trust-artifact name is necessary if the publication workflow derives it deterministically from the already validated build artifact identity.

## 5. Recommended job and permission architecture

Keep the existing publication operation as a non-OIDC job and add a dependent PDD signing job.

### 5.1 Workflow-level permissions

Set the workflow default to read-only:

- `actions: read`
- `contents: read`

Do not grant `id-token: write` at workflow scope.

### 5.2 Publication job

The publication job retains only the permissions it needs:

- `actions: read`
- `contents: read`
- `packages: write`

It remains responsible for validating upstream runs/artifacts, downloading source and verification evidence, publishing the PDD OCI artifact and writing the receipt.

After publication, it must generate the deterministic PDD Statement v1 using the receipt and source trust evidence. It must make the exact predicate available to the PDD signing utility without reconstructing or editing the predicate. Prefer extending the generator with a separately atomically written predicate output rather than adding an ad hoc workflow JSON transformation.

The publication job uploads an attempt-scoped signing-input artifact containing at minimum:

- PDD publication receipt;
- original PDD Statement v1;
- exact PDD binding predicate;
- any non-secret metadata required to correlate the evidence.

The existing receipt artifact remains available under its current name and format for compatibility.

### 5.3 PDD signing job

Add a dependent job with `needs: publish`. It alone receives:

- `actions: read` (only if required for artifact operations);
- `contents: read`;
- `packages: write`;
- `id-token: write`.

The job must:

1. Download the exact attempt-scoped signing-input artifact produced by the current publication run.
2. Validate the publication receipt and derive the immutable PDD reference from its repository and digest; do not accept a mutable tag or an uncorrelated job output as the signing subject.
3. Install the pinned Cosign v3.1.4 using the same pinned installer revision already used by the product-image workflow.
4. Authenticate to GHCR using the job's package-scoped GitHub token.
5. Invoke `cosign_pdd_trust.py sign` with the exact immutable PDD reference, Statement v1 and predicate.
6. Independently invoke `cosign_pdd_trust.py verify` against the same immutable reference and expected predicate.
7. Validate and retain the normalized verification result, including the expected provisional rejection.
8. Upload a correlated trust-evidence artifact without exporting OIDC tokens, registry credentials or secrets.

The PDD signer utility checks the current workflow identity and runtime context. Therefore the signing operation must execute directly in `ndf-publish-product-deployment-descriptor.yml` on `refs/heads/main` with `workflow_dispatch`; do not move signing into a reusable workflow or another workflow.

## 6. Provisional-policy verification behavior

The PDD verification utility intentionally writes a normalized result with:

- signature, signer and transparency verification marked true after successful Cosign verification;
- one verified PDD binding attestation;
- `decision.status = rejected`;
- sole reason `IDENTITY_POLICY_PROVISIONAL`.

It then exits non-zero while the identity policy remains provisional. The workflow must distinguish this expected policy rejection from a cryptographic verification failure. It must not turn the result into a trusted status or mask arbitrary non-zero exits.

The signing integration should capture the verifier exit code and log, then require all of the following before treating the observation job as successful:

- the exact expected provisional-policy rejection message;
- a present, schema-valid normalized result;
- exact PDD repository/digest;
- signature, signer and Rekor/transparency verification true;
- exactly one verified binding attestation for the PDD digest;
- rejected decision with exactly `IDENTITY_POLICY_PROVISIONAL`.

Any other non-zero exit, missing output, schema failure or mismatch fails the job. The evidence must retain the rejected decision unchanged.

## 7. Publication receipt and evidence correlation

The receipt remains the authoritative publication record. The signature and binding attestation must both target `artifact.immutable_reference` from that receipt.

The attempt-scoped evidence chain must preserve:

1. source build run ID and attempt;
2. exact build evidence artifact name;
3. exact source-image Cosign trust artifact name;
4. PDD binding-verification run ID and artifact name;
5. PDD descriptor ID and canonical content hash;
6. PDD OCI repository, digest and immutable reference;
7. generated Statement and predicate;
8. PDD signing result;
9. PDD verification result and verified Cosign attestation output.

The signing job must verify the receipt-derived digest and preserve the original receipt. It must not replace the receipt with a trust result or claim that the provisional identity is trusted.

## 8. Failure and security boundaries

- A failed publication job prevents signing through the normal `needs` dependency.
- A failed signing or cryptographic verification job makes the overall publication workflow fail.
- No signing job runs with a missing or invalid receipt, binding statement, predicate or source trust result.
- OIDC permission is confined to the PDD signing job.
- The publication job does not receive OIDC permission.
- The consumer workflow remains read-only and is not modified in .4.4.
- No `contents: write`, `actions: write`, wildcard identity, tlog bypass or mutable artifact reference is introduced.
- The `product-pdd-publication` identity remains provisional.
- This integration does not modify product-image trust behavior or candidate signing.
