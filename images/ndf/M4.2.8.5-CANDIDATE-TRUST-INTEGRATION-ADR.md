# ADR — Split Candidate Artifact Trust Across M4.2, M4.3 and M4.4

**Status:** Accepted NDF working agreement; DT Master producer adoption pending  
**Repository:** NdfTechLabs/frappe_docker  
**Baseline:** NDF main; DT Master develop M4.1 accepted architecture  
**Date:** 16 November 2026  
**Related contract:** M4.2.8.5 — DT Master Candidate Producer / NDF Consumer Contract

## 1. Context

The accepted M4.1 architecture assigns distinct ownership to NDF Frappe Docker, DT Master and DT Tenant. NDF owns product composition, image construction, validation, publication, Product Deployment Descriptors (PDDs) and NDF-produced artifact evidence. DT Master owns Deployment Candidate creation and lifecycle, infrastructure and Bench orchestration, Deployment Build and Bench Deployment records, deployment eligibility and deployment authorization. DT Tenant is a tenant-facing service client and does not independently orchestrate Docker or build product images.

The current NDF repository contains candidate intake, OCI transport validation, candidate-to-lock adaptation, candidate-driven build orchestration, PDD generation/publication and correlated build-result machinery. It also defines the DT Master candidate-origin trust predicate. The DT Master develop-branch M4.1 specifications assign runtime adapter and Docker orchestration implementation to M4.3, and Deployment Candidate/Deployment Build lifecycle, candidate submission, asynchronous build tracking, descriptor/digest verification and immutable product deployment to M4.4.

Implementing the DT Master producer in M4.2 would cross the approved repository/milestone boundary and couple NDF completion to implementation owned by later DT Master milestones.

## 2. Decision

The NDF-side working agreement for M4.2.8.5 adopts the following contract decisions: (1) candidate identity is the exact DT Master Frappe document name with a shared 140-character constraint; (2) the payload mapping is reconciled to the M4.1 DocType fields and optional `requested_version` remains optional; (3) the NDF consumer targets the proposed GHCR/ORAS layout, subject to formal DT Master adoption; (4) result v1 remains unchanged and a separate digest-bound trust-evidence report is transported beside it; and (5) correlation IDs are required canonical UUIDs generated by DT Master and retained across retries. Actual producer workflow identity and GitHub App actor remain deferred until M4.4 live implementation.

Split implementation of the already accepted M4.1 producer/consumer architecture across the existing milestones:

1. **M4.2 (NDF Frappe Docker):** define the interoperable DT Master producer contract and implement the NDF consumer, candidate-origin verification, NDF image/PDD trust integration, and correlated NDF build evidence. Use deterministic fixtures and adversarial tests for DT Master-produced inputs. Do not modify DT Master or DT Tenant.
2. **M4.3 (DT Master):** implement the accepted Node/Bench ownership and runtime-orchestration foundation, including Host/Docker adapters, Docker/Compose lifecycle, durable operations, worker execution, endpoint registration and required infrastructure/secret execution mechanisms. M4.3 provides the runtime foundation; it is not the owner of the complete candidate build/deployment lifecycle.
3. **M4.4 (DT Master):** implement the DT Master Deployment Candidate producer and lifecycle, candidate OCI publication, candidate-origin signing/attestation, dispatch to NDF, Deployment Build tracking, asynchronous result reconciliation, independent NDF image/PDD verification and immutable product deployment through M4.3 adapters.
4. **M4.7:** perform live cross-repository end-to-end, security, migration, recovery, rollback and production-readiness acceptance.

This decision allocates implementation work. It does not alter, reopen or supersede the accepted M4.1 architecture, data ownership, security model, runtime adapter contract, durable operation contract, secret transport contract or deployment authorization policy.

## 3. Trust and ownership invariants

The following accepted rules remain binding:

- A component signs and attests only to artifacts it produces.
- DT Master signs and attests to its own candidate OCI artifact.
- NDF independently verifies DT Master's candidate signature, producer identity, transparency evidence, candidate-origin predicate, immutable subject digest and exact payload bytes. NDF never signs or re-attests the DT Master candidate.
- NDF signs and attests to the NDF-produced image and PDD artifacts.
- DT Master independently verifies the NDF image signature/provenance and PDD signature/PDD-to-image binding before considering deployment eligibility.
- A successful build or cryptographic verification is not deployment authorization. Bench Deployment policy and execution gates remain separate.
- Signer identity policy remains provisional until its separately authorized review. Implementation and staging tests must not weaken identity policy or grant deployment authorization.

## 5. Result ownership and trust-result semantics

The M4.1 Section 16.7 contract requires three separately typed trust outcomes:

1. NDF verification of DT Master's candidate-origin signature/attestation.
2. DT Master verification of the NDF image signature and SLSA provenance.
3. DT Master verification of the NDF PDD signature and PDD-to-image binding attestation.

These are not all decisions that NDF can authoritatively report. The implementation must preserve verifier ownership:

- The **NDF terminal build result** reports NDF's candidate-origin verification outcome and immutable report reference, and provides immutable references to NDF-produced image/PDD signatures, attestations and NDF-side verification reports.
- The **DT Master Deployment Build record** stores the NDF result and independently performs the image and PDD verification. It records its own two verification outcomes and report references.
- The **DT Master aggregate build/trust view** correlates all three outcomes using the shared correlation ID and exact candidate/image/PDD digests. It must not attribute Master verification decisions to NDF.

The current NDF deployment-build-result-v1 schema does not contain the complete trust-evidence structure required for this handoff. M4.2.8.5 must define a versioned result extension without silently changing v1 semantics. Because v1 rejects additional properties, a new major result schema version or an explicitly versioned companion trust-evidence report is required. The normative contract must choose and test one approach before implementation.

A trust-policy rejection must not be represented as an eligible successful build. Where build execution completed but trust policy rejects the artifact (including provisional identity policy), the result must preserve both facts separately and the overall acceptance outcome must remain non-successful/non-eligible.

## 6. M4.2 acceptance boundary

M4.2 may implement and accept the NDF side using controlled candidate fixtures, including:

- valid candidate payload, OCI envelope and candidate-origin statement fixtures;
- invalid signature, signer, issuer, transparency evidence or predicate;
- candidate ID, artifact digest, layer digest and payload hash mismatches;
- invalid dispatch/correlation context;
- malformed, missing or unsupported candidate data;
- image/PDD trust-evidence absence, mismatch or policy rejection;
- result correlation, attempt identity, immutability and sanitized failure cases.

Fixture acceptance proves NDF consumer enforcement only. It does not prove DT Master serializer compatibility, real GHCR/ORAS publication, actual DT Master OIDC identity, live dispatch or cross-repository interoperability. Those require M4.4 producer implementation and M4.7 integration acceptance.

M4.2.9 must record the deferred live interoperability gate explicitly. It must not describe fixtures or static workflow tests as a live end-to-end run.

## 7. Consequences

### Positive

- M4.2 remains within its approved NDF repository and milestone scope.
- NDF consumer behavior can be implemented and tested without waiting for DT Master application changes.
- DT Master receives a concrete, versioned producer specification before M4.4 implementation.
- M4.3 can focus on the accepted runtime/orchestration foundation without absorbing candidate-build lifecycle work.
- M4.4 can implement the producer against an already tested consumer contract.
- Verifier ownership and deployment authorization remain explicit.

### Constraints and follow-up

- The candidate payload field mapping must be reconciled against the actual DT Master Deployment Candidate serializer when it is implemented; no serializer is assumed to exist today.
- The detailed GHCR/ORAS candidate OCI layout is an NDF producer/consumer proposal, not a transport mechanism mandated by M4.1. DT Master must explicitly adopt it before production dispatch.
- Exact DT Master OIDC certificate identity and workflow path/ref must be observed from a real M4.4 signing run before the NDF allowlist is finalized.
- The candidate ID constraints must be consistent across candidate payload and origin predicate schemas.
- Retention must follow the platform audit-retention decision; GitHub Actions artifacts are transport/evidence, not a substitute for DT Master's durable Deployment Build record.
- NDF must not receive candidate-package write credentials, and DT Master must not receive NDF product/PDD package-write credentials.

## 8. Approval and change control

This ADR is proposed for review. Acceptance records agreement on milestone allocation and implementation boundaries only. It does not authorize DT Master M4.3/M4.4 implementation, change any M4.1 decision, confirm signer identity policy, promote production artifacts or grant deployment authorization.

Any proposed change to M4.1 artifact ownership, operation ownership, adapter authority, secret ownership or deployment authorization requires the existing explicit architecture change process.
