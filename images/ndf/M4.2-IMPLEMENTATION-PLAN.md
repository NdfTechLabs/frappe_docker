## 4. Findings driving the implementation

The readiness review identified the following required changes:

1. **Source revision traceability:** preserve upstream Bench acquisition through `bench init --apps_path` using the requested branch/tag references. Capture the actual commit acquired for every Bench app and Frappe after acquisition; verify those revisions and publish them in the descriptor. The resolver's pre-build SHA is resolution-time evidence, not proof of the installed revision.
2. **Resolution policy enforcement:** policies such as `require_immutable_commit` and `fail_on_unverified_compatibility` must be enforced across inherited composition. Branch names must not be classified as development or production references; reference kind and provenance are recorded independently.
3. **Application descriptor completeness:** the current `application-manifest-v1` does not yet capture the complete approved Marketplace App Descriptor. Extend the existing schema/resolver path and define migration rules; do not create a competing manifest system.
4. **Capability and service composition:** distinguish Bench applications, independently built runtime services, explicitly selected optional capabilities and external service dependencies.
5. **Immutable base images:** pin builder and runtime base images by OCI digest, recording platform and provenance.
6. **Installed-source verification:** image validation must inspect actual installed Git HEADs and compare them with the lock, including the Frappe framework.
7. **Product Deployment Descriptor:** add a versioned descriptor generated from the actual verified image and bound to its exact OCI digest.
8. **Candidate-driven CI/CD:** extend existing workflows to accept authorized Deployment Candidate inputs and return structured, traceable, idempotent build results. Initial DT Master integration may poll; authenticated callbacks can be a later enhancement.
9. **Artifact trust:** implement signing, attestations and automated verification. Missing, invalid, untrusted or mismatched trust evidence must block production eligibility.

These findings are the approved implementation drivers. Detailed file-level changes and decisions are to be documented as each work package is implemented.

## 8. Implementation controls and decisions to preserve

- Preserve the upstream Frappe Docker foundation; extend the existing layered build/runtime architecture.
- Extend the existing resolver, lock and image builder; do not create a competing manifest resolver or builder.
- Record requested Git refs separately from actual acquired source commits. Resolution-time SHA observations are useful provenance but do not prove what Bench acquired. The verified post-acquisition commit inventory and published OCI digest are authoritative identities for the built artifact.
- Keep independent service artifacts separate from Bench applications.
- Require explicit selection of optional capabilities; do not silently include them in production compositions.
- Keep GHCR publishing credentials within NDF/GitHub Actions. DT Master must not receive unrestricted publishing credentials.
- Build success alone does not establish production eligibility. Compatibility, source integrity, descriptor validation and artifact trust must all pass.
- Keep DT Master orchestration and DT Tenant site lifecycle responsibilities out of this repository's M4.2 implementation.
- Preserve existing product build behaviour through regression coverage as the pipeline is extended.
- Document technical decisions, schema changes, affected files, tests, failures and resolutions during the relevant work package.

## 11. M4.2.3 dependency ownership decision — 2026-11-13

**Accepted architecture: native dependency resolution with NDF verification (Option A).** This decision governs M4.2.3 and supersedes any conflicting M4.2.3 adapter-resolution implementation sequence in subordinate documents.

### 11.1 Responsibility split

- NDF owns product composition, optional capability/service selection, compatibility and requested application source-reference policy.
- Product manifests retain rolling branch references, and Bench acquires the requested branch through its existing upstream path. NDF records the actual checked-out commit after acquisition as build provenance. A pre-build SHA observation does not replace the branch or prove the acquired revision. A later build follows the branch again and may acquire a newer commit.
- Upstream Bench and its native package managers/build mechanisms own Python, Node and OS dependency resolution and installation. NDF must not duplicate these resolvers or installers.
- NDF captures the installed package inventory after the native installation/build stages and verifies it against the accepted target runtime, approved source policies, base inventory and build requirements.
- NDF records supporting provenance needed to substantiate source policy: consumed dependency/lockfile identities and hashes, native installer/resolver versions and configuration where observable, repository/artifact evidence, restricted-egress/build records, actual installed inventories, source revisions and base-image digests.
- An installed package list alone does not prove package origin. Where available evidence cannot establish an applicable source-policy requirement, report the gap or fail the relevant eligibility check; do not claim provenance that the inventory cannot support.

### 15.1 Source verification boundary

The build must inspect the actual Bench-acquired Frappe and application repositories before `.git` cleanup. At minimum, evidence must identify the canonical credential-free repository origin and actual Git HEAD for each repository. A deterministic source-tree fingerprint must also be captured so that the retained source files can be compared with the verified pre-cleanup state.

The exact fingerprint algorithm and treatment of generated, ignored, untracked, submodule and installation-modified files remain detailed-design items. A Git commit identifier alone is not sufficient proof that the retained image filesystem still contains the corresponding source tree.

The source evidence must be carried forward and cryptographically bound to the final image digest. The independent verifier must not treat the build-time success report as proof by itself.

### 15.2 Independent composition verification

Verification must derive the expected composition from the authoritative generated lock and composition inputs, then inspect the actual image. It must fail closed for missing or unexpected Bench applications and for missing or unexpected independent services. It must preserve the M4.2.3 separation between Bench applications, independent services and external requirements, and correctly account for explicitly selected optional capabilities.

### 15.3 Publication and consumer artifacts

Registry publication is gated on successful build validation and required independent verification. The published image is identified by its immutable OCI digest, not merely by a tag. Consumer-facing deployment and verification artifacts accompany the image and identify the exact digest to which they apply.

The detailed artifact schemas and division of responsibility between M4.2.5 verification evidence and the M4.2.6 Product Deployment Descriptor remain subject to their respective work-package contracts. This approval does not move the Product Deployment Descriptor implementation into M4.2.5.

### 15.4 Retention and cleanup

Retention must be evaluated and configured independently for:

- GitHub Actions workflow artifacts;
- GHCR packages, image manifests, tags and untagged images; and
- release assets or another durable evidence store.

Temporary CI retention must not be mistaken for the supported lifetime of a production image or its deployment evidence. Cleanup must not remove an image digest or its required evidence while a retained deployment, rollback path or audit obligation still depends on it.

Exact retention periods, GitHub repository/organization maximums, GHCR cleanup behaviour and any durable evidence-storage mechanism remain to be established through configuration inspection and a separate retention-policy proposal. No numeric retention period is approved by this decision.

### 15.5 Implementation boundary

The six principles above are approved. M4.2.5 implementation has now been authorized, beginning with M4.2.5.1. The source-tree fingerprint algorithm ndf-source-tree-sha256-v1 is defined and its standalone utility and initial tests are committed. Remaining design items include the Git tracked/untracked/ignored-file provenance policy; source-evidence schema; independent verifier interface and trust boundary; service-composition inspection mechanism; publication workflow dependency and failure handling; consumer artifact contract; and numeric retention/cleanup policy. Implementation must continue package-by-package with tests and evidence; approval does not imply completion of A10 or A11.

### 15.6 M4.2.5 implementation authorization and first checkpoint — 14 November 2026

The platform owner accepted the proposed A10/A11 implementation plan and authorized work to begin with M4.2.5.1. The standalone source-tree fingerprint utility uses algorithm ndf-source-tree-sha256-v1. It fingerprints directories, complete regular-file contents, executable-bit state and symbolic-link targets; excludes only .git entries; rejects unsupported filesystem objects; and uses globally sorted relative paths and length-prefixed canonical JSON records.

Initial local tests: 12 passed. Local compileall passed. These are focused tests only; full NDF regression, lint/pre-commit and CI remain outstanding. The utility is not yet integrated into the build inventory capture or Containerfile. A10 and A11 remain pending acceptance.

The fingerprint establishes filesystem snapshot equality, not by itself correspondence to a Git commit. M4.2.5.2 must establish tracked-content correspondence to actual Git HEAD and classify untracked, ignored and generated files before the fingerprint can support the full A10 claim.
