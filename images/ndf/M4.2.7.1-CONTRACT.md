# M4.2.7.1 — Candidate Artifact and Workflow Contract

**Repository:** NdfTechLabs/frappe_docker
**Baseline:** feat/M4.2.6
**Status:** NDF-side contract proposal; DT Master and DT Tenant remain read-only references.

## 1. Ownership

DT Master owns candidate creation, authorization, lifecycle, build-attempt records and deployment eligibility. NDF consumes and validates the candidate, builds/verifies an image, publishes the image and PDD, and emits build evidence. NDF does not create candidate/build DocTypes or decide deployment readiness. DT Tenant has no direct NDF integration.

The NDF schemas are validation views mapped to the documented DT Master contracts, not replacements for authoritative Master records. Candidate schema 1.0.0 is reconciled to the documented M4.1 Deployment Candidate fields. The exact Frappe document name is `candidate_id`; `candidate_code` remains a separate business identifier. The NDF payload and origin predicate share the same 140-character candidate ID constraint. M4.4 must validate the actual serializer output before production dispatch.

## 2. Candidate OCI transport

Dedicated private package: ghcr.io/ndftechlabs/dt-master-deployment-candidates

DT Master publishes exactly one candidate JSON file as an ORAS-compatible OCI artifact in the dedicated private package. The producer and consumer contract is:

| OCI element            | Required value                                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------------------------- |
| Registry/repository    | `ghcr.io/ndftechlabs/dt-master-deployment-candidates`                                                   |
| Manifest artifact type | `application/vnd.ndf.deployment-candidate.v1`                                                           |
| Config                 | ORAS default empty config; media type `application/vnd.oci.empty.v1+json`, empty JSON object bytes `{}` |
| Layer count            | Exactly one                                                                                             |
| Layer filename         | `deployment-candidate.json`, represented by descriptor annotation `org.opencontainers.image.title`      |
| Layer media type       | `application/vnd.ndf.deployment-candidate.v1+json`                                                      |
| Manifest annotations   | `io.ndf.candidate.id`, `io.ndf.candidate.schema-version`, and `io.ndf.candidate.payload-sha256`         |
| Payload                | UTF-8 JSON bytes conforming to `deployment-candidate-v1.schema.json`; no tar/gzip wrapping              |

The manifest artifact type and layer media type are intentionally distinct. The layer title annotation is the filename ORAS uses when pulling the file. The candidate publisher must run ORAS with the candidate file as a single file argument (not a directory), the explicit artifact type and layer media type, and the three manifest annotations. It must capture the pushed manifest digest and calculate SHA-256 over the exact candidate JSON file bytes before dispatch.

The dispatch envelope carries candidate ID, digest-pinned OCI reference, SHA-256 of the exact candidate JSON payload bytes and a required canonical lowercase UUID correlation ID. DT Master generates the correlation ID at request start and retains it across retries. The three manifest annotations must agree with the envelope and the parsed candidate. The NDF consumer requires the config descriptor to be the specified empty config, exactly one layer with the specified media type and title, and no unexpected layers or file paths.

Canonical reference: `ghcr.io/ndftechlabs/dt-master-deployment-candidates@sha256:<64 lowercase hex>`

Tags are discovery labels only. NDF rejects tag-only references, alternate registries/packages, malformed references and references whose digest differs from the authenticated envelope. Verify the OCI manifest digest through ORAS, validate artifact type/config/layer structure and manifest annotations, pull by the digest-pinned reference, then verify the exact downloaded payload bytes against both the layer descriptor digest/size and authenticated envelope payload SHA-256 before parsing. Registry manifest digest, OCI layer digest and dispatch payload SHA-256 are separate integrity checks; where the layer is the uncompressed single JSON file, the layer digest and payload SHA-256 must match.

Master documentation mandates immutable reference plus digest but does not prescribe OCI, ORAS or GHCR. GHCR is the selected integration direction; this detailed layout is the NDF producer/consumer proposal that must be explicitly accepted and implemented by DT Master before production dispatch.

## 3. Package permissions and identity separation

| Actor                         | Credential                    | Minimum permission                                    | Prohibited access           |
| ----------------------------- | ----------------------------- | ----------------------------------------------------- | --------------------------- |
| DT Master candidate publisher | Master workflow GITHUB_TOKEN  | packages: write on candidate package                  | NDF image/PDD package write |
| DT Master dispatcher          | GitHub App installation token | Actions: write on NDF repository, limited to dispatch | GHCR credentials            |
| NDF candidate reader          | NDF workflow GITHUB_TOKEN     | packages: read on candidate package                   | Candidate package write     |
| NDF image/PDD publisher       | NDF workflow GITHUB_TOKEN     | packages: write on NDF-owned image/PDD packages       | Candidate package write     |

The candidate package is private and explicitly grants NDF repository Actions access with read permission. Master publishes with its own workflow token; NDF reads with its own workflow token. The App token authorizes dispatch only and is not GHCR authentication. NDF job permissions are scoped narrowly; only publication jobs receive packages: write. The workflow verifies expected dispatching App/repository/event context; candidate ID alone is not authentication.

Do not grant Master write access to NDF product/PDD packages or NDF write access to the candidate package.

## 4. Digest verification and fail-closed rules

1. Validate dispatch envelope and authenticated dispatch context before registry access.
2. Allow only exact GHCR host and candidate package path, with @sha256 and 64 lowercase hex characters. Reject tags and other forms.
3. Fetch OCI manifest by digest and require returned digest to equal requested digest.
4. Validate OCI artifact/media type and require exactly one candidate JSON layer with expected media type/name.
5. Verify downloaded layer bytes against the authenticated payload SHA-256 before JSON parsing.
6. Parse JSON with duplicate-key rejection; validate schema; then validate candidate identity, unique app IDs, descriptor digests, immutable commits, supported product/runtime/platform and composition hash.
7. Reject mismatch; never fall back to tag, alternate registry or stale artifact.
8. Candidate values must never become shell code, workflow names, paths or arbitrary build commands.

## 5. Invalid references and artifact cases

Reject tag-only and missing-digest references; malformed, uppercase or mismatched digests; wrong registry/owner/package; URL schemes, query/fragment, whitespace, traversal and extra path components; returned OCI digest mismatch; wrong artifact/media type; missing/multiple candidate layers or wrong layer name; payload SHA mismatch; invalid/duplicate-key JSON; unsupported schema; candidate ID mismatch; duplicate app identity; missing descriptor digest; mutable commit; composition hash mismatch; unsupported product/runtime/platform; unapproved parameters; secrets, tenant data, FQDN, TLS keys or arbitrary commands. Intake failures are terminal for that run and prevent all build/publication stages.

## 6. Retention and audit

Candidate artifacts remain available for the lifetime of every referencing candidate/build record plus the platform audit-retention period. Do not delete or overwrite referenced candidate artifacts. Configure package cleanup and administrative access so referenced versions are not automatically pruned. Digest pinning provides content identity, not permanent availability: GHCR package administrators can delete versions. Tags are not used for post-dispatch retrieval.

NDF result artifacts and PDD references remain retrievable for the corresponding Master build/audit retention period; workflow logs/artifacts alone are not the durable system of record. The platform authority must define the numeric retention period; NDF does not invent a conflicting schedule. Deletion requires coordinated approval and retained digest/deletion audit evidence.

## 7. Workflow composition

DT Master dispatches with a narrowly scoped GitHub App installation token. Use reusable workflow_call stages where existing interfaces can be safely extracted: a thin candidate orchestrator calls candidate validation, build/image verification/publication and PDD stages. Preserve existing manual product workflows and reuse their validated scripts/stages. Keep permissions at the narrowest job boundary.

## 8. Result and retry contract

NDF emits deployment-build-result-v1 JSON binding candidate ID, immutable OCI reference and manifest digest, payload digest, correlation ID, NDF workflow run/source commit, status, composition hash, resolved lock hash, immutable image digest, PDD reference/digest/content hash, provenance and safe failure code/summary. A successful result requires image and PDD evidence from the same build. Results contain no secrets, raw stack traces, shell output or tenant/customer data.

Every NDF run is a distinct attempt/result. Retries never overwrite terminal results. NDF does not claim exactly-once dispatch; DT Master owns request idempotency and Deployment Build lifecycle.
