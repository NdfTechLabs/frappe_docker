**Repository:** `NdfTechLabs/frappe_docker`  
**Branch:** `feat/M4.2.8`

## 1. Purpose

Select a deterministic Cosign toolchain for M4.2.8.3 and record the CLI behavior that the local signing/verifier implementation must target. This is a dependency and interface decision only. It does not modify production workflows or claim that NDF signing has been operationally tested.

## 2. Selected versions and immutable pin

| Component | Selection | Pin/evidence |
|---|---|---|
| Cosign CLI | `v3.1.4` | Immutable upstream release; published 20 October 2026. Release notes include fixes for image-index local bundle discovery and verification handling. |
| Installer action | `sigstore/cosign-installer` v4.1.2 | Full action commit: `6f9f17788090df1f26f669e9d70d6ae9567deba6` |
| Installer action integrity | Upstream `action.yml` at v4.1.2 | Blob SHA observed from GitHub: `4c29a093505a39dbafcf25cc5d573f0b4df6f8a6`. The action verifies the downloaded Cosign release binary against release checksums. |
| Requested CLI version | `v3.1.4` | Pass explicitly as `cosign-release: v3.1.4`; do not rely on the installer's default version. |

The installer v4 line is required for Cosign v3. The action is pinned to a full commit SHA, not a movable tag. The installer itself validates the downloaded Cosign release binary using its published checksum metadata. The selected Cosign version is explicit so an installer update cannot silently change the CLI version.

## 3. Why Cosign 3.1.4

- It is the latest upstream Cosign release observed on 15 November 2026.
- Cosign 3.1.x uses the Sigstore bundle format by default while retaining verification support for legacy bundles.
- The release includes subsequent fixes to attestation handling and image-index bundle discovery.
- The selected installer v4.1.2 supports Cosign v3 and permits an explicit `cosign-release` input.

No third-party signing action is selected. NDF will call the Cosign CLI directly so the exact commands, identity parameters, digest subject and fail-closed behavior remain visible in repository-owned scripts/workflows.

## 4. CLI contract for the implementation

All image operations must use a fully qualified immutable OCI reference:

```text
ghcr.io/<owner>/<image>@sha256:<64-lowercase-hex>
```

Signing job requirements:

- Job permission `id-token: write` is required for GitHub OIDC keyless signing.
- The signing job also needs `packages: write` to publish signature and attestation OCI referrers to GHCR.
- No private signing key or long-lived signing secret is introduced.
- Signing is performed only after the existing staging digest, image validation and publication evidence gate succeed.

Target CLI forms to be exercised against the pinned binary:

```bash
cosign version

# Keyless image signature over the immutable digest.
cosign sign --yes "$IMAGE_REF"

# SLSA provenance v1 attestation over the same immutable digest.
cosign attest --yes --type slsaprovenance1 \
  --predicate "$PROVENANCE_PREDICATE" "$IMAGE_REF"

# Independent signature verification; exact identity and issuer are mandatory.
cosign verify "$IMAGE_REF" \
  --certificate-identity "$EXPECTED_CERTIFICATE_IDENTITY" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com"

# Independent provenance verification; exact identity, issuer and predicate type.
cosign verify-attestation "$IMAGE_REF" \
  --type slsaprovenance1 \
  --certificate-identity "$EXPECTED_CERTIFICATE_IDENTITY" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com"
```

The `slsaprovenance1` type is required for the SLSA Provenance v1 predicate URI (`https://slsa.dev/provenance/v1`). Do not use the older `slsaprovenance` type, which represents the v0.2 predicate family.

Cosign verification must not use `--insecure-ignore-tlog`, identity regular expressions, issuer regular expressions, `--check-claims=false`, or a mutable image tag. Rekor/transparency verification remains enabled. A failed command or absent signature/attestation is a hard failure.

## 5. Provenance payload shape

The repository's existing `ndf-image-provenance-v1.schema.json` validates an in-toto Statement with:

- `_type = https://in-toto.io/Statement/v1`;
- exactly one subject containing the exact image digest;
- `predicateType = https://slsa.dev/provenance/v1`;
- a SLSA provenance v1 predicate and the NDF `ndf_build` evidence extension.

Cosign's `attest --predicate` input is the predicate document, not a pre-wrapped in-toto Statement. The implementation must therefore generate a predicate JSON file from the validated NDF build evidence and let Cosign construct/sign the in-toto envelope. The verified output from `cosign verify-attestation` must be decoded and reconstructed/validated as the complete Statement against the existing schema. Do not feed a complete Statement as the predicate input.

The subject digest must be the same immutable digest used by `cosign sign`. The provenance generator must derive every claim from the existing build metadata, lock, inventory, validation reports and source-provenance evidence; it must not synthesize missing facts.

## 6. Verification boundary

Cosign is responsible for cryptographic verification of:

- signature validity against the Sigstore trusted root;
- Fulcio certificate chain and keyless identity;
- exact certificate identity and OIDC issuer;
- Rekor transparency evidence (including inclusion proof);
- attestation signature and in-toto subject claim.

NDF's verifier remains responsible for additional semantic checks:

- the certificate identity is an exact entry in the artifact trust policy;
- the workflow/ref/event/repository and reusable workflow claims meet NDF policy;
- the attestation predicate type is exactly SLSA provenance v1;
- the single attestation subject digest equals the requested image digest;
- the NDF provenance statement passes its JSON Schema and evidence cross-checks;
- all existing image validation and publication-gate evidence remains valid.

A successful Cosign command alone is not an NDF production-eligibility decision.

## 7. Workflow boundary for M4.2.8.3

The product publication workflow currently performs build, staging validation, publication gate and optional official source-tag promotion in one job. The future integration must insert signing and independent verification after the publication gate and before promotion.

The preferred least-privilege split is:

1. **Build/validate job:** existing permissions; push staging image and produce immutable digest plus evidence.
2. **Sign job:** `packages: write`, `id-token: write`; consume immutable digest and validated evidence; sign and attest exact digest.
3. **Verify job:** `packages: read`, `contents: read`; no OIDC token permission; independently verify signature, signer identity, transparency and provenance.
4. **Promote job:** `packages: write`, no OIDC token; only runs after the verification job succeeds; promotes the exact verified digest and rechecks the resulting tag digest.

If the existing workflow's matrix or evidence transport makes this split unsafe, stop and document the blocker rather than broadening permissions or weakening the gate. Staging-only builds must remain non-promoted.

The separate release workflow must also be updated in its own later substep to verify trust before semantic/stable tag promotion. This toolchain package does not modify that workflow.

## 8. Acceptance and remaining checks

This package accepts the version/pin selection and CLI design based on upstream release metadata and documentation. It does not yet accept command execution or workflow interoperability.

Before production workflow changes:

- run the pinned installer and verify `cosign version` reports `v3.1.4`;
- exercise `sign`, `attest --type slsaprovenance1`, `verify` and `verify-attestation` against a disposable GHCR image using a controlled GitHub Actions test workflow;
- capture the real Fulcio certificate identity and GitHub OIDC claims;
- verify that Cosign v3.1.4 output can be decoded into the exact in-toto Statement shape required by the NDF schema;
- confirm that missing Rekor evidence, wrong identity, wrong issuer, wrong predicate type and wrong digest all fail.

No production workflow changes are included in M4.2.8.3.1.
