# M4.2.7.5 — Correlated Build Result Contract

**Repository:** `NdfTechLabs/frappe_docker`  
**Branch:** `feat/M4.2.7`  
**Status:** Contract baseline for implementation  
**Schema:** `schemas/deployment-build-result-v1.schema.json`

## 1. Authority and scope

NDF emits one terminal build result for each candidate workflow run attempt. DT Master remains the owner of candidate lifecycle, request idempotency, deployment eligibility and deployment decisions. NDF reports build evidence only; it does not mark a candidate deployable or ready.

This work package changes only `NdfTechLabs/frappe_docker`. It does not implement callbacks, signing/attestation, DT Master or DT Tenant changes, runtime deployment, or official product-tag promotion.

## 2. Result identity and correlation

The result identity is deterministic within one NDF attempt:

- `result_id = ndf-<run_id>-<run_attempt>`
- `workflow.run_id` and `workflow.run_attempt` identify the GitHub Actions execution.
- `candidate_id`, exact digest-pinned `candidate_artifact_ref`, its manifest digest, exact payload SHA-256 and optional `correlation_id` are copied from the authenticated dispatch envelope.
- The result artifact name is `ndf-candidate-result-<run_id>-<run_attempt>`.
- A GitHub rerun increments `run_attempt`; a separate dispatch receives a new `run_id`. Neither can overwrite an earlier result artifact.

The candidate ID and correlation ID are opaque values, not authorization credentials, paths, artifact names or registry destinations. NDF does not promise exactly-once dispatch. DT Master reconciles duplicate requests using its own request/candidate lifecycle and the returned run correlation.

## 3. Terminal status semantics

The terminal result writer emits only:

- `succeeded`: dispatch gate, candidate intake/adapter, image build/verification and PDD verification/publication all concluded successfully, and the required outputs are present and mutually bound.
- `failed`: at least one required stage failed or the success evidence is missing, malformed or inconsistent.
- `cancelled`: a required stage was cancelled and no required stage failed. If GitHub cancels the entire workflow before the finalizer can run, the GitHub run conclusion is authoritative and Master must reconcile the missing result.

`queued` and `in_progress` remain reserved schema values for future status-query integration; this finalizer does not publish interim results. A skipped downstream job caused by an earlier failure is not itself a success or a separate failure cause.

## 4. Required bindings

Every result contains schema version, result ID, candidate ID, immutable candidate reference and manifest digest, exact candidate payload SHA-256, workflow repository/name/run ID/run attempt/run URL/source commit, terminal status and start time.

A successful result additionally requires:

- candidate composition hash and exact lock-v2 SHA-256;
- image repository, immutable image digest and digest-addressed image reference;
- PDD immutable OCI reference, OCI digest and canonical content hash;
- provenance reference to the originating NDF workflow run;
- completion timestamp.

The successful result is assembled from outputs of the current parent workflow attempt only. The PDD reusable stage already validates its evidence against candidate identity, image digest, payload hash, lock hash and composition hash. The result writer cross-checks the PDD outputs and build outputs before allowing `succeeded`.

For failed/cancelled results, composition/lock/image/PDD fields are included only when safely available and validated. They are not fabricated when intake or an earlier stage did not produce them.

## 5. Failure classification and sanitization

Stable failure codes are stage-oriented and allowlisted:

- `DISPATCH_NOT_AUTHORIZED`
- `CANDIDATE_INTAKE_FAILED`
- `CANDIDATE_ADAPTER_FAILED`
- `IMAGE_BUILD_OR_VERIFICATION_FAILED`
- `PDD_PUBLICATION_FAILED`
- `RESULT_EVIDENCE_INVALID`
- `WORKFLOW_CANCELLED`

The summary is a fixed, non-sensitive sentence selected by the result writer. Do not copy exception text, logs, command output, registry credentials, secrets, tenant/customer data or arbitrary upstream strings into the result.

## 6. Transport and retention

The finalizer validates the result against the versioned Draft 2020-12 schema, writes JSON atomically, and uploads exactly one attempt-scoped artifact with `if-no-files-found: error`. The result artifact uses the repository's configured GitHub Actions artifact retention policy; the current implementation requests 90 days. GitHub run metadata remains the execution-level fallback. Artifact storage is transport, not a replacement for the DT Master Deployment Build record.

The finalizer job uses least privilege: `contents: read` and `actions: read`; it does not receive `packages: write`.

## 7. Idempotency and immutability

The writer refuses to overwrite an existing output file. Artifact names are derived exclusively from GitHub run ID and attempt. Re-running the same attempt cannot create a second logically different result under the same result ID; the finalizer must fail closed if its deterministic result file already exists. New attempts get distinct result IDs and artifact names. No mutable candidate-level `latest` result is published.

## 8. Acceptance criteria

M4.2.7.5 is complete when:

1. The schema requires exact candidate payload hash and workflow run attempt, and applies success-only evidence requirements.
2. The result writer strictly parses trusted workflow metadata, derives the candidate manifest digest from the immutable reference, enforces terminal status semantics and validates the complete result against the schema.
3. The entry workflow has a finalizer job with `if: always()` and dependencies on every candidate stage.
4. Success is possible only when all required upstream jobs succeeded and the image/PDD outputs are present and valid.
5. Failure and cancellation produce sanitized terminal results when the finalizer can execute; missing results remain reconcilable from GitHub run metadata.
6. Result artifacts are unique per run/attempt, immutable, validated and uploaded with a deterministic name.
7. Tests cover success, each stage failure, cancellation, missing outputs, malformed references/hashes, correlation propagation, attempt identity, output overwrite protection and schema rejection.
8. Workflow contract tests verify job ordering, `always()`, least privilege, artifact naming/retention and no package-write permission on the finalizer.
9. Local NDF regression, `actionlint`, all pre-commit hooks and `git diff --check` pass. A synthetic GitHub Actions staging run is recorded separately before .7.4/.7.5 are declared operationally accepted.

M4.2.7.5 does not close the real DT Master OCI producer/consumer gate and does not authorize M4.2.8.
