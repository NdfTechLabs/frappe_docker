## 1. Purpose and authority

This document is the authoritative NDF target-runtime support baseline for M4.2.3 package resolution.

It defines which operating-system, architecture, Python and Node runtime families NDF may target when resolving package dependencies for the current Frappe v16 layered product images. It also defines which native package-manager adapter combinations may be implemented first.

This is a support boundary, not a claim that every adapter is already implemented or accepted. A combination is production-supported only after the exact target metadata can be captured from the selected base-image digest and the corresponding adapter passes target-specific integration tests.

The matrix is derived from:

- NDF's current product image definitions and image-build implementation.
- NDF's actual layered Containerfile and product build/publish workflows.
- The upstream Frappe Docker image definitions and published `frappe/base` and `frappe/build` v16 image metadata.

Mutable image tags are observations, not immutable runtime identities. Every actual build must record the resolved builder and runtime image digests and the exact runtime versions observed inside those images.

## 2. NDF build-path facts

The three current NDF products — `dhanaerp-master-v16`, `dalali-v16` and `vincowoods-v16` — are defined in `images/ndf/image-definitions/images-v1.json`.

The NDF build implementation selects `images/layered/Containerfile` directly. That Containerfile:

1. Uses `frappe/build:${FRAPPE_BRANCH}` as the builder stage.
2. Runs the existing Bench acquisition path, including `bench init --apps_path` and the requested Frappe/application branches.
3. Uses `frappe/base:${FRAPPE_BRANCH}` as the final backend/runtime stage.
4. Copies the acquired Bench from the builder into the runtime stage.

The builder and runtime images are separate image inputs. They must both be recorded and digest-pinned by the later immutable-image work. The package-resolution target is the **final runtime image**, while source/build tooling requirements must additionally be compatible with the builder image.

### 2.1 NDF workflow platform behaviour

| Workflow | Current platform behaviour | Consequence |
| --- | --- | --- |
| `.github/workflows/ndf-build-product.yml` | Hard-codes `linux/amd64` for CI build and validation | Current automated PR/push validation proves amd64 only |
| `.github/workflows/ndf-publish-product.yml` | Defaults to `linux/amd64`; offers `linux/amd64,linux/arm64` as an explicit multi-platform option; configures QEMU when arm64 is selected | NDF publication supports amd64 by default and can request amd64 + arm64 |
| `images/ndf/scripts/build_image.py` | Accepts a comma-separated platform list; rejects multiple platforms for local `--load`; allows multi-platform registry `--push` | Buildx platform selection is configurable, but this does not by itself prove every platform is tested |

The upstream published v16 base and build image tags are multi-platform and list both `linux/amd64` and `linux/arm64`. NDF's current validation workflow does not yet exercise arm64. Therefore arm64 is an available publication target, but its NDF adapter/build acceptance is conditional on explicit arm64 validation.

## 3. Authoritative target-runtime matrix

### 3.1 Current product target

| Dimension | NDF v16 target baseline | Status | Resolution rule |
| --- | --- | --- | --- |
| Image architecture | `linux/amd64` | **Supported / CI validated** | Default NDF build and publish target |
| Image architecture | `linux/arm64` | **Conditional** | Upstream images publish this architecture and NDF publish workflow exposes it; require NDF arm64 build, validation and adapter tests before marking generally supported |
| OS family | Debian | **Supported** | Current upstream v16 base/build image layers identify Debian |
| OS distribution/release | Debian 13 (Trixie) | **Observed baseline; digest-bound per build** | Recent published v16 base/build image metadata identifies Trixie; record `/etc/os-release` from the exact digest used |
| OS package tooling | `apt` / `dpkg` | **Supported** | Current layered image path is Debian-based and upstream Containerfiles use `apt-get`; use target-native apt/dpkg tooling |
| Python implementation | CPython | **Supported** | Upstream images are based on the official `python:3.14-slim-trixie` image family |
| Python version | 3.14.10 observed in recent v16 image metadata | **Observed baseline; exact digest-bound** | Record `python --version`, implementation, `sysconfig.get_config_var("SOABI")`, `sys.implementation.cache_tag` and platform tags from the exact base digest |
| Python ABI family | CPython 3.14 (`cp314`) | **Supported family; exact SOABI capture required** | Do not substitute a runner's ABI or infer architecture-specific SOABI strings |
| Node.js major | 24.x | **Supported major line** | Upstream v16 image metadata declares `NODE_VERSION=24` and installs Node through NVM |
| Node.js exact version | Not fixed by the major-only declaration | **Must be captured per base-image digest** | Record `node --version` and `npm --version` from the exact runtime image; do not resolve against an arbitrary Node 24 patch |
| libc/platform | Debian Trixie platform ABI | **Exact value must be captured** | Record libc implementation/version and architecture from the selected image; use these for Python wheel and Node native package compatibility |
| Python resolver | `uv` preferred; `pip` only where target-resolution tests pass | **Adapter implementation pending** | Resolve for exact CPython 3.14 target, ABI, architecture and Debian platform; never use host defaults |
| Node resolver | `npm` | **Initial adapter target** | Resolve for exact Node 24.x patch, target OS/architecture and libc; yarn/pnpm remain disabled until separately approved and tested |
| OS resolver | `apt` | **Initial adapter target** | Resolve only against Debian 13/Trixie repositories for the target architecture; use `dpkg` semantics for installed-version/inventory verification |

### 3.2 Builder versus runtime responsibilities

| Component | Builder image: `frappe/build:version-16` | Runtime image: `frappe/base:version-16` |
| --- | --- | --- |
| Purpose | Bench/app acquisition, Python package/build operations and asset compilation | Runs the resulting Frappe Bench |
| OS family | Debian | Debian |
| Observed release | Trixie in recent v16 image metadata | Trixie in recent v16 image metadata |
| Architecture | amd64 and arm64 published | amd64 and arm64 published |
| Python | CPython 3.14.10 observed in recent v16 metadata | CPython 3.14.10 observed in recent v16 metadata |
| Node | Node 24 major declared by upstream image build configuration | Node 24 major declared by upstream image build configuration |
| OS package manager | apt/dpkg | apt/dpkg |
| Additional packages | Includes build toolchain and development headers required to build dependencies | Contains runtime libraries and runtime services; do not assume builder-only development packages exist |

A package that requires compilation may need builder-stage dependencies even when the resulting runtime package is installed into the final image. Such build-only requirements must not be confused with packages required by the running Bench. M4.2.4 must define the controlled build-stage/runtime-stage installation handoff.

## 4. Adapter support decision

The initial adapter implementation scope is deliberately narrow.

| Ecosystem | Supported target | Initial native adapter | Production support boundary |
| --- | --- | --- | --- |
| Python | CPython 3.14.10 target family on Debian 13, amd64; arm64 conditional | `uv`; `pip` only after equivalent target-resolution tests | Exact Python patch, SOABI, architecture, libc/platform tags and source profile are mandatory inputs |
| Node | Node.js 24.x on Debian 13, amd64; arm64 conditional | `npm` | Exact installed Node and npm versions are mandatory inputs; Node 24 major alone is insufficient for a resolved lock |
| OS | Debian 13 (Trixie), amd64; arm64 conditional | `apt` with `dpkg` inventory/version semantics | Exact distribution identity, release, architecture and approved repository profile are mandatory inputs |

The following are **not currently approved production targets**:

- Ubuntu, even though NDF developers or CI runners may use Ubuntu hosts.
- Debian Bookworm or any other Debian release as an interchangeable target.
- RPM-family distributions and `dnf`/YUM.
- Alpine and `apk`.
- musl-based targets.
- Alternative Python implementations such as PyPy.
- Python versions other than the selected v16 base-image runtime.
- Node major versions other than 24.
- Yarn and pnpm as package-resolution adapters.

They may be introduced only through an explicit target-matrix revision, matching image definitions, repository profiles, adapter support and integration tests. Host operating-system details must never be used as a substitute for the target image.

## 5. Runtime metadata required for every candidate

The matrix defines supported families. A concrete resolution candidate must bind those families to the exact images and runtime values used for that candidate.

The following metadata is mandatory:

### 5.1 Image identity

- Builder image reference and immutable OCI digest.
- Runtime/base image reference and immutable OCI digest.
- Platform-specific manifest digest for every selected architecture.
- Buildx target platform.
- Upstream image tag as descriptive provenance only.

### 5.2 Operating system

- `/etc/os-release` values: `ID`, `VERSION_ID`, `VERSION_CODENAME`, `PRETTY_NAME`.
- Architecture (`dpkg --print-architecture` and OCI platform).
- libc implementation and exact version.
- apt/dpkg versions.
- Approved apt source-profile identifier and repository/snapshot metadata identity.
- Installed base package inventory with exact package versions and architectures.

### 5.3 Python

- `sys.implementation.name`.
- `platform.python_version()`.
- `sys.implementation.cache_tag`.
- `sysconfig.get_config_var("SOABI")`.
- `sysconfig.get_platform()`.
- Python executable identity and implementation build metadata.
- pip/uv resolver name and exact version used by the adapter.
- Approved Python index/source-profile identifier and repository metadata identity.

### 5.4 Node

- `node --version`.
- `npm --version`.
- Node executable identity and architecture.
- `process.platform`, `process.arch`, and relevant libc/runtime information.
- Approved npm registry/source-profile identifier and repository metadata identity.
- Corepack/package-manager state where relevant to the build contract; this does not enable Yarn or pnpm adapters by itself.

A candidate must fail closed if required metadata cannot be obtained from the exact selected image digest.

## 6. Repository and package-source boundary

The target matrix does not approve arbitrary public repositories or publisher-selected package indexes.

The following NDF-controlled source profiles remain a separate decision and must be defined before native adapters are enabled for production:

- Python package index profile for Debian 13/CPython 3.14.
- npm registry profile for Node 24.
- Debian 13/Trixie apt repository profile for each supported architecture.
- Snapshot/immutability policy for repository metadata and package artifacts.
- Credential handling and trusted CA configuration for private sources.

The resolver must record the source-profile identity and repository metadata/snapshot identity. If a source cannot provide sufficient integrity/provenance for a deterministic candidate, resolution fails closed.

## 7. Base package inventory

The base dependency disposition requires a trusted inventory produced from the exact runtime base-image digest, not a generic list of packages assumed to exist in Frappe images.

The inventory producer must capture package identity, exact installed version and architecture using the target's native package database. Its provenance must bind the inventory to the base image digest.

This document does not declare any individual OS package to be present in the base image. That inventory is a separate implementation deliverable and must be verified against the exact image before a dependency can be classified as satisfied by `base`.

## 8. Mutable upstream tags and version drift

The upstream `version-16` image tags are rolling tags. Docker Hub's published v16 image metadata is updated over time; the observed Python patch and image digests can therefore change without the tag name changing.

Consequently:

1. `frappe/base:version-16` and `frappe/build:version-16` are source references, not immutable runtime identities.
2. NDF must capture and pin their OCI digests for each candidate/build.
3. Runtime versions must be inspected from the digest actually selected, not copied from this document as permanent values.
4. A new digest with changed Python, Node, OS release, libc or package inventory is a new target-runtime identity and must trigger re-resolution and compatibility checks.
5. Rolling Frappe/application Git branch behaviour remains unchanged. Runtime image digest pinning does not replace requested application branch references or convert resolver-time SHAs into Bench acquisition inputs.

The values in this document are the evidence-based baseline observed on 10 November 2026, not a promise that upstream rolling tags will remain unchanged.

## 11. Decision summary

1. Initial NDF v16 target OS is Debian 13 (Trixie), using apt/dpkg.
2. Initial Python target family is CPython 3.14.10, with exact ABI/platform metadata captured from the selected image digest.
3. Initial Node target family is Node.js 24.x; the exact installed patch and npm version must be captured from the selected image digest.
4. amd64 is the current NDF CI-validated architecture.
5. arm64 is an upstream-published and NDF-publish-selectable target, but remains conditional until NDF validates it end to end.
6. Initial package adapters are Python `uv` (preferred, with pip only after tests), Node `npm`, and Debian `apt`.
7. RPM/dnf, Alpine/apk, Ubuntu, Bookworm, musl, PyPy, other Python/Node majors, Yarn and pnpm are not production targets at this stage.
8. All concrete runtime identities are digest-bound and inspected. Rolling upstream tags are never treated as immutable identities.
9. This matrix does not change rolling Frappe/application branch acquisition semantics.
