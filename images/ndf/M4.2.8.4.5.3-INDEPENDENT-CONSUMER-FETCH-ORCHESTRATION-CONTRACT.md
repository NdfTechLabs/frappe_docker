## 1. Objective

Orchestrate the already implemented self-contained PDD and product-image Cosign verification primitives within the existing PDD fetch path. The consumer must independently verify the PDD OCI artifact, its PDD-to-image binding attestation, and the source-image SLSA provenance attestation; correlate the independently verified provenance predicate with the binding claim; and retain the existing descriptor, registry, evidence-inventory, evidence-hash and image-binding checks.

This work package defines the Python consumer orchestration and its machine-readable result. It does not change the GitHub Actions workflow, signer policy, publication process or deployment authorization.

## 2. Existing implementation baseline

The existing `images/ndf/scripts/fetch_product_deployment_descriptor.py` already:

- validates the publication receipt schema and internal immutable PDD reference;
- fetches the PDD OCI manifest and artifact by immutable digest;
- validates artifact type, media type, annotations and receipt correlation;
- downloads the PDD and evidence bundle;
- validates the descriptor, content hash, image digest and platform;
- validates exact published file inventory and binding-report bytes;
- re-runs the PDD/image evidence-binding verification.

The existing Cosign primitives provide:

- `cosign_pdd_trust.verify_pdd(..., self_contained=True)`;
- `cosign_image_trust.verify_image(..., self_contained=True)`.

Each primitive independently verifies the immutable artifact signature and attestation using Cosign v3.1.4, exact workflow identity/issuer/event/repository/ref constraints, source-SHA-constrained second-pass verification, normal Sigstore trusted-root/Rekor verification, complete v0.1 compatibility validation and NDF semantic validation. Each writes its normalized artifact trust result and exact second-pass attestation output before raising the expected provisional-policy exception.

The fetch path currently reports `verified` after descriptor/evidence checks. That status must not be reused to imply cryptographic trust or deployment authorization.

## 3. Required orchestration sequence

The consumer must execute the following ordered stages. A failure in any technical or structural stage is fatal and must not be converted into an expected provisional-policy outcome.

### 3.1 Receipt and PDD retrieval

1. Validate the publication receipt using the existing strict receipt schema and immutable-reference checks.
2. Use only `artifact.immutable_reference` from the receipt to retrieve the PDD OCI artifact. The receipt is a retrieval locator and metadata correlation input, not proof of cryptographic trust.
3. Preserve all current ORAS manifest, artifact type, media type, annotation, receipt, descriptor, content-hash, file-inventory, evidence-byte-hash, sidecar and evidence-binding checks.
4. Reject symlinks, unexpected files, missing files, duplicate JSON keys, malformed JSON and non-empty output directories as currently required.
5. Do not read or consume producer trust-result files, producer trust-evidence manifests, signing-input artifacts, local expected predicates, build artifacts or producer attestation payloads as trust evidence.

### 3.2 Independent PDD verification

1. Invoke `cosign_pdd_trust.verify_pdd` with:
   - the receipt's immutable PDD `repository@sha256:<digest>`;
   - `self_contained=True`;
   - no `expected_predicate_path`;
   - dedicated result-output and raw-attestation-output paths.
2. The primitive must retrieve the binding attestation directly from the registry and independently validate the PDD signature, signer identity, issuer, workflow claims, source SHA, Rekor evidence, exact PDD subject and complete binding Statement/predicate.
3. Load the verified Statement from the primitive's exact second-pass attestation output. Do not use a producer copy or an unverified registry payload.
4. Normalize only the Statement `_type` for NDF semantic validation, as already defined by the accepted v0.1 compatibility contract. Preserve the original verified bytes separately.
5. Require the PDD subject repository and digest to equal the immutable PDD reference.
6. Validate the binding predicate against the PDD binding schema and independently validated descriptor:
   - descriptor ID and canonical content SHA-256;
   - subject image repository, immutable digest and platform;
   - lock SHA-256;
   - source provenance predicate type and claimed predicate SHA-256;
   - originating workflow repository, path, ref, run ID, attempt and source commit.
7. Correlate the predicate's descriptor and image claims with the retrieved PDD and publication receipt. Any disagreement is a hard failure.

### 3.3 Derive and independently verify source image

1. Derive the image immutable reference exclusively from the validated PDD binding predicate:
   `predicate.subject_image.repository@predicate.subject_image.digest`.
2. Do not derive the image reference from the receipt, descriptor, producer result, local lock, environment variable or caller-supplied argument. Those sources may be compared against the derived value but may not select it.
3. Validate the derived reference with the immutable image-reference parser. Tags and mutable references are forbidden.
4. Invoke `cosign_image_trust.verify_image` with:
   - the derived immutable image reference;
   - `self_contained=True`;
   - no `expected_predicate_path`;
   - dedicated result-output and raw-attestation-output paths.
5. The primitive must retrieve the SLSA attestation directly from the registry and independently validate image signature, exact signer identity, issuer, workflow claims, source SHA, Rekor evidence, subject repository/digest and complete NDF provenance schema.
6. Load the verified SLSA Statement from the primitive's exact second-pass attestation output. Do not use a producer artifact or PDD binding predicate as a substitute for the source-image attestation.
7. Require the source provenance subject repository/digest and NDF platform to equal the immutable reference and PDD binding predicate. Also require agreement with the independently validated PDD descriptor and receipt.
8. Compute SHA-256 over the verified SLSA `predicate` object using NDF-JSON-CANONICAL-V1: sorted keys, compact separators, `ensure_ascii=False`, UTF-8 and exactly one trailing LF.
9. Require the computed predicate hash to equal `predicate.source_provenance.predicate_sha256` from the independently verified PDD binding Statement. A mismatch is a hard failure.

### 3.4 Preserve and validate primitive trust results

Each primitive writes an `artifact-trust-verification-result-v1` JSON result. The orchestrator must:

1. Load each result with strict JSON parsing (duplicate-key rejection, non-finite value rejection, object root, no symlink).
2. Validate it against `artifact-trust-verification-result-v1.schema.json`.
3. Correlate artifact kind, repository, digest, immutable reference, predicate type, subject digest, signer identity, issuer, workflow ref, signature status and transparency status with the independently verified artifact and identity-policy entry.
4. Load the shared identity policy independently through the existing policy loader; the normalized primitive result schema does not contain a policy-status field. Record the loaded global policy status in the consumer report and require both primitive verifications to have used that same policy file and identity-policy version.
5. Require signature verification, signer identity validation, transparency verification and attestation verification to be true.
6. Never infer success from the primitive exception text alone. A provisional result is recognized only when the result file is present, schema-valid, fully correlated, the loaded policy status is `provisional_until_live_certificate_observation`, and the result has exactly `decision.status = rejected` and `decision.reason_codes = ["IDENTITY_POLICY_PROVISIONAL"]`.
7. Treat missing/invalid result files, any other reason code, an unexpected decision, an unrecognized or changed policy status, or any mismatch as a technical failure.
8. Preserve the normalized result JSON and exact raw second-pass attestation output as consumer evidence.

The orchestrator may catch the primitive's provisional-policy exception only to inspect the just-written result under the rules above. It must not broadly catch Cosign, schema, identity, Rekor, I/O or other verification errors and reinterpret them as provisional rejection.

### 3.5 Existing descriptor/evidence binding

The current independent PDD/evidence verification remains mandatory. The consumer must not weaken or skip:

- descriptor schema and canonical content hash;
- registry manifest digest, artifact type, media type and annotations;
- published evidence inventory and file count;
- every published evidence file's hash and size;
- binding report hash and report correlation;
- lock and sidecar validation;
- source image repository, digest and platform correlation;
- Docker/registry image binding verification.

A descriptor/evidence-only mode, if retained for compatibility, must be explicitly labelled non-trust-verifying and must not produce the complete consumer trust report or an exit code indicating trust acceptance.

## 4. Consumer verification report

Add a versioned schema at:

`images/ndf/schemas/pdd-consumer-verification-report-v1.schema.json`

The report must use `additionalProperties: false` at every object boundary and include at least:

- `schema_version`: `1.0.0`;
- `verification_id`: unique non-empty identifier;
- `verified_at`: timezone-aware RFC 3339 timestamp;
- `execution`: terminal technical execution state, with successful completion distinct from trust;
- `pdd`: immutable reference, repository, digest, descriptor ID/content hash, signature result, signer/issuer/workflow identity, transparency result, binding predicate type/hash, source commit and policy status;
- `source_image`: immutable reference, repository, digest, platform, signature result, signer/issuer/workflow identity, transparency result, SLSA predicate type, canonical predicate SHA-256, source commit and policy status;
- `correlation`: explicit booleans and compared values for PDD subject, descriptor, image repository/digest/platform, source SHA and predicate-hash equality;
- `evidence`: descriptor/evidence binding status, published file count, binding-report hash, and references/hashes for retained evidence files;
- `trust_decision`: `trusted` or `rejected`, with unique reason codes;
- `deployment_authorization`: always `not_granted` in this work package.

The report must not contain a top-level `status: verified`, `trusted: true`, or any field that implies deployment authorization while the identity policy is provisional. Prefer explicit `execution.status = completed` alongside `trust_decision.status = rejected`.

When both identities are provisional and all technical checks pass:

- `execution.status = completed`;
- both artifact trust results remain `rejected` with exactly `IDENTITY_POLICY_PROVISIONAL`;
- top-level `trust_decision.status = rejected`;
- top-level `trust_decision.reason_codes = ["IDENTITY_POLICY_PROVISIONAL"]`;
- `deployment_authorization = not_granted`.

If policy is confirmed in a future, separately authorized policy change, the orchestration may report a trusted decision only when both primitive results independently report trusted and every structural, cryptographic and correlation check passes. This work package must not modify or confirm policy.

## 5. CLI and exit-code contract

Extend the existing fetch CLI with explicit paths/options for:

- Cosign executable (default `cosign`);
- consumer report output;
- PDD trust-result and raw-attestation outputs;
- source-image trust-result and raw-attestation outputs.

The normal full-consumer invocation must always perform both artifact trust verifications and existing evidence binding. It must not accept expected predicate paths.

Exit codes:

- `0`: all checks pass and both verified identities are confirmed by the shared policy; top-level trust decision is trusted.
- `2`: all cryptographic, structural, evidence and correlation checks pass, but both applicable identity results are the exact expected provisional rejection. The complete rejected consumer report and evidence must be written.
- `1`: technical failure, missing/invalid evidence, schema violation, mismatch, Cosign/Rekor failure, incomplete result, unexpected policy status or unexpected trust decision.

If one identity is provisional and the other confirmed, or if policy status differs between primitive results, fail closed with exit code 1 until a separate policy contract defines mixed-identity decisions. Do not broaden the expected negative outcome.

## 6. Security invariants

- PDD and image references are immutable digest references throughout trust verification.
- The image reference is derived only from the verified PDD binding predicate.
- No producer trust result, trust-evidence manifest, signing-input artifact, expected predicate file, local build output or caller-supplied source SHA is used as proof.
- Both signatures and both attestations are independently verified from registry output with Cosign v3.1.4.
- Normal Sigstore trusted-root and Rekor verification remains enabled.
- Exact certificate identity, OIDC issuer, event, repository, ref and source-SHA constraints remain enforced by the existing primitives.
- The first verified Statement supplies the source SHA; the second verification pass enforces it and its exact raw output is retained.
- Only the explicit v0.1 Statement envelope compatibility rule is allowed; only `_type` may be normalized for semantic validation.
- The full NDF schemas and all cross-artifact correlations are mandatory.
- No credentials, tokens or secrets are written to result files or uploaded artifacts.
- Consumer workflow permissions remain read-only: `actions: read`, `contents: read`, `packages: read`; no `id-token: write`, package write or repository write.
- No production promotion, tag mutation, signing, policy update or deployment authorization is introduced.

## 7. Required tests

Use deterministic fake Cosign/ORAS/Docker runners. Unit tests must not make network calls.

### 7.1 Happy-path and provisional behavior

1. Both self-contained verifiers are invoked with immutable references, no expected-predicate paths and `self_contained=True`.
2. PDD image reference is derived from the verified binding predicate, not receipt or descriptor values.
3. Image provenance is loaded from the exact second-pass Cosign output.
4. Canonical predicate hash matches the PDD binding claim.
5. Both provisional primitive results are schema-valid and fully correlated.
6. The complete consumer report is written with execution completed, trust rejected and deployment authorization not granted.
7. CLI exits 2 for the exact expected dual-provisional case.
8. A future confirmed-policy fixture may exercise exit 0, but tests must not modify the repository policy.

### 7.2 Fail-closed/adversarial cases

Cover at least:

- mutable/tag PDD or image reference;
- PDD signature/attestation failure, image signature/attestation failure, Cosign version mismatch;
- failed Rekor/transparency verification;
- malformed, duplicate, missing or extra-field Statement;
- v0.1 envelope normalization that changes any field other than `_type`;
- wrong PDD subject repository/digest;
- wrong image subject repository/digest/platform;
- image reference sourced from receipt/descriptor rather than verified binding;
- wrong PDD/image signer identity, issuer, event, repository, ref or source SHA;
- invalid PDD binding schema or SLSA provenance schema;
- descriptor ID/content hash mismatch;
- wrong lock SHA or predicate type;
- canonical predicate hash mismatch;
- PDD/receipt/descriptor/binding/provenance disagreement;
- missing, malformed, symlinked or duplicate-key trust result;
- primitive exception with no result file;
- exception accompanied by malformed result or non-provisional rejection;
- one provisional and one confirmed result, or policy-status mismatch;
- producer trust result or evidence manifest being present but ignored;
- missing/tampered evidence, unexpected files, symlinks and binding report mismatch;
- output write failure and partial report cleanup/atomicity;
- `--skip-image-binding` or any descriptor-only mode never yielding a complete trusted consumer report.

### 7.3 Regression and validation

- Existing PDD retrieval, receipt, descriptor, evidence inventory/hash and binding tests remain passing.
- Existing PDD and image Cosign primitive tests remain passing.
- Producer-side verifier call sites continue to use default producer mode with expected predicates.
- Full NDF test suite, compileall, pre-commit, actionlint if workflows change, and diff check pass.

## 8. Implementation boundaries and handoff

Included:

- consumer orchestration inside `fetch_product_deployment_descriptor.py`;
- strict consumer report generation and schema;
- focused unit/adversarial tests for orchestration and result correlation;
- CLI support for the full consumer report and evidence paths.

Excluded:

- changes to `.github/workflows/ndf-fetch-product-deployment-descriptor.yml`;
- upload/report workflow integration;
- live staging execution;
- changes to Cosign primitives unless a concrete orchestration contract defect is discovered and separately reviewed;
- identity policy changes or confirmation;
- production promotion and deployment authorization.

After this contract is accepted, implement the orchestration and schema as a separately validated change. Then proceed to M4.2.8.4.5.4 for read-only fetch-workflow integration, .4.5.5 for full adversarial/regression acceptance, and .4.5.6 for live staging.

## 9. Acceptance criteria

M4.2.8.4.5.3 is accepted only when:

1. Both PDD and image trust primitives are independently invoked in self-contained mode.
2. The image reference is derived only from the validated PDD binding predicate.
3. The source SLSA predicate is read from Cosign's exact second-pass verified output.
4. Canonical predicate hash equality and all descriptor/receipt/image correlations are enforced.
5. Both primitive result files are schema-validated and only exact provisional rejection is handled as expected.
6. A complete versioned consumer report is emitted with separate execution, trust and deployment-authorization states.
7. Exact dual-provisional success exits 2 and never reports trusted/verified/authorized.
8. All technical, schema, identity, Rekor, evidence and correlation failures exit 1.
9. Existing evidence and binding checks remain mandatory.
10. Focused, adversarial and regression tests plus repository validation pass.
11. No workflow integration, policy confirmation, promotion or deployment authorization is included.
