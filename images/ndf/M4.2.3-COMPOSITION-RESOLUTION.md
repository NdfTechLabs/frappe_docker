## 1. Objective

Extend the existing NDF manifest resolver so a composition root can deterministically resolve:

- Descriptor-backed Bench applications and their transitive Bench-app dependencies.
- Required and explicitly selected optional dependencies.
- Product and capability manifest composition.
- Independent service artifacts and external service requirements.
- Framework/runtime compatibility and dependency constraints against an explicit target matrix.
- A deterministic lock retaining all M4.2.1 source-reference, policy, checksum and composition-integrity guarantees.

This work extends `images/ndf/scripts/resolve_manifest.py`. It does not create a parallel resolver, install applications into a running Bench, build images, acquire Bench sources, deploy services or implement DT Master orchestration.

## 2. Repository audit baseline

The following facts were confirmed on the merged `main` baseline (M4.2.2 merge commit `ab221a55c6b18d84d5d26db9019444a06724d97b`):

1. `ManifestLoader.validate()` always validates against `application-manifest-v1.schema.json`; the v2 composition schema is not yet integrated into the resolver.
2. `ManifestLoader.load()` recursively loads `includes`, but does not load entries from the manifest's `capabilities` collection.
3. `compose_applications()` only reads embedded legacy `name`/`repository` application entries.
4. `validate_composition_descriptors()` validates v2 composition and safely loads directly referenced Marketplace App Descriptors, but deliberately performs no dependency graph or Git resolution.
5. `collect_production_metadata_issues()` checks descriptor readiness and accepts optional dependency selection identifiers, but the composition schema does not yet define the complete selection contract.
6. The v2 schema's `services` collection is currently an array of unconstrained objects. There is no typed independent service descriptor or service lock contract.
7. Existing v1 product manifests declare optional capabilities with `required: false` and `install_by_default: false`. Existing production manifests and v1 product locks must remain readable; no bulk migration is part of this package.
8. The existing lock v2 validator proves source-manifest inventory, required application composition, dependencies, installation order, reference provenance, framework identity and policy consistency. These guarantees are mandatory regression constraints.

## 3. Composition model

The resolver will expose four separate inventories. They must never be collapsed into one Bench application list.

| Inventory             | Meaning                                                        | Resolution output                                                                       |
| --------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Bench applications    | Frappe/Bench-installable apps, including Frappe and ERPNext    | Ordered application lock entries; only this inventory feeds Bench acquisition           |
| Independent services  | Separately built or distributed container/service artifacts    | Service lock entries; never included in Bench `apps.json`                               |
| External requirements | Managed external dependencies such as hosted APIs or databases | Declarative external-requirement lock entries; no container image or Bench app identity |
| Capabilities          | Optional, composable manifest groups                           | Explicit selection record plus the selected capability's resolved contents              |

The composition root owns product-specific selection and source-ref overrides. Marketplace App Descriptors own reusable app identity, release metadata, source repository, compatibility and dependency declarations. Service descriptors own independent service identity and artifact metadata.

### 3.1 Descriptor-backed Bench applications

For every descriptor-backed application, the resolver must preserve these distinct values:

- `app_id`: stable Marketplace identity.
- `bench_app_name`: Bench installation/module name.
- `release.version`: declared SemVer release identity, when present.
- `target_ref`: requested Git branch, tag or commit from the composition entry (otherwise the descriptor default).
- `ref`: resolution-time full Git commit SHA.
- `reference_kind` and `resolved_ref`: M4.2.1 reference provenance.
- Descriptor path and SHA-256: the exact descriptor input used for resolution.

The declared release version must never be inferred from a Git tag, branch, commit SHA or repository state. A descriptor dependency constraint is checked against the target descriptor's declared release version. If that release version is absent, a dependency requiring a version constraint is unresolved and production resolution fails closed.

Legacy embedded application entries remain supported for v1 manifests and for explicit migration composition entries. A legacy entry must not be silently upgraded into a Marketplace release identity.

### 3.2 Dependency graph

- Required Bench-app dependencies are resolved transitively.
- A required dependency may be satisfied by an already composed legacy/core Bench app or by a catalogue descriptor.
- A descriptor-backed dependency not yet selected is added from its canonical catalogue path only when it is declared required.
- Optional dependencies are not auto-added. They require an explicit selection in the composition root.
- Every incoming version constraint for a selected app must accept the same declared release version. Missing release identity, malformed ranges, or a failed constraint blocks production resolution.
- Duplicate Marketplace IDs, duplicate Bench install names, conflicting source identities, missing dependencies and cycles fail closed.
- Installation order is deterministic and topological. Stable tie-breaking is by canonical Bench app name; declared composition order is retained as provenance, not allowed to override dependency order.

### 3.3 Optional capability selection

The v2 composition root will carry an explicit boolean selection for each optional capability reference. Required capabilities are always included. Optional capabilities are loaded only when selected; an absent selection must not be interpreted as consent to include an optional capability.

For v1 manifests, current behaviour remains unchanged: optional capability declarations are not implicitly loaded by this new v2 selection mechanism. Existing `includes` semantics and optional include handling remain intact.

A selected capability contributes its manifest, selected applications, services, external requirements and nested selected capabilities to the same deterministic composition graph. Capability selection decisions (including explicit non-selection) are recorded in the lock so two different selections cannot produce indistinguishable lock content.

### 3.4 Independent services and external requirements

M4.2.3 will add a versioned service descriptor contract under `images/ndf/schemas/` and a canonical service descriptor catalogue under `images/ndf/descriptors/services/`.

A service descriptor identifies a separately distributed service artifact or an external managed requirement. It must not use Bench app fields or be passed to Bench acquisition. Container/service artifacts must identify an immutable artifact reference suitable for deterministic composition; mutable tags alone are not production pins. External requirements remain declarative and identify their provider/requirement contract without pretending to be an image.

The resolver records selected service and external requirement identities, descriptor checksums, dependency edges and immutable artifact references. It does not build, pull, run, configure or orchestrate them. Those actions remain outside M4.2.3.

## 4. Target compatibility and package resolution

Production resolution requires an explicit target runtime/framework matrix. A major-only label such as `"16"` is not an exact runtime version and must not be silently converted into an invented patch release.

The v2 composition contract will define the target values needed by selected descriptors (Frappe, ERPNext when selected, Python, Node when required, and OS distribution/package-manager identity). Compatibility checks use the ecosystem-specific semantics already established in M4.2.2:

- Frappe, ERPNext and Node: npm-compatible SemVer.
- Python: PEP 440.
- OS packages: native package-manager semantics; Debian and RPM versions are not compared with a generic shared comparator.

The resolver will reject missing target values when a selected descriptor requires them. It will not infer compatibility from a publisher claim or treat a successful Git reference resolution as compatibility evidence.

Dependency selection policies remain as defined in M4.2.2:

- `constraint`: evaluate the declared constraint against the selected exact version.
- `latest_compatible`: allowed only for supported package-manager dependencies; resolution must produce and lock an exact selected version.
- Base dependencies: verify against the declared base/runtime target; do not schedule duplicate installation.
- Runtime-compatible dependencies: resolve as controlled build inputs.
- Environment-level dependencies: mark the composition as requiring a different image/runtime contract; never treat them as ad-hoc runtime additions.

Package-manager lookups must use native ecosystem tooling/adapters and return exact version plus source/provenance metadata. No publisher-provided executable hooks are permitted. OS dependency resolution is delegated to the native distribution package manager. If a deterministic candidate cannot be selected, resolution fails rather than recording an unresolved range as if it were a selected version. The adapter execution model, normalized request/result contract, target-platform requirements, source-profile controls, lock representation and source-local dependency boundary are specified in [M4.2.3-A — Package Resolution Contract](M4.2.3-A-PACKAGE-RESOLUTION-CONTRACT.md).

## 5. Lock contract and M4.2.1 integrity

The implementation will extend the existing lock-generation and validation path, not create a separate lock file or resolver. The existing lock version will be retained only if the extension remains backward-compatible and unambiguous; any incompatible structural change must use an explicit lock-version migration rather than silently changing v2 meaning.

The resolved lock must include:

- Existing product, framework, effective policy, resolver provenance and source-manifest inventory.
- Descriptor-backed application identity, declared release version, descriptor path/checksum, requested Git ref, resolution SHA, reference kind and canonical resolved ref.
- Resolved dependency edges, dependency constraints, selected package versions and deterministic installation order.
- Explicit capability selections.
- Independent service artifacts and external requirements in their own inventories.
- Descriptor checksums and source manifest checksums needed to reproduce and validate the composition.

Validation must prove that the lock exactly represents the loaded source graph and selected composition. It must reject omitted, substituted, duplicated or reordered dependencies; changed descriptor content; altered release identity; changed requested refs; changed resolution SHAs; policy weakening; service/application cross-contamination; and inconsistent framework identity.

The following guarantees remain unchanged:

1. Inherited resolution policy is restrictive.
2. Full immutable Git commit SHAs are recorded.
3. Requested ref, reference kind, canonical resolved ref and resolution SHA remain distinct.
4. Resolver SHA is not Bench-acquired source proof; actual acquisition belongs to M4.2.4.
5. Lock validation against unchanged manifests checks complete source inventory and exact composition.
6. Legacy lock v1 is a migration input, not silently accepted as lock v2.
7. Existing v1 manifests remain readable and their existing product locks are not regenerated by this work package.

### Mandatory M4.2.2 transferred acceptance item

Tests must prove that descriptor `app_id` and declared release version survive composition and lock generation independently of:

- The requested Git ref.
- The resolution-time commit SHA.

Actual Bench-acquired SHA remains an M4.2.4 responsibility.

## 6. Implementation sequence

1. **Resolver schema integration:** select v1/v2 schema by manifest version; preserve existing v1 behaviour and errors.
2. **Capability graph loading:** explicitly load selected v2 capability manifests with cycle/duplicate/path checks and complete manifest provenance.
3. **Descriptor composition:** load directly selected descriptors and resolve required transitive Bench-app dependencies from the canonical catalogue.
4. **Optional dependency selection:** add a typed composition selection contract and pass selected dependency identities into production metadata validation.
5. **Compatibility resolution:** validate selected descriptor release versions and all dependency constraints against one explicit target matrix.
6. **Service/external composition:** add typed service descriptor schema/catalogue fixtures and resolve independent service/external inventories.
7. **Dependency package selection:** implement the native adapter contract in [M4.2.3-A](M4.2.3-A-PACKAGE-RESOLUTION-CONTRACT.md); resolve supported package-manager dependencies to exact versions with provenance; preserve base/runtime/environment-level dispositions.
8. **Lock extension:** serialize deterministic app/service/capability/package inventories and descriptor checksums; validate the exact source composition.
9. **Regression and integration tests:** retain all v1 and M4.2.1 tests; add negative and determinism tests for every new composition boundary.
10. **Documentation and acceptance:** update this document, tracker and README with actual implementation/test evidence before PR.

## 7. Explicit exclusions

- Bench source acquisition and post-acquisition Git HEAD capture (M4.2.4).
- Immutable base-image selection/build (M4.2.4).
- Image content verification (M4.2.5).
- Product Deployment Descriptor generation (M4.2.6).
- Candidate-driven GitHub Actions integration (M4.2.7).
- Signing and attestations (M4.2.8).
- DT Master Docker orchestration, deployment and runtime service lifecycle.
- DT Tenant site-level app installation or lifecycle operations.

## 8. Implementation checkpoint — 2026-11-10

The first implementation pass is committed on the M4.2.3 feature branch.

### Delivered in this checkpoint

- The existing `ManifestLoader` now selects the v1 or v2 application-manifest schema by `manifest_version`. Legacy v1 capability declarations remain non-loading; v1 include semantics remain unchanged.
- V2 capability references require explicit `selected` booleans for optional capabilities. Required capabilities always load. Selected capability manifests join the same graph for policy aggregation, source-manifest checksums, application composition and lock provenance. Duplicate references and include/capability path collisions fail closed.
- V2 compositions require an exact `target_runtime` matrix. Frappe major identity is checked against the product framework major. Descriptor Frappe/ERPNext/Node ranges use npm-compatible SemVer; Python ranges use PEP 440.
- Canonical Marketplace App Descriptors are loaded and validated by the existing descriptor validator. Required Bench-app dependencies are closed transitively from `descriptors/apps/<app_id>.json`; optional dependencies require explicit `selected_optional_dependencies` entries. Missing dependencies, unknown selections, duplicate app identities, conflicting source-ref overrides, cycles and unsatisfied declared release constraints fail closed.
- Descriptor-backed lock entries retain `app_id`, declared `release_version`, descriptor path/checksum, requested `target_ref`, resolution SHA, reference kind and resolved ref as separate values.
- Python, Node and OS package dependencies consume exact `target_runtime.package_versions` selections that include version, source and resolver provenance. Python/Node constraints are checked using their ecosystem semantics. OS constraints currently require exact version equality and a matching distribution/package-manager context.
- Added `service-descriptor-v1.schema.json`. Independent container services require OCI digest-pinned image references; external requirements carry provider/requirement metadata. Service dependencies close transitively from the canonical service descriptor catalogue and are topologically ordered in inventories separate from Bench applications.
- Lock v2 now records target runtime, explicit capability selections, independent services, external requirements and descriptor-backed application identity/package selections. Lock validation checks the target matrix, capability selections, independent inventory identity/type/digest/dependency order and exact composition against source descriptors. Existing M4.2.1 checks for manifest inventory, app composition, Git provenance, policy and framework identity remain in the same validator.
- Build preparation still consumes only the lock's `applications` inventory. Independent services and external requirements are not passed to Bench `apps.json`.

### Explicit package-resolution boundary

This checkpoint validates and locks exact package selections supplied in `target_runtime.package_versions`; it does not execute pip/npm/apt/dnf or query package repositories itself. The `source` and `resolver` fields bind each selection to the native ecosystem resolver that produced it. OS package range evaluation remains delegated to native package-manager tooling; until that adapter is integrated, only exact OS version equality is accepted. Do not interpret this as proof that a package is the latest compatible candidate unless the declared resolver produced and attested that selection.

### Added regression coverage — execution pending

The test suite now includes coverage for v1/v2 schema selection, explicit optional capability selection and lock tampering, descriptor dependency closure and version constraints, exact package selection/provenance, target compatibility, independent service/external inventories, transitive service closure and cycle detection, service separation from Bench `apps.json`, service lock tampering, and descriptor identity/release/ref/SHA separation in lock generation and validation.

**No test result is claimed yet.** The new and existing test suites, compilation and pre-commit checks still need to be run against this branch. Production manifests and product locks have not been modified or regenerated.
