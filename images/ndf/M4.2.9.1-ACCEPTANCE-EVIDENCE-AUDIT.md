## 1. Purpose and method

This is a read-only assessment of the implementation and evidence already present at the audit baseline. It does not change implementation behavior, retroactively promote a deferred result to a pass, or authorize production release/deployment.

The review inspected the approved M4.2 plan and tracker, the M4.2.4–M4.2.8 package records, the M4.2.6.7 and M4.2.7 final acceptance records, the candidate producer/consumer contract, the cross-workflow acceptance record, and the relevant NDF workflow/script/schema/test inventory.

Status terminology:

- **Satisfied (scoped):** the required behavior has evidence for the stated product/platform or repository-local contract. The scope limitation remains part of the result.
- **Partial:** some local behavior is verified, but a required part of the criterion or its evidence is not yet established.
- **Deferred (external):** the evidence depends on DT Master, a real producer identity, or a separately authorized operational action. This is neither passed nor failed.
- **Documentation reconciliation:** implementation evidence exists, but a stale or contradictory record prevents an unambiguous parent acceptance claim.

#### M4.5 — Runtime application management

M4.1 §§16.2, 16.3 and 16.8 establish the intended split:

1. NDF publishes immutable Marketplace App Descriptors with stable app identity, release, descriptor schema, repository, immutable source commit, compatibility, dependencies, build/install metadata and evidence.
2. DT Master assigns/validates app identity, synchronizes technical release metadata, and separately governs publisher/listing approval.
3. Product Inclusion Request is distinct from marketplace release approval. NDF validates inclusion and proposes product-manifest changes through its normal pull-request/maintainer process.
4. Bench Environment Application is the authoritative inventory of apps available in a shared Bench runtime. Tenant Installed App remains site-specific state.
5. If an app is unavailable in the Bench, DT Master requests a new immutable NDF-built composition/replacement Bench; it must not mutate shared Bench code in place.
6. DT Tenant remains a tenant-facing client of DT Master. It does not own Docker, infrastructure, Bench composition or NDF publishing credentials.

NDF has a Marketplace App Descriptor schema, but the current descriptor tree contains only `dt_ecommerce.json` and `dt_recomendations.json`. The current Dalali/core product composition manifests still use `application-manifest-v1` and include several other apps without registered Marketplace App Descriptor files. The PDD schema makes `descriptor_path` and `descriptor_sha256` optional, and its application record does not directly require `app_id` or release version. Therefore descriptor-backed identity is not yet complete across the product application inventory; this aligns with the documented M4.2.7 CAND-03 partial disposition.

The current AI/automation capability also declares two inline services, but the shared `service-descriptor-v1` schema only carries service artifact/provider identity and dependencies. The PDD service record likewise does not carry executable service topology, and the capability's own declarations explicitly retain unconfirmed runtime fields for one service. These facts cannot be promoted to verified Compose/health/readiness declarations without source confirmation and an authoritative NDF contract.

NDF has the descriptor schema and limited catalogue as a technical foundation, but the PDD mapping gap above means the exact per-app identity/release/descriptor reference must be made reliably consumable by the deployment consumer.

The current DT Master `api/marketplace.py` remains the legacy execution path: it resolves the latest minor release with `git ls-remote --tags`, queues install/upgrade/uninstall against a Tenant Site, and runs the executor with platform authority. The DT Master file-level audit explicitly assigns this strategy for replacement in M4.5 because it can mutate shared Bench code. It is not the accepted target architecture.

The current DT Tenant `api/marketplace.py` proxies install/upgrade/uninstall requests to DT Master, which is directionally consistent with DT Master owning execution. However, the current proxy envelope contains extension name and FQDN rather than the complete future request identity/idempotency/operation contract. The DT Master source audit also records tenant-binding, authorization, operation-idempotency and realtime-correlation controls that must be enforced in the future service path.

**M4.5 boundary:** M4.2 supplies immutable app descriptors, composition/build evidence and the PDD contract. It does not implement DT Master marketplace governance, App Installation Request lifecycle, Bench availability records or DT Tenant site-level execution. Those remain M4.5/M4.6 responsibilities.
