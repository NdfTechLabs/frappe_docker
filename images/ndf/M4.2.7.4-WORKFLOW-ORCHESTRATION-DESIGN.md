# M4.2.7.4 — Candidate-Driven Workflow Orchestration Design

**Repository:** `NdfTechLabs/frappe_docker`
**Work package:** M4.2.7.4 — Candidate-Driven Workflow Orchestration
**Status:** Implemented and locally verified — candidate entry/intake, reusable prepared-input image build/verification, reusable PDD verification/publication and correlated result finalizer are implemented. Live GitHub Actions operational acceptance is deferred to the DT Master integration milestone.
**Branch:** `feat/M4.2.7`

## 1. Purpose and boundaries

Define how an authorized DT Master dispatch enters NDF, how the validated candidate is passed through reusable NDF build and publication stages, and how one immutable result is returned for the corresponding GitHub Actions attempt.

All implementation remains in `NdfTechLabs/frappe_docker`. DT Master and DT Tenant remain read-only contract references. NDF does not own candidate lifecycle, tenant authorization, deployment readiness or runtime deployment.

This document records the intended workflow architecture. It does not claim that the workflows or the cross-repository producer are implemented.

## 2. Existing workflow baseline

The current NDF workflows are manual `workflow_dispatch` workflows:

- `.github/workflows/ndf-build-product.yml` — local Buildx build and image validation; uploads build evidence.
- `.github/workflows/ndf-publish-product.yml` — staging push, image validation, publication gate and optional promotion to the official immutable product tag.
- `.github/workflows/ndf-verify-product-deployment-binding.yml` — independent PDD generation/validation and image/evidence binding verification.
- `.github/workflows/ndf-publish-product-deployment-descriptor.yml` — publishes the verified PDD and evidence as an OCI artifact.
- `.github/workflows/ndf-fetch-product-deployment-descriptor.yml` — independently retrieves and verifies a published PDD artifact.
- `.github/workflows/ndf-release-product.yml` — existing release/promotion path.

These workflows currently rely on workflow-dispatch inputs, run IDs, artifact names and source-workflow path checks. Reusable extraction must explicitly preserve or replace those assumptions; simply adding `workflow_call` to a file is not sufficient.

## 3. Candidate entry workflow

Add a dedicated entry point:

`.github/workflows/ndf-build-candidate.yml`

Trigger:

- `workflow_dispatch` only, so the authorized DT Master GitHub App can invoke the workflow.
- Dispatch ref must be `refs/heads/main`.
- The workflow must reject actors other than the configured DT Master GitHub App bot identity (repository variable, for example `NDF_MASTER_DISPATCH_ACTOR`). The exact actor value must be configured from the actual installed App; do not guess or hard-code an unverified slug.
- Production dispatch remains disabled until the real DT Master OCI producer/serializer gate in Section 10 is closed.

Required dispatch inputs:

- `candidate_id`
- `candidate_artifact_ref` — exact digest-pinned GHCR reference
- `candidate_payload_sha256` — SHA-256 of the exact candidate JSON layer bytes

Optional input:

- `correlation_id` — carried through to the result when supplied. NDF does not use it as authorization.

The input values are untrusted. Pass them to Python through step/job environment variables, never interpolate them into shell source, dynamic paths, action references, workflow names or command fragments. The intake script remains authoritative for reference, digest, OCI, schema and semantic validation.

## 4. Intended orchestration graph

The candidate workflow is a thin coordinator. It should invoke reusable workflows through `workflow_call` after the NDF-only candidate intake and candidate-to-lock adapter have completed.

```text
DT Master GitHub App
        |
        | workflow_dispatch(candidate_id, digest-pinned ref, payload SHA, correlation ID)
        v
ndf-build-candidate.yml
        |
        +--> dispatch actor + main-ref gate
        |
        +--> candidate-intake job
        |      packages: read
        |      ORAS fetch by digest
        |      verify OCI manifest/layer/payload
        |      validate schema + semantic policy
        |
        +--> candidate-to-lock job
        |      deterministic candidate -> existing lock-v2/build inputs
        |      no competing resolver or manifest model
        |
        +--> reusable image build/verification stage
        |      build unique staging reference
        |      validate image + evidence + publication gate
        |
        +--> reusable PDD verification/publication stage
        |      generate and independently validate PDD
        |      verify image/evidence binding
        |      publish PDD OCI artifact
        |
        +--> result job (runs on success or failure)
               validate result schema
               upload immutable run-correlated result artifact
               expose safe summary
```

The candidate-to-lock adapter is M4.2.7.3 and is a prerequisite to connecting candidate input to image construction. This workflow design can be implemented in parallel only where it does not bypass or duplicate that adapter.

## 5. Reusable workflow boundaries

The implementation should extract callable stages with explicit, versioned inputs and outputs. Proposed boundaries:

### 5.1 Image build and verification

Reusable workflow: `.github/workflows/ndf-reusable-build-verify.yml`

Inputs should identify:

- candidate ID (correlation only, not a shell/path component);
- validated candidate artifact or candidate-to-lock output artifact name;
- product image definition selected by the validated adapter;
- target platform(s) already accepted by NDF policy;
- unique staging tag derived inside NDF from `github.run_id` and `github.run_attempt`.

Outputs/evidence:

- image repository and immutable digest;
- lock-v2 SHA-256 and composition hash;
- build metadata, build result, inventory, source/composition verification and image-verification evidence;
- publication-gate report;
- exact uploaded evidence artifact name.

The reusable workflow must reuse `prepare_build.py`, `build_image.py`, `validate_image.py` and `gate_image_publication.py`. It must not implement a second resolver, builder or image validator.

### 5.2 PDD verification and publication

Reusable workflow: `.github/workflows/ndf-reusable-pdd.yml`

Inputs:

- source build run ID and exact evidence artifact name;
- exact image repository/digest and verified build outputs;
- candidate ID and candidate artifact reference/digest;
- composition and lock hashes.

Required operations:

- generate PDD from verified build evidence;
- independently validate the PDD;
- independently verify image/evidence binding;
- publish the PDD/evidence OCI artifact;
- return immutable PDD artifact reference, OCI digest and content hash.

The existing standalone verification, publication and fetch/consumer workflows remain available for manual operations and independent post-publication checks. The candidate orchestrator must not skip the independent PDD validator or binding verifier.

### 5.3 Manual workflow compatibility

Existing manual product workflows remain supported with their current user-facing inputs and safety behavior:

- product selection and platform allowlists remain;
- official product-tag promotion remains opt-in and main-only;
- staging publication remains distinct from official promotion;
- standalone PDD verification/publication/fetch workflows remain usable.

Where practical, manual workflows should become thin wrappers around the same reusable build/verification stages. Their existing run/artifact ownership checks must be refactored to accept the reusable caller identity safely. Do not weaken source-run validation merely to make a workflow callable.

## 6. Permissions and credentials

Use per-job least privilege. The top-level candidate workflow should not grant broad write permissions to every job.

| Job/stage                     | Required token permissions                           | Reason                                                     |
| ----------------------------- | ---------------------------------------------------- | ---------------------------------------------------------- |
| Entry/gate                    | `contents: read`                                     | Read workflow code and policy                              |
| Candidate intake              | `contents: read`, `packages: read`                   | Read NDF code and private candidate OCI package            |
| Candidate-to-lock             | `contents: read`                                     | Read manifests, schemas and resolver code                  |
| Image build/push/verification | `contents: read`, `packages: write`                  | Push unique staging image and pull/inspect it              |
| PDD publication               | `contents: read`, `actions: read`, `packages: write` | Retrieve exact build evidence and publish PDD OCI artifact |
| Result                        | `contents: read`, `actions: read`                    | Validate and upload run-correlated result artifact         |

The exact permissions may be reduced after implementation proves a stage does not need one. Reusable workflows cannot elevate permissions beyond those granted by the caller; caller job permissions must therefore explicitly grant the minimum needed by that called stage.

Credential separation:

- DT Master uses its own GitHub App installation token only to dispatch the NDF workflow.
- NDF candidate intake uses NDF's own `GITHUB_TOKEN` with read access to the candidate package.
- NDF image/PDD publication uses NDF's own job-scoped `GITHUB_TOKEN`.
- No GHCR write token, PAT or NDF secret is passed to DT Master.
- No token is placed in candidate JSON, artifacts, logs or result fields.

## 7. Correlation, retries and concurrency

- GitHub `run_id` + `run_attempt` identifies one NDF execution attempt and is the basis for unique artifact names.
- Candidate ID, candidate manifest digest, payload SHA-256 and optional correlation ID are carried unchanged through each stage.
- Result `result_id` is stable for the NDF run/attempt, not merely the candidate ID.
- Do not use unvalidated candidate IDs as concurrency-group expressions, artifact path segments, image tags or registry destinations.
- Do not cancel an in-progress candidate run when another dispatch for the same candidate arrives. Each dispatch is a separately auditable attempt; DT Master owns request idempotency and reconciliation.
- A retry is a new run/attempt and must not overwrite prior result or evidence artifacts.
- Result status must be one of the schema-defined values. Success requires the exact image digest, PDD reference/digest/content hash, lock hash, composition hash and provenance reference. Failure returns a stable safe code and sanitized summary only.

## 8. Failure behavior and result production

The final result job must run with `if: always()` and inspect upstream job conclusions. It must never infer success from a partial artifact.

Fail-closed sequence:

- Intake failure: no adapter, build or publication.
- Adapter failure: no image build or publication.
- Build or image-verification failure: no PDD publication.
- PDD generation, independent validation, binding or publication failure: no successful result.
- Missing, expired, mismatched or wrong-run artifacts: fail the attempt.
- Cancellation: report cancelled when a final result can safely be produced; otherwise the GitHub run conclusion remains authoritative and DT Master reconciles the missing result.

The result writer must emit only the safe schema-defined failure code/summary. Raw stack traces, shell output, secrets and tenant information are not cross-repository result content.

## 9. Testing strategy

Add workflow and helper tests for:

1. Required/optional dispatch input validation and malformed input rejection.
2. Non-main ref and non-allowlisted actor rejection.
3. Digest-pinned candidate identity and payload hash propagation.
4. Reusable workflow input/output contracts and artifact names.
5. Job dependency ordering and fail-closed behavior.
6. Permission declarations and no GHCR write permission on intake.
7. Unique staging image references and no candidate-controlled registry/path values.
8. Image digest, lock hash and composition hash agreement across stages.
9. PDD digest/content hash and image subject binding.
10. Success, failure and cancellation result schemas.
11. Duplicate dispatch/retry creates separate run evidence without overwriting.
12. Existing manual product build/publish/release/PDD workflows retain their current behavior.

Static workflow parsing/lint tests are necessary but not sufficient for operational acceptance. A live GitHub Actions candidate run remains required, but is deferred until the main-branch dispatch prerequisites are legitimately available: the configured DT Master GitHub App actor and a candidate artifact conforming to the agreed producer contract. Do not weaken the actor/ref gate or substitute a developer identity to manufacture a staging run.

## 10. Cross-repository producer/consumer acceptance gate

This gate remains OPEN.

Before production candidate dispatch:

- DT Master must explicitly accept the OCI layout in `M4.2.7.1-CONTRACT.md`.
- DT Master must serialize candidate JSON conforming to `deployment-candidate-v1.schema.json`.
- Its ORAS publication must produce the exact artifact type, empty config, one uncompressed JSON layer, filename annotation and manifest annotations.
- Dispatch inputs must contain the exact candidate ID, digest-pinned OCI reference and SHA-256 of the exact JSON payload bytes.
- NDF must retrieve a real artifact published by DT Master and pass the complete intake validator.
- Candidate reference/digest and payload hash recorded by NDF must match the Master candidate record.

Mocked ORAS tests, synthetic fixtures and NDF-owned test artifacts do not close this cross-repository gate. Until the gate is closed, the workflow remains non-production. The deferred operational run is tracked by `M4.2.7.6-ACCEPTANCE.md` and will be executed at the corresponding DT Master milestone.

### 2026-11-15 — Reusable candidate image build and verification increment

The candidate entry workflow now invokes `.github/workflows/ndf-reusable-build-candidate.yml` through `workflow_call` after the intake/preparation job succeeds.

- The reusable stage downloads the exact attempt-scoped prepared artifact and verifies its handoff candidate ID, immutable OCI reference, payload hash, workflow run ID/attempt, image ID and exact lock-v2 SHA-256.
- It rejects symlinks in the downloaded artifact and requires the adapter's candidate lock-v2, `apps.json`, `build-metadata.json` and composition mapping.
- It runs the NDF regression suite, then invokes `build_image.py --prepared-inputs-dir` with `linux/amd64`; normal preparation and `--output-dir` are not used.
- The image is pushed only to a unique `candidate-<run_id>-<run_attempt>` staging tag. The Buildx digest is compared with the registry tag, the exact staging image is pulled, and the existing image validation and publication-evidence gate are applied.
- The generated evidence is uploaded as `ndf-candidate-build-<run_id>-<run_attempt>`. The reusable workflow exposes the verified image digest and evidence artifact name for the next stage.
- The candidate path does not promote the image to an official product tag. Existing manual product build/publish/release and PDD workflows remain unchanged.
- Static contract tests now cover prepared-input-only build handoff, attempt binding, digest verification and absence of official-tag promotion. Local execution, action/YAML validation and a real GitHub Actions staging run remain pending.

This increment is an implementation state, not acceptance evidence. It does not yet generate/publish a PDD or produce the terminal deployment-build result. The real DT Master OCI producer/consumer gate remains open.
