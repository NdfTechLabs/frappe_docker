## 1. Purpose and authority

This plan defines the NDF implementation required to satisfy the accepted M4.1 candidate/build/result contract and the M4.2.7 work-package scope in `M4.2-IMPLEMENTATION-PLAN.md`.

The requirements audit is recorded in `M4.2.7-READINESS-AUDIT.md`.

No files, DocTypes, APIs, workflows or implementation branches are to be created in those repositories as part of this work package.

This plan does not authorize M4.2.8 artifact signing/attestation, M4.3 runtime orchestration, M4.4 deployment execution, M4.5 runtime application management or M4.6 tenant integration.

## 2. Objective

Allow an authorized DT Master workflow invocation to submit a candidate ID and immutable candidate artifact reference to NDF; validate the complete candidate; reuse the established NDF composition, lock, image build, verification, publication and PDD machinery; and return a structured result that DT Master can independently retrieve and verify.

NDF is responsible for build correctness and artifact production. DT Master remains responsible for candidate lifecycle, authorization, deployment eligibility and deployment decisions.

## 3. Accepted input and output contracts

### 3.1 Input

The NDF entry workflow accepts only the minimum documented dispatch envelope:

- Candidate identifier.
- Immutable candidate artifact reference.
- Candidate artifact digest (or a verifiable digest obtained from the immutable reference).
- Contract/schema version.
- Correlation/request identifier where specified by the agreed envelope.

The candidate artifact contains the complete composition and approved build parameters defined by the DT Master M4.1 contract. NDF validates the full artifact against a versioned NDF-side input schema aligned with that contract.

Do not accept candidate-supplied shell commands, arbitrary workflow names, arbitrary script paths, credentials, tenant data, FQDNs, TLS material, Node ports or unrestricted registry destinations.

The selected transport direction is a private GHCR OCI artifact package, `ghcr.io/ndftechlabs/dt-master-deployment-candidates`, addressed by manifest digest. The NDF-side contract is recorded in `M4.2.7.1-CONTRACT.md`. The DT Master source documentation requires an immutable reference and digest but does not itself prescribe GHCR/ORAS; cross-repository serializer/media-type agreement remains a pre-production dependency.

### 3.2 Result

NDF produces a versioned, machine-readable result containing, at minimum:

- Result schema version.
- Candidate ID and request/correlation ID.
- Candidate artifact reference and digest.
- Workflow identity, workflow run ID and source commit.
- Terminal or in-progress build status.
- Image repository and immutable image digest, when published.
- PDD immutable artifact reference and digest, when published.
- PDD content hash.
- Composition hash and resolved lock hash.
- Build provenance reference.
- Safe failure code and sanitized summary, when unsuccessful.
- Start and completion timestamps.

The result must be associated with one candidate and one build attempt. A retry is a new workflow/build attempt; prior terminal results are immutable. The result is build evidence, not a deployment authorization or candidate-ready decision.

The result transport and retention must support DT Master polling of workflow status/artifacts initially. An authenticated callback is not part of this work package unless separately approved; the accepted architecture permits polling first and callback later.

## 5. Workflow design principles

1. Add a candidate-driven orchestration entry point; do not replace the existing manual product workflows.
2. Reuse the established NDF resolver, lock-v2, build preparation, image construction, source/composition verification, publication gate and PDD generation/publication/consumer validation.
3. Avoid a second image builder, second dependency resolver, second image validator or competing PDD schema.
4. Use reusable `workflow_call` stages where existing interfaces can be safely extracted; the intended structure is a thin candidate orchestrator calling validation, build/image verification/publication and PDD stages. Preserve existing manual product workflows.
5. Do not pass untrusted candidate fields directly into GitHub Actions expressions, shell fragments, environment variable names, paths or command strings.
6. Validate candidate data before checkout/build/publication steps that consume it.
7. Restrict workflow permissions to the minimum required for candidate retrieval, workflow/artifact operations and NDF publication.
8. GHCR write credentials remain in NDF and must not be passed to DT Master.
9. Use immutable candidate, image and PDD references. Mutable tags may be discovery locators only.
10. Ensure failed validation prevents build and publication; failed image verification prevents publication; failed PDD generation/publication prevents a success result.
11. Preserve existing manual product workflows and regression coverage.
12. Result artifacts and logs contain no secret values, raw credentials, tenant data or unredacted sensitive diagnostics.

## 6. Idempotency and retry semantics

- Every accepted workflow execution is associated with a candidate ID and a unique build-attempt/workflow-run identity.
- Repeated dispatch of the same candidate must not overwrite or mutate a prior terminal result.
- A new attempt must be separately identifiable and traceable.
- NDF must not claim exactly-once execution from GitHub Actions dispatch alone. Duplicate dispatch and ambiguous outcomes must be handled by explicit attempt identity and result reconciliation.
- Result generation must be deterministic for the same verified inputs and outputs, apart from explicitly time/run-specific envelope fields.
- Failure summaries use stable safe error codes; raw stack traces and shell output are not returned as the cross-repository result.

The owning DT Master operation model remains authoritative for request idempotency and business lifecycle. NDF provides the execution/run identity and result evidence required by that model.

## 8. Dependencies and open implementation decisions

The following M4.2.7.1 decisions are now recorded in `M4.2.7.1-CONTRACT.md`; implementation must preserve them:

1. **Candidate artifact transport — selected NDF proposal:** private GHCR OCI artifact package, digest-pinned reference, ORAS-compatible publication/retrieval; the exact artifact type, empty config, one uncompressed JSON layer, filename annotation and manifest annotations are specified in `M4.2.7.1-CONTRACT.md`. DT Master producer compatibility must be confirmed before production dispatch.
2. **Dispatch authentication — selected:** narrowly scoped GitHub App installation token for dispatch; workflow GITHUB_TOKENs separately publish/read GHCR packages.
3. **Candidate schema — recorded:** NDF intake schema v1.0.0 and result schema v1.0.0; no changes to Master-owned schemas or records.
4. **Workflow composition — selected direction:** thin orchestrator plus reusable `workflow_call` stages where extraction is safe.
5. **Attempt identity:** one immutable result per NDF run; retries are new attempts; Master owns request idempotency.
6. **Retention:** candidate/result/PDD references remain available for the corresponding Master record and audit-retention lifetime; numeric duration is set by platform governance, not invented by NDF.
7. **Candidate mapping:** deterministic mapping into existing NDF resolver/lock-v2 inputs; no competing composition model.

Any contract ambiguity must be documented and escalated for agreement with the DT Master owner before implementation depends on it. Do not fill gaps by inventing new platform DocTypes or silently changing the accepted architecture.
