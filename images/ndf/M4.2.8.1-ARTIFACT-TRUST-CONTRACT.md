# M4.2.8.1 — Artifact Trust Contract and Mechanism Selection

**Repository:** `NdfTechLabs/frappe_docker`
**Implementation branch:** `feat/M4.2.8`
**Baseline:** merged M4.2.7 on `main`
**Status:** Contract drafted; implementation not started
**Scope:** M4.2.8.1 only

## 1. Purpose and authority

This work package defines how NDF establishes and independently verifies the authenticity and provenance of OCI artifacts produced by the NDF build pipeline. It precedes implementation of signing, attestations and production-eligibility gates.

The user approved **Cosign keyless signing with GitHub Actions OIDC**, Sigstore transparency-log evidence and strict NDF workflow identity verification as the trust foundation on 15 November 2026.

NDF is authoritative for the trust evidence attached to NDF-produced images and Product Deployment Descriptor (PDD) OCI artifacts. DT Master remains responsible for consuming and enforcing the trust contract when deciding deployment eligibility. A successful NDF build result is not, by itself, a deployment authorization.

This package does not change DT Master or DT Tenant, perform live cross-repository acceptance, or implement runtime deployment.

## 2. Read-only baseline audit

The following paths were inspected on `main` after M4.2.7 PR #17 merged at `1d67cfc8e434b46ca1f5dbcb30ebe282818f4f19`.

| Existing path | Current behavior | Trust gap to close |
| --- | --- | --- |
| `.github/workflows/ndf-publish-product.yml` | Builds and pushes a unique staging tag; checks Buildx digest against registry tag; validates image contents and evidence; runs `gate_image_publication.py`; optionally promotes the exact digest to the official immutable source tag on `main`. | No cryptographic signature or provenance attestation is produced or verified before official promotion. Staging-only builds can run without official promotion and must not become production-eligible merely because image validation passed. |
| `.github/workflows/ndf-release-product.yml` | Resolves an existing immutable source tag, promotes its exact digest to semantic and stable tags, and checks digest equality. | Promotion checks digest consistency but does not independently require a trusted signature and accepted provenance. |

| `images/ndf/scripts/publish_product_deployment_descriptor.py` and `verify_product_deployment_binding.py` | Publish immutable PDD OCI artifact and verify its exact bytes, OCI digest, image digest and evidence bindings. | No cryptographic signer identity or authenticated statement binding PDD artifact digest to image digest. |

### 2.1 Existing evidence that must remain authoritative

- Image identity is the OCI manifest digest, not a mutable tag.
- PDD identity is its immutable OCI `repository@sha256:...` reference and manifest digest; its internal canonical content hash is a separate value.
- PDD already binds to the subject image digest and includes exact-byte evidence references/hashes.
- Candidate results already correlate candidate ID, candidate artifact, image digest, PDD OCI digest/content hash and GitHub workflow run/attempt.
- Existing source-provenance, image-validation, composition-verification and evidence-binding reports remain the build facts from which attestations are derived.

Signing must not replace any existing validation, independent verification, digest binding or publication gate.

## 3. Mechanism selection

### 3.1 Selected foundation

Use **Sigstore Cosign keyless signing** with GitHub Actions OIDC:

- GitHub Actions obtains an OIDC identity token using job-scoped `id-token: write`.
- Cosign uses that identity to obtain a short-lived signing certificate from Fulcio.
- Signing events are recorded in the Sigstore transparency log (Rekor).
- Signature and attestation verification validates the Sigstore trust root, certificate identity, OIDC issuer, artifact subject digest and transparency evidence.
- No long-lived private signing key is stored in GitHub Secrets or distributed to DT Master.

The GitHub Actions OIDC issuer expected by verification is `https://token.actions.githubusercontent.com`.

### 3.2 Why keyless Cosign

This matches the existing GitHub Actions build and GHCR publication model, avoids introducing a long-lived NDF signing secret, supports OCI image and OCI artifact signing, and allows consumers to verify signer identity independently.

Cosign/Sigstore is the trust mechanism, not the build provenance source. NDF must still construct truthful, digest-bound predicates from its independently verified build evidence.

### 3.3 Tooling and version control

The implementation must pin the Cosign release/tool installation deterministically and test the selected CLI syntax against that pinned version. GitHub Actions used for installation must be pinned according to repository action-pinning policy. Do not rely on an unpinned `latest` binary or floating third-party action tag.

The exact Cosign release and action SHA are implementation decisions for M4.2.8.2, after compatibility checks; this contract does not guess a version.

## 4. Trust subjects and signed artifacts

NDF signs only artifacts it produces or publishes after its own verification gates.

| Subject | Sign? | Required trust evidence | Production eligibility |
| --- | --- | --- | --- |
| NDF product image OCI manifest digest | Yes | Cosign signature plus SLSA provenance attestation bound to exact image digest | Only after signature, identity, provenance and existing image checks pass |
| NDF candidate-build image OCI manifest digest | Yes | Same image signature and provenance, bound to the candidate workflow run and source commit | Only after candidate authorization, image verification and trust verification pass |
| NDF PDD OCI artifact manifest digest | Yes | Cosign signature plus NDF PDD-image-binding attestation bound to exact PDD digest and exact image digest | Only after PDD/evidence binding and trust verification pass |
| DT Master-supplied candidate OCI artifact | No | NDF validates candidate schema, immutable reference and payload hash under the existing intake contract; producer trust remains a DT Master responsibility | It is not an NDF-built deployable image and does not inherit NDF signer identity |
| Mutable tags, workflow artifacts, logs and result JSON | No standalone artifact signature in this package | Their relevant identities are captured as claims/references in signed attestations or receipts | Never treated as trust subjects by tag/name alone |

### 4.1 Image provenance predicate

The image attestation will use the in-toto Statement model with a SLSA provenance predicate (version selected and pinned during implementation). Its subject must be the exact OCI image digest.

The predicate must be generated from verified NDF evidence and include, at minimum, supported claims for:

- NDF repository identity and source commit;
- triggering workflow identity, run ID and run attempt;
- product/image ID and target platform;
- immutable lock-v2 SHA-256 and composition identity;
- actual acquired source revision inventory;
- build invocation/builder identity and relevant build parameters;
- image validation, source provenance verification, composition verification and evidence-binding outcomes; and
- candidate ID and digest-pinned candidate artifact reference when the image came from the candidate workflow.

A claim may be omitted only where the relevant build mode does not provide it. Do not invent values or turn unknown facts into verified claims.

### 4.2 PDD-to-image binding predicate

Sign the PDD OCI artifact digest and attach a separately verifiable in-toto attestation whose subject is that exact PDD OCI digest.

The versioned NDF predicate type will be:

`https://ndftechlabs.com/attestations/pdd-image-binding/v1`

The predicate must include:

- PDD OCI repository and manifest digest;
- PDD canonical content SHA-256 and descriptor ID;
- subject image repository and immutable image digest;
- image platform;
- exact lock-v2 SHA-256;
- source image provenance/verification reference and digest where available; and
- originating NDF workflow repository, path, run ID, attempt and source commit.

The verifier must prove that the PDD's embedded image digest and content hash match the signed predicate and that the PDD OCI artifact itself is the attestation subject. The predicate is an additional authenticated relationship, not a replacement for existing PDD binding verification.

## 5. Signer identity and verification policy

### 5.1 Issuer

All NDF keyless signatures and attestations must use the GitHub Actions OIDC issuer:

`https://token.actions.githubusercontent.com`

### 5.2 Identity allowlist

Verification must use exact expected certificate identity values, not a wildcard matching any GitHub workflow or any identity in the repository.

Expected workflow identities are based on these NDF workflow paths:

- Product image publication: `NdfTechLabs/frappe_docker/.github/workflows/ndf-publish-product.yml`
- Product PDD publication: `NdfTechLabs/frappe_docker/.github/workflows/ndf-publish-product-deployment-descriptor.yml`
- Candidate image build: `NdfTechLabs/frappe_docker/.github/workflows/ndf-build-candidate.yml` (the reusable build job is called by this authorized entry workflow).
- Candidate PDD publication: `NdfTechLabs/frappe_docker/.github/workflows/ndf-build-candidate.yml` (the reusable PDD job is called by this authorized entry workflow).

The expected identity form is the GitHub Actions workflow URI associated with the approved `refs/heads/main` execution. Exact certificate identity strings and any reusable-workflow identity claims must be confirmed with a real signing run before being frozen in verifier configuration. This is an explicit implementation validation requirement, not permission to broaden the allowlist.

### 5.3 Required policy checks

A trusted artifact must satisfy all of the following:

1. Cosign signature/attestation cryptographically verifies against the Sigstore trusted root.
2. Certificate OIDC issuer exactly matches the GitHub Actions issuer above.
3. Certificate identity exactly matches an approved NDF workflow identity and `refs/heads/main`.
4. Repository and workflow path are the expected NDF-owned values; no fork, pull-request, tag or arbitrary branch identity is accepted for production trust.
5. The signature or attestation subject digest exactly matches the requested OCI artifact digest.
6. Required transparency-log evidence is present and verifies. A missing, invalid or unverifiable Rekor inclusion proof fails closed.
7. Required predicate type and schema are recognized and validated.
8. Provenance claims agree with independently verified NDF build evidence and PDD binding data.
9. Candidate builds additionally satisfy the existing dispatch authorization and candidate correlation contract.
10. No mutable tag is accepted as the subject identity; resolve it to a digest first and verify that digest.

### 5.4 Reusable workflow identity

Because candidate build and PDD jobs execute through reusable workflows, M4.2.8 implementation must inspect the actual OIDC token claims and resulting Sigstore certificate identity for the caller/reusable workflow combination. The allowlist may include a reusable workflow identity only when it is explicitly pinned to the expected repository, workflow path, ref and approved caller relationship. Do not infer this identity format from the workflow YAML alone.

## 6. Workflow permissions and boundaries

Permissions are job-scoped and least-privilege:

| Job responsibility | Required permissions |
| --- | --- |
| Existing image build/push | Existing `contents: read`, `packages: write`; add `id-token: write` only to the job that performs keyless signing/attestation |
| Product image trust verification | `contents: read`, `packages: read`; no `id-token: write` |
| PDD publication/signing | `contents: read`, `packages: write`, `actions: read` where run/artifact lookup is needed; add `id-token: write` only to the signing job |
| PDD fetch/consumer verification | `contents: read`, `packages: read`, and only the existing minimum read permissions needed to retrieve the publication receipt |
| Candidate image signing | `contents: read`, `packages: write`, `id-token: write` on the authorized candidate build/signing job |
| Candidate PDD signing | `contents: read`, `packages: write`, `actions: read` as needed, plus `id-token: write` only on the signing job |
| Result finalizer | Retain current `actions: read`, `contents: read`; no `packages: write` and no OIDC token |

No job receives `contents: write`, `actions: write`, organization administration or unrestricted repository administration permissions for signing.

If a signing stage is separated from a build/publish stage, pass only immutable digest references and validated evidence artifact identities between jobs. Do not pass registry credentials or OIDC tokens as job outputs or artifacts.

## 7. Trust gate placement

### Product image

The required sequence is:

1. Build and push to unique staging reference.
2. Verify staging tag resolves to Buildx digest.
3. Run existing image/content/source/composition/evidence validation.
4. Run existing publication gate.
5. Sign exact image digest and publish required provenance attestation.
6. Independently verify signature and attestation against the fixed trust policy.
7. Only then, when `publish=true` on `main`, promote the exact trusted digest to the official immutable source tag.
8. Verify the official tag resolves to the same digest.

A staging-only run may create trust evidence for diagnostics only if explicitly designed to do so, but must not be interpreted as production-eligible. The official promotion gate is authoritative.

### Product PDD

1. Validate source run/artifact ownership.
2. Independently verify the PDD, image binding and exact evidence bytes.
3. Publish the PDD OCI artifact and resolve its immutable manifest digest.
4. Sign the exact PDD OCI digest.
5. Publish the PDD-image-binding attestation with the PDD OCI digest as subject.
6. Independently verify signature, identity, transparency evidence and predicate/image binding.
7. Emit the publication receipt only after all trust checks pass.

### Candidate pipeline

1. Preserve the existing main-ref and actual DT Master GitHub App actor authorization gate.
2. Preserve candidate intake, immutable reference, payload hash and lock adapter validation.
3. Build and independently validate the NDF candidate image.
4. Sign/attest the exact NDF image digest under the authorized NDF candidate workflow identity.
5. Verify image trust before candidate PDD publication.
6. Publish, sign and attest the exact PDD OCI digest and image relationship.
7. Verify PDD trust before the terminal result can report success.
8. Include signature/attestation references and verification outcomes in the correlated result contract only after their schema and compatibility are reviewed in a later implementation package.

No fabricated candidate, developer actor substitution or authorization-gate weakening is permitted.

## 8. Failure semantics

Trust verification is fail-closed. The following conditions prevent official promotion, trusted PDD publication, or candidate success:

- no signature or required attestation;
- invalid signature, malformed bundle or invalid certificate chain;
- wrong OIDC issuer;
- signer identity not on the exact allowlist;
- unapproved branch, tag, fork, pull request or workflow path;
- absent or invalid transparency-log proof;
- unsupported predicate type/version or invalid predicate schema;
- attestation subject digest differs from the requested OCI digest;
- provenance source commit, workflow run/attempt, product identity, platform, lock hash or evidence claims conflict with verified build records;
- PDD subject digest, PDD content hash, image digest or lock hash does not match the independently verified PDD;
- mutable tag used instead of an immutable digest;
- registry cannot provide the artifact/signature/attestation needed for complete verification; or
- trust service/network errors prevent verification.

Retries may be implemented for transient service failures, but a retry exhaustion is a failure, never an implicit pass or bypass. Existing staging artifacts may remain for diagnosis; they are not promoted or marked production-eligible.

## 9. Acceptance criteria for M4.2.8.1

M4.2.8.1 is complete when the following contract is documented and reviewed:

1. Existing product image, release, PDD and candidate publication/verification paths are audited.
2. NDF-owned trust subjects are explicitly enumerated; externally produced DT Master candidate input is excluded from NDF signing.
3. Cosign keyless signing with GitHub Actions OIDC and Sigstore transparency evidence is selected.
4. Image provenance predicate and PDD-to-image binding predicate are defined and versioned.
5. Exact workflow identity allowlist, issuer and main-ref requirements are defined; reusable workflow identity validation is called out as a runtime acceptance requirement.
6. Least-privilege job permission matrix is documented, including job-scoped `id-token: write`.
7. Trust gate placement is defined for product publication, PDD publication/fetch, release promotion and candidate success.
8. Fail-closed conditions and negative acceptance cases are enumerated.
9. Existing digest, PDD binding, source-provenance, image validation and candidate authorization contracts are preserved.
10. Implementation packages and external integration boundaries are explicit.

### Required negative test cases for implementation

- Missing image signature; wrong image digest signature.
- Signature from wrong repository, fork, branch, tag, pull-request workflow or workflow path.
- Wrong OIDC issuer; wildcard identity accidentally accepted.
- Missing, malformed or invalid Rekor transparency evidence.
- Missing or unsupported SLSA provenance predicate.
- Provenance subject digest mismatch; source SHA, lock SHA, platform, product ID, run ID or run attempt mismatch.
- PDD signature missing or bound to a different PDD OCI digest.
- PDD binding attestation with wrong image digest, descriptor ID or content hash.
- PDD and image signed by an unapproved identity.
- Registry or Sigstore verification unavailable after retry exhaustion.
- Candidate pipeline skips signing/verification but attempts to report success.
- Product release attempts to promote an unsigned or untrusted source digest.
- An unsigned staging-only image is incorrectly classified as production-eligible.

## 11. External dependencies and boundaries

- DT Master must independently implement verification of NDF signatures and attestations before treating NDF artifacts as production-eligible. That consumer work is not performed in this repository.
- The real DT Master candidate producer/consumer operational acceptance for M4.2.7 remains deferred until a real candidate OCI artifact and actual configured GitHub App actor are available.
- Sigstore public services (Fulcio, Rekor and TUF trust-root distribution) are external runtime dependencies. Verification must fail closed if trust cannot be established.
- The exact Cosign release, action commit SHAs, concrete certificate identity strings and reusable-workflow OIDC claims must be validated before implementation acceptance.
