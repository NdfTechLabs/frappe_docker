**Scope:** M4.2.2 only

## 1. Objective

Extend the existing NDF application-manifest and resolver path into the approved, versioned Marketplace App Descriptor and dependency contract.

The descriptor must let NDF and downstream DT Master determine:

- What a Frappe application is, where its source is maintained, and which release is selected.
- Which Frappe/ERPNext and Python/Node runtime versions the application supports.
- Which other Bench applications and package dependencies it requires.
- Which build and installation metadata is needed to construct a compatible Bench image.
- Whether a dependency is already supplied by the product base image, can be added compatibly at runtime/build time, or requires a new environment image.
- Which fields are declared facts, which are compatibility evidence, and which values are resolved later into the composition lock.

This package extends the current manifest/resolver contract. It must not create a competing resolver, dependency manager, build engine, service orchestrator or DT Master runtime implementation.

## 2. Existing manifest model — discovery baseline

The current `application-manifest-v1.schema.json` describes a product or capability composition root. It is not yet a complete Marketplace App Descriptor.

Current top-level sections include:

- `manifest_version`, `id`, `name`, `description`
- `framework`
- `profile`
- `resolution`
- `includes` and `capabilities`
- `applications`
- `services`
- `validation`
- Product-specific `deployment` metadata

Current application entries commonly contain:

- `name`, `repository`, `target_ref`, `ref`
- `required`, `install_order`
- `dependencies` (currently a list of Bench app names)
- `compatibility_status`
- Optional `notes`

Some entries also contain fields such as `source_status` and `production_policy`. These are currently informal application-specific properties rather than a consistent typed contract.

The current schema permits `additionalProperties`, so it does not yet enforce a complete, versioned application descriptor or dependency vocabulary.

### Current gaps to address

1. **Release identity:** there is no consistent application release/version declaration separate from the requested Git reference and resolver's resolution-time SHA.
2. **Framework compatibility:** current entries use a free-text `compatibility_status`; they do not declare supported Frappe/ERPNext version ranges in a machine-comparable form.
3. **Runtime compatibility:** application-specific Python and Node.js version ranges are not consistently declared.
4. **Dependency typing:** `dependencies` only names other Bench apps. It does not describe Python packages, Node packages, OS packages, external requirements or dependency ownership.
5. **Dependency disposition:** the manifest does not distinguish packages already supplied by a base image, compatible additions, and dependencies that require an image/runtime change.
6. **Build metadata:** Python packaging, Node package/build requirements, OS build packages, build context and other build inputs are not consistently represented.
7. **Installation metadata:** app identity, install behaviour, migration requirements and supported Bench installation expectations are not fully typed.
8. **Compatibility evidence:** there is no consistent structure for recording tested framework/runtime versions, test evidence and verification status.
9. **Migration:** schema evolution and treatment of existing manifest v1 application entries are not yet specified.

## 3. Architectural boundaries to preserve

### 3.1 Composition manifest versus Marketplace App Descriptor

The product/capability manifest remains the composition root: it selects which applications and capabilities belong in a product build and supplies product-specific choices such as `required`, selected `target_ref` and composition order.

The Marketplace App Descriptor supplies reusable application metadata: identity, release metadata, compatibility ranges, dependency declarations, build requirements and install metadata.

The selected representation and reference relationship are defined in section 7.1. Product manifests must not duplicate descriptor-owned source-of-truth metadata or create a second resolver.

**Accepted design:** retain the current product/capability manifest hierarchy and resolver as the composition interface; reference separate versioned, typed Marketplace App Descriptor files from application entries. Product-specific source selection remains explicit in the composition manifest and resolved lock.

### 3.2 Source identity versus release compatibility

Keep these concepts distinct:

- Application release/version: human- and marketplace-facing release identity.
- Requested source reference: branch, tag or explicit commit selected by the product composition.
- Resolution-time SHA and reference provenance: recorded by the M4.2.1 composition lock.
- Actual Bench-acquired commit: captured by M4.2.4 after Bench acquisition.
- Verified installed source revision: checked by M4.2.5.

A compatibility range is not a source pin. A Git reference is not a compatibility declaration. A resolution-time SHA is not proof of installed source.

### 3.3 Dependency ownership categories

The descriptor and dependency model must preserve three distinct dispositions:

| Category | Meaning | Expected handling |
|---|---|---|
| Base dependency | Already provided by the approved product/base image | Validate presence/version; do not install a duplicate |
| Runtime-compatible dependency | Can be added without changing the Bench's resolved OS/Python/Node runtime contract | Resolve and install through the controlled dependency/build path |
| Environment-level dependency | Requires a different OS library, Python/Node runtime, system toolchain or incompatible ABI | Require a new compatible image/environment; do not inject ad hoc into a running Bench |

Dependency records must identify the ecosystem and package identity, supported version constraint, disposition and any source/build metadata needed to resolve them deterministically.

### 3.4 Keep Bench applications and independent services separate

Only Frappe/Bench-installable apps belong in the application descriptor/application composition inventory.

Independent services remain represented by the existing `services` concept and are not converted into Bench apps or passed to Bench's app acquisition input. M4.2.3 owns full service/capability composition and resolution; M4.2.2 may define shared descriptor vocabulary only where required, without implementing service orchestration.

External managed dependencies (for example, a SaaS endpoint) must not be misclassified as Bench apps or container services.

## 4. Descriptor contract areas

The schema design should cover the following typed groups. Exact required/optional status and nesting are to be finalized through the schema and migration review.

| Group | Required information |
|---|---|
| Descriptor identity | Descriptor schema/version, stable app ID, display name, publisher/maintainer, description |
| Source/release | Canonical repository, release/version identifier, selected source reference kept distinct from resolved lock SHA |
| App classification | Bench-installable app identity and supported Frappe app/module identity |
| Framework compatibility | Supported Frappe and, where applicable, ERPNext version ranges |
| Runtime compatibility | Supported Python and Node.js ranges; any required package-manager/toolchain constraints |
| Bench app dependencies | Required/optional app dependencies and compatible version ranges |
| Python dependencies | Distribution name, version constraint, dependency disposition, source/build metadata |
| Node dependencies | Package name, version constraint, package manager and build/runtime scope |
| OS dependencies | Package identity, supported version constraint, distribution/package manager, build/runtime scope and environment-level classification |
| Build metadata | Build system, manifest/lock files, build context, required build packages and supported build steps |
| Install metadata | Bench install identity, install/migrate expectations, required setup metadata and any declared hooks |
| Compatibility evidence | Status, tested framework/runtime matrix, evidence reference and verification metadata |
| Security/provenance hints | Source ownership and license metadata where declared; no secrets or credentials |

Do not add arbitrary executable shell commands as untrusted marketplace metadata. Any build/install action that can execute code must be constrained to the trusted build process and validated against an explicit policy.

## 6. Schema and migration strategy

M4.2.1 established lock v2. M4.2.2 must now define the next application descriptor schema without invalidating the lock's meaning or silently mutating source identities.

The implementation must specify:

1. Whether the composition manifest schema advances to a new major schema version, and how its `manifest_version` relates to descriptor schema version.
2. How existing `application-manifest-v1` product/capability manifests are read during transition.
3. How current application-entry fields map to the new typed descriptor contract.
4. Which legacy fields are preserved, deprecated or rejected.
5. How missing compatibility/dependency/build metadata is represented without inventing values.
6. Whether migration is read-only/reporting first or produces an explicit migrated file; no in-place bulk rewrite without review.
7. How source manifest checksums in lock v2 are regenerated after an approved schema/data migration.
8. How resolver compatibility is maintained during the transition and when v1 input support may be removed.

Migration must be deterministic and testable. A v1 manifest must not silently acquire fabricated runtime ranges, package dependencies or compatibility evidence.


## 7. Descriptor/composition decision and versioned schema contract

### 7.1 Relationship: separate descriptor files referenced by composition roots

Decision: use separate reusable Marketplace App Descriptor JSON files, referenced by product/capability composition entries through a repository-relative `descriptor` path. Do not embed full descriptors in product manifests and do not duplicate descriptor-owned metadata in composition roots.

Proposed catalogue convention: `images/ndf/descriptors/apps/<app-id>.json`.

| Concern | Owner |
|---|---|
| Stable app identity, publisher, canonical repository, release metadata, Bench app/module identity | Marketplace App Descriptor |
| Framework/runtime compatibility declarations and evidence | Marketplace App Descriptor |
| Typed Bench/Python/Node/OS dependencies | Marketplace App Descriptor |
| Declarative build and installation requirements | Marketplace App Descriptor |
| Product/capability inclusion, required/optional selection, selected source ref, composition/install order, product validation and deployment choices | Composition manifest |
| Resolved immutable source SHA and resolution provenance | M4.2.1 composition lock |
| Actual Bench-acquired source SHA | M4.2.4 |
| Installed source revision verification | M4.2.5 |

The descriptor's `app_id` is the stable platform identity. `app_module.bench_app_name` is the actual Frappe Bench install name; they may be equal but are distinct concepts. The canonical repository is descriptor-owned. The release version is optional until declared by the publisher; it is never inferred from a Git tag, branch or resolved SHA.

A new composition entry contains `descriptor` (required), `required` (required), optional `target_ref`, optional `install_order`, and optional composition-specific `notes`. `target_ref` overrides the descriptor's optional `source.default_ref`. If neither is present, resolution must fail rather than silently selecting a moving ref. `ref` is retained only as a temporary legacy migration field. Product manifests must not override the canonical repository.

Descriptor paths must be normalized repository-relative paths that remain inside the repository. Reject path traversal, missing descriptor files, duplicate app IDs and descriptor/app identity mismatches.

Composition manifest v1 embedded application entries remain readable during transition. Composition manifest v2 supports both descriptor references and a legacy-entry branch. Do not bulk-convert existing product manifests until individual descriptors are authored and reviewed.

### 7.2 Schema files

- `schemas/marketplace-app-descriptor-v1.schema.json`: reusable app metadata; `descriptor_version` is independently versioned and currently `1.0.0`.
- `schemas/dependency-v1.schema.json`: shared typed dependency definitions referenced by the app descriptor.
- `schemas/application-manifest-v2.schema.json`: composition root schema supporting descriptor references and legacy embedded entries during transition.

Composition `manifest_version` and descriptor `descriptor_version` are independent. `manifest_version: 2.0.0` identifies the new composition-entry contract; `descriptor_version: 1.0.0` identifies the reusable app metadata contract. A revision to one does not automatically require a revision to the other.

### 7.3 Dependency sub-schemas and version semantics

`dependency-v1.schema.json` defines four dependency kinds:

- `bench_apps`: other Bench app IDs, required/optional semantics and optional version constraint. These are graph/composition dependencies, not package-manager installs.
- `python`: Python distribution name, explicit required/optional flag, optional PEP 440 version specifier and version-selection policy, disposition, optional source and build requirement.
- `node`: package name, explicit required/optional flag, optional npm-compatible SemVer range and version-selection policy, package manager, build/runtime scope and disposition.
- `os`: package name, explicit required/optional flag, native distribution family/package manager, optional native version constraint and version-selection policy, build/runtime scope and disposition.

Disposition is exactly `base`, `runtime_compatible` or `environment_level`. Base dependencies are validated against the approved base image. Runtime-compatible dependencies may be resolved through the controlled image build. Environment-level dependencies change the OS/runtime/toolchain contract and require a different image/environment; they are not permission to mutate a running Bench.

Version comparison is ecosystem-specific: Frappe/ERPNext and Node use SemVer-compatible ranges; Python uses PEP 440 specifiers; OS package versions use the declared native package manager's semantics. A compatibility constraint is not an immutable source pin. Parser/library choices and normalization rules must be pinned and tested before resolver integration.

### 7.4 Declarative execution and compatibility evidence

Descriptors record package/lockfile/build-system requirements and declarative installation policy only. They do not accept arbitrary shell commands, Python snippets or publisher-supplied executable hooks. Any trusted hook must be selected from NDF-controlled build policy.

Compatibility status is explicit (`verified`, `pending`, `incompatible`, `experimental`). Evidence records identify evidence kind, reference, result, optional timestamp and tested version matrix. A declared range or branch name alone is not evidence. Missing ranges and evidence remain absent; migration must not fabricate them.

### 7.5 Schema implementation status

The three schemas are an initial contract baseline. They require schema-validation fixtures, semantic validation and review before resolver changes. Existing product manifests have not been rewritten, no compatibility/dependency facts have been invented, and resolver code has not been changed.


### 7.6 Contract review findings before resolver integration

The initial schemas were tightened during fixture/test design:

- Composition v2 now validates the core framework/profile structures and typed include/capability/application entries while retaining product-specific extension fields.
- Descriptor installation metadata requires `bench_installable: true`; the descriptor contract is specifically for Bench-installable apps.
- A descriptor marked `verified` must include at least one evidence record with a `passed` result. A version range or source branch alone cannot satisfy this condition.
- Dependency package dispositions apply to Python, Node and OS package requirements. Bench app dependencies remain composition-graph edges and do not carry package installation dispositions.
- Descriptor references are normalized repository-relative POSIX paths. The validator rejects absolute paths, parent traversal, Windows separators, missing files and symlinks resolving outside the repository.
- A composition cannot contain duplicate Marketplace `app_id` values or duplicate Frappe `bench_app_name` install identities.
- A source ref must be supplied by the composition entry's `target_ref` or the descriptor's `source.default_ref`. Empty/whitespace refs are rejected.
- JSON Schema format assertions are enabled for URI and date-time fields.

Known contract limitations intentionally left for the resolver integration design review:

- Supplied SemVer and PEP 440 constraints and exact tested-version values are now parsed by the pinned implementations recorded in section 7.7.2. OS package version syntax remains delegated to the target package manager. Constraint intersection, dependency satisfiability and exact package selection remain M4.2.3 resolver responsibilities.
- The v2 composition schema retains legacy embedded entries for migration, but this validation module does not resolve or convert legacy entries into descriptor records. The existing v1 resolver remains the authoritative legacy path.
- Descriptor validation currently checks individual descriptor schema and uniqueness within the selected composition. It does not yet resolve Bench dependency graphs, test dependency version intersections, or verify that dependency app IDs are included. Those are resolver/composition responsibilities after this contract is approved.
- The descriptor fixtures use existing NDF app source/repository/ref/dependency declarations. Compatibility remains `pending`; no Frappe/Python/Node ranges or package dependencies have been invented. Synthetic package records in tests are explicitly validation-only examples.

## 7.7 Contract decisions — M4.2.2 acceptance review

The following decisions are the approved contract baseline for the remaining M4.2.2 schema and validator work. They refine the initial schemas; they do not authorize resolver integration before the M4.2.2 acceptance gate.

### 7.7.1 Authoring completeness versus production eligibility

Marketplace descriptors may be incomplete while being authored. Authoring validation checks structure, identity, allowed fields, path safety and the validity of any metadata that is supplied. It must report missing information without inventing defaults, version ranges, package dependencies or compatibility evidence.

Authoring validity is not production eligibility.

Production eligibility is a separate, fail-closed assessment against the selected product image and runtime. M4.2.2 provides a metadata-readiness gate: every selected required dependency must be classified, its version policy must be explicit, its constraint must parse when supplied, and required compatibility declarations/evidence must be present. This gate only determines whether the descriptor may enter production resolution; it does not claim the dependency has been resolved. M4.2.3 and subsequent build validation must prove that the dependency graph is satisfiable against the selected environment and that every selected version is locked. Any missing, ambiguous, unsupported or unresolved required dependency or compatibility input blocks production image eligibility. Optional dependencies that are not selected do not block the build; selected optional dependencies are subject to the same checks as required dependencies.

An intentionally unconstrained dependency must be represented by an explicit selection policy, not by silently treating a missing version constraint as a wildcard. Production resolution must record the exact selected package/application versions in the immutable build/lock evidence. M4.2.2 defines the metadata contract and validation levels; dependency graph resolution and full environment satisfiability remain M4.2.3 responsibilities.

### 7.7.2 Ecosystem-specific version syntax and comparison

Version strings are not interchangeable. The contract assigns one syntax and comparison authority to each ecosystem:

| Ecosystem | Contract syntax and comparison |
|---|---|
| Marketplace app release identity | Exact SemVer 2.0.0 version, when declared |
| Bench app dependency | npm-compatible SemVer range checked against the target app descriptor's declared release version |
| Frappe framework | npm-compatible SemVer 2.0.0 ranges |
| ERPNext | npm-compatible SemVer 2.0.0 ranges |
| Node.js runtime | npm-compatible SemVer 2.0.0 ranges |
| Node packages | npm-compatible SemVer range syntax |
| Python runtime | PEP 440 version/specifier semantics |
| Python distributions | PEP 440 version/specifier semantics |
| OS packages | Native package-manager version semantics; never compare Debian and RPM versions using a shared generic comparator |

SemVer ranges are validated with the pinned Python `semantic-version` implementation using its npm-compatible `NpmSpec` parser. Python constraints are validated with the pinned `packaging` implementation using PEP 440 `SpecifierSet` semantics. The current toolchain pins are recorded in `requirements-test.txt` and must be changed only through a reviewed dependency update. Debian-family package versions must be evaluated using Debian package semantics; RPM-family versions must be evaluated using RPM semantics. OS package satisfiability is delegated to the target distribution's native package tooling/solver, not approximated by string comparison.

The implementation pins `semantic-version==2.10.0` for npm-compatible SemVer ranges and `packaging==25.0` for PEP 440 specifiers in `requirements-test.txt`. These implementations must be upgraded only through a reviewed dependency change. Invalid syntax, unsupported operators, ambiguous ecosystem identifiers or unavailable comparison support are validation failures. The resolver must normalize constraints deterministically and test intersections where multiple declarations constrain the same dependency. A constraint is not a release identity, Git ref or immutable source pin.

### 7.7.3 Missing dependency constraints and explicit selection policy

A missing constraint is permitted during authoring and is reported as incomplete metadata. It is not interpreted as an implicit wildcard and is not silently upgraded to a production-compatible declaration.

For production eligibility, each required dependency must have either:
- an explicit ecosystem-valid version constraint; or
- an explicit, supported selection policy authorizing compatible-version selection for that dependency.

The second case is not unconstrained execution: the resolver must evaluate the selected target environment, select a satisfiable version, and record the exact resolved version and source/repository provenance in immutable build evidence. It applies to package-manager dependencies, not Bench app graph edges. Bench app dependencies require an explicit SemVer constraint checked against the target app descriptor's declared SemVer release. If the target descriptor has no declared release version, the dependency edge remains unresolved and blocks production eligibility; a Git tag, branch or SHA must not be used as a substitute. Source selection remains the composition manifest's responsibility. If the selected policy cannot produce a deterministic, supportable result, production eligibility fails. Schema changes must make this distinction explicit for Bench app, Python, Node and OS dependency records.

### 7.7.4 Compatibility evidence requirements

Compatibility declarations and compatibility evidence are separate facts. A declared range states what an application claims to support; evidence records what was actually tested.

A descriptor may remain `pending`, `experimental` or `incompatible` while being authored. A descriptor marked `verified` must have passed evidence produced or independently reviewed under NDF-controlled verification. A publisher declaration, upstream branch name, release tag or declared version range alone cannot establish NDF-verified compatibility.

A qualifying NDF verification record must identify:
- the tested Frappe version;
- the tested ERPNext version when ERPNext is part of the target;
- the tested Python version;
- the tested Node.js version when relevant to the app's build/runtime; tested version values themselves must be valid exact SemVer or PEP 440 versions, not range expressions;
- the evidence reference, verification kind, result and test timestamp.

Evidence must identify its authority (publisher/upstream versus NDF). A `verified` status requires at least one passed NDF-authority record with the applicable tested-version matrix. Tested versions must be exact valid ecosystem versions and must satisfy the descriptor's corresponding declared compatibility ranges. Missing or inapplicable matrix entries must be explicit; they must not be fabricated. Production metadata readiness checks that the evidence matrix covers the selected app's required runtime dimensions; M4.2.3 checks coverage against the selected target runtime.

### 7.7.5 Operational dependency disposition semantics

The package dependency dispositions have these operational meanings:

| Disposition | Required interpretation | Prohibited interpretation |
|---|---|---|
| `base` | The exact dependency is already supplied by the approved base image/runtime and its installed version is validated against the declared requirement. The app descriptor does not install a duplicate. | Merely assuming a package exists because it is commonly present in a Frappe image. |
| `runtime_compatible` | The dependency may be added during the controlled immutable image build without changing the approved OS family, OS ABI/shared-library contract, Python interpreter/ABI, Node runtime, system toolchain or other declared runtime contract. Its build/runtime scope must be explicit. | Installing arbitrary OS libraries, changing interpreter/runtime versions, mutating a running Bench, or treating every pip/npm package as automatically compatible. |
| `environment_level` | The dependency changes or requires a different OS/runtime/ABI/shared-library/toolchain contract. It requires a separately resolved and built compatible image/environment revision. | Injecting it ad hoc into an existing running Bench or silently changing the base image. |

Disposition is determined by the effect on the resulting environment, not solely by the package manager used. A Python distribution with native extensions or system-library requirements may be environment-level. A Node package used only for asset compilation is a build-scoped dependency; a runtime package is evaluated against the runtime contract. Base dependencies must declare a version constraint so the already-installed package can be checked; `latest_compatible` is not valid for a base dependency because the base image cannot select a replacement version. Base-image inventory and package versions must be verified, not presumed.

### 7.7.6 NDF-controlled build and installation policy identifiers

Marketplace descriptors remain declarative. They may reference named policies from an NDF-maintained, versioned allowlist/catalogue, but they cannot define executable commands, scripts, arbitrary Python snippets, shell fragments, package-manager hooks or their own policy implementations.

Build and installation policy identifiers are resolved only against NDF-controlled policy definitions. Each catalogue entry carries a policy version, description and NDF implementation identifier; the NDF-owned implementation defines the permitted action, inputs, execution context and trust requirements. Unknown, retired, unapproved or incompatible policy identifiers fail validation. Descriptor metadata cannot override the policy definition. The initial NDF catalogue intentionally contains no custom build or installation policies; custom execution remains unavailable until a policy is separately reviewed, implemented and allowlisted.

The existing generic `custom_policy` and `trusted_hook` values must not imply permission to execute publisher code. Schema refinement will replace ambiguous free-form execution semantics with explicit NDF policy references. Operator actions remain declarative instructions and are not automatically executed by the image builder.

### 7.7.7 Descriptor catalogue filename and identity validation

The canonical catalogue path is `images/ndf/descriptors/apps/<app_id>.json`. For a descriptor stored in this catalogue, the filename stem must exactly equal its declared `app_id`. This prevents a valid descriptor from being silently substituted under another catalogue identity.

Composition descriptor paths must be normalized repository-relative POSIX paths. Reject absolute paths, parent traversal, Windows separators, empty or whitespace-padded paths, redundant path components, symlink escapes, missing files and non-canonical path spellings. Resolve the path within the repository root before reading it. Duplicate Marketplace `app_id` values and duplicate `bench_app_name` values within a selected composition remain errors.

### 7.7.8 Work-package boundary

M4.2.2 defines and validates descriptor metadata, version syntax, evidence shape, policy references, dependency disposition and production-resolution metadata readiness. It does not resolve the complete Bench dependency graph, calculate transitive dependency closure, detect graph cycles, compose independent services/capabilities or select a final install order. Those are M4.2.3 responsibilities.

M4.2.2 must not modify the M4.2.1 resolver/lock behavior until the descriptor contract is accepted. Subsequent resolver integration must preserve descriptor identity, declared release identity, requested Git ref, resolution-time SHA and actual Bench-acquired SHA as separate values.
