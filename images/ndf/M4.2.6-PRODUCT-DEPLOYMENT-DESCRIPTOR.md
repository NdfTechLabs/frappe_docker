# M4.2.6 — Product Deployment Descriptor

**Repository:** `NdfTechLabs/frappe_docker`  
**Integration baseline:** `main`  
**Planning branch:** `feat/m4.2.5-image-verification`  
**Status:** Approved for implementation planning; implementation not started  
**Approval date:** 14 November 2026  
**Scope:** M4.2.6 only

## 1. Purpose

M4.2.6 defines and produces the versioned Product Deployment Descriptor (PDD) that DT Master will consume to understand and deploy a verified NDF product image.

The descriptor is the machine-readable deployment contract for the **complete deployable product runtime**. It is not merely an inventory of applications baked into an image. It must describe the product composition and runtime topology needed by a deployment consumer, while distinguishing image-baked facts from environment-specific deployment allocations.

This package builds on the immutable image construction and verification evidence produced by M4.2.4 and M4.2.5.

## 2. Architectural ownership and boundaries

- **NDF Frappe Docker owns** the authoritative descriptor schema, descriptor generation, descriptor validation and immutable publication contract.
- **DT Master consumes** the published descriptor, independently validates its contract and integrity, and supplies environment-specific deployment allocations through explicitly permitted overrides.
- **DT Tenant is not a descriptor consumer.** It continues to submit tenant-facing requests through DT Master.
- The descriptor must be derived from verified build/image evidence. It must not claim that requested configuration was installed or observed unless the evidence proves that fact.
- The descriptor is immutable once published. A changed image or changed deployable composition produces a new descriptor identity.
- M4.2.6 prepares a stable contract for later workflow integration; it does not implement candidate-driven CI/CD, signing/attestations, Docker orchestration or tenant deployment.

The formal schema is maintained in NDF. DT Master must consume that contract rather than maintaining a competing schema.

## 3. Descriptor content model

The schema and generator must account for the following logical areas. Exact field names, requiredness, and versioning rules are finalized in M4.2.6.2.

| Area | Required meaning |
|---|---|
| Descriptor identity | Schema/contract version, product identity, descriptor identity and deterministic content identity |
| Artifact identity | OCI repository, exact immutable image digest, supported platform(s), and image metadata needed to identify the artifact |
| Build/source identity | Composition lock identity and digest, source/build identity, and references to the verification evidence used to establish the descriptor |
| Bench application inventory | Exact application identities and immutable source revisions included in the Bench runtime |
| Runtime components | Framework and other verified runtime components, with versions/identities supported by build evidence |
| Service topology | Product services, their roles, image/artifact identities where applicable, commands or declared execution contracts, dependencies, readiness/health semantics and service relationships |
| External requirements | External services/capabilities required by the product but not packaged as Bench applications or NDF-built services |
| Storage requirements | Logical persistent/transient storage needs, mount/volume intent, persistence and backup characteristics; no node-specific allocation |
| Networking requirements | Logical service exposure, internal communication and required ports/protocols; no allocated host ports or tenant-specific endpoints |
| Configuration contract | Non-secret configuration requirements, defaults where safe, and references to secret/configuration inputs without embedding their values |
| Provenance and verification | Exact evidence references, evidence digests, verification statuses and binding to the image digest |

The descriptor describes product-level requirements and immutable artifact facts. It must not contain deployment-instance state.

## 4. Environment-specific values and prohibited content

DT Master is responsible for binding the descriptor to a specific infrastructure node and deployment environment. Only explicitly allowlisted deployment parameters may be overridden, for example:

- replica counts and resource allocations;
- host-port and ingress bindings;
- concrete storage resource/volume bindings;
- secret references and external-service endpoint bindings.

Overrides must not silently change the product image, image digest, application composition, service command or other immutable product facts. Changes to those facts require a new candidate/build and descriptor.

The descriptor must not contain tenant credentials, database passwords, API secrets, customer data, site FQDNs, node-specific ports, TLS private keys, live tenant configuration or arbitrary shell commands. Secrets are represented only as references to an external secret-management mechanism.

## 5. Approved implementation sequence

The following seven steps are approved and must be executed in dependency order.

| Step | Work package | Scope | Deliverables |
|---|---|---|---|
| **M4.2.6.1** | Read-only consumer contract audit | Inspect the actual `dt_master@develop` consumer architecture and compare it with NDF's verified build, image and evidence outputs. Identify authoritative sources, gaps, ownership and future consumer expectations. No DT Master or DT Tenant code changes. | Field-source mapping; consumer contract audit; documented gaps and assumptions |
| **M4.2.6.2** | Descriptor schema and contract finalization | Define the versioned PDD schema, required/optional fields, semantics, identity, compatibility/versioning rules and validation constraints. | Versioned JSON Schema; field reference; compatibility and versioning policy |
| **M4.2.6.3** | Descriptor generator | Generate a deterministic descriptor from the actual verified image and its evidence. Use authoritative artifacts rather than re-resolving or guessing build state. | Generator; deterministic output; positive and negative generator tests |
| **M4.2.6.4** | Independent descriptor validator | Validate schema, internal consistency, completeness, references and invariants independently of the generator. Fail closed on malformed or contradictory descriptors. | Independent validator; validation report/schema as appropriate; adversarial tests |
| **M4.2.6.5** | Image and evidence binding | Bind the descriptor to the exact OCI image digest, composition lock and M4.2.5 verification evidence. Ensure all referenced identities and digests agree. | Digest/evidence binding checks; integrity tests; tamper/mismatch fixtures |
| **M4.2.6.6** | Publication and consumption contract | Define immutable descriptor publication, stable retrieval/reference semantics and the contract DT Master will use to retrieve and verify it. Do not implement the later candidate workflow. | Publication layout/reference contract; retrieval and verification expectations; consumer handoff documentation |
| **M4.2.6.7** | Acceptance testing and documentation | Run full regression and descriptor-specific tests, exercise representative product descriptors and adversarial cases, and synchronize milestone documentation. | Acceptance fixtures; regression results; updated plan, tracker and M4.2.6 documentation |

## 6. Acceptance criteria

M4.2.6 is complete only when all criteria below have recorded evidence:

1. The descriptor schema is versioned, documented and authoritative in NDF.
2. The descriptor describes the complete deployable product runtime, including the distinction between Bench applications, runtime services and external requirements.
3. Descriptor data is derived from authoritative build and verification evidence; unsupported claims are rejected or omitted.
4. Generation is deterministic for identical authoritative inputs.
5. An independent validator checks schema and cross-field consistency and fails closed on invalid or contradictory input.
6. The descriptor is bound to the exact OCI image digest and the corresponding composition lock and M4.2.5 verification evidence.
7. Tampered evidence, mismatched digests, missing required data, invalid references and unsupported schema versions are rejected.
8. Published descriptor identity and content are immutable; a changed deployable composition requires a new descriptor.
9. The contract distinguishes immutable product facts from explicitly allowlisted environment-specific overrides.
10. No secret values, tenant-specific deployment state or arbitrary executable commands are embedded in the descriptor.
11. Representative product fixtures and regression tests pass, and documentation matches the implemented contract.
12. DT Master consumption expectations are documented against `dt_master@develop`, without implementing the consumer in this package.

## 7. Explicit exclusions

The following remain outside M4.2.6:

- Deployment Candidate and candidate-driven workflow orchestration (M4.2.7);
- artifact signing, attestations and trust-policy enforcement (M4.2.8);
- end-to-end M4 integration acceptance beyond the descriptor boundary (M4.2.9);
- DT Master implementation, Bench Environment/Deployment Candidate DocType implementation and runtime orchestration (M4.3 and later);
- DT Tenant implementation changes;
- official GHCR product promotion. M4.2.5's staging gate is accepted, while its live official-promotion evidence remains deferred pending explicit release authorization.

M4.2.6 may define the descriptor's provenance/evidence references so that M4.2.8 can add signing and attestations later, but it must not implement signing.

| M4.2.6.2 — Schema and contract | 0.5–1 day |
| M4.2.6.3 — Generator | 1–1.5 days |

Any such gap will be recorded during M4.2.6.1 before implementation scope is expanded.

## 9. Exit and handoff

At completion, NDF must provide DT Master with:

- the authoritative versioned descriptor schema and field semantics;
- deterministic descriptor generation from verified image inputs;
- independent descriptor validation and machine-readable failure behavior;
- exact digest and evidence binding;
- immutable publication and retrieval/reference semantics;
- representative accepted descriptors and adversarial test evidence.

M4.2.7 may then integrate descriptor production into candidate-driven workflows. M4.2.8 may add signing and attestations. M4.2.9 consolidates integration documentation and end-to-end acceptance. M4.3 remains downstream of the approved M4.2 work packages.
