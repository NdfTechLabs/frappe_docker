# M4.2.8.4.5.1 — Independent PDD Consumer Verification Contract

**Repository:** `NdfTechLabs/frappe_docker`  
**Implementation branch:** `feat/M4.2.8.4.5-independent-consumer-verification`  
**Base:** `main` at `a042e49b27dc13cfc45023d29acc52a80204588f`  
**Status:** Accepted implementation baseline; implementation not yet accepted  
**Date:** 16 November 2026

## 1. Objective

Extend the existing PDD retrieval path so a consumer independently verifies the PDD OCI signature, PDD-to-image binding attestation, and source-image SLSA provenance before it can report a trusted result.

The consumer must use only the publication receipt and immutable OCI references. It must not consume the producer's trust-verification result, trust-evidence manifest, signing-input artifact, locally generated expected predicate, or any other producer-side verification output as proof of trust.

Existing descriptor validation, registry-manifest validation, exact evidence inventory, evidence-byte hashes, build sidecars, and image/PDD binding checks remain mandatory.

## 2. Existing consumer gap

The current `images/ndf/scripts/fetch_product_deployment_descriptor.py`:

- validates the publication receipt;
- resolves the PDD by immutable `repository@sha256:digest`;
- checks the registry manifest, artifact type and annotations;
- downloads the PDD and evidence bundle;
- validates descriptor identity/content hash and evidence inventory;
- re-runs PDD/image evidence binding verification.

It does not currently verify the PDD Cosign signature or PDD binding attestation, and it does not retrieve the source-image SLSA attestation from the immutable image digest. Its current `verified` status therefore means descriptor/evidence binding only and must not be treated as cryptographic artifact trust.

## 3. Independent verification sequence

The consumer must perform the following sequence, failing closed on every missing, malformed, ambiguous, mismatched, or unverifiable input.

### 3.1 Publication receipt and immutable PDD

1. Validate the publication workflow run is completed successfully, is the exact PDD publication workflow, and ran from `main`.
2. Validate the exact receipt artifact belongs to that run and attempt.
3. Validate the receipt schema and internal immutable reference:
   `repository@sha256:<digest>`.
4. Resolve and fetch the PDD OCI artifact by that immutable digest, never by its locator tag.
5. Verify the fetched registry manifest digest, artifact type, required media type, annotations, and receipt binding.
6. Retain all existing descriptor, evidence inventory, evidence hash, and image binding checks.

### 3.2 PDD signature and PDD binding attestation

1. Use the pinned Cosign `v3.1.4` toolchain.
2. Verify the signature for the exact PDD immutable reference.
3. Verify the PDD binding attestation for the same immutable reference and exact predicate type:
   `https://ndftechlabs.com/attestations/pdd-image-binding/v1`.
4. Require exact certificate identity:
   `https://github.com/NdfTechLabs/frappe_docker/.github/workflows/ndf-publish-product-deployment-descriptor.yml@refs/heads/main`.
5. Require OIDC issuer `https://token.actions.githubusercontent.com`, event `workflow_dispatch`, repository `NdfTechLabs/frappe_docker`, ref `refs/heads/main`, and the exact source SHA derived from the verified Statement.
6. Use normal Sigstore trusted-root and Rekor verification. Do not add `--insecure-ignore-tlog`, disable claim checks, or accept a caller-supplied identity.
7. Require exactly one verified binding Statement, with its subject repository and digest equal to the PDD OCI artifact.
8. Validate the complete Cosign Statement v0.1 compatibility profile observed with Cosign v3.1.4. Normalize only the envelope `_type` for semantic comparison with the NDF Statement v1 contract; preserve and validate every other field. Reject unknown fields and ambiguous/multiple statements.
9. Validate the complete PDD binding predicate against the PDD schema and receipt: descriptor ID, canonical PDD content hash, PDD repository/digest, image repository/digest/platform, lock hash, source provenance predicate type/hash, and originating workflow claims.

### 3.3 Source-image SLSA attestation

1. Derive the image reference only from the validated PDD binding predicate:
   `subject_image.repository@subject_image.digest`.
2. Verify the image signature and SLSA attestation from the registry using Cosign `v3.1.4`; do not consume a local predicate file or source-build artifact.
3. Require exact product-image identity:
   `https://github.com/NdfTechLabs/frappe_docker/.github/workflows/ndf-publish-product.yml@refs/heads/main`.
4. Require the same exact OIDC issuer, workflow trigger, repository and ref constraints, and bind the certificate to the source SHA extracted from the verified SLSA Statement.
5. Require the verified SLSA Statement subject repository and digest to match the immutable image reference.
6. Validate the complete NDF SLSA provenance Statement v0.1 compatibility profile and NDF image provenance schema, including product identity, platform, workflow claims, lock digest, composition and validation claims.
7. Compute SHA-256 over the verified predicate object serialized using NDF-JSON-CANONICAL-V1: sorted keys, compact separators, `ensure_ascii=False`, and one trailing LF.
8. Require the computed value to equal `predicate.source_provenance.predicate_sha256` in the verified PDD binding predicate.
9. Require source image repository, digest and platform to agree across the PDD descriptor, binding predicate and verified source provenance.

The consumer must not accept a publisher-supplied expected predicate as a substitute for retrieving and validating the signed source-image attestation.

### 3.4 Trust decision and consumer result

The shared identity policy currently has status `provisional_until_live_certificate_observation`. Therefore, successful cryptographic verification of both PDD and source-image artifacts must not be converted into a trusted decision.

The consumer must distinguish:

- **Verification execution:** all cryptographic and structural checks completed successfully.
- **Trust decision:** rejected while the applicable signer identity policy remains provisional.
- **Deployment authorization:** not granted by this work package.

The machine-readable consumer report must retain separate PDD and source-image trust results, including signature, signer, transparency, attestation subject, predicate hash, policy status, and reason codes. The top-level decision must be `rejected` with `IDENTITY_POLICY_PROVISIONAL` while policy remains provisional. It must never emit `status: verified` or `trusted: true` in that state.

Recommended CLI exit contract:

- `0`: every verification passed and the identity policy permits a trusted result.
- `2`: all cryptographic and structural checks passed, but the exact expected provisional identity-policy rejection applies.
- `1`: technical verification failure, invalid evidence, policy mismatch, missing evidence, or any unexpected decision.

The staging workflow may treat exit code 2 as an expected negative trust outcome solely to preserve and upload the complete consumer evidence. Its summary must say **REJECTED: IDENTITY_POLICY_PROVISIONAL**, not verified or trusted. Exit code 2 must never authorize a deployment or promotion. Unexpected trust decisions remain hard failures.

## 4. Workflow permissions and boundaries

The consumer fetch workflow remains read-only:

- `actions: read`
- `contents: read`
- `packages: read`

It must not request `id-token: write`, package write, contents write, actions write, or repository administration. It must not sign, attest, mutate registry artifacts, or change identity policy.

The workflow must retrieve the publication receipt from the exact publication run, but must independently retrieve PDD and image attestations from the OCI registry. Producer-side trust evidence artifacts may be retained for audit; they are not inputs to the consumer's trust decision.

The consumer report and retrieved PDD/evidence bundle should be uploaded as an attempt-scoped artifact with 90-day retention. Do not pass credentials, OIDC tokens, or secrets through outputs or artifacts.

## 5. Required implementation and tests

Expected implementation surface:

- `images/ndf/scripts/cosign_pdd_trust.py`: support self-contained verification from the verified registry Statement without a caller-supplied expected predicate; retain exact identity/SHA and v0.1 compatibility validation.
- `images/ndf/scripts/cosign_image_trust.py`: support self-contained source-image provenance verification from the verified registry Statement without a caller-supplied expected predicate; retain exact identity/SHA, schema and Rekor checks.
- `images/ndf/scripts/fetch_product_deployment_descriptor.py`: orchestrate receipt, PDD signature/attestation, source-image signature/attestation, predicate-hash comparison and existing PDD/evidence checks; produce a structured consumer trust report.
- `.github/workflows/ndf-fetch-product-deployment-descriptor.yml`: install pinned Cosign, invoke the independent consumer path, clearly distinguish expected provisional rejection from technical failure, and upload consumer evidence.
- Add a consumer report schema and focused tests. Extend workflow contract tests to enforce read-only permissions and absence of OIDC/signing steps.

Adversarial tests must cover at least:

- mutable/tag-only PDD and image references;
- wrong PDD digest, wrong image digest, wrong subject repository or platform;
- missing, duplicate, malformed or unexpected Statement fields;
- wrong PDD or image certificate identity, issuer, event, repository, ref or source SHA;
- failed signature verification or missing/invalid Rekor inclusion;
- wrong predicate type, predicate hash, lock hash or descriptor content hash;
- source provenance that is not retrieved from Cosign-verified registry output;
- v0.1 envelope normalization that changes fields other than `_type`;
- tampered PDD/evidence bytes, missing files, unexpected files and symlinks;
- provisional policy producing a rejected result and never a verified/trusted result;
- unexpected policy decisions and Cosign command failures failing closed.

## 7. Acceptance criteria

M4.2.8.4.5 is accepted only when:

1. The consumer verifies PDD signature and binding attestation independently by immutable digest.
2. The consumer verifies source-image signature and SLSA provenance independently by immutable image digest.
3. Exact signer identity, issuer, workflow, ref and source-SHA constraints are enforced for both artifacts.
4. Normal Rekor verification is required for both artifacts.
5. Statement v0.1 compatibility is explicit, schema-bound and tested without altering any semantic field.
6. The computed canonical source provenance predicate hash equals the PDD binding claim.
7. Existing PDD descriptor, registry and evidence binding checks remain intact.
8. The consumer uses no producer trust result, signing-input artifact, local expected predicate or OIDC signing permission.
9. Missing, tampered, ambiguous, mismatched or unavailable evidence fails closed.
10. Live staging publish/fetch round trip completes and produces independently reviewable consumer evidence.
11. The trust decision remains rejected while identity policy is provisional; no deployment authorization or production promotion is introduced.

## 8. Out of scope

- Confirming either signer identity policy.
- Production release, promotion or deployment authorization.
- Candidate image/PDD signing or candidate consumer integration.
- DT Master consumer implementation.
- Weakening existing source provenance, PDD evidence, registry digest, signer identity or Rekor checks.
