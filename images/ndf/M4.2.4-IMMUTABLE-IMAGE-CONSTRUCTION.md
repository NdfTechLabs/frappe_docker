# M4.2.4 — Immutable Image Construction

**Status:** In Progress — first successful product image build; build-evidence capture remains incomplete  
**Feature branch:** `feat/m4.2.4-immutable-image-construction`  
**Depends on:** M4.2.1–M4.2.3 (complete and merged)  
**Next package:** M4.2.5 — Image Verification

## 1. Objective

Construct a product image from the current approved manifests and requested rolling Git references, using upstream Bench for application acquisition and native dependency installation. Capture what Bench actually acquired and what the builder actually installed, use digest-pinned builder/runtime base images, and bind the build evidence to the produced image digest.

This package must restore working product-image builds without reviving the obsolete lock-v1 files or introducing a second dependency resolver/installer.

## 2. Accepted architectural invariants

1. **Manifests are the composition source of truth.** Every build generates a fresh lock-v2 composition from the current manifest tree. Existing checked-in `images/ndf/locks/*.lock.json` files are obsolete lock-v1 artifacts: they are not inputs, migration targets, or authority for a build.
2. **Requested refs remain rolling.** The generated lock records each requested `target_ref` and the resolver's resolution-time SHA/provenance. Bench still receives the requested branch/tag ref. The resolution-time SHA is not substituted for the requested ref and is not proof of the commit Bench acquired.
3. **Bench owns acquisition and installation.** Keep the existing `bench init --apps_path` path. Do not add another Git checkout, Python/Node/OS dependency resolver, or installer. Bench/native package managers perform dependency installation.
4. **Actual acquisition is observed after Bench.** Capture the Git HEAD and repository identity of Frappe and each installed application from the actual Bench workspace before the Containerfile removes `.git` metadata.
5. **Installed state is evidence, not a new lock resolver.** Capture post-install Python, Node and OS package inventories, dependency/lockfile identities and hashes, and the native installer/tool versions and selected installation path where observable. Do not infer package origin from a package list alone.
6. **Base inputs are immutable.** Resolve builder and runtime image references to approved platform-specific manifest digests, validate them against the accepted RT-01 base-inventory evidence, and pass digest references to BuildKit. Mutable tags must not be the effective `FROM` inputs.
7. **Image identity is digest-based.** Capture Buildx's produced image digest and bind build metadata/evidence to it. Do not claim an immutable artifact from a mutable tag alone.
8. **Keep package boundaries.** M4.2.4 captures build evidence and constructs the image. M4.2.5 independently verifies image contents and captured evidence. M4.2.6 defines the Product Deployment Descriptor and its publication contract.

## 3.1 Compatibility and production-reference disposition

The earlier preflight interpretation of the manifest compatibility values as unresolved technical incompatibilities was incorrect. The platform owner has confirmed that the currently declared applications are compatible with the Frappe v16 target and its underlying technology line. The old values were stale status metadata and are corrected in this branch.

- Selected application declarations now use `compatibility_status: "verified"`; descriptor-backed NDF ecommerce applications carry an explicit platform-owner attestation.
- The descriptor schema distinguishes a maintainer attestation from an executed automated/manual test. The attestation records the authority, reference, date and attesting role; it does not claim that M4.2.4 product image integration tests have already run.
- Strict fail-closed resolution remains unchanged. Missing, pending or incompatible status still fails resolution.
- Existing production source refs are retained exactly as declared, including `version-16`, `version-3`, `version-1`, `main` and `develop`. Branch names do not independently determine production eligibility; the resolver records requested refs and per-build commit provenance.
- No application branch is renamed, permanently SHA-pinned or rewritten to an invented v2 branch. Lock-v2 is the generated build-lock format; it does not require bulk conversion of the existing v1 composition manifests.
- Optional capabilities remain opt-in. `dt_delivery` remains excluded from remote production resolution while its source is local-only, regardless of its compatibility disposition.

The correction removes the stale compatibility gate as a blocker to fresh lock generation. It does not assert that product images have already built or that all application-level functional tests have run. M4.2.4 must still exercise the real Bench acquisition/build path and capture its evidence.

### Validator and evidence-contract gap assessment

The current `validate_image.py` is a basic composition/label validator, not the full independent image-evidence verifier described for M4.2.5.

It currently verifies:
- expected application directory names exist and no unexpected app directories are present;
- `sites/apps.txt` matches the application names in build metadata;
- selected OCI/NDF labels match build metadata; and
- exactly one lock manifest entry matches the product manifest path, with its checksum used for the manifest label.

It does **not** currently:
- recompute the lock file SHA-256 and compare it with `metadata.lock.sha256`;
- validate that the lock is version 2 and that its application composition agrees with build metadata;
- inspect actual Git HEADs or repository identities for Frappe and the installed applications;
- compare actual acquired commits with the lock's resolver-time provenance;
- capture or verify Python, Node, dpkg, dependency-file or installer evidence; or
- bind a captured build-inventory document to the produced image digest.

The current Containerfile runs `bench init --apps_path` and then removes application `.git` directories. No source-state capture is performed between those operations. The build metadata's `resolved_sha` values are resolver-time ref observations, not proof of the commits Bench actually acquired.

Buildx metadata records the build invocation, source revision and base-image materials. `build-result.json` records the produced image digest. Neither currently contains the missing post-Bench application and installed-state inventory.

**Disposition:** the first image-build and basic validation path is proven. M4.2.4 is not complete because its accepted post-Bench capture and evidence-transport requirements (§4.3–§4.4) remain unimplemented. Keep independent acceptance checks in M4.2.5; do not expand the M4.2.4 capture work into a second resolver or installer.

## 4. Implementation sequence

### 4.1 Fresh per-build lock-v2 generation

- Load and validate the selected image definition and current product manifest composition.
- Resolve current requested Git refs through the existing resolver and generate lock-v2 data.
- Validate the generated lock against current manifest checksums, source policy, target runtime and accepted base-inventory evidence.
- Write the lock atomically under the per-build output directory; do not read, overwrite or migrate the obsolete checked-in lock-v1 files.
- Generate Bench `apps.json` from the fresh lock using the requested refs, excluding Frappe because the Containerfile supplies it through `FRAPPE_PATH`/`FRAPPE_BRANCH`.
- Include the generated lock's path and SHA-256 in build metadata.

**Exit evidence:** deterministic unit tests for fresh generation, rolling refs, manifest changes, optional capability selection, invalid refs/policies, output isolation and lock-v2 validation. A build must not depend on the checked-in lock-v1 files.

### 4.2 Digest-pinned base and builder inputs

- Select the approved base-inventory record for the requested target runtime/platform.
- Validate its manifest, checksums, stage identities and builder/runtime image digests using the existing A.4 validator.
- Load and validate the accepted RT-01 inventory manifest and both checksum-bound stage inventories using the existing A.4 validator.
- Require the builder/runtime repository identities and platform to match the accepted record; use its platform-specific manifest digests, not the descriptive rolling tags or index digests, as the effective image references.
- Pass the builder and runtime digest references to the Containerfile/BuildKit as explicit, independent inputs. Keep `FRAPPE_BRANCH` exclusively for Bench's requested Frappe source ref.
- Fail closed when inventory evidence is missing/altered, either stage reference does not match its approved repository and digest, or the requested platform is unsupported.
- Keep the supported build platform at `linux/amd64`. The publish workflow no longer offers ARM64 until RT-02 supplies accepted ARM64 inventory evidence.

**Exit evidence:** tests proving both stages receive the exact accepted digest references and that missing, altered, tag-only and wrong-platform evidence is rejected.

### 4.3 Post-Bench build inventory capture

Capture from the actual Bench workspace after `bench init --apps_path` has completed and before source-control metadata is removed:

- Frappe and every installed app: canonical repository identity, requested ref, actual Git HEAD, and relevant checkout identity.
- Bench version and the actual Python installation path selected by Bench (`uv` or `pip`), with tool versions and Python runtime identity.
- Node/Yarn versions and the installed Node package inventory for apps that declare/install Node dependencies.
- Python installed distribution inventory.
- Debian/dpkg installed package inventory for the builder stage, plus runtime-stage inventory where required by the approved stage model.
- Dependency/lockfile names and SHA-256 hashes consumed by the native installation path.
- Capture timestamp and platform/build-stage identity, with deterministic inventory ordering and no credentials, tokens or ambient environment secrets.

Do not assume that `uv` is always selected: RT-01 established that Bench 5.31.1 selects `uv` when `use_uv()` is enabled and otherwise uses pip. Record the actual branch and version used for that build. Bench uses Yarn for an app with a root `package.json`.

**Exit evidence:** isolated tests using local Git repositories and synthetic inventories; fail-closed tests for missing repositories/HEADs, malformed inventory, path escape, nondeterministic ordering, secret leakage and hash mismatch.

### 4.4 Evidence transport and digest binding

- Define one versioned build-inventory document with explicit schema and stable application/package ordering.
- Make the captured inventory available to the resulting image/build evidence without retaining application `.git` directories in the final runtime image.
- Record the generated lock digest, manifest/source checksums, base/builder digests, actual acquired Git HEADs, dependency-file hashes, installed inventory hashes, installer evidence, Buildx metadata and produced image digest in the build result.
- Keep evidence generation separate from independent image acceptance checks, which belong to M4.2.5.
- Avoid embedding secrets, raw credential-bearing URLs or unnecessary environment data.

**Exit evidence:** deterministic schema/serialization tests and an integration test proving that the produced digest is linked to the exact generated lock and captured inventory.

### 4.5 Product build workflow and regression acceptance

- Restore build-input validation against freshly generated lock-v2 data, not checked-in lock-v1 files.
- Make the NDF product workflow invoke the same fresh-generation/build path as local builds.
- Build and inspect the supported AMD64 product images in CI; preserve build inventory, build metadata and validation inputs as artifacts.
- Retain explicit local-vs-publish separation. M4.2.4 does not silently turn CI validation into a GHCR release.
- Run focused tests, the full NDF suite, compile checks, all pre-commit hooks, and the product image build matrix.

**Exit evidence:** all supported product builds reach and complete Buildx; generated evidence is present and digest-bound; no lock-v1 input is read; full regression and lint pass.

## 5. Explicit exclusions

- No v1-to-v2 lock migration and no checked-in lock-v1 regeneration.
- No permanent pinning of rolling product application branches to commit SHAs.
- No second checkout or custom Python/Node/OS resolver/installer.
- No independent installed-state acceptance implementation from M4.2.5.
- No Product Deployment Descriptor or publication mechanism from M4.2.6.
- No candidate-driven workflow contract from M4.2.7.
- No signing/attestation implementation from M4.2.8.
- No ARM64 acceptance without corresponding approved target-runtime/base-inventory evidence.
- No production GHCR release as a side effect of pull-request validation.
