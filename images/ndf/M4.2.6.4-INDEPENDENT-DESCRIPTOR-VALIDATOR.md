# M4.2.6.4 — Independent Product Deployment Descriptor Validator

**Status:** Implementation in progress; user-run validation pending  
**Owner:** NDF Frappe Docker  
**Input contract:** \`schemas/product-deployment-descriptor-v1.schema.json\`  
**Implementation:** \`scripts/validate_product_deployment_descriptor.py\`  
**Tests:** \`tests/test_validate_product_deployment_descriptor.py\`

## 1. Purpose

Provide an independent validation path for a serialized Product Deployment Descriptor (PDD). The validator must be able to reject a malformed or internally contradictory descriptor without importing, invoking or trusting the generator that produced it.

The authoritative PDD v1 JSON Schema remains the structural contract. The validator adds checks that JSON Schema alone cannot express: deterministic identity derivation, canonical content integrity, evidence-reference consistency, composition cross-field consistency and dependency-graph validity.

A successful result means that the descriptor passes this contract validator. It is not a registry availability check, deployment approval, artifact signature verification or proof that referenced evidence files still exist.

## 2. Independence boundary

- The validator is a separate executable Python module.
- It does not import the PDD generator, the evidence binder or generator-private helpers.
- It loads the authoritative PDD v1 schema from \`images/ndf/schemas/\`.
- It independently implements \`NDF-JSON-CANONICAL-V1\` for integrity verification.
- It accepts a serialized descriptor path and returns a structured JSON result with a process exit status.
- It performs no writes to the descriptor and does not modify build or publication artifacts.

This separation prevents a generator defect from automatically being repeated by the validator's implementation path.

## 3. Validation sequence

The validator applies checks in this order:

1. **Strict JSON parsing**
   - UTF-8 JSON object required.
   - Duplicate object keys are rejected instead of silently accepting the last value.
   - Non-finite JSON constants are rejected.
2. **Authoritative schema**
   - Validate against the checked-in Draft 2020-12 PDD schema.
   - Apply JSON Schema format checks.
   - Reject unsupported schema versions and unknown fields as defined by the schema.
3. **Content integrity**
   - Recompute SHA-256 using \`NDF-JSON-CANONICAL-V1\`.
   - Exclude only \`integrity.content_sha256\` from the canonical digest input.
   - Reject floating-point values and digest mismatches.
4. **Descriptor and artifact identity**
   - Recompute \`descriptor_id\` from product ID, platform and exact OCI digest.
   - When \`artifact.immutable_reference\` is present, require it to equal \`repository@digest\`.
5. **Evidence-reference inventory**
   - Require the exact eleven logical M4.2.5 evidence names.
   - Reject duplicate names, duplicate paths, unsafe relative paths and missing/extra entries.
   - Cross-check build metadata, lock-v2, composition-verification and runtime-inventory references against the corresponding PDD evidence records.
   - When a requirement-verification reference points to one of the eleven PDD evidence records, require its hash to match. Other declaration-owned evidence references remain opaque references for the later publication/consumption contract.
6. **Composition and requirement consistency**
   - Require unique Bench application identities and paired application descriptor path/hash fields.
   - Require runtime framework identity to match its Bench application record.
   - Require artifact platform to match measured runtime platform.
   - Reject service/external-requirement identity collisions, including collisions with Bench application names.
   - Require every declared service dependency to resolve and reject self-dependencies and cycles.
   - Require service requirement declarations and state to agree with the composition inventory.

## 4. Validation report

The CLI emits one JSON object to standard output.

Successful validation returns:

- \`status: passed\`;
- PDD schema version and descriptor ID;
- immutable image digest and content SHA-256;
- evidence-record count;
- the names of the completed validation groups.

Failure returns \`status: failed\` and a concise error string, and exits with status code \`1\`. Success exits with status code \`0\`. This report is a validation result, not a new signed attestation.

Example invocation:

\`\`\`bash
python images/ndf/scripts/validate_product_deployment_descriptor.py \\
  --descriptor /path/to/product-deployment.json
\`\`\`

An alternate schema path may be supplied with \`--schema\` for controlled tests. Production validation must use the repository's authoritative schema.

## 5. Scope boundary with M4.2.6.5

M4.2.6.4 validates the descriptor's internal evidence inventory and cross-field hash references. When a requirement-verification reference targets one of the eleven PDD evidence records, its declared hash must agree. Other requirement-evidence references are retained as opaque external references; their retrieval/binding semantics are a publication/consumption concern. The validator does **not** reopen the eleven referenced files and recompute their byte hashes or sizes, inspect an OCI registry, pull an image, or re-run the M4.2.5 verifiers.

M4.2.6.5 owns the byte-level binding exercise: descriptor evidence entries must be checked against the actual evidence files, the lock-v2 bytes and the exact OCI image digest. Keeping those operations separate prevents the independent contract validator from becoming a second image/evidence acquisition pipeline.

Signing, attestations and trust policy remain M4.2.8. Candidate workflow integration remains M4.2.7. DT Master consumption and orchestration remain outside M4.2.6.

## 6. Adversarial test coverage

The validator test suite exercises:

- acceptance of a generator-produced valid descriptor through the independent validation path;
- descriptor tampering and content-hash mismatch;
- descriptor ID and immutable-reference mismatch;
- duplicate and unsafe evidence references;
- build metadata and lock-v2 hash-reference mismatch;
- framework/application and artifact/runtime platform mismatch;
- inconsistent service requirement state;
- unresolved service dependencies and dependency cycles;
- schema-invalid descriptors;
- floating-point values prohibited by the canonicalization profile;
- duplicate JSON object keys;
- absence of generator and evidence-binder imports from the validator.

Implementation remains pending user-run focused and full NDF regression tests. No acceptance claim is made until those results are reviewed.
