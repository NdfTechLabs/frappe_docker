# M4.2.8.2.2 — Artifact Trust Signer Identity Policy

**Repository:** `NdfTechLabs/frappe_docker`
**Branch:** `feat/M4.2.8`
**Status:** Provisional policy; live certificate identity confirmation required
**Scope:** M4.2.8.2.2

## 1. Purpose

Define which GitHub Actions identities may sign NDF product images, candidate images and PDD OCI artifacts. This policy is consumed by the trust verifier; it does not itself perform verification or change workflows.

## 2. Fixed trust anchors

- OIDC issuer: `https://token.actions.githubusercontent.com`
- Repository: `NdfTechLabs/frappe_docker`
- Ref: `refs/heads/main`
- Event: `workflow_dispatch`
- Certificate identity matching: exact string equality only.
- Identity regular expressions and wildcard fallbacks: prohibited.
- Rekor inclusion proof: required; absence or failed verification rejects the artifact.

Cosign keyless verification requires an expected certificate identity and OIDC issuer. GitHub workflow identity URIs follow the form `https://github.com/ORG/REPO/.github/workflows/WORKFLOW.yml@refs/heads/BRANCH`. See the [Sigstore verification guidance](https://docs.sigstore.dev/quickstart/verification-cheat-sheet/) and [GitHub OIDC claim reference](https://docs.github.com/en/actions/reference/security/oidc).

## 3. Authorized workflow identities

The machine-readable allowlist is:

`images/ndf/policies/artifact-trust-identity-policy-v1.json`

It contains four trust purposes:

| Purpose         | Caller workflow identity                                        | Called workflow constraint                         |
| --------------- | --------------------------------------------------------------- | -------------------------------------------------- |
| Product image   | `ndf-publish-product.yml@refs/heads/main`                       | None; direct workflow                              |
| Product PDD     | `ndf-publish-product-deployment-descriptor.yml@refs/heads/main` | None; direct workflow                              |
| Candidate image | `ndf-build-candidate.yml@refs/heads/main`                       | `ndf-reusable-build-candidate.yml@refs/heads/main` |
| Candidate PDD   | `ndf-build-candidate.yml@refs/heads/main`                       | `ndf-reusable-pdd-candidate.yml@refs/heads/main`   |

The full certificate identity strings are recorded in the JSON policy.

## 4. Reusable workflow identity

GitHub OIDC distinguishes the calling workflow from the called reusable workflow. The caller is represented by `workflow_ref`; a reusable-workflow job additionally exposes `job_workflow_ref` and `job_workflow_sha`.

For candidate signing, verification must require both:

1. The exact certificate identity and caller workflow ref for `ndf-build-candidate.yml`.
2. The exact called workflow ref configured for the trust purpose being verified.

The candidate image signing job must match `ndf-reusable-build-candidate.yml`; the candidate PDD signing job must match `ndf-reusable-pdd-candidate.yml`. The called-workflow commit SHA must be captured and checked against the workflow revision used by the run. It must not be inferred from a branch name alone.

See [GitHub's reusable-workflow OIDC documentation](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-with-reusable-workflows).

## 5. Provisional status and runtime confirmation

The workflow URI identities above are exact expected values derived from the repository's current workflow paths. They are **not yet production-confirmed**.

Before this policy is treated as final, M4.2.8.3–.5 must perform a real keyless signing run and inspect the resulting Fulcio certificate and available certificate extensions. Confirm:

- Exact certificate identity string.
- Exact OIDC issuer.
- Caller workflow identity and ref.
- For reusable jobs, called workflow identity and commit SHA.
- Event name and repository/ref claims.
- Rekor inclusion proof.

If the observed identity differs, update the policy based on captured evidence. Do not broaden it with a wildcard or regex to make verification pass.

## 6. Existing authorization remains authoritative

For candidate builds, this signer policy supplements but does not replace the existing candidate dispatch gate. The configured DT Master GitHub App actor, main-ref restriction, candidate intake validation and correlation checks remain mandatory.

A signature proves that an approved workflow identity signed an artifact. It does not prove that the candidate was authorized by DT Master unless the existing candidate authorization evidence also passes.

## 7. Acceptance criteria

- Policy JSON parses and is schema-validated.
- Duplicate trust-purpose IDs and duplicate certificate identities are rejected unless a documented artifact-purpose distinction requires the same caller identity (candidate image/PDD).
- Issuer, repository, ref, event and certificate identity comparisons are exact.
- Missing required claims fail closed.
- Reusable workflow jobs require exact caller and called-workflow checks.
- Unconfigured or unobserved identities cannot be treated as production-confirmed.
- No workflow behavior changes are included in this substep.
