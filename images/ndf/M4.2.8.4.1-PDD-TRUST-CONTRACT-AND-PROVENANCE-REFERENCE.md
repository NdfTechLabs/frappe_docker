# M4.2.8.4.1 — PDD Trust Contract and Provenance Reference Semantics

**Repository:** `NdfTechLabs/frappe_docker`
**Branch:** `feat/M4.2.8`
**Status:** Contract and baseline audit complete; implementation decisions accepted for .4.2–.4.5
**Date:** 16 November 2026
**Depends on:** M4.2.8.1 artifact trust contract; M4.2.8.2 trust schemas and validators; M4.2.8.3.5 live product-image Cosign interoperability

## 1. Purpose

Finalize the PDD publication, source-image provenance, PDD binding attestation and consumer verification contract before executable workflow integration.

This step resolves the meaning and retrieval of `source_provenance.predicate_sha256`, records the current publication/consumer handoff, and defines the exact trust checks required on both sides.

## 2. Decision: source provenance hash semantics

The PDD binding predicate uses:

```json
"source_provenance": {
  "predicate_type": "https://slsa.dev/provenance/v1",
  "predicate_sha256": "<64 lowercase hexadecimal characters>"
}
```

**Definition:** `predicate_sha256` is the SHA-256 digest of the UTF-8 bytes of the verified SLSA Provenance v1 `predicate` JSON object, serialized using the existing NDF canonical JSON representation used by `cosign_image_trust.py`:

- JSON object keys sorted lexicographically;
- compact separators `,` and `:`;
- `ensure_ascii=False`;
- one trailing LF byte;
- UTF-8 encoding.

Equivalently:

`SHA256((json.dumps(predicate, sort_keys=True, separators=(",", ":"), ensure_ascii=False) + "\n").encode("utf-8"))`

The producer and consumer must use the same canonicalization implementation or byte-for-byte equivalent tested code.

### 2.1 What this hash does and does not identify

It hashes **only the verified SLSA predicate object**. It does not hash:

- the in-toto Statement wrapper (`_type`, `subject`, `predicateType`);
- the DSSE envelope or base64 payload representation;
- the Sigstore bundle or certificate;
- the Rekor entry, inclusion proof or transparency log index;
- the JSON output framing emitted by the Cosign CLI;
- a local evidence file's incidental indentation or key order.

This is intentional. Cosign v3.1.4 emits an in-toto Statement v0.1 wrapper for the generic explicit SLSA predicate URI, while NDF's canonical producer contract remains Statement v1. Hashing the predicate object makes the binding independent of this outer wrapper version while still binding every SLSA/NDF predicate claim.

The field was previously named `attestation_sha256`. That name incorrectly implied a digest of the complete signed attestation. It is renamed to `predicate_sha256` in the not-yet-live PDD binding schema before the contract is consumed. No deployed PDD binding v1 artifact is being migrated by this change.

## 3. Source image provenance retrieval and independent verification

The source provenance is not retrieved from the PDD publication receipt, nor is a local build-evidence file treated as proof of a signed attestation.

The consumer derives the immutable source image reference from the validated PDD:

`<PDD artifact.repository>@<PDD artifact.digest>`

The source image attestation is retrieved from the OCI registry/Sigstore using Cosign's verification operation against that immutable image digest. The verifier must:

1. Require a fully qualified immutable `repository@sha256:<digest>` reference. Mutable tags are not accepted.
2. Run Cosign v3.1.4 `verify` for the image signature and `verify-attestation --type https://slsa.dev/provenance/v1` for the attestation.
3. Use the exact `product-image-publication` identity policy: certificate identity, OIDC issuer, event, repository, ref and source commit constraints; no wildcard/regex fallback.
4. Keep normal Sigstore trusted-root and Rekor inclusion verification enabled.
5. Extract exactly one verified in-toto Statement from Cosign's verified output.
6. Accept the strict Cosign v0.1 wrapper profile established by M4.2.8.3.5, while validating the complete SLSA predicate against the canonical NDF image-provenance schema without rewriting the verified payload.
7. Require the statement subject repository and digest to equal the PDD's immutable source image reference.
8. Require predicate type `https://slsa.dev/provenance/v1` and validate the NDF build metadata, including workflow source commit and image/lock/composition claims.
9. Compute `predicate_sha256` from the verified predicate object using NDF-JSON-CANONICAL-V1.
10. Compare the computed value with `source_provenance.predicate_sha256` in the PDD binding statement.

The source-image trust check must be independently performed by the PDD consumer. A publication receipt, build artifact, unverified local provenance file or PDD binding statement cannot substitute for Cosign verification.

### 3.1 Expected predicate file is not required for the consumer

The existing product-image publication verifier requires the original generated predicate file and compares it exactly with the verified Cosign predicate. That remains mandatory in the producer's own publication/staging workflow.

A consumer does not possess the producer's private job workspace and must not trust a copy of the expected predicate supplied alongside the PDD. The consumer path therefore needs a distinct self-contained verification mode (implemented in .4.3/.4.5) that:

- obtains the predicate only from successful Cosign verification;
- validates the complete predicate schema and exact subject;
- validates the signer and transparency evidence;
- computes the canonical predicate hash itself;
- does not accept caller-supplied expected predicate content.

Do not weaken or remove the existing producer-side exact expected-predicate comparison to implement consumer verification. Keep producer and consumer modes explicit and separately tested.

## 4. PDD publication and evidence handoff

Current baseline on `feat/M4.2.8` (fast-forwarded to the merged `main` baseline before implementation):

- `.github/workflows/ndf-publish-product-deployment-descriptor.yml` is `workflow_dispatch`-only, restricted to `refs/heads/main`, validates source build and binding-verification run ownership, downloads the exact artifacts, and invokes the PDD publisher.
- `publish_product_deployment_descriptor.py` publishes the validated PDD/evidence bundle using ORAS, resolves and re-fetches the exact immutable OCI manifest digest, and writes a publication receipt containing the immutable reference.
- `ndf-publish-product-deployment-descriptor.yml` currently has a single `publish` job with `actions: read`, `contents: read`, `packages: write`. It does not currently request OIDC.
- `ndf-fetch-product-deployment-descriptor.yml` is read-only for packages and retrieves the receipt by publication run/artifact name.
- `fetch_product_deployment_descriptor.py` checks the receipt schema, immutable OCI digest, manifest digest, artifact type/annotations, PDD content hash and evidence inventory, then re-runs the existing image/evidence binding verification.
- The current consumer does not yet perform Cosign verification for either the PDD artifact or source image provenance.

### 4.1 Publication-to-signing handoff

The publication workflow must preserve the existing source-run and artifact ownership checks. After ORAS publication, the publisher must expose the immutable PDD reference and receipt as a run/attempt-scoped artifact for a separate signing job.

The signing job must consume only the publication job's matching output/artifact and independently validate:

- publication run ID and attempt;
- exact PDD publication workflow path, repository, main ref and workflow source SHA;
- PDD OCI repository and immutable digest;
- registry manifest digest equals the publication receipt digest;
- descriptor ID/content hash and image repository/digest/platform;
- existing PDD/evidence binding report and source image identity.

Only the signing job receives `id-token: write` and the minimum GHCR package-write permission required by Cosign. The publication job may retain the minimum ORAS package-write permission it needs, but it does not receive OIDC. The consumer remains package-read-only and never receives OIDC or package-write permission.

The publisher must not accept a caller-provided digest as authoritative. It derives the digest from ORAS publication/manifest inspection as it does today.

## 5. PDD binding statement contract

The PDD binding Statement v1 subject is exactly one subject:

- `name`: PDD OCI repository;
- `digest.sha256`: exact PDD OCI manifest digest.

The predicate binds:

- descriptor ID and canonical PDD content SHA-256;
- subject image repository, immutable image digest and platform;
- exact lock-v2 SHA-256;
- source provenance predicate type and canonical predicate SHA-256;
- PDD publication workflow repository/path/ref/run ID/run attempt/source commit.

The statement must be deterministically generated from the validated PDD, immutable publication receipt, independently verified source image provenance and actual workflow context. It must reject any disagreement across those sources. It must not infer run IDs, source commits, image references or hashes from tags or user inputs.

The schema now names the source field `predicate_sha256`; the old `attestation_sha256` name is rejected.

## 6. Consumer verification order and result semantics

The consumer must perform the following checks before it can report the PDD as verified:

1. Validate publication run and receipt ownership.
2. Fetch the PDD OCI artifact by its immutable digest and verify the registry manifest digest.
3. Verify the PDD artifact signature with Cosign under the exact `product-pdd-publication` identity, issuer and workflow constraints, with Rekor verification enabled.
4. Verify the PDD-image-binding attestation against that same PDD digest; validate the complete Statement v1 schema and exact predicate claims.
5. Retrieve and independently verify the source image signature and SLSA provenance attestation by the PDD's immutable image digest.
6. Compute the source predicate hash from the verified predicate and compare it with the PDD binding claim.
7. Validate PDD canonical content hash, descriptor identity, evidence file inventory and all existing evidence hashes.
8. Re-run the existing PDD/image evidence binding verifier and compare its result with the published binding report.
9. Emit a normalized result that separately records signature, signer, transparency, PDD binding attestation, source image provenance and evidence-binding outcomes.

Any missing, ambiguous, malformed, mismatched, expired/unavailable or unverifiable trust evidence fails closed.

A cryptographically successful Cosign operation is not by itself an authorization decision. While either relevant signer identity policy entry remains provisional, the normalized decision must remain `rejected` with the corresponding provisional-policy reason. It must not be reported as authorized/trusted, and it must not authorize production promotion. This PDD work package does not confirm either policy entry.

## 7. Explicit non-goals

- Hashing or pinning the DSSE envelope, Sigstore bundle or Rekor entry in the PDD binding predicate.
- Treating a local provenance JSON file or publication receipt as cryptographic proof.
- Requiring the consumer to download the original build job's expected predicate artifact.
- Weakening the producer's exact expected-predicate comparison.
- Changing the canonical NDF image provenance Statement v1 contract.
- Confirming product-image or PDD signer identity policy.
- Enabling official product promotion.
- Candidate image/PDD signing or DT Master consumer integration.

## 8. Acceptance criteria

M4.2.8.4.1 is accepted when:

1. `predicate_sha256` is defined exactly as SHA-256 of the NDF-JSON-CANONICAL-V1 UTF-8 serialization of the verified SLSA predicate object, including one trailing LF.
2. The schema rejects the ambiguous legacy `attestation_sha256` field and requires `predicate_sha256`.
3. The source provenance is retrieved by immutable image digest and independently verified with Cosign, exact signer constraints and Rekor.
4. Producer verification continues to require exact comparison with its original expected predicate; consumer verification uses a distinct self-contained path and never trusts a supplied expected predicate.
5. The PDD publisher-to-signer handoff and least-privilege job permissions are specified.
6. Consumer verification order and provisional-policy result semantics are explicit.
7. Schema and focused regression tests pass.
