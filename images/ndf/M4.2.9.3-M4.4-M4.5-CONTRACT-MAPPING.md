## 1. Purpose and ownership

This document maps the accepted M4.1 producer/consumer contracts to the current NDF artifacts and the inspected DT Master/DT Tenant source state. It is a read-only interoperability review. It does not implement M4.4 or M4.5, modify either consumer repository, or authorize deployment.

- **NDF owns:** Marketplace App Descriptor technical content, product composition, immutable image construction, Product Deployment Descriptor generation/publication, build evidence, NDF-side candidate validation and build result artifacts.
- **DT Master owns:** candidate lifecycle and serialization, app identity registration/governance, build/deployment records, producer signing identity, infrastructure/Bench orchestration, deployment eligibility and runtime application lifecycle.
- **DT Tenant owns:** tenant-facing marketplace and lifecycle requests; it calls DT Master and does not directly orchestrate Docker, Bench composition or NDF builds.

The NDF schemas are consumer-validation contracts. They do not replace DT Master DocTypes or its durable lifecycle records.

**Disposition:** The NDF candidate schema is broadly aligned with the M4.1 semantic input. DT Master must validate its actual serializer output against the exact NDF schema before production dispatch. The serializer and producer are not present in the inspected DT Master tree.

### 2.2 OCI package transport adoption

The NDF-side proposal specifies a private GHCR candidate package, ORAS-compatible single-file OCI artifact, exact manifest/layer media types, filename annotation, manifest annotations and digest/payload-byte verification.

M4.1 requires an immutable candidate OCI reference/digest and signed origin evidence, but does not prescribe GHCR, ORAS or the exact manifest layout. The GHCR/ORAS envelope is therefore an **NDF working proposal pending explicit DT Master adoption**, not a completed cross-repository contract.

Before M4.4 dispatch is enabled, both owners must agree:

1. Registry/package ownership and package visibility.
2. Manifest artifact type, config descriptor, layer count/name/media type and annotations.
3. Exact payload-byte SHA-256 and manifest-digest semantics.
4. Package permissions: Master publishes with its own token; NDF reads with its own token; the dispatch App token has Actions scope only.
5. Retention/deletion rules for candidate artifacts referenced by durable Master records.

### 2.3 Candidate-origin trust

M4.1 requires DT Master to sign the exact candidate OCI manifest digest and attest the candidate ID, payload hash, producer repository/workflow/ref/source commit, run/attempt and correlation ID. NDF independently verifies issuer, exact certificate identity, Rekor evidence, statement subject, predicate schema and exact payload bytes before intake/adaptation.

NDF implements the verifier and fail-closed workflow gate. The checked-in DT Master identity policy remains `provisional_until_live_certificate_observation`. The actual producer workflow, certificate identity and OIDC claims must be observed from a genuine M4.4 run and separately reviewed. Until then:

- no live candidate dispatch is accepted as a successful producer integration;
- no wildcard or inferred certificate identity is allowed;
- the provisional policy must continue to reject before candidate intake/adaptation;
- no developer identity may substitute for the configured DT Master GitHub App actor.

## 3. M4.4 — PDD consumer mapping

### 3.1 Image and build identity

The NDF PDD v1 schema provides:

- product identity and an optional publisher-declared release;
- OCI repository, immutable digest and platform;
- NDF build repository/commit/workflow run/time;
- lock-v2 identity, app/service/external composition and composition-verification evidence;
- runtime inventory with an explicit `builder_stage` scope;
- typed requirement domains and the eleven-file M4.2.5 evidence set;
- canonical descriptor integrity hash.

DT Master must verify PDD schema/version, artifact digest, subject image digest, content hash, evidence references and image/PDD signatures/attestations before deployment eligibility. A structurally valid PDD is not a deployment authorization.

### 3.2 Material gaps against M4.1 §16.5

| M4.1 consumer expectation                                            | Current NDF PDD v1 state                                                                                                | Required disposition                                                                                                                                                                               |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Per-app `app_id`, release and immutable descriptor digest            | Application entries require `app_name`, repository, requested ref and actual commit; descriptor path/hash are optional. | Do not infer app_id/release from Git tags or mutable refs. Define an immutable descriptor reference and explicit mapping for descriptor-backed apps. Legacy apps without descriptors remain a gap. |
| Exact final runtime versions                                         | PDD labels current inventory as `builder_stage`; final runtime package inventory is not independently claimed.          | Consumer must not treat builder-stage packages/tools as final runtime facts. Either add final-runtime evidence or keep this requirement explicitly unverified.                                     |
| Complete Compose-compatible service topology                         | Service records currently identify service kind, descriptor, image/provider and dependencies.                           | Not sufficient to run a Compose deployment. NDF must provide authoritative service execution definitions or a versioned immutable Compose/topology artifact.                                       |
| Health/readiness, internal ports/protocols and resource requirements | Not fully represented by the shared service descriptor/PDD v1.                                                          | Declare only from pinned source/product policy and test evidence. Unknown is not equivalent to no requirement.                                                                                     |
| Storage and persistence roles/mount semantics                        | PDD domain can be `not_declared`.                                                                                       | DT Master must block deployment when required storage facts are unknown; do not infer from Host paths.                                                                                             |
| Networking, ingress and endpoint purposes                            | PDD domain can be `not_declared`; concrete allocations belong to Master.                                                | NDF must distinguish product-declared internal topology from Master-owned host ports, FQDNs, TLS and external endpoint allocation.                                                                 |
| Operations: initialization, migration, backup/restore/recovery       | PDD domain can be `not_declared`.                                                                                       | Define product capabilities only where NDF has authoritative procedures and verification.                                                                                                          |
| Infrastructure capacity                                              | Platform architecture can be recorded; CPU/memory/storage minimums are not fully declared.                              | Do not infer resource sizing. Master must reject or require an explicit approved profile where mandatory capacity is unknown.                                                                      |

The NDF PDD audit intentionally chose truthful evidence-state semantics (`not_declared`, `declared`, `verified`) rather than fabricated deployment facts. This is correct fail-closed behavior. M4.4 must treat `not_declared` as unknown and reject a deployment when that domain is mandatory for the selected product/runtime profile.

### 3.3 PDD versioning decision required

M4.2.9 must decide whether the app-identity and service-topology gaps require:

- a backward-compatible additive PDD v1 field/schema revision where semantics permit; or
- a new major PDD schema when requiredness/meaning changes.

Do not modify PDD v1 in a way that silently changes field meaning or breaks the accepted published descriptor contract. Any new service topology artifact must be immutable, digest-bound and referenced from the PDD; NDF remains the authority for its content, while Master owns environment allocations.

## 4. M4.5 — Marketplace App Descriptor and runtime application management

### 4.1 Accepted release/inclusion lifecycle

M4.1 §§16.2–16.3 and 16.8 establish:

1. NDF publishes an immutable Marketplace App Descriptor containing stable app_id, exact release, repository/commit, compatibility, dependencies and build/install metadata.
2. DT Master validates the descriptor, synchronizes technical metadata and separately controls publisher/listing approval.
3. Product Inclusion Request is distinct from marketplace release approval.
4. NDF validates product inclusion and proposes a product-manifest change through a pull request; an authorized maintainer merges it.
5. NDF builds/publishes a new immutable product image. Release approval or listing does not automatically upgrade an active Bench.

NDF has the versioned descriptor schema and two checked-in descriptor examples (`dt_ecommerce`, `dt_recomendations`). The current product manifests still include legacy application declarations without matching registered descriptor files. The candidate/PDD contracts must not claim complete registered descriptor provenance for those apps. This is consistent with the M4.2.7 CAND-03 Partial disposition.

### 4.2 Current DT Master/DT Tenant implementation versus target

The inspected DT Master `api/marketplace.py` remains Git-tag based: it calls `git ls-remote --tags` to resolve the latest minor release and queues install/upgrade/uninstall against the Tenant Site. The file-level audit records that this path can mutate shared Bench code and is to be replaced in M4.5 by app availability, App Installation Request and immutable replacement Bench composition.

The inspected DT Tenant `api/marketplace.py` is a proxy to DT Master for install/upgrade/uninstall, which is directionally consistent with Master owning execution. Its current request envelope is not yet the full accepted idempotent operation contract. DT Master must bind the request to authenticated tenant/service identity, validate site/Bench ownership and app availability, persist an idempotency key and operation identity, and return a safe correlated status. Tenant-controlled FQDN alone is not proof of tenant ownership.

These are M4.5/M4.6 implementation responsibilities, not NDF code tasks.

## 6. Acceptance and test strategy

NDF-local tests can prove schema compatibility, candidate intake rejection, candidate-to-lock integrity, image/PDD digest binding, trust-report correlation, fail-closed behavior and permission/workflow contracts. They cannot prove a DT Master producer certificate, real cross-repository candidate exchange, Master PDD consumer behavior or DT Tenant operation lifecycle.

The final M4.2 regression matrix must therefore distinguish:

1. **NDF executable acceptance:** run focused tests for candidate, PDD, trust, result/evidence and workflow contracts, then the full NDF suite and static checks.
2. **NDF live artifact acceptance:** retain the existing real image/PDD staging and consumer evidence, with exact digests/run IDs.
3. **External integration acceptance:** mark DT Master candidate producer, signer observation, PDD consumer and DT Tenant request lifecycle as pending M4.4/M4.5/M4.6/M4.7 evidence. Do not simulate these with developer identities or fixtures.

A controlled live negative release-workflow test is a separate M4.2.9 activity and requires explicit dispatch authorization. It must use the provisional identity policy, expect the trust gate to reject, and must not create or promote a release tag.

## 7. Proposed A20 disposition

A20 remains **Partial** until the owners resolve INT-01, INT-03, INT-04 and INT-05 sufficiently for the M4.4/M4.5 consumers to validate the documented contracts. NDF can complete its own schema/mapping documentation and fail-closed tests in M4.2.9, but must not claim a fully deployable runtime contract while mandatory service/runtime facts are unknown.

No M4.4/M4.5 implementation or production deployment authorization is included in this mapping.
