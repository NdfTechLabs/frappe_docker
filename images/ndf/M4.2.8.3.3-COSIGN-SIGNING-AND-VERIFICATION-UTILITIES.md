## 1. Purpose and boundary

Provide repository-owned, testable operations for signing and independently verifying NDF-produced product image digests with Cosign keyless signing. These utilities are the trust primitives that later workflow integration will call.

This package is limited to the direct product-image publication identity:

`NdfTechLabs/frappe_docker/.github/workflows/ndf-publish-product.yml@refs/heads/main`

Candidate reusable-workflow identities and PDD signing are not in scope.

No production publishing, release, candidate, or PDD workflow is changed in this package. No image is promoted. A successful local/unit test does not establish live Fulcio/Rekor interoperability.

## 2. Toolchain and trust policy

- Require Cosign CLI `v3.1.4`; reject another version.
- Load and schema-validate `artifact-trust-identity-policy-v1.json`.
- Select exactly one identity entry with ID `product-image-publication` and artifact kind `product_image`.
- Use the exact certificate identity and exact issuer from that entry/policy.
- Require exact GitHub workflow trigger `workflow_dispatch`, repository `NdfTechLabs/frappe_docker`, ref `refs/heads/main`, and the current workflow source commit.
- Do not use identity or issuer regular expressions.
- Do not pass `--insecure-ignore-tlog`, `--private-infrastructure`, `--check-claims=false`, or a mutable image reference.
- Do not treat the provisional identity policy as trusted. Until a real signing run confirms the Fulcio identity/claims and the policy is explicitly changed to `confirmed`, verification output must be rejected with reason `IDENTITY_POLICY_PROVISIONAL`.

The certificate identity URI binds the workflow path and ref. Cosign's exact GitHub certificate-extension checks additionally bind trigger, repository, ref and source SHA.

## 3. Immutable subject and provenance requirements

Every signing and verification operation requires:

`ghcr.io/<owner>/<image>@sha256:<64-lowercase-hex>`

Reject tags, tag-plus-digest references, malformed digests and references whose repository differs from the provenance Statement subject.

Before signing:

1. Validate the complete Statement with `artifact_trust.validate_image_provenance_statement`.
2. Require exactly one subject and exact subject digest equality with the requested image reference.
3. Require predicate type `https://slsa.dev/provenance/v1`.
4. Require the predicate file to decode to exactly the Statement's `predicate` object.
5. Require the Statement workflow metadata to equal the actual GitHub Actions runtime context accepted by the product-image identity contract.
6. Require `GITHUB_ACTIONS=true`; signing must not be run from a developer workstation.

## 4. Signing contract

The signing utility invokes the pinned Cosign binary using argument arrays (never a shell command string):

```bash
cosign sign --yes "$IMAGE_REF"
cosign attest --yes --type slsaprovenance1 \
  --predicate "$PREDICATE_FILE" "$IMAGE_REF"
```

The image signature and SLSA provenance attestation must both be attached to the exact same immutable digest. A partial signing failure is a hard failure; no success result is emitted.

Signing requires GitHub OIDC and registry write permissions supplied by the caller workflow. The utility itself does not acquire or broaden permissions.

## 5. Independent verification contract

The verifier performs two separate Cosign operations against the same immutable digest:

- `cosign verify --output json` for the image signature.
- `cosign verify-attestation --type slsaprovenance1` for the SLSA provenance attestation.

Both commands must receive the exact `--certificate-identity` and `--certificate-oidc-issuer` values, plus exact GitHub certificate-extension constraints for workflow trigger, workflow repository, workflow ref and source SHA.

Cosign's normal Sigstore bundle verification remains enabled. No option may disable Rekor/transparency verification. A successful command is the evidence that the signature/attestation cryptography, Fulcio trust and transparency proof passed under Cosign's trusted root.

The verifier must then:

1. Decode the verified attestation output without trusting arbitrary text or unverified input.
2. Accept only an in-toto Statement v1 with predicate type `https://slsa.dev/provenance/v1`.
3. Validate the full Statement against the NDF image provenance schema.
4. Require exactly one subject matching the requested image digest and repository.
5. Require its NDF workflow claims to match the policy identity and source SHA.
6. Reject missing, ambiguous, malformed or multiple incompatible verified statements.
7. Emit a normalized result validated against `artifact-trust-verification-result-v1.schema.json`.

A result is `trusted` only if all cryptographic, identity, transparency, subject and semantic checks pass **and** the signer policy status is `confirmed`. A cryptographically valid result under a provisional identity policy is emitted as `rejected` with `IDENTITY_POLICY_PROVISIONAL`; the CLI exits non-zero. No provisional identity may authorize image promotion.

## 6. Test contract

Tests must use a fake Cosign executable/subprocess runner; unit tests must not require registry, OIDC, Fulcio or Rekor access.

Required coverage:

- immutable image reference parsing and rejection of mutable/tagged references;
- exact tool version enforcement;
- exact identity-policy selection and rejection of missing/ambiguous policy entries;
- signing refuses local/non-Actions execution and mismatched predicate/Statement;
- exact sign and attest argument construction;
- verification commands include exact identity, issuer, trigger, repository, ref and source SHA;
- no insecure transparency/claims bypass flags;
- non-zero Cosign exit status fails closed;
- malformed/empty/multiple verification outputs fail closed;
- DSSE envelope decoding and complete Statement decoding;
- wrong predicate type, subject digest, repository, workflow path/ref/event/SHA rejected;
- NDF schema validation is mandatory;
- provisional policy never returns a trusted decision;
- confirmed policy returns trusted only when every required check passes;
- normalized result validates against its schema.

## 7. Acceptance boundary

M4.2.8.3.3 is accepted only when the utilities and adversarial tests pass the focused suite, full NDF regression, compileall, pre-commit, actionlint where workflow files are touched, and diff checks.

Acceptance proves the local utility contract and mocked command integration only. A dedicated live GitHub Actions run using a disposable NDF-owned GHCR image must still confirm the actual Fulcio certificate identity, GitHub claims, Rekor inclusion proof and Cosign v3.1.4 output shape before the policy can be marked `confirmed` or production workflows can consume a trusted result.
