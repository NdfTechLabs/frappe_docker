# M4.2.8.6 — Cross-workflow acceptance

**Status:** In progress — NDF-local cross-workflow acceptance.
**Branch:** `feat/M4.2.8.6-cross-workflow-acceptance`
**Trust-policy boundary:** DT Master candidate-origin identity remains provisional.
**Acceptance type:** repository-level integration contract, adversarial regression and static workflow/permission review. This document does not claim a live DT Master producer/consumer run.

## 1. Purpose

Verify that the independently implemented trust components form one fail-closed trust chain across:

1. NDF product-image build, signing, independent verification and official promotion;
2. PDD publication, signing and independent PDD/source-image consumer verification;
3. DT Master candidate dispatch, candidate-origin verification, candidate intake, image build, PDD publication and correlated terminal result.

The acceptance checks both the positive contract (a trusted result can progress only when all required evidence and stages succeed) and negative contract (rejected, provisional, missing, mismatched or cross-attempt evidence cannot authorize promotion, produce a successful candidate result or grant deployment authorization).

## 2. Explicit non-goals and security boundaries

- Do not change the DT Master candidate-origin policy from `provisional_until_live_certificate_observation`.
- Do not invent a certificate identity, producer workflow path/ref, event claim, candidate ID, OCI artifact, signature or attestation.
- Do not dispatch the production candidate workflow using a developer identity or a test-only bypass.
- Do not promote product images, release tags or stable tags during this acceptance.
- Do not infer deployment authorization from a valid signature, a successful build, a valid PDD or a verified evidence bundle.
- Do not treat fixture-based confirmed-policy tests as confirmation of the production signer identity.
- Live DT Master interoperability remains deferred until M4.4 supplies a genuine signed candidate and observed producer identity. Runtime operational acceptance remains subject to M4.7.

## 4. Job dependency and permission invariants

### Candidate workflow

Required dependency chain:

`dispatch-gate → verify-candidate-origin → prepare-candidate → build-candidate → publish-candidate-pdd`

The terminal result job runs with `if: always()` and observes all stage outcomes, but it does not bypass the gates. It has only `actions: read` and `contents: read`.

### Product image workflow

- `sign-trust`: `id-token: write` and registry write, only for signing.
- `verify-trust`: registry read only; no OIDC authority.
- `promote`: registry write but no OIDC authority; it validates the normalized trusted decision and exact digest again before promotion.

### PDD publication and consumer

- `sign-pdd` is the only PDD publication job with OIDC signing authority.
- PDD publication has registry write but no OIDC authority.
- The independent PDD/source-image consumer is read-only and must always report `deployment_authorization=not_granted`.

### Release workflow

- Source trust verification is read-only and must succeed before the release job can run.
- Release re-resolves the source tag and enforces continuity with the exact verified digest.
- The release job has registry write but no OIDC authority.

## 5. Attempt isolation contract

All workflow artifacts that cross job or workflow boundaries must include the relevant source run ID and run attempt, or be selected through an exact upstream artifact name validated against the source run. Candidate terminal identities must remain:

- Result: `ndf-<run_id>-<run_attempt>`
- Trust report: `ndf-<run_id>-<run_attempt>-trust`
- Bundle: `ndf-<run_id>-<run_attempt>-evidence`

Rerunning a workflow increments the attempt and must produce a new result/report/bundle identity. Existing outputs are immutable and must not be overwritten.

5. signing OIDC and registry permissions are confined to the intended jobs;
6. focused and full NDF tests plus all static checks pass;
7. live producer-dependent work is clearly deferred without weakening the policy.
