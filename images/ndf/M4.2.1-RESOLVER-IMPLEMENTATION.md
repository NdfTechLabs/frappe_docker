## 1. Objective

Correct the existing NDF manifest resolver so production resolution cannot silently bypass inherited manifest policy and so the composition lock preserves the requested source references, the reference kind, the resolution-time commit observed by the resolver, compatibility evidence and deterministic composition ordering.

The resolver's SHA is a **resolution-time source snapshot**, not proof of the commit that Bench later acquires. NDF's current upstream-compatible image construction uses `bench init --apps_path` and branch/tag references. The actual acquired commits must be captured after Bench acquisition in M4.2.4, verified in M4.2.5 and included in the Product Deployment Descriptor in M4.2.6.

This package does not force the build to install from the resolver's pre-build SHA and does not classify branch names as development or production references.

## 2. Baseline and confirmed behaviour

The feature branch was created from `main` at `f36539a76f8d5363d6115e82bf26515e53f5090e`.

The resolver:

1. Loads and schema-validates a manifest and recursively loads includes.
2. Deduplicates shared included manifests.
3. Composes required applications and rejects conflicting definitions.
4. Validates dependencies and computes installation order.
5. Resolves `target_ref` through Git to a full commit SHA.
6. Writes a lock containing manifest checksums, repository, requested `target_ref`, resolved `ref`, dependencies and ordering.
7. Validates lock structure, checksums, commit SHA syntax and dependency order.

The build preparation currently emits `apps.json` using repository plus `target_ref`; the layered Containerfile passes it to `bench init --apps_path`. Frappe itself is selected using `FRAPPE_BRANCH`. Consequently, the SHA resolved before the build is not guaranteed to be the commit acquired by Bench. That mismatch is deliberately addressed in M4.2.4–M4.2.6, not by changing the upstream Bench acquisition model in M4.2.1.

## 3. Resolver policy contract

Policy is evaluated across every manifest actually loaded into the selected product composition. A child manifest cannot weaken a restriction imposed by its parent or another included manifest.

| Policy                             | Aggregation | Secure default | Meaning                                                                                                                                                                                          |
| ---------------------------------- | ----------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `require_immutable_commit`         | Logical OR  | `true`         | Every requested source reference must resolve to a full 40-character commit SHA, which is recorded as resolution-time evidence in the lock. It does not claim that the build installed that SHA. |
| `fail_on_unverified_compatibility` | Logical OR  | `true`         | Every required app must carry the accepted normalized status `verified`. Missing or other statuses are unverified.                                                                               |

Policy values must be booleans. Invalid types fail resolution. Effective policy is computed over the complete loaded manifest graph and applied to every required Bench application, including Frappe.

### Git reference semantics

The resolver distinguishes:

- `branch`: a named Git branch;
- `tag`: a named Git tag, with annotated tags peeled to their commit;
- `commit`: an explicitly supplied 40-character commit SHA.

The lock retains the original `target_ref`, selected `reference_kind`, canonical `resolved_ref` and resolution-time commit SHA in `ref`.

**Branch names do not determine production eligibility.** Names such as `main`, `master`, `develop`, `version-16` or organization-specific branch names may represent maintained production lines. The resolver must not hardcode branch names or prefixes as development-only, and it must not reject a branch solely because it is a branch. A branch is acceptable when it resolves successfully to a full commit SHA and the applicable compatibility policy is satisfied.

If a future product requirement needs to prohibit a reference category, it must use an explicit source-kind policy (for example, an allowed set of `branch`, `tag` and `commit` kinds). That is distinct from guessing intent from a branch name and is not introduced by this correction.

Tag resolution takes precedence over a same-named branch; annotated tags are peeled to their commit. An explicit commit reference is fetched and verified to resolve to that exact commit.

### Compatibility status

The only accepted verified value is the normalized status `verified`. Any other value, including missing, pending or free-text verification instructions, is unverified. If effective `fail_on_unverified_compatibility` is true, resolution fails and reports affected apps.

Do not rewrite existing application statuses to `verified` without actual compatibility evidence. Do not change application source references merely to make a resolver test pass.

## 4. Composition lock v2 contract

The existing `ref` field remains the resolution-time full Git commit SHA. Its meaning must be documented accurately:

- `target_ref`: requested branch, tag or explicit commit.
- `ref`: commit SHA observed when the resolver resolved that reference.
- `reference_kind`: `branch`, `tag` or `commit`.
- `resolved_ref`: canonical selected Git reference.
- `compatibility_status`: compatibility evidence used during resolution.
- `resolution_policy`: effective inherited policy.
- `manifests`: source manifest SHA-256 checksums.
- `installation_order` and dependencies: deterministic Bench application ordering.
- `framework`: source-selection evidence consistent with the Frappe application entry.

The lock is a **composition-resolution record**, not a build inventory and not proof of installed source revisions. M4.2.4 must preserve the requested refs when preparing the upstream Bench input and capture the actual acquired commits. M4.2.5 must validate those commits. M4.2.6 must publish the verified inventory in a descriptor bound to the final image digest.

The lock validator must reject unsupported versions, missing/invalid effective policy, malformed commit SHAs, invalid reference provenance, duplicate apps/manifests, invalid checksums, changed source manifests, missing dependencies, incorrect dependency order and policy violations detectable from recorded evidence.

## 6. Test requirements

1. Root policy cannot be weakened by an included manifest.
2. Included policy cannot be weakened by the product manifest.
3. Multiple included policies aggregate deterministically.
4. Invalid non-boolean policy values fail.
5. Branches named `main`, `master`, `develop`, `version-16` and other valid names are not classified by name and are accepted when they resolve to a full SHA and compatibility is verified.
6. Exact tag wins over a same-named branch; annotated tags resolve to the peeled commit.
7. Branch, tag and explicit commit provenance is retained in the lock.
8. Missing compatibility status fails when strict policy applies.
9. Any status other than `verified` fails when strict policy applies.
10. Every required app has a valid 40-character resolution-time commit SHA.
11. Lock v2 validation rejects missing policy/provenance/invalid SHA.
12. Lock generation is deterministic.
13. Lock comparison and `--check` remain safe and non-mutating.
14. CLI failure does not overwrite an existing lock.
15. Full test suite and relevant static checks pass.

## 9. Migration and build consequences

Existing version-1 locks require migration to v2. Product manifests with unresolved compatibility statuses must continue to fail closed until maintainers establish evidence. Existing branch references do not need replacement merely because of their names or because they are branches.

A successful resolver run proves that the requested reference resolved to a commit at resolution time. It does not prove that Bench later acquired that same commit. A build may acquire a later commit if the branch advances between resolution and acquisition. That is why the actual post-acquisition inventory is authoritative for the image.
