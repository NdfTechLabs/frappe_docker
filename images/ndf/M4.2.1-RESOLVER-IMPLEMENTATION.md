## 1. Objective

Correct the existing NDF manifest resolver so production resolution cannot silently bypass manifest policy, and so the generated lock records the effective policy and the immutable source identities that the resolver actually selected.

This package extends the existing resolver and `application-manifest-v1` path. It does not introduce a second resolver, a complete Marketplace App Descriptor (M4.2.2), service/capability composition (M4.2.3), build installation changes (M4.2.4), or image verification (M4.2.5).

### Existing behaviour

The resolver currently:

1. Loads and schema-validates a manifest and recursively loads required/optional includes.
2. Deduplicates shared included manifests.
3. Composes required applications and rejects conflicting definitions.
4. Validates application dependencies and computes installation order.
5. Uses `git ls-remote` to resolve a `target_ref` to a 40-character commit SHA.
6. Writes lock version 1 with source-manifest SHA-256 checksums and application `repository`, `target_ref`, `ref`, dependencies and installation order.
7. Validates lock structure, source-manifest checksums, SHA syntax and dependency order.

### Confirmed gaps

- Resolution policy is not calculated over the full include graph.
- `require_immutable_commit`, `allow_development_branches` and `fail_on_unverified_compatibility` are declared in manifests but not enforced.
- The current lock does not record effective policy or the provenance/classification of each selected Git reference.
- `resolve_git_ref` prefers a branch over a same-named tag and returns only a SHA; it loses whether the selected ref was a branch or tag.
- Compatibility values such as `target_ref_to_verify`, `verify_stable_v16_ref`, `verify_version_16_hooks_and_dependencies` and `pending_frappe_v16_validation` are not treated as blockers.
- The core manifest sets `allow_development_branches: false` and `fail_on_unverified_compatibility: true`, yet includes `telephony` at `develop` and `helpdesk` at `main`; applications also carry non-verified compatibility statuses. Existing lock version 1 contains these resolved applications without policy evidence.
- Test fixtures use the obsolete/misspelled `immutable_commit` key rather than the production key `require_immutable_commit`, so tests do not accurately exercise the declared policy.

## 3. Policy model to implement

Policy must be evaluated across every manifest actually loaded into the selected product composition. A child manifest cannot weaken a restriction imposed by its parent or another included manifest.

### Effective policy aggregation

| Policy | Aggregation | Secure default when omitted | Meaning |
|---|---|---|---|
| `require_immutable_commit` | Logical OR across loaded manifests | `true` for production resolution | Every selected source must resolve to and be represented by a full immutable commit SHA in the lock. |
| `allow_development_branches` | Logical AND across loaded manifests | `false` | A permissive child cannot override a prohibition elsewhere in the composition. |
| `fail_on_unverified_compatibility` | Logical OR across loaded manifests | `true` for production resolution | Every required app must carry an explicitly accepted verified status. Missing status is unverified. |

Policy values must be booleans when present. Invalid types fail resolution. The effective policy must be computed once from the complete loaded graph and applied to all required Bench applications, including Frappe.

### Development-reference classification

The resolver must distinguish explicit commit SHA references, tags and branches, and retain the selected ref kind as well as the resolved commit SHA. An explicit 40-character commit reference must be fetched and verified to resolve to that exact commit. A mutable branch name must not be mistaken for a tag merely because both share a name. Tag resolution should take precedence when an exact tag exists; annotated tags must be peeled to their commit.

For the current M4.2.1 policy contract, branch names conventionally identifying moving development lines — `develop`, `development`, `dev`, `main`, `master`, `nightly`, and names under corresponding development prefixes — are classified as development branches. The classification function must be explicit and unit-tested. Stable release branches such as `version-16` are not classified as development branches solely because they are Git branches.

If effective `allow_development_branches` is false, a selected development branch is rejected before lock generation. If true, it may be resolved but must remain explicitly identified in the lock. This setting does not make a branch immutable: `require_immutable_commit` still requires the resolved SHA. Explicit commit references are recorded as `reference_kind: commit`; tags and branches retain their canonical `refs/tags/...` and `refs/heads/...` identities.

### Compatibility status

For this package, the only accepted verified value is the exact normalized status `verified`. Any other value, including missing, pending, target-ref-to-verify or free-text verification instructions, is unverified. If effective `fail_on_unverified_compatibility` is true, resolution fails and reports every affected app and its status.

Do not silently rewrite existing application statuses to `verified`. Existing manifests must be updated only after actual compatibility evidence is established by the responsible maintainers. The current product manifests are expected to fail closed until those statuses and prohibited refs are corrected.

## 4. Immutable source and lock contract

The existing `ref` field remains the resolved full Git commit SHA for backward-compatible consumers. M4.2.1 extends the current lock version to version 2 and records:

- Effective resolution policy.
- Each app's original `target_ref`.
- Resolved full commit SHA in `ref`.
- Selected Git reference kind (`commit`, `branch` or `tag`).
- Selected canonical Git ref name.
- Compatibility status used for the decision.
- Manifest source checksums as today.
- Resolver identity/version and deterministic application ordering.

The lock validator must reject:

- Unsupported lock versions.
- Missing/invalid effective policy.
- Missing or malformed 40-character hexadecimal commit SHAs.
- Invalid reference kind or missing selected-ref provenance.
- Duplicate apps/manifests.
- Invalid checksums or changed manifest content (unless checksum verification is explicitly disabled for lock comparison).
- Dependencies missing from the lock or appearing after dependants.
- Policy violations detectable from the recorded effective policy and app evidence.

A lock is a resolution record, not proof that the build installed those SHAs. Build preparation and image installation enforcement remain M4.2.4; actual installed HEAD verification remains M4.2.5.

## 6. Test requirements

At minimum:

1. Root prohibition cannot be weakened by an included manifest.
2. Included prohibition cannot be weakened by the product manifest.
3. Multiple included policies aggregate deterministically.
4. Invalid non-boolean policy values fail.
5. `develop`, `main`, `master`, `nightly` and configured development prefixes are rejected when development branches are prohibited.
6. Stable release refs such as `version-16` remain eligible.
7. Exact tag wins over same-named branch and annotated tags resolve to peeled commit.
8. Permitted development branch is explicitly represented in lock provenance.
9. Missing compatibility status fails when strict policy applies.
10. Any status other than `verified` fails when strict policy applies.
11. Verified compatibility passes.
12. Every required app has a valid 40-character resolved commit SHA.
13. Lock v2 validation rejects missing policy/provenance/invalid SHA.
14. Lock generation is deterministic.
15. Existing lock comparison and `--check` behaviour remain safe and non-mutating.
16. CLI failure does not overwrite an existing lock.
17. Full test suite and relevant static checks pass.

## 9. Known migration consequence

The currently checked-in product locks were generated without enforcement of the declared production policy. The inspected DhanaERP Master lock includes `telephony: develop` and `helpdesk: main`, and the corresponding source manifest records unresolved compatibility states. These locks cannot be treated as policy-compliant merely because they contain commit SHAs.

M4.2.1 must fail closed. Existing manifests/locks will need explicit maintainer remediation and regeneration after evidence is available. A failed production resolution is the correct outcome until the composition satisfies the approved policy.
