# M4.2.7.2 — Candidate Intake and Validation

**Repository:** NdfTechLabs/frappe_docker
**Branch:** feat/M4.2.7
**Status:** Locally accepted; see the 2026-11-15 M4.2.7.2 tracker acceptance record
**Implementation:** `scripts/intake_deployment_candidate.py`

## 1. Scope

This work package consumes one authenticated dispatch envelope containing:

- `candidate_id`
- digest-pinned `artifact_reference`
- SHA-256 of the exact serialized candidate JSON bytes (`payload_sha256`)

NDF validates and retrieves the artifact, validates the payload and emits a local validated candidate file for later build orchestration. It does not create or own DT Master candidate/build records, authorize tenant operations, deploy sites, or call DT Tenant.

## 2. OCI producer/consumer layout

The implementation enforces the proposal in `M4.2.7.1-CONTRACT.md`:

| Element              | Required value                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------- |
| Repository           | `ghcr.io/ndftechlabs/dt-master-deployment-candidates`                                       |
| Reference            | Exact repository plus `@sha256:<64 lowercase hex>`                                          |
| Manifest media type  | `application/vnd.oci.image.manifest.v1+json`                                                |
| Manifest schema      | OCI image manifest schemaVersion 2                                                          |
| Artifact type        | `application/vnd.ndf.deployment-candidate.v1`                                               |
| Config media type    | `application/vnd.oci.empty.v1+json`                                                         |
| Config bytes         | `{}`                                                                                        |
| Config digest/size   | SHA-256 of those exact two bytes; size 2                                                    |
| Layers               | Exactly one                                                                                 |
| Layer media type     | `application/vnd.ndf.deployment-candidate.v1+json`                                          |
| Layer title          | `deployment-candidate.json` via `org.opencontainers.image.title`                            |
| Manifest annotations | `io.ndf.candidate.id`, `io.ndf.candidate.schema-version`, `io.ndf.candidate.payload-sha256` |

The manifest digest returned by ORAS, layer descriptor digest/size, and dispatch payload SHA-256 are distinct checks. Because the agreed layer is one uncompressed JSON file, its descriptor digest and payload SHA-256 must identify the same bytes.

## 3. Intake stages

1. Parse the reference using an exact GHCR repository allowlist. Reject tags, alternate hosts/packages, uppercase digest hex, URL syntax, whitespace, query/fragment and extra path components.
2. Fetch the manifest by digest with ORAS. Require the returned digest to equal the requested digest. Validate manifest media type/schema version, artifact type, exact empty config, exactly one layer, layer media type/title/digest/size, and required manifest annotations.
3. Pull by the same immutable reference. Require the ORAS response reference to match, reject symlinks and unexpected files, then verify exact layer size and SHA-256.
4. Verify the payload SHA-256 against the authenticated dispatch envelope before parsing. Decode strict UTF-8 JSON, reject duplicate keys and non-finite constants, validate against the Draft 2020-12 candidate schema, and bind candidate ID to the dispatch envelope.
5. Enforce semantic invariants: unique app IDs, descriptor reference/digest consistency, immutable Git commit identities, supported product identity from `image-definitions/images-v1.json`, and framework version matching the authoritative product manifest.
6. Write the validated candidate atomically only after every validation stage passes.

The validated candidate is subsequently translated by `scripts/adapt_candidate_to_lock.py` (M4.2.7.3); intake itself does not create lock-v2 or Bench build inputs.

## 4. Test strategy

Unit tests use a deterministic fake ORAS process boundary; they do not require registry credentials or network access. Tests cover:

- reference allowlist and digest syntax;
- OCI manifest media type, artifact type, empty config, layer count/type/title and manifest annotations;
- returned manifest digest mismatch;
- payload hash mismatch and layer byte tampering;
- duplicate JSON keys and schema violations;
- candidate ID mismatch;
- duplicate app IDs, descriptor reference/digest mismatch and mutable commits;
- unsupported products and product/framework mismatch;
- successful intake using a digest-pinned reference and exact payload bytes.

A real GHCR integration test with a DT Master-produced artifact remains a separate cross-repository acceptance gate. Unit tests cannot prove that the Master serializer and ORAS publisher produce this exact layout.

## 5. Cross-repository production gate

Production dispatch remains disabled until DT Master:

1. accepts the NDF OCI producer/consumer layout;
2. serializes the documented candidate fields to schema version 1.0.0;
3. publishes one uncompressed `deployment-candidate.json` layer with the required artifact type, media type, empty config and annotations;
4. dispatches the exact immutable reference, candidate ID and payload SHA-256; and
5. supplies a real artifact that NDF retrieves and validates successfully.

Only `NdfTechLabs/frappe_docker` is modified in M4.2.7.2. DT Master and DT Tenant remain read-only references.
