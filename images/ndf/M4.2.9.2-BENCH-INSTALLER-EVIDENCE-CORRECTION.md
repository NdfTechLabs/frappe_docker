# M4.2.9.2 — Bench Installer and Dependency-Input Evidence Correction

**Status:** Implemented on the M4.2.9 branch; focused/local validation pending
**Date:** 17 November 2026
**Repository:** `NdfTechLabs/frappe_docker`
**Branch:** `feat/M4.2.9-integration-documentation-testing`

## 1. Problem

M4.2.4 currently records available `uv` and `pip` versions and hashes detected dependency-file candidates. It does not record which Python installer Bench selected for the actual build or distinguish files used by Bench's editable-app installation path from other detected candidate lock/requirements files.

This leaves an avoidable provenance ambiguity in the accepted M4.2.3 Option A handoff. NDF must continue to use upstream Bench and native package managers; it must not implement a second resolver or installer.

## 2. Upstream Bench behavior inspected

The accepted RT-01 build inventory reports Bench **5.31.1**. The corresponding upstream source tag resolves to commit:

`frappe/bench@v5.31.1` — `660bc2898500dc33828056c1228e5a1d538573b1`.

The source paths inspected at that tag:

- `bench/utils/__init__.py`: `use_uv()` selects UV by default and disables it only when `BENCH_DISABLE_UV` is `1`, `true` or `yes`.
- `bench/app.py`: `App.install()` uses `uv pip install -e <app_path> --python <bench.python>` when `use_uv()` is true; otherwise it uses `<bench.python> -m pip install --upgrade -e <app_path>`. When an app has `package.json` and the install is not using cached dependencies, it invokes `yarn install --check-files`.
- `bench/utils/bench.py`: developer-mode dependency installation has a separate path that reads `pyproject.toml` `[tool.bench.dev-dependencies]` or `dev-requirements.txt`. The current NDF Containerfile creates an empty `sites/common_site_config.json`; the build must not claim developer-mode dependency files were consumed unless developer mode is actually enabled.

These are the upstream behaviors to observe, not reimplement.

## 3. Approved implementation approach

1. From the existing Bench executable's Python interpreter, import the actual installed `bench.utils.use_uv` function and evaluate it in the build environment. Do not infer the selected installer solely from the presence of the `uv` binary.
2. Record the normalized `BENCH_DISABLE_UV` state, selected Python installer (`uv` or `pip`), Bench version, and SHA-256 fingerprints of the upstream `use_uv` and `App.install` source functions. Do not persist arbitrary environment variables.
3. For each app, record the project metadata inputs present for editable installation (`pyproject.toml`, `setup.py`, `setup.cfg`) with exact path and SHA-256.
4. For each app with `package.json`, record the Bench-selected Node installation path (`yarn install --check-files`) and the exact `package.json`/optional `yarn.lock` hashes. If `package.json` is absent, record that the Bench Node installation path is not invoked for that app.
5. Retain the existing `dependency_files` collection, but describe it as detected candidates. Do not label `uv.lock`, `requirements.txt`, `Pipfile.lock`, or other detected files as consumed unless the inspected Bench code path actually reads them.
6. Add schema validation and positive/negative tests. The capture remains read-only: it does not install packages, change environment variables, modify app repositories or alter Bench behavior.

## 4. Evidence semantics

The new evidence distinguishes:

- **Selected installer:** the actual branch selected by the installed Bench `use_uv()` function.
- **Project/install inputs:** metadata/lock files relevant to the actual Bench `App.install()` code path for each app.
- **Detected candidates:** additional dependency/lock files found in the source tree, not automatically proof of consumption.
- **Installed inventory:** packages measured after Bench installation, as already recorded.

The source-function fingerprints bind the recorded selection to the exact installed Bench implementation. Python project metadata files are recorded as available backend inputs, while \`package.json\` and an optional \`yarn.lock\` identify the Bench Yarn path. This does not prove the origin of every transitive package; installed-package inventory and source/registry evidence limitations remain explicit.

## 5. Compatibility and boundaries

- Keep the existing build-inventory v1 contract backward-compatible by adding an optional typed evidence object; old inventory artifacts remain schema-valid.
- New builds must emit the new object and fail closed if the Bench selection cannot be observed from the actual installed Bench interpreter.
- Keep NDF's capture outside the package-manager execution path. No custom dependency solver, package installer, network proxy or alternate app checkout is introduced.
- No change to product manifest refs, Bench app acquisition, Buildx base digests, image publication, signing or trust policy.
- The evidence is captured before Git metadata cleanup and is included in the existing runtime inventory and image-digest-bound evidence bundle.

## 6. Acceptance tests

- Selected UV when the installed `use_uv()` function returns true.
- Selected pip when `BENCH_DISABLE_UV` disables UV.
- Fail closed when the Bench executable/interpreter/function cannot be inspected.
- Record the exact Bench source-function hashes and selected installer.
- Record per-app editable-install metadata and Yarn inputs with exact hashes.
- Distinguish an app without `package.json` from one using Yarn.
- Preserve candidate-file inventory without claiming unrelated files were consumed.
- Existing capture, source-provenance, image-verification and full NDF regression suites remain green.

**Disposition:** This correction is within the approved M4.2.4 post-Bench evidence responsibility and supports M4.2.9 integration acceptance. It does not change the upstream Bench ownership decision.
