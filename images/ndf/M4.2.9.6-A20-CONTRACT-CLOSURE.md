## 1. Acceptance interpretation

A20 is a contract-documentation criterion. It requires NDF to publish a sufficiently precise producer/consumer interface for DT Master and DT Tenant to implement in their assigned milestones. It does not require M4.4/M4.5 implementation, a live DT Master producer, production signer approval, final deployment topology for every product, or M4.7 runtime acceptance to be completed inside M4.2.

This closure does not waive downstream requirements. It records the interface, owner, validation rules and explicit gates so downstream work does not need to invent or reinterpret them.

## 2. INT-01 — Candidate OCI transport contract

NDF adopts the exact consumer-side GHCR/ORAS envelope already enforced by `images/ndf/scripts/intake_deployment_candidate.py` and `.github/workflows/ndf-build-candidate.yml`:

| Element | Normative value |
| --- | --- |
| Private package | `ghcr.io/ndftechlabs/dt-master-deployment-candidates` |
| Reference | Exact repository plus immutable lowercase `@sha256:<64-hex>` manifest digest; tags and alternate repositories are rejected. |
| OCI manifest | `schemaVersion: 2`; `application/vnd.oci.image.manifest.v1+json`; artifact type `application/vnd.ndf.deployment-candidate.v1`. |
| Config | `application/vnd.oci.empty.v1+json`; exact bytes `{}`; matching SHA-256 digest and byte size. |
| Layers | Exactly one layer, media type `application/vnd.ndf.deployment-candidate.v1+json`. |
| Layer title | `deployment-candidate.json`, carried as `org.opencontainers.image.title`. |
| Manifest annotations | `io.ndf.candidate.id`; `io.ndf.candidate.schema-version` = `1.0.0`; `io.ndf.candidate.payload-sha256`. |
| Payload | SHA-256 over the exact JSON layer bytes; the same value is passed to NDF dispatch and verified against the pulled bytes and manifest annotation. |
| Payload schema | `images/ndf/schemas/deployment-candidate-v1.schema.json`, version `1.0.0`. |

DT Master publishes the immutable artifact, signs the exact OCI manifest digest and attaches the M4.1 candidate-origin attestation. The signed predicate binds candidate ID, artifact repository/digest, exact payload hash, correlation ID, producer repository/workflow/ref/source commit and run/attempt. NDF verifies the exact subject digest, payload bytes, predicate schema, issuer/certificate identity and transparency evidence before candidate intake or adaptation.

Dispatch inputs are `candidate_id`, `candidate_artifact_ref`, `candidate_payload_sha256` and canonical `correlation_id`. DT Master uses its own narrowly scoped registry credential; NDF reads with `packages: read`; the dispatch GitHub App has only the Actions permission required to invoke the workflow. NDF image-publishing credentials remain NDF-only.

**Acceptance boundary:** NDF-side contract adoption and enforcement are documented. DT Master producer serialization/publication and package-retention behavior must conform before live dispatch. The actual producer certificate/workflow identity remains provisional until observed from a genuine M4.4 run and separately approved. No live producer interoperability is claimed.

## 3. INT-03 — Marketplace identity and descriptor ownership

The M4.1 ownership model is preserved:

- NDF publishes the immutable technical Marketplace App Descriptor for an application release.
- DT Master assigns/validates the stable `app_id`, owns the marketplace Extension/Extension Version records and governance, and synchronizes an immutable technical metadata snapshot for marketplace operations.
- A DT Master Deployment Candidate carries each selected app's `app_id`, `release_version`, `descriptor_ref`, `descriptor_digest`, source identity and immutable commit.
- Product inclusion remains a separate decision from marketplace release approval. DT Master approval does not silently mutate an existing product or Bench.

The two NDF descriptor files `dt_ecommerce.json` and `dt_recomendations.json` are test fixtures. They are not production marketplace registrations. Production product manifests intentionally remain v1 while the corresponding real registrations and immutable descriptor snapshots are established. No bulk manifest migration is required or authorized by this A20 documentation closure.

Known implementation boundary: the current NDF candidate adapter retains `descriptor_ref` and `descriptor_digest` as candidate metadata, while the existing manifest-v2 resolver loads repository-relative descriptor files. The adapter does not yet retrieve/verify a DT Master snapshot and carry that registry identity through lock-v2 and PDD. M4.4/M4.5 must implement and test that exact snapshot handoff. Descriptorless legacy v1 apps remain explicitly descriptorless until registered and migrated through an authorized product-manifest change. Release versions must never be inferred from Git refs or commits.

## 4. INT-04 — Compose topology and deployment profile

The existing executable upstream Compose foundation is retained; no parallel topology schema is introduced. The current NDF repository contains:

| File | Declared role |
| --- | --- |
| `compose.yaml` | Base Bench services: configurator, backend, frontend, websocket, short/long queues, scheduler and shared sites volume. |
| `overrides/compose.mariadb.yaml` | MariaDB service, health check and persistent database volume. |
| `overrides/compose.redis.yaml` | Redis cache/queue services and queue persistence. |
| `overrides/compose.https.yaml` | Traefik HTTPS ingress and certificate storage. |
| `overrides/compose.noproxy.yaml` | Direct frontend port publication without the proxy service. |

A deployment profile is an explicit selection of the base Compose file and applicable overrides. Each file reference is immutable when resolved against the NDF source commit recorded in PDD `build.source_commit`; downstream consumers must not fetch a mutable branch or silently substitute another configuration. The existence of a file does not mean it was selected for a particular product.

NDF owns the service definitions. DT Master owns node/Bench-specific Compose project identity, networks, host ports, storage allocation/lifecycle, external endpoints, secret injection, ingress/TLS and deployment sequencing. It may override only parameters explicitly declared configurable by NDF. The current files do not establish complete health/readiness semantics for every service or product; unknown mandatory readiness facts remain a deployment gate.

## 5. INT-05 — Runtime and requirement-domain consumer mapping

Manifest v2 `target_runtime` describes declared framework/runtime/platform and image identities. PDD v1 separates measured runtime inventory from declared deployment requirements and explicitly identifies inventory scope (`builder_stage` or `final_runtime_image`). The seven requirement domains map as follows:

| PDD domain | Product-side declaration | DT Master consumer responsibility |
| --- | --- | --- |
| `services` | Required/optional service identities, immutable artifacts and dependencies. | Resolve service placement and dependency readiness. |
| `storage` | Persistent paths, volume semantics and durability needs. | Allocate storage backend/volumes and lifecycle. |
| `networking` | Internal ports/protocols and endpoint purposes. | Allocate node ports, networks, ingress and external endpoints. |
| `configuration` | Supported configuration keys and explicitly configurable parameters. | Supply environment values and secrets through approved providers. |
| `health_readiness` | Declared readiness/liveness probes and probe semantics. | Execute and aggregate health checks; unknown mandatory probes block readiness. |
| `operations` | Initialization, migration, backup/restore and recovery requirements. | Orchestrate and authorize operational procedures. |
| `infrastructure` | Supported OS/architecture and evidence-backed resource/capacity constraints. | Evaluate target node/Bench suitability. |

Evidence states remain normative: `not_declared` means unknown, not 'not required'; `declared` means an authoritative declaration exists but is not independently verified; `verified` requires supporting evidence with an explicit scope. Builder-stage inventory must not be represented as final-runtime inventory. A Compose service's presence does not imply its readiness, storage, network or capacity requirements have been fully declared. DT Master determines which domains are mandatory for a selected deployment profile and fails closed when mandatory facts are unknown or insufficient.
