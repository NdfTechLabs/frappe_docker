# M4.2.8.4.3 — PDD Cosign Signing and Verification Utility Contract

**Repository:** `NdfTechLabs/frappe_docker`
**Branch:** `feat/M4.2.8`
**Status:** Accepted — implementation and local validation passed
**Date:** 16 November 2026
**Depends on:** M4.2.8.4.1 accepted contract and M4.2.8.4.2 accepted deterministic binding generator

## 1. Objective

Add an artifact-specific Cosign utility for Product Deployment Descriptor (PDD) OCI artifacts. It must sign the exact immutable PDD digest, attach the deterministic PDD-to-image binding predicate, and independently verify the PDD signature and binding attestation.

This step delivers reusable command-line utilities and mocked/adversarial tests only. The implementation and local validation are accepted. It does not modify publication or fetch workflows, confirm signer identity policy, authorize promotion, or implement candidate trust.

## 2. Existing implementation to reuse

The product-image implementation in `images/ndf/scripts/cosign_image_trust.py` establishes the accepted operational patterns:

- Cosign CLI pinned to `v3.1.4`;
- immutable OCI references only;
- argument-array subprocess execution, without shell interpolation;
- keyless `cosign sign` and `cosign attest`;
- normal Cosign trusted-root and Rekor verification (no tlog bypass);
- exact certificate identity, OIDC issuer, trigger, repository, ref and source-SHA checks;
- strict extraction of exactly one verified in-toto Statement v0.1 from Cosign's verified output;
- atomic result/output writes and normalized artifact-trust result validation.

The PDD utility must be a separate module, `images/ndf/scripts/cosign_pdd_trust.py`. Do not alter product-image signing or verification semantics merely to share implementation. Shared helpers may be extracted only if that refactor is behavior-preserving and independently tested; it is not required for .4.3.

## 3. PDD signing contract

### 3.1 Artifact identity

- Require a fully qualified immutable reference: `<repository>@sha256:<64 lowercase hex>`.
- Reject tags, tag-plus-digest references, malformed digests and non-fully-qualified repositories.
- Load and schema-validate the existing identity policy.
- Select exactly one identity entry with ID `product-pdd-publication` and artifact kind `pdd`.
- Require a direct workflow identity (no reusable workflow).
- Require issuer `https://token.actions.githubusercontent.com`.
- Require exact workflow reference:
  `NdfTechLabs/frappe_docker/.github/workflows/ndf-publish-product-deployment-descriptor.yml@refs/heads/main`.
- Require GitHub Actions runtime context, `refs/heads/main`, `workflow_dispatch`, the expected repository and the exact PDD publication workflow path.
- Require the Statement workflow claims (repository, path, ref, run ID, run attempt and source commit) to equal the actual runtime context.

### 3.2 Inputs and validation

The signing operation accepts:

- immutable PDD OCI reference;
- original NDF PDD binding Statement v1;
- its predicate JSON object;
- policy path and Cosign binary override for tests/controlled execution.

Before invoking Cosign:

1. Strictly parse JSON (reject duplicate keys, non-finite values, symlinks and non-object roots).
2. Validate the complete original Statement v1 against `pdd-image-binding-v1.schema.json`.
3. Validate its PDD subject repository and digest against the immutable OCI reference.
4. Require exactly one subject.
5. Require the predicate file to equal the Statement's predicate object exactly.
6. Validate the predicate's PDD-to-image claims using the existing artifact-trust validator.
7. Require the predicate workflow identity and run context to equal the actual GitHub Actions runtime context.
8. Require the exact `product-pdd-publication` policy entry and approved OIDC issuer.
9. Require Cosign CLI version `v3.1.4`.

Only after all checks pass:

- execute `cosign sign --yes <pdd-repository>@<pdd-digest>`;
- execute `cosign attest --yes --type https://ndftechlabs.com/attestations/pdd-image-binding/v1 --predicate <predicate-file> <pdd-repository>@<pdd-digest>`.

Use argument arrays, never a shell command string. Do not pass credentials or OIDC tokens as arguments, outputs or artifacts.

### 3.3 Signing result

Return a structured non-authorizing summary containing status, PDD repository/digest, predicate type, canonical predicate SHA-256, identity ID and current policy status. A successful Cosign command means the artifact was signed; it does not mean the signer policy is confirmed or the artifact is eligible for promotion.

## 4. PDD verification contract

### 4.1 Verification sequence

Given only an immutable PDD OCI reference and output paths:

1. Parse and validate the immutable PDD reference.
2. Load the exact `product-pdd-publication` identity entry and policy.
3. Require Cosign `v3.1.4`.
4. Run `cosign verify --output json` with exact certificate identity, issuer, workflow trigger, repository and ref constraints. Keep normal Rekor verification enabled.
5. Run `cosign verify-attestation --type https://ndftechlabs.com/attestations/pdd-image-binding/v1` with the same exact identity constraints.
6. Extract exactly one verified in-toto Statement v0.1 from the Cosign output. Reject zero, multiple, malformed or ambiguous statements.
7. Validate the strict PDD Cosign v0.1 compatibility profile, including the complete PDD binding predicate. The original NDF producer contract remains Statement v1; only the verified Cosign wrapper is accepted as v0.1 interoperability output.
8. Require the verified statement subject repository and digest to equal the immutable PDD reference.
9. Require the predicate type to equal `https://ndftechlabs.com/attestations/pdd-image-binding/v1`.
10. Validate all PDD binding claims: descriptor ID/content hash, subject image repository/digest/platform, lock hash, source provenance predicate type/hash and workflow identity.
11. Obtain the source commit from the verified binding predicate's workflow claim. Re-run both signature and attestation verification with `--certificate-github-workflow-sha <source_commit>`.
12. Extract the statement again and require exact equality with the first verified statement.
13. Compute the canonical SHA-256 of the verified binding predicate using NDF-JSON-CANONICAL-V1.
14. Emit and schema-validate a normalized trust result for artifact kind `pdd`.

The utility must not accept a caller-supplied source SHA as authoritative. It is learned from the cryptographically verified attestation and then applied as an exact certificate claim constraint.

### 4.2 Exact predicate comparison modes

The producer-side verification mode accepts the expected locally generated predicate and requires exact JSON-object equality with the verified Cosign predicate. Missing expected predicate input must fail closed.

The consumer's self-contained verification mode is out of scope for .4.3 and is implemented in .4.5. It must not be simulated by trusting an unverified sidecar or by weakening producer comparison.

### 4.3 Normalized trust result

Use the existing `artifact-trust-verification-result-v1` schema:

- `artifact.kind = pdd`;
- repository, digest and immutable reference identify the exact PDD OCI artifact;
- signature, signer and transparency verification fields are true only after successful Cosign verification;
- exactly one verified PDD binding attestation is recorded, with subject digest equal to the PDD digest and `predicate_sha256` equal to the canonical verified binding predicate hash;
- `decision.status = trusted` only when policy status is `confirmed`;
- while policy is provisional, emit `decision.status = rejected` and the sole reason `IDENTITY_POLICY_PROVISIONAL`.

The provisional result is cryptographic evidence only; it must never authorize promotion or be described as trusted.

## 5. Strict Cosign compatibility profile

Cosign v3.1.4's generic explicit predicate-URI path may return an in-toto Statement v0.1 wrapper. NDF's generated PDD binding remains Statement v1.

Add a dedicated strict compatibility schema for the verified PDD wrapper. Require:

- `_type = https://in-toto.io/Statement/v0.1`;
- one subject with repository name and SHA-256 digest;
- exact PDD binding predicate URI;
- complete predicate fields and types constrained by the existing PDD binding schema.

Validate the wrapper profile, then validate the same predicate and subject through the existing canonical PDD binding validation path. Do not rewrite or mutate the verified payload for comparison or hashing. Do not reuse the image-provenance v0.1 schema because its predicate contract is different.

## 6. Error handling and security requirements

- Fail closed on missing, malformed, duplicate, ambiguous or mismatched inputs and verification output.
- Fail closed on policy identity mismatch, issuer mismatch, unexpected workflow, event, ref or source SHA.
- Never use `--insecure-ignore-tlog`, `--check-claims=false`, wildcard identity, regex fallback or a non-pinned Cosign version.
- Never trust a success exit code without parsing and validating the verified signature/attestation output.
- Do not infer certificate identity from the local workflow environment; Cosign verification must authenticate it.
- Do not treat a local trust-result JSON as cryptographic proof.
- Preserve provisional policy rejection; do not edit policy status in this step.
- Do not change workflows, publication/fetch scripts, schemas unrelated to the strict Cosign wrapper, product-image trust behavior or candidate authorization.

## 8. Acceptance criteria

1. Strict immutable PDD reference parsing rejects mutable and malformed references.
2. Identity selection is exact, unique and direct-workflow only.
3. Signing validates the original Statement v1, exact predicate equality, PDD subject digest, complete binding schema and runtime workflow claims before any Cosign write.
4. Signing invokes only pinned Cosign v3.1.4 with the exact PDD digest and predicate type.
5. Verification requires normal signature and Rekor-backed attestation verification under exact identity/issuer/event/repository/ref constraints.
6. Exactly one valid Cosign Statement v0.1 is extracted and its predicate validates against the PDD binding schema.
7. Verification repeats both Cosign checks with the source commit obtained from the verified predicate and requires statement equality across passes.
8. The normalized result validates against the existing trust-result schema and remains rejected while policy is provisional.
9. Adversarial tests cover altered subjects/predicates, wrong workflow identity, wrong SHA, malformed/duplicate/multiple statements, Cosign failures, version mismatch and provisional policy.
10. Focused tests, full NDF suite, compileall, pre-commit, actionlint and diff checks pass.

## 9. Explicitly out of scope

- Live PDD signing or publication round-trip (workflow integration/acceptance).
- Confirming the PDD signer identity policy or enabling official promotion.
