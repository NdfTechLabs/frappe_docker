# M4.2.8.5 — DT Master Candidate Producer / NDF Consumer Contract

**Status:** Proposed — pending DT Master producer-contract review  
**Contract owner:** NDF Frappe Docker (consumer specification); DT Master (candidate data and producer authority)  
**Baseline:** Accepted DT Master M4.1 Section 16; NDF M4.2.7 and M4.2.8.1 contracts  
**Scope:** NDF-side implementation in M4.2; DT Master producer implementation in M4.4  
**Date:** 16 November 2026

## 1. Purpose and authority

This document reconciles the existing NDF candidate intake/trust contracts with the accepted DT Master M4.1 Deployment Candidate, Deployment Build, asynchronous request/result and artifact-trust architecture.

It defines the producer/consumer boundary required for M4.2.8.5. It does not create a new candidate owner, build owner, operation owner, runtime adapter or deployment authority. It does not change M4.1.

The normative architectural authority remains the accepted DT Master M4.1 specification, particularly Sections 14.11–14.14, 15.6 and 16. The NDF schemas are versioned validation/transport contracts mapped to the authoritative DT Master records; they are not replacement DocTypes or a competing lifecycle model.

## 2. Ownership

| Concern | Authoritative owner | Contract behavior |
|---|---|---|
| Deployment Candidate record, authorization and lifecycle | DT Master | Creates and freezes the candidate input snapshot |
| Candidate OCI artifact, signature and candidate-origin attestation | DT Master | Publishes and authenticates the exact candidate artifact it produces |
| Candidate intake, origin verification and build-input adaptation | NDF | Independently verifies and consumes the candidate; does not mutate Master records |
| Product manifest, composition resolution and immutable build lock | NDF | Resolves the candidate into the NDF-owned product build model |
| Product image and PDD | NDF | Builds, validates, publishes, signs and attests to these NDF-produced artifacts |
| Deployment Build record and request idempotency | DT Master | Tracks NDF workflow/run attempts and reconciles terminal results |
| Image/PDD trust verification for deployment eligibility | DT Master | Independently verifies NDF artifacts and records its own decisions |
| Bench Deployment and deployment authorization | DT Master | Applies separate capacity, readiness, policy, operation and cutover gates |

DT Tenant is not a direct participant in candidate OCI publication or NDF build execution.

## 3. Contract flow

1. DT Master creates and validates a Deployment Candidate and freezes an immutable build-input snapshot.
2. DT Master serializes the snapshot according to the agreed candidate payload schema.
3. DT Master publishes the exact serialized payload as a digest-addressed OCI artifact.
4. DT Master signs the exact candidate OCI manifest digest and attaches the candidate-origin attestation whose subject is that same digest.
5. DT Master dispatches the candidate ID, immutable artifact reference, exact payload SHA-256 and shared correlation ID to the authorized NDF entry workflow.
6. NDF validates dispatch context and independently verifies the DT Master signature, signer identity, OIDC issuer, transparency evidence, candidate-origin predicate, OCI subject digest, OCI envelope and exact payload bytes before parsing/adapting the candidate.
7. NDF resolves the candidate into its existing immutable build lock, builds and verifies the product image, then signs and attests to the NDF-produced image digest.
8. NDF generates and publishes the PDD bound to that exact image digest, then signs and attests to the PDD OCI digest and PDD-to-image relationship.
9. NDF emits one immutable terminal result for the exact NDF workflow run/attempt, with candidate correlation, build outputs and NDF-side trust evidence.
10. DT Master retrieves/reconciles the result, independently verifies the image signature/provenance and PDD signature/binding, and records its own trust outcomes in Deployment Build.
11. DT Master may then evaluate the separate Bench Deployment policy. Neither build success nor trust verification automatically authorizes deployment.

The build is asynchronous. DT Master must not hold an HTTP request open while NDF builds. The initial integration may poll GitHub workflow status and attempt-scoped artifacts. A later authenticated callback may be added only if it preserves the same idempotent result contract.

## 4. Candidate payload mapping

### 4.1 Accepted DT Master semantic input

The M4.1 candidate contract requires the immutable build input to identify:

- candidate ID and request/schema version;
- target product and product composition;
- selected app_id, release and descriptor digests;
- requested optional capabilities;
- supported runtime constraints or explicitly selected runtime profile;
- approved build parameters and platform targets;
- composition hash and source/provenance references.

The candidate must not contain tenant credentials, database passwords, API secrets, customer data, arbitrary shell commands, Node-specific ports, site FQDNs, TLS private keys or live tenant configuration.

### 4.2 Existing NDF payload schema

NDF currently validates against `images/ndf/schemas/deployment-candidate-v1.schema.json` (schema version `1.0.0`). Its required top-level fields are:

- `schema_version`
- `candidate_id`
- `candidate_code`
- `candidate_type`
- `product`
- `framework_version`
- `composition_hash`
- `applications`
- `optional_capabilities`
- `runtime_profile`
- `runtime_constraints`
- `target_platforms`
- `approved_build_parameters`
- `provenance_refs`

Application entries include app_id, app_name, release_version, descriptor_ref, descriptor_digest, app_source_type, app_source, requested_version, immutable_commit, is_required and change_action.

### 4.3 Required field mapping review

The following mapping is the starting reconciliation. It is not evidence that a DT Master serializer already emits these keys.

| NDF payload field | Accepted DT Master source concept | Reconciliation requirement |
|---|---|---|
| schema_version | Candidate request/schema version | Agree exact version and migration policy |
| candidate_id | Deployment Candidate identity | Map to immutable DocType identity; align schema constraints |
| candidate_code | Candidate code/business identifier | Confirm authoritative Master field or remove from NDF required payload |
| candidate_type | Candidate type | Confirm authoritative Master field and allowed values |
| product.id / product.release | Target product and release | Map to canonical NDF product identity/release |
| framework_version | Selected framework/runtime compatibility | Define whether this is a selected exact framework version or a constraint |
| composition_hash | Frozen desired product composition | Define canonicalization and recomputation owner; NDF must independently recompute |
| applications[] | Selected app_id/release/descriptor digests | Map every field to accepted Master candidate application rows and immutable NDF descriptor identities |
| optional_capabilities | Requested optional capabilities | Map to canonical manifest-relative capability identifiers |
| runtime_profile | Selected runtime profile | Distinguish product image runtime from DT Master Host/Docker deployment runtime |
| runtime_constraints | Supported runtime constraints | Define schema, allowed keys and intersection semantics |
| target_platforms | Approved platform targets | Map to explicit supported OCI platforms |
| approved_build_parameters | Approved build parameters | Define allowlist; values cannot become commands or arbitrary workflow inputs |
| provenance_refs | Source/provenance references | Define allowed reference types and immutable identity requirements |
| base_deployment | Existing optional NDF field | Confirm whether this is a Master-owned deployment reference, an NDF compatibility input, or should be removed |

Before production dispatch, every required NDF field must have one authoritative Master source or a documented deterministic derivation. No value may be fabricated by the NDF adapter. Fields with no accepted Master source must not remain mandatory merely for convenience.

### 4.4 Candidate identity and schema constraints

The current candidate payload schema limits candidate_id to 140 characters and applies a character pattern. The candidate-origin predicate schema currently permits up to 200 characters and does not apply the same pattern. These constraints must be reconciled so the payload, OCI annotations, predicate, dispatch envelope and Master record all identify the same candidate without truncation or normalization.

The exact limit and pattern are an open contract decision pending comparison with the authoritative DT Master naming/serialization rules. Do not silently truncate, case-fold or rewrite candidate IDs.

## 5. Dispatch envelope and authorization

The NDF entry workflow accepts the existing M4.2.7 envelope:

| Field | Meaning |
|---|---|
| `candidate_id` | Exact DT Master candidate identity |
| `candidate_artifact_ref` | Fully qualified digest-pinned OCI reference |
| `candidate_payload_sha256` | SHA-256 of exact serialized candidate JSON bytes |
| `correlation_id` | Shared cross-repository correlation identifier; optional only where the accepted operation contract permits it |

The envelope values are untrusted input. NDF must validate the actual GitHub dispatch actor/repository/event context and require the configured DT Master GitHub App actor. Candidate ID or correlation ID is not authentication.

The actual GitHub App actor identity must be configured from the installed application. No developer identity, synthetic actor or relaxed gate is permitted.

DT Master owns request idempotency and candidate lifecycle. NDF creates a distinct result for each GitHub run ID and run attempt; it does not promise exactly-once dispatch. Repeated dispatches/retries must be reconciled by DT Master using candidate/request identity, correlation ID and NDF run/attempt identity.

## 6. Candidate OCI transport proposal

The existing NDF consumer proposal uses:

- private GHCR package: `ghcr.io/ndftechlabs/dt-master-deployment-candidates`;
- OCI manifest artifact type: `application/vnd.ndf.deployment-candidate.v1`;
- exactly one uncompressed UTF-8 JSON layer named `deployment-candidate.json`;
- layer media type: `application/vnd.ndf.deployment-candidate.v1+json`;
- empty OCI config with media type `application/vnd.oci.empty.v1+json` and exact bytes `{}`;
- manifest annotations for candidate ID, schema version and payload SHA-256;
- immutable reference form `ghcr.io/ndftechlabs/dt-master-deployment-candidates@sha256:<64 lowercase hex>`.

The OCI manifest digest, layer descriptor digest/size and authenticated payload SHA-256 are distinct checks. Because the agreed layer is a single uncompressed JSON file, its layer digest and payload SHA-256 must identify the same bytes.

**Adoption status:** M4.1 requires an immutable candidate artifact reference/digest and signed candidate-origin evidence; it does not mandate GHCR, ORAS or this exact manifest layout. This detailed transport is the existing NDF proposal. DT Master must explicitly accept it before implementing its producer or enabling production dispatch. M4.2 may implement and test the NDF consumer against deterministic fixtures without claiming producer interoperability.

NDF accepts only the exact approved registry/package and digest-pinned reference. No tag fallback, alternate registry, extra layer, wrapped payload, unexpected file, or caller-supplied digest substitution is permitted.

## 7. Candidate-origin attestation

DT Master is the producer and signer. NDF is the independent verifier.

- Predicate type: `https://ndftechlabs.com/attestations/deployment-candidate/v1`
- Schema: `images/ndf/schemas/deployment-candidate-origin-predicate-v1.schema.json`
- Statement subject: exact candidate OCI repository and manifest digest.

The existing predicate schema requires:

- schema_version;
- candidate_id;
- candidate_artifact.repository and candidate_artifact.digest;
- candidate_payload_sha256;
- producer.repository;
- producer.workflow_path, producer.workflow_ref and producer.source_commit;
- workflow_run.run_id and workflow_run.run_attempt;
- correlation_id, or explicit null where the accepted request has no correlation ID.

The producer's attestation must bind the exact artifact subject and the exact payload bytes. NDF recomputes payload SHA-256 after retrieval and compares it with the dispatch envelope, OCI layer descriptor, manifest annotation and signed predicate. All values must agree.

NDF independently verifies:
1. exact immutable OCI subject digest;
2. Cosign signature and Sigstore trusted root;
3. exact GitHub Actions OIDC issuer;
4. exact DT Master certificate identity and approved workflow/ref constraints;
5. Rekor transparency evidence;
6. in-toto Statement and candidate-origin predicate type/schema;
7. candidate ID, producer/run identity and correlation claims;
8. exact OCI manifest/config/layer layout;
9. exact layer bytes, size and SHA-256;
10. candidate schema, semantic invariants and composition hash.

The producer workflow path/ref and certificate identity must be frozen only after the actual M4.4 producer implementation is reviewed and a live certificate observation is captured. No wildcard identity or regex fallback may be used.

The predicate type/schema URLs are identifiers for the versioned contract. Their existence in source does not establish that the public URLs currently resolve.

## 8. NDF image and PDD trust chain

After candidate-origin verification and candidate-to-lock adaptation:

1. NDF builds the image from the accepted immutable NDF composition/lock inputs.
2. NDF validates the actual image digest, installed source inventory, composition and required evidence.
3. NDF signs the exact NDF-produced image digest and publishes its SLSA provenance attestation.
4. NDF independently verifies the image signature, signer, transparency evidence, provenance subject and required claims under the candidate-workflow identity policy.
5. NDF generates the PDD bound to that exact image digest and verified evidence.
6. NDF publishes the PDD OCI artifact, signs its exact OCI digest and publishes the PDD-to-image-binding attestation.
7. NDF independently verifies the PDD signature, signer, transparency evidence, binding predicate and source image provenance correlation.
8. NDF emits terminal result only after required stages complete and their outputs are cross-checked.

The candidate artifact remains DT Master-owned throughout. NDF signs only the image/PDD artifacts it produces.

The trust result must distinguish cryptographic verification from policy authorization. While the relevant signer identity policy remains provisional, a cryptographically valid signature may still yield a rejected trust decision with `IDENTITY_POLICY_PROVISIONAL`. This is not a trusted result and must not permit promotion or deployment.

## 9. Correlated result and record ownership

### 9.1 Existing NDF result v1

The current NDF result identifies:
- result ID derived from NDF run ID and run attempt;
- candidate ID, immutable candidate OCI reference/digest and exact payload SHA-256;
- optional shared correlation ID;
- NDF repository, workflow, run ID, run attempt, source commit and run URL;
- terminal status and timestamps;
- composition hash and resolved lock hash;
- immutable image digest/reference;
- immutable PDD reference/digest/content hash;
- provenance reference and sanitized failure code/summary.

The result is attempt-scoped and immutable. A rerun is a new attempt; a new dispatch is a new run. The result artifact is transport evidence, not the authoritative Deployment Build record.

### 9.2 Required trust-result separation

The accepted M4.1 Section 16.7 contract requires three trust outcomes. They must be represented without crossing verifier ownership:

| Trust result | Verifier | Authoritative record/report |
|---|---|---|
| DT Master candidate-origin signature/attestation | NDF | NDF result references immutable NDF candidate-origin verification report |
| NDF image signature and SLSA provenance | DT Master | DT Master Deployment Build stores its independently generated verification report |
| NDF PDD signature and PDD-to-image binding | DT Master | DT Master Deployment Build stores its independently generated verification report |

The NDF result must carry:
- candidate-origin verification decision and stable reason code;
- immutable reference/hash for the NDF candidate-origin verification report;
- immutable image signature/provenance references and NDF-side verification report;
- immutable PDD signature/binding-attestation references and NDF-side verification report;
- exact image/PDD/candidate subject digests to which each report applies.

NDF must not invent or pre-populate DT Master's image/PDD verification decisions. DT Master creates those results after independently verifying the artifacts and persists them in its Deployment Build record. The Master record correlates all three outcomes using candidate ID, request/correlation ID, NDF run/attempt and exact digests.

### 9.3 Versioning

The existing `deployment-build-result-v1.schema.json` uses `additionalProperties: false`; consumers cannot safely receive new trust fields without an explicit versioned contract.

M4.2.8.5 must choose and implement one of:
- a new major result schema version (recommended if trust evidence is part of the terminal result); or
- a separately versioned, digest-bound trust-evidence report referenced by the existing result.

Do not silently add fields to v1 or redefine `succeeded`. The selected model must preserve failed/cancelled results, exact run/attempt identity, no-overwrite behavior, sanitized errors and success-only evidence requirements.

The overall terminal acceptance outcome must not be `succeeded` when required trust policy rejects an artifact. If the underlying build completed but trust policy rejected it, preserve the successful build-stage fact separately from the non-successful/non-eligible overall result and record the exact trust rejection reason. A successful build result must never be interpreted as deployment authorization.

### 9.4 Retention and reconciliation

DT Master owns the durable Deployment Build record and request idempotency. GitHub workflow run metadata and NDF attempt-scoped result artifacts provide transport/reconciliation evidence. The platform must define the audit-retention period and ensure referenced candidate/image/PDD artifacts and trust reports remain retrievable for that period. The NDF's current 90-day GitHub Actions artifact retention is not automatically the platform's retention policy.

## 10. Failure and adversarial requirements

The NDF consumer must fail closed for:
- missing, malformed, tag-only or wrong-registry candidate references;
- returned OCI manifest digest mismatch;
- wrong artifact type, config, layer count, media type, filename or annotations;
- layer size/digest/payload SHA mismatch;
- invalid UTF-8/JSON, duplicate JSON keys, non-finite values or schema violations;
- candidate ID, correlation, producer repository/workflow/ref/run/attempt mismatch;
- invalid signature, wrong signer, wrong issuer, missing/invalid Rekor evidence or unrecognized predicate;
- unsupported or mutable source descriptors/commits;
- duplicate app identities, unsupported product/framework/platform or composition-hash mismatch;
- unapproved build parameters, secrets, tenant data, site FQDNs, TLS material or arbitrary commands;
- missing/mismatched NDF image or PDD trust evidence;
- provisional or rejected trust policy;
- missing, inconsistent, fabricated or cross-attempt result evidence.

Fixtures prove NDF rejection/acceptance behavior. They do not prove the live DT Master producer exists or interoperates.

## 12. Open items before production dispatch

The following are deliberately unresolved until DT Master producer implementation and review:

1. Exact mapping of NDF payload fields to authoritative Deployment Candidate DocType fields/child rows.
2. Whether `candidate_code`, `candidate_type` and `base_deployment` are authoritative Master fields, derived fields or unnecessary NDF payload requirements.
3. Final candidate ID length/pattern shared by DocType, payload, OCI annotations, predicate and dispatch.
4. DT Master acceptance of the proposed GHCR/ORAS OCI artifact layout and package permission model.
5. Exact DT Master producer workflow path/ref and observed OIDC certificate identity.
6. Actual GitHub App actor identity configured as `NDF_MASTER_DISPATCH_ACTOR`.
7. Platform artifact/evidence retention period and registry deletion protections.
8. Final choice between result schema v2 and a separate versioned trust-evidence report.
9. Exact immutable report transport/reference format for the NDF and Master verification reports.

These are contract adoption/implementation gates, not permission to weaken verification or change M4.1 ownership.
