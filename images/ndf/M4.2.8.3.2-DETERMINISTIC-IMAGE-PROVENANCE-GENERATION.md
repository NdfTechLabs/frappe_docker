# M4.2.8.3.2 — Deterministic Image Provenance Generation

**Repository:** `NdfTechLabs/frappe_docker`
**Branch:** `feat/M4.2.8`
**Status:** Implementation checkpoint; local validation and acceptance pending
**Date:** 15 November 2026
**Depends on:** M4.2.8.2 trust schemas/utilities and M4.2.8.3.1 pinned Cosign CLI contract

## 1. Purpose and boundary

Implement a deterministic generator that derives an image SLSA Provenance v1 predicate from the existing NDF build and verification evidence. It must produce both the predicate JSON consumed by `cosign attest --type slsaprovenance1` and a complete in-toto Statement used for local schema and semantic validation.

This package does not sign artifacts, call Fulcio/Rekor, verify Cosign signatures, modify production workflows, promote images, or change the existing publication gate. Those responsibilities remain in later M4.2.8.3 packages.

## 2. Proposed implementation

Add:

- `images/ndf/scripts/generate_image_provenance.py`
- `images/ndf/tests/test_generate_image_provenance.py`

The generator accepts an existing build-output/evidence directory, product/framework identity, staging and publication references, trusted GitHub Actions workflow context, and explicit output paths. It derives the immutable subject digest from the Buildx and registry build result rather than accepting a caller-supplied digest.

Implemented CLI:

```bash
python images/ndf/scripts/generate_image_provenance.py \\
  --build-output-dir <build-output-dir> \\
  --image-id <image-id> \\
  --framework-major <major> \\
  --candidate-image-ref <staging-image-reference> \\
  --publication-image-ref <publication-image-reference> \\
  --predicate-output <path>/image-provenance-predicate.json \\
  --statement-output <path>/image-provenance-statement.json
```

Workflow metadata is read only from the GitHub Actions environment (`GITHUB_REPOSITORY`, `GITHUB_WORKFLOW_REF`, `GITHUB_REF`, `GITHUB_EVENT_NAME`, `GITHUB_RUN_ID`, `GITHUB_RUN_ATTEMPT`, `GITHUB_SHA`). The generator requires the NDF repository, the exact product-image workflow path `.github/workflows/ndf-publish-product.yml` on `refs/heads/main`, and `workflow_dispatch`. It rejects all other workflow paths; the broader schema path pattern does not replace this runtime allowlist.

Expected outputs:

- `image-provenance-predicate.json` — SLSA Provenance v1 predicate only; passed to Cosign.
- `image-provenance-statement.json` — complete in-toto Statement with the exact image subject; validated locally against `ndf-image-provenance-v1.schema.json`.

Both files must be stable JSON (UTF-8, sorted keys, fixed indentation, trailing newline) and written atomically. The generator must not embed a generated-at timestamp or other nondeterministic value unless a trustworthy source value is explicitly part of the contract.

## 3. Authoritative evidence inputs

The generator must consume and cross-check the existing NDF outputs rather than invent a parallel build record:

- lock-v2 file and its exact SHA-256;
- `build-metadata.json`;
- `buildx-metadata.json`;
- `build-result.json`;
- `build-inventory.json`;
- `build-evidence.json`;
- `source-provenance.json`;
- `source-provenance-verification.json`;
- `source-tree-verification-post-cleanup.json`;
- `source-tree-verification-runtime.json`;
- `image-composition-verification.json`;
- `image-validation.json`;
- `image-verification-evidence.json`;
- the successful `gate_image_publication.py` result.

The generator consumes these exact files and fails closed when any is missing, unsafe, malformed or inconsistent.

## 4. Required cross-checks and claims

At minimum:

1. The subject is the exact immutable image digest confirmed by both Buildx metadata and the registry build result. Reject tags as provenance subjects.
2. The product/image ID, repository, platform, framework version and source commit agree across the relevant build metadata and gate result.
3. Recompute the lock SHA-256 from the actual lock bytes and compare it with every authoritative recorded lock hash.
4. Recompute report/evidence hashes from the exact files. Do not trust a hash merely because it appears inside another JSON report. **`composition_sha256` is SHA-256 over the exact bytes of `image-composition-verification.json`**, which must have `status=passed` and the same lock-v2 hash. This is the adopted composition-hash definition; no canonical reserialization is performed.
5. Require successful image validation, source-provenance verification, source-tree post-cleanup/runtime verification, composition verification and evidence binding. A report must identify the same image digest and lock where its contract requires those bindings.
6. Derive actual source repository revisions from the captured build inventory and source-provenance records. Cross-check repository identity and commit values; do not use requested refs as a substitute for acquired commits.
7. Obtain repository, workflow path, ref, event, run ID, run attempt and source commit from the actual GitHub Actions runtime context. Validate them against the approved identity policy and the provenance schema. Do not accept caller-supplied arbitrary workflow metadata as trusted context.
8. Require the workflow ref to be `refs/heads/main` for this publication path, consistent with the current schema and trust policy.
9. Include candidate claims only when a valid candidate context is present and independently cross-checked against the prepared candidate input and result/evidence contract. Omit candidate claims for normal product builds.
10. Do not claim builder properties, build parameters, timestamps, or dependency facts that the existing evidence does not support.

The provenance extension must satisfy `images/ndf/schemas/ndf-image-provenance-v1.schema.json`. The SLSA predicate must remain valid SLSA Provenance v1; the NDF extension is not a replacement for the standard predicate fields.

## 5. Determinism and failure behavior

- Identical validated inputs and identical workflow context must produce byte-identical output files.
- JSON object key ordering and serialization must be explicit and stable.
- Evidence hashes must be recomputed from bytes.
- Reject duplicate JSON keys, non-finite numbers, malformed digests, mutable references, malformed SHAs, missing reports, failed statuses and cross-file disagreement.
- Never silently repair, normalize away or choose between conflicting evidence.
- Write outputs atomically; on failure, do not leave a partial output that could be signed.
- Do not create a successful provenance statement if any required validation or evidence-binding gate is missing.

## 6. Tests

Focused tests must cover:

- valid product-build evidence produces schema-valid predicate and complete Statement;
- identical inputs produce identical bytes and SHA-256 values;
- exact subject digest mismatch and mutable reference rejection;
- lock hash tampering and mismatch across metadata;
- missing, failed, malformed or altered verification reports;
- source repository/commit disagreement;
- workflow repository/path/ref/event/run/attempt/source-commit mismatch;
- platform/product/framework disagreement;
- candidate claims omitted for product builds and included only for fully validated candidate context;
- atomic output behavior and no partial files after failure;
- rejection of unsupported or fabricated claims.

The tests must use synthetic fixtures with explicit provenance and must not claim live signing or registry trust.

## 7. Acceptance criteria

M4.2.8.3.2 is accepted only when:

- the generator emits both required files from the existing evidence contract;
- the complete Statement validates against the existing NDF image-provenance schema;
- the predicate is exactly the SLSA Provenance v1 predicate expected by the pinned Cosign CLI;
- all digest, lock, source, workflow and validation cross-checks are enforced;
- deterministic byte-for-byte output is demonstrated;
- adversarial/mutation tests reject invalid evidence;
- focused tests, full NDF regression, compileall, pre-commit and `git diff --check` pass.

## 8. Implementation checkpoint (15 November 2026)

- Added `images/ndf/scripts/generate_image_provenance.py` and focused tests in `images/ndf/tests/test_generate_image_provenance.py`.
- The generator derives the exact image subject from `build-result.json` and `buildx-metadata.json`, then independently reruns `verify_publication_candidate` and requires exact equality with the stored `publication-gate.json` result.

- Source revisions are derived from the build inventory and cross-checked against both source-provenance capture and independent source-provenance verification. Requested refs are not used as acquired revisions.
- It emits the SLSA predicate separately from the complete in-toto Statement and validates the Statement against the existing NDF schema.
- The adopted `composition_sha256` definition is the SHA-256 of exact `image-composition-verification.json` bytes.
- No production workflow, publication gate, trust schema or existing provenance schema was changed.
