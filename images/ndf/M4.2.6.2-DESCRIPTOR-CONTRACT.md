# M4.2.6.2 — Product Deployment Descriptor Contract

**Status:** Schema and contract finalized for implementation
**Schema:** `product-deployment-descriptor-v1.schema.json`
**Schema version:** `1.0.0`
**JSON Schema dialect:** Draft 2020-12
**Owner:** NDF Frappe Docker
**Consumer:** DT Master

## 1. Contract principles

The PDD separates three classes of information:

1. **Evidence-backed facts:** exact OCI image digest and platform, build identity, composition lock, actual application commits, measured runtime inventory, and references to M4.2.5 verification evidence.
2. **Explicit product requirements:** services, storage, networking, configuration, health/readiness, operations and infrastructure requirements only where authoritative product declarations exist.
3. **Environment-owned allocations:** concrete node paths, host ports, volumes, endpoints, secret references and other deployment-instance bindings are supplied by DT Master. They are not PDD product facts.

NDF owns this schema and its generation/validation semantics. DT Master consumes the published descriptor and applies only its separately governed deployment allocations. DT Tenant is not a PDD consumer.

## 2. Evidence-state semantics

Every requirement domain uses one of three states:

| State          | Contract meaning                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `not_declared` | No authoritative declaration is present. This is unknown/not specified, not proof that no requirement exists.                    |
| `declared`     | An authoritative declaration exists, but the PDD does not claim independent verification of that requirement.                    |
| `verified`     | One or more declarations exist and the stated claims have supporting verification evidence. Verification scope must be explicit. |

Schema validation checks the structure of these states. The independent PDD validator in M4.2.6.4 must additionally verify declaration references, hashes, evidence bindings and cross-field consistency. A structurally valid PDD is not, by itself, a deployability approval.

## 3. Top-level contract

- `schema_version`: exact PDD schema version.
- `descriptor_type`: fixed identifier `ndf.product-deployment`.
- `descriptor_id`: deterministic identity derived from product ID, platform and exact image digest. It is not a content hash.
- `product`: manifest product ID/name; release is included only when explicitly declared by an authoritative source. A tag or Git ref must never be promoted to a semantic release.
- `artifact`: repository, immutable OCI digest and target platform. Tags are informational only.
- `build`: source repository/commit, workflow run identity and build timestamp; build commit is distinct from application commits.
- `composition`: lock-v2 identity, actual app source identities, selected service/external requirement identities and the independent composition verification reference.
- `runtime_inventory`: exact measured inventory and an explicit scope. Current build inventory is builder-stage evidence; it must not be described as final runtime inventory.
- `requirements`: declared product requirements, independently separated from environment allocations.
- `evidence`: the exact eleven-file M4.2.5 evidence set, with path, SHA-256 and byte size.
- `integrity`: canonical descriptor content digest using NDF JSON Canonicalization v1. The `integrity.content_sha256` field is excluded from its own digest calculation.

## 4. Requirement domains

The schema defines these domains:

- `services`
- `storage`
- `networking`
- `configuration`
- `health_readiness`
- `operations`
- `infrastructure`

A domain marked `not_declared` must have empty declaration and verification arrays. A domain marked `declared` must have at least one authoritative declaration. A domain marked `verified` must have both declarations and verification evidence.

The first version does not invent Compose commands, entrypoints, health checks, storage mounts, retention policies, host ports, ingress routes, resource sizing, backup/restore procedures or capacity requirements. If those facts are needed for a deployable product, their authoritative declaration is a prerequisite to claiming that requirement domain is complete.

## 5. Application and service classification

Bench applications remain separate from independently distributed container services and external requirements.

Application records carry the exact actual Git commit, repository and requested ref. The actual commit is the immutable source identity; the requested ref is retained as provenance only.

Container service records identify the service descriptor and its digest, immutable image reference when declared, and dependency identities. They do not claim a complete runnable topology unless the source descriptor is extended with authoritative execution semantics and the corresponding evidence.

External requirement records identify provider and requirement, not concrete endpoints or credentials. Endpoint allocation belongs to DT Master.

## 6. Environment allocation boundary

The PDD must not contain:

- node-specific filesystem paths or concrete volume names;
- allocated host ports, tenant FQDNs, ingress bindings or concrete endpoints;
- secret values, credentials, private keys or tenant secret references;
- tenant database/site state or customer data;
- arbitrary shell commands or unreviewed executable hooks.

A later consumer contract may define an explicit allowlist for deployment overrides. An override cannot change image digest, application composition, service identity, immutable service artifact or other PDD product facts.

## 7. Identity, integrity and versioning

- The artifact identity is the OCI repository + digest + platform tuple. Mutable tags never establish identity.
- `descriptor_id` is deterministic from product ID, platform and image digest. A changed image digest therefore produces a new descriptor identity.
- `integrity.content_sha256` is SHA-256 over **NDF-JSON-CANONICAL-V1**: UTF-8 JSON, recursively sorted object keys, compact separators (no insignificant whitespace), non-ASCII characters preserved, and floating-point values prohibited. Only `integrity.content_sha256` is omitted from the digest input. This is an explicitly versioned NDF canonicalization profile; it is not a claim of RFC 8785 conformance. Non-finite JSON numbers are rejected. This avoids a self-referential hash.
- Schema changes that break field meaning, requiredness or validation semantics require a new major schema version and schema ID. Backward-compatible additive optional fields may use a minor version. Corrections that do not change the contract may use a patch version.
- Consumers must reject unknown major schema versions and must not silently ignore unknown immutable product facts.

## 8. Explicit evidence limitations at schema finalization

The current NDF evidence supports image digest, lock identity, source provenance, source-tree verification, application inventory, composition verification and builder-stage runtime inventory. The current service descriptor supports service kind, artifact/provider identity and dependency relationships, but not a complete executable deployment topology.

No authoritative declarations were identified for product storage, networking, health/readiness, operational procedures or infrastructure capacity. These domains therefore remain representable as `not_declared`; this is a transparent evidence gap, not an assertion that the product needs none.

## 9. Handoff to subsequent steps

- **M4.2.6.3:** generate the PDD only from the exact verified image and evidence bundle.
- **M4.2.6.4:** independently validate schema, identity derivation, references, evidence hashes, requirement-state semantics and cross-field consistency.
- **M4.2.6.5:** bind descriptor, image digest, lock-v2 and M4.2.5 evidence.
- **M4.2.6.6:** define immutable publication and consumer retrieval.
- **M4.2.6.7:** add representative positive/negative fixtures and update acceptance evidence.

Signing/attestation remains M4.2.8; candidate-driven CI remains M4.2.7; DT Master orchestration remains M4.3+.

## 10. M4.2.6.3 generator input contract

The generator consumes one completed build-output directory. It requires the generated lock-v2, build metadata, Buildx metadata/result, build inventory, build-evidence record, source provenance and independent verification reports, image-composition report, image-validation report, image-verification-evidence binding and a ready publication-gate report.

The generator does not resolve refs, rebuild images, inspect mutable tags or infer runtime state. It verifies the exact eleven-file M4.2.5 evidence bundle using the existing evidence binder, checks the image/lock/inventory digest relationships, and cross-checks actual application commits against source provenance and service inventories against composition verification.

The build source commit, workflow run ID and timezone-qualified build completion timestamp are explicit generator inputs. They are not fabricated from product tags or application commits. The timestamp is mandatory because the current build metadata does not record a trustworthy build completion time.

The current inventory is explicitly emitted with `runtime_inventory.scope = builder_stage`. A final-runtime inventory is not claimed by the generator.

The generated descriptor is written atomically and validated against the authoritative PDD schema before publication. The generator emits no environment-specific allocation values.
