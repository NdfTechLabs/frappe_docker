## 1. Purpose

Define the package-resolution contract used by the existing NDF composition resolver to resolve Python, Node and OS package dependencies into exact, provenance-bearing selections.

This contract extends the existing resolver. It does not introduce a parallel manifest resolver, dependency manager, image builder or deployment system.

The contract establishes:

- The boundary between composition inputs and resolved package outputs.
- A common adapter interface for Python, Node and OS package managers.
- Target-runtime and repository-source requirements.
- Package selection, dependency-graph and provenance records.
- Lock generation and offline lock-validation behaviour.
- Isolation, security and deterministic-resolution requirements.
- The boundary between package resolution and rolling-branch Bench application acquisition.

## 2. Governing architecture

### 2.1 Two independent resolution responsibilities

NDF must preserve two distinct processes:

| Responsibility | Input | Output | Owner |
| --- | --- | --- | --- |
| Application source selection | Product/capability manifest and Marketplace App Descriptor | Requested Git reference and resolver-time reference provenance | Existing composition resolver |
| Package dependency resolution | Descriptor package dependencies, target runtime and approved package-source policy | Exact package selections, dependency closure and package provenance | Package Resolution Coordinator and native adapters |

Package resolution must not change application source selection.

### 2.2 Rolling application references are preserved

NDF product manifests define application source references using rolling branches by default. Image construction honours those references.

For example, if the composition requests `develop`:

- The requested reference remains `develop`.
- M4.2.3 may record a resolver-time SHA as reference provenance.
- The resolver-time SHA must not replace `develop` in Bench acquisition inputs.
- M4.2.4 continues to use the requested branch through the existing upstream Bench acquisition path.
- M4.2.4 captures the actual Git commit checked out for each application and Frappe after acquisition.
- M4.2.5 verifies the acquired revisions against the build inventory.

The SHA recorded during M4.2.3 is not evidence that the same SHA was installed. The actual acquired SHA is build provenance captured after acquisition.

Package versions are resolved independently of application Git references. A moving application branch does not implicitly select or pin a Python, Node or OS package version.

### 2.3 Existing resolver remains authoritative

The existing `ManifestLoader`, descriptor validation, composition graph, lock generation and lock validation remain the orchestration path.

The package layer is a subordinate resolution service invoked by the existing resolver after selected descriptors and optional dependencies have been determined.

It must not:

- Create another composition or manifest resolver.
- Acquire Bench application source repositories.
- Replace requested rolling branches with commit SHAs.
- Install applications into a running Bench.
- Build, publish or deploy OCI images.
- Install packages into the CI runner, developer workstation or production runtime.
- Execute publisher-provided commands or hooks.

## 3. Resolution inputs and outputs

### 3.1 Inputs

The package-resolution request is constructed from:

1. The selected Marketplace App Descriptors in the resolved composition graph.
2. Required package dependencies and explicitly selected optional package dependencies.
3. Each dependency's ecosystem, package identity, version policy, version constraint, disposition and scope.
4. The exact target runtime/platform matrix.
5. An NDF-approved package-source profile.
6. The approved native resolver implementation and version.
7. A trusted base-runtime package inventory for dependencies classified as `base`.

The product composition declares requirements and target intent. It must not supply fabricated resolution results.

### 3.2 Resolution output

Native adapters return exact package selections and dependency edges. The coordinator normalizes these results and passes them to the existing lock-generation path.

The current `target_runtime.package_versions` field is therefore a transitional input representation, not the long-term authority for selected package versions. The target runtime belongs in composition inputs; resolved package selections belong in the generated lock.

The package-resolution representation is an approved additive extension to the existing composition lock v2. Existing v2 fields retain their current meanings. The extension is defined by its own `package_resolution.schema_version`; it does not increment `lock_version`. Legacy v2 locks without this section follow the compatibility and migration rules in §10.4.

### 3.3 No unresolved ranges in a resolved lock

A resolved lock must never represent a range such as `>=2,<3` as though it were an installed package version.

It must record the exact selected version, the request/constraint that produced it, the resolver and source provenance, and the dependency edges needed to understand the selected closure.

If an exact candidate cannot be resolved, resolution fails closed.

## 4. Target runtime and platform contract

Resolution is performed for the declared target, never implicitly for the CI runner's host environment. The target-runtime input describes the image/platform that will run the Bench. The builder image is recorded separately because source/build tooling may need to be compatible with it; builder-only packages must not be treated as runtime packages.

### 4.1 Required target identity

A concrete candidate target records:

| Area | Required identity |
| --- | --- |
| OCI platform | Operating system and architecture, for example `linux/amd64` |
| Builder image | Source reference, OCI index digest when applicable, platform-specific manifest digest and selected platform |
| Runtime/base image | Source reference, OCI index digest when applicable, platform-specific manifest digest and selected platform |
| Operating system | Distribution family, `ID`, `VERSION_ID`, codename, architecture, libc implementation/version and package-manager name/version |
| Python | Exact version, implementation, cache tag, SOABI, platform tag and executable identity/build metadata |
| Node | Exact Node version, npm version, platform, architecture, modules ABI and Node-API version |
| Frappe/ERPNext | Existing exact compatibility version fields; these remain distinct from image/runtime identity |
| Package source | NDF-approved source-profile identity is supplied to the resolver request, not inferred from the target's public image metadata |

The current compatibility fields `target_runtime.frappe`, `target_runtime.erpnext`, `target_runtime.python` and `target_runtime.node` retain their existing string/version semantics. The additional metadata is additive and must not replace or reinterpret those fields.

### 4.2 Target-runtime request representation

The v2 composition target-runtime object retains the existing compatibility fields and adds these structured fields:

- `platform`: `os` and `architecture` identifying the OCI target platform.
- `images.builder` and `images.runtime`: each records the descriptive source reference, immutable platform-specific manifest digest, optional index digest and platform.
- `os`: retains `distribution_family` and the existing string `package_manager`; adds distribution `id`, `pretty_name`, `version_id`, `codename`, `architecture`, package-manager version, package-database name/version and `libc` implementation/version.
- Python metadata: `python_implementation`, `python_cache_tag`, `python_soabi`, `python_platform`, `python_executable`, and `python_build`.
- Node metadata: `npm`, `node_platform`, `node_architecture`, `node_abi`, `node_api`, and `node_executable`.

The exact field names and types are part of the versioned request contract and are declared in `application-manifest-v2.schema.json`. These additive fields remain optional at composition-schema read time to preserve existing v2 manifest compatibility; a package-resolution candidate must nevertheless fail closed unless all fields required for its selected ecosystem and target are present. A.5 fixtures will verify both schema compatibility and request-level completeness. The existing `target_runtime.package_versions` remains transitional input only; it is not the authoritative location for resolved package selections.

### 4.3 Evidence-backed initial target

The accepted RT-01 evidence establishes the AMD64 baseline for the exact inspected builder/runtime digests: Debian GNU/Linux 13.7 (Trixie), CPython 3.14.10, Node.js 24.22.2, npm 11.19.1, glibc 2.41, APT 3.0.4 and dpkg 1.22.22. The exact OCI digests and ABI/platform values are recorded in the authoritative target-runtime matrix.

RT-01 acceptance applies only to those inspected AMD64 digests. ARM64 remains conditional pending NDF build, image-validation and adapter testing. A new digest requires fresh runtime capture even when its mutable tag is unchanged.

Do not infer missing target details. If a selected package requires an attribute absent from the target, resolution fails with a precise diagnostic. Only operating-system and package-manager combinations supported by NDF product images and later adapter tests may be enabled.

## 5. Adapter execution model

All adapters implement one normalized interface. Their execution environments may differ by ecosystem.

### 5.1 Hybrid execution

| Adapter | Execution environment | Required behaviour |
| --- | --- | --- |
| Python | Isolated temporary environment on the CI runner | Resolve against explicit Python version, implementation, ABI, OS/platform and architecture parameters |
| Node | Isolated temporary environment on the CI runner | Resolve against explicit Node version, OS, CPU architecture and libc/platform parameters where applicable |
| OS | Disposable target-specific environment | Run the native package manager against repositories for the exact target distribution and architecture |

Python and Node adapters must not inherit the runner's Python/Node version, platform tags, global packages, package configuration or credentials as implicit resolution inputs.

OS resolution must not query the CI runner's host repositories when the target image uses another distribution or release. It must execute in a disposable environment matching the target distribution and architecture.

No adapter may install packages into the host runner or an existing Bench. Resolution environments are temporary and disposable.

### 5.2 Initial native resolver implementations

The adapter registry is NDF-owned and versioned.

Initial approved implementation candidates:

| Ecosystem | Native resolver | Notes |
| --- | --- | --- |
| Python | `uv` 0.13.7 (exact NDF policy pin; no implicit fallback) | PEP 440; explicit target Python/platform selection; lock records exact resolver version |
| Node | `npm` initially; `yarn` or `pnpm` only when explicitly enabled and tested | npm-compatible SemVer; explicit target OS/CPU/libc and Node engine context |
| Debian-family OS | `apt` tooling | Resolve against target distribution repositories and architecture |
| RPM-family OS | `dnf` tooling | Resolve against target distribution repositories and architecture |
| Alpine | `apk` tooling | Only after a target-specific adapter and acceptance tests exist |

An adapter must not silently substitute a different resolver. The lock records the exact resolver name and version used.

The initial production support matrix must be limited to combinations covered by integration tests and used by NDF's supported product image targets. Unsupported combinations fail closed.

## 6. Package selection policy

### 6.1 `constraint`

- A declared version constraint is mandatory.
- Candidate selection is performed only by the relevant native package-resolution adapter.
- The selected exact version is checked using ecosystem-native comparison semantics:
  - Python: PEP 440 through the Python packaging implementation.
  - Node: npm-compatible SemVer through the npm SemVer implementation.
  - Debian OS packages: dpkg-compatible version ordering through the native `dpkg --compare-versions` command.
- Debian constraints accept a bare exact version or one Debian relation using `<<`, `<=`, `=`, `>=` or `>>`, followed by one version operand. Bare versions mean exact equality. Unsupported or malformed relation syntax fails closed.
- Debian comparison must preserve epoch, upstream-version, Debian-revision, tilde and numeric-component ordering. It must not use lexical string comparison or an approximate Python implementation.
- The offline comparator validates recorded selections and dependency edges only. It must not contact repositories, inspect available candidates, update package indexes or perform dependency resolution.
- Every incoming constraint for the same normalized package identity must be satisfied by the same selected version.
- An empty intersection or unavailable candidate fails resolution.
- The exact selected version is written to the lock.

### 6.2 `latest_compatible`

- No explicit version string may be supplied with this policy.
- The native resolver selects the latest candidate it can establish as compatible with the declared target and approved source profile at resolution time.
- The exact selected version and the candidate-selection context are recorded in the lock.
- It is a resolution-time policy, not a floating instruction to image construction.
- A later candidate may resolve a newer version and therefore produce a different lock.

### 6.3 Base dependencies

- Base dependencies must use an explicit fixed version constraint; `latest_compatible` is not permitted.
- The selected version is verified against a trusted inventory of the approved base runtime/image.
- Base dependencies are not scheduled for installation.
- If the base inventory is unavailable, untrusted or does not contain the required package/version, resolution fails. The resolver must not assume that a package exists because it is commonly included in an image.
- The base inventory identity must be retained as provenance and checked against the actual base image during image construction/verification.

### 6.4 Runtime-compatible dependencies

- Resolve to exact versions for the target runtime/platform.
- Record them as controlled image-build inputs.
- The image builder installs them only through the approved build process.
- They must not change the declared OS family, OS ABI, Python interpreter/ABI, Node runtime, system toolchain or other target-runtime contract.

### 6.5 Environment-level dependencies

- Resolve package identity/version only where doing so helps identify the required environment change.
- Mark the composition as requiring a changed image/runtime contract.
- Do not present the current target as production-ready if the dependency cannot be satisfied within that target contract.
- Do not inject these dependencies into a running Bench or silently expand the current runtime contract.
- A revised target/base-image contract and a new candidate resolution are required before image construction can proceed.

## 7. Dependency graph and normalization

### 7.1 Graph closure

Adapters must resolve the transitive package dependency closure for the selected direct package requirements, subject to the selected target and source profile.

The normalized graph must distinguish:

- Direct dependencies declared by Marketplace App Descriptors.
- Transitive dependencies introduced by native package resolution.
- Dependency edges and the package that introduced each edge.
- Optional dependencies that were explicitly selected.
- Dependencies classified as base, runtime-compatible or environment-level.

A package shared by multiple applications is one selected package node for the same ecosystem and normalized package identity. Its selected version must satisfy every incoming constraint and target requirement.

### 7.2 Ecosystem-specific identity

Package identities must be normalized according to ecosystem rules, not by a generic lowercase transformation:

- Python: canonical project-name normalization consistent with Python package-index conventions.
- Node: npm package identity rules, including scoped package names.
- OS: distribution/package-manager-specific identity; package names and architectures must remain distinct where the native package manager treats them as distinct.

The same textual package name in different ecosystems represents different package identities.

### 7.3 Dependency conflicts

Fail closed on:

- Unsatisfied or contradictory constraints.
- Missing package candidates.
- Missing transitive dependencies.
- Unsupported target/runtime/platform combinations.
- Ambiguous package source selection.
- Repository metadata that cannot establish a trustworthy exact candidate.
- Inconsistent package identity or dependency graph results.
- A base dependency that is absent or has the wrong installed version.

## 8. Normalized adapter interface

The concrete Python classes and function names are implementation choices, but every adapter must satisfy the following logical contract.

### 8.1 Resolution request

A request contains:

- `ecosystem`
- `target`: exact ecosystem-relevant runtime/platform target
- `requirements`: normalized direct package requirements, including identity, version policy, constraint, required/optional selection, disposition and scope
- `source_profile`: identifier of an NDF-approved registry/repository profile
- `resolver_policy`: approved resolver name/version and resolution options
- `base_inventory`: trusted package inventory reference when base dependencies are present
- `resolution_context`: candidate ID and policy/provenance context

The request must not contain arbitrary publisher-supplied shell commands or executable hooks.

### 8.2 Resolution result

A result contains:

- Ecosystem and exact target identity.
- Resolver name and exact resolver version.
- Approved source/repository profile identity.
- Exact selected package records.
- Direct/transitive classification.
- Requested constraint or version-selection policy.
- Dependency edges.
- Artifact hashes/integrity metadata when provided by the ecosystem.
- Repository snapshot/metadata identity where available.
- Base/runtime/environment-level disposition and installation decision.
- Structured warnings and errors.

A successful result contains no unresolved package requirement.

### 8.3 Failure result

Adapters return structured, actionable failures, including at least:

- Unsupported target.
- Unsupported package manager or resolver.
- Invalid requirement/constraint.
- No candidate satisfying the request.
- Conflicting constraints.
- Repository unavailable or untrusted.
- Missing/incomplete repository metadata.
- Unresolvable transitive dependency.
- Timeout/resource limit.
- Integrity/hash verification failure.

A failed adapter must not return a partial result that the coordinator treats as a complete resolution.

## 9. Package source and repository policy

Package sources are governed by NDF policy, not arbitrary publisher input.

- The composition may select an NDF-approved source profile by identifier.
- The profile defines permitted registries/repositories, trust requirements, mirror/snapshot configuration and credentials policy.
- Descriptor-level Python source metadata is a requested source hint, not permission to access an arbitrary endpoint. It must be checked against the approved source policy.
- Node registry and OS repository configuration are supplied by approved NDF profiles.
- Credentials are injected from protected CI secrets at execution time.
- Credentials must never appear in descriptors, manifests, lock files, logs or error messages.
- Repository URLs with embedded credentials are rejected.
- Unapproved repositories, redirects or source substitutions fail closed.

Where repository snapshot identifiers are available, they must be recorded. Where an ecosystem does not provide immutable repository snapshots, the lock must record the exact selected versions, artifact hashes where available, source identity and resolver metadata. The system must not claim stronger repository reproducibility than the source ecosystem can provide.

## 10. Lock integration and validation

The existing composition lock remains the single authoritative lock for application, service and package composition. Do not create a separate package lock that can drift from it.

### 10.0.1 Lock v2 package-resolution extension — accepted

The platform owner approved retaining `lock_version: 2` and adding one top-level `package_resolution` object. The extension has its own `schema_version`; it does not change the meaning of existing lock v2 fields.

The section is authoritative for the normalized package graph. Existing per-application `package_dependencies` remain the descriptor-level direct package selection/provenance records. They are inputs against which the normalized graph is validated; they are not the transitive graph and must not be treated as a second graph authority.

### 10.0.2 Top-level structure

A package-resolution-complete lock uses this structure:

```json
{
  "lock_version": 2,
  "target_runtime": {},
  "applications": [
    {
      "name": "example_app",
      "app_id": "example_app",
      "package_dependencies": []
    }
  ],
  "package_resolution": {
    "schema_version": 1,
    "source_policy_catalogue_version": "1.0.0",
    "source_profiles": [],
    "base_inventory": null,
    "packages": [],
    "dependency_edges": []
  }
}
```

This is a structural illustration, not a populated lock or a replacement for the full composition lock. The top-level `target_runtime` remains the authoritative target identity for the entire lock; it is not duplicated inside `package_resolution`. A package-resolution record is valid only for that exact target.

### 10.0.3 Package identity and package records

Every entry in `packages` represents one selected package instance at one exact version. The same package name may therefore appear more than once when the ecosystem legitimately permits multiple installed instances, notably Node dependency trees.

Each package record has these fields:

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | Yes | Stable package-instance key derived from ecosystem, normalized name, exact version and architecture where applicable. |
| `ecosystem` | Yes | `python`, `node` or `os`. |
| `name` | Yes | Ecosystem-normalized package name. |
| `version` | Yes | Exact selected version in the ecosystem's native version representation. |
| `architecture` | OS only | Native package architecture; required for OS package identity, including values such as `amd64` or `all`. |
| `source_profile` | Yes | Identifier of the enabled NDF source profile used. |
| `source` | Yes | Effective registry/repository identity from that profile; never a publisher-controlled arbitrary URL. |
| `resolver` | Yes | Native resolver name. |
| `resolver_version` | Yes | Exact resolver executable version. |
| `direct` | Yes | True when selected to satisfy at least one descriptor-level direct requirement; false when introduced only transitively. |
| `requested_by` | Yes | Sorted, unique Marketplace App Descriptor `app_id` values that directly requested this package instance; empty for purely transitive instances. |
| `disposition` | Yes | Effective disposition: `base`, `runtime_compatible` or `environment_level`. |
| `install` | Yes | Whether the image build must install this package. Must agree with disposition and base-inventory evidence. |
| `scope` | Yes | Package installation scope, using the descriptor/build policy's defined scope vocabulary. |
| `integrity` | Yes | Array of artifact integrity records; empty only when the approved ecosystem/source provides no artifact hash. |
| `repository_metadata` | Yes | Repository provenance object; records authenticated repository metadata identity/hash for OS packages and the available registry/artifact provenance for Python/Node. |

Package identity rules:

- Python names use canonical project-name normalization consistent with PEP 503: lowercase and replace each run of `-`, `_` or `.` with `-`. Version parsing and comparison use PEP 440.
- Node names use npm package-name rules, including the complete scope for scoped packages. Version parsing and comparison use npm-compatible SemVer.
- OS names retain the target distribution/package-manager identity. The package architecture is part of identity; Debian version comparison uses dpkg-compatible ordering. The offline validator invokes `dpkg --compare-versions` as a comparison primitive only; APT candidate selection and repository resolution remain exclusively with the native APT adapter.
- The stable `id` is the canonical tuple `ecosystem|normalized-name|exact-version|architecture`. The architecture component is an empty string for Python and Node and is mandatory for OS packages. These identity components cannot contain the tuple delimiter.
- Exact version is part of the package-instance identity. This permits distinct Node versions to coexist where npm's dependency tree requires them. It does not permit multiple installed versions of one Python distribution in the same target environment or contradictory selections for the same OS package/architecture.
- The same name in different ecosystems is always a different package identity.

A package record describes the selected instance, not every request that led to it. Direct descriptor requests remain recorded in each application's `package_dependencies`, including the descriptor's `version_policy` and an additive `requested_constraint` field (the exact declared constraint, or null when the policy is `latest_compatible`). OS selections also retain the native resolver-selected `architecture`; this is output provenance, not a publisher-controlled descriptor field. Those per-application records remain authoritative for direct request semantics. `requested_by` links the normalized package instance back to the requesting descriptor identities without copying their constraints or policies into a second source of truth. For a package reached through multiple direct requests, every requesting `app_id` is retained once in sorted order. Transitive relationships and their native constraints are represented by dependency edges, not by inventing a direct requester.

### 10.0.4 Dependency edges

Each `dependency_edges` entry represents one resolved parent-to-dependency relationship and contains:

| Field | Required | Meaning |
| --- | --- | --- |
| `from` | Yes | The `id` of the package instance that declares/requires the dependency. |
| `to` | Yes | The `id` of the exact selected dependency package instance. |
| `constraint` | Yes | The dependency requirement as declared by the parent package metadata, in the ecosystem-native constraint syntax. |

Rules:

- Both endpoints must identify exactly one record in `packages`.
- An edge must point to the exact selected dependency instance that satisfies its constraint.
- Duplicate edges are prohibited.
- The graph must include the complete active dependency closure for the selected target and resolver configuration. Dependencies excluded by platform markers or an unselected optional feature are not active edges.
- Direct descriptor requirements are linked to package nodes through each application's `package_dependencies` and the node's `requested_by`; they are not fabricated as package-to-package edges.
- Dependency cycles are permitted in the native package dependency graph when present in complete output from an approved ecosystem resolver. Package-graph validation still enforces unique package identities/edges, valid endpoints, ecosystem-native constraint satisfaction, resolver/source provenance, integrity metadata and reachability from direct selections. It does not impose DAG semantics on package edges. This exception applies only to package dependency graphs; application/Bench-app, manifest/capability and service-composition cycles remain prohibited and continue to fail closed.
- The same parent may have edges to multiple versions of a Node package when the resolved npm dependency tree requires distinct instances.

### 10.0.5 Source and resolver provenance

`source_policy_catalogue_version` records the exact `catalogue_version` from the NDF package-source profile catalogue used for resolution. `source_profiles` is a sorted, unique array of the profile identifiers actually used by package records. Every package's `source_profile` must appear in that array and resolve to an enabled profile in that catalogue version.

The package record's `source`, `resolver` and `resolver_version` identify the effective source and exact executable used. The resolver must be permitted for the package's ecosystem and source profile. The lock must not contain credentials, credential-bearing URLs, temporary paths or secret-bearing resolver arguments.

`integrity` contains zero or more records with the algorithm and digest for the exact artifact selected/downloaded, plus an artifact identity when the ecosystem exposes one. A hash must never be invented. If the approved source publishes an integrity value, it must be recorded and verified; if it does not, the record must make that absence explicit through an empty array.

`repository_metadata` preserves the strongest available repository provenance. For Debian, it must identify the authenticated Release/InRelease metadata and its hash, together with the repository/profile identity. PyPI and npm profiles do not provide immutable repository snapshots; the lock records exact selected versions, effective source identity and artifact integrity where available, and must not claim snapshot reproducibility.

### 10.0.6 Base inventory reference

`base_inventory` is `null` when no selected OS package has disposition `base`. Python and Node package presence is not established by this A.4 evidence; those ecosystems require their own separately approved native inventory contract.

When one or more OS base packages are present, `base_inventory` is a stage-aware object:

```json
{
  "schema_version": 1,
  "evidence_reference": "images/ndf/inventories/debian-trixie-amd64/<runtime-platform-digest>",
  "manifest_file": "inventory-manifest.json",
  "manifest_sha256": "<64-lowercase-hex>",
  "inventories": {
    "builder": {
      "image_manifest_digest": "sha256:<builder-platform-digest>",
      "platform": "linux/amd64",
      "package_database": "dpkg",
      "package_database_version": "<exact-version>",
      "inventory_file": "builder/dpkg-inventory.tsv",
      "inventory_sha256": "<64-lowercase-hex>",
      "package_count": 408
    },
    "runtime": {
      "image_manifest_digest": "sha256:<runtime-platform-digest>",
      "platform": "linux/amd64",
      "package_database": "dpkg",
      "package_database_version": "<exact-version>",
      "inventory_file": "runtime/dpkg-inventory.tsv",
      "inventory_sha256": "<64-lowercase-hex>",
      "package_count": 286
    }
  }
}
```

The values above are illustrative, not accepted runtime facts. The referenced repository evidence directory contains the versioned inventory manifest and the two sanitized TSV files. The manifest checksum and each TSV checksum are verified offline. The evidence directory is keyed by the runtime platform-specific OCI manifest digest; the builder and runtime inventory entries independently bind their own image manifest digests.

Stage mapping is mandatory for native OS package records:
- `scope: "build"` is checked only against the builder inventory.
- `scope: "runtime"` is checked only against the runtime inventory.

The selected inventory must match the corresponding image's platform-specific digest and platform. An exact dpkg package name, installed version and architecture match is required. Presence in the other stage does not satisfy the dependency. The top-level `target_runtime.images.builder` and `target_runtime.images.runtime` identities must match the respective evidence inventory identities; no second target object is introduced.

Every OS package with disposition `base` must be present in the stage-selected inventory at the exact selected version and architecture. Such a package has `install: false`. A missing, mismatched, wrong-stage or unverifiable base package fails closed. A package with disposition `runtime_compatible` is an image-build installation input. A package with disposition `environment_level` makes the current target ineligible for production image construction until a revised target/base-image contract is resolved.

The evidence is specifically a native Debian dpkg inventory. It does not prove Python distribution or Node package presence. A package declared in either of those ecosystems cannot be classified as `base` using this evidence. An ecosystem-native inventory contract must be separately approved before that classification is supported.

The producer, evidence layout, sanitization requirements and M4.2.4/M4.2.5 handoff are defined in [M4.2.3-A.4 — Base Package Inventory Handoff](M4.2.3-A.4-BASE-INVENTORY-HANDOFF.md).

### 10.0.7 Target binding

The package graph is scoped to the lock's top-level `target_runtime`, including its platform, runtime versions and immutable runtime-image identity. No second target object is stored in `package_resolution`.

Validation must require the target-runtime fields needed by every selected ecosystem and verify that the base inventory refers to the same runtime image/platform. A lock generated for one target cannot be reused for another target, even if the package names and versions happen to match.

### 10.1 Lock validation is not re-resolution

Lock validation must not query live package registries or attempt to choose newer candidates. It validates the recorded result offline against:

- Source manifest and descriptor checksums.
- Selected direct requirements and explicit optional selections.
- Exact top-level target runtime/platform identity.
- Ecosystem-normalized package identities and exact versions.
- Direct request provenance and all incoming constraints, evaluated using the ecosystem-specific comparison interface (PEP 440, npm SemVer or dpkg-compatible Debian ordering).
- Dependency-edge endpoint integrity, constraint satisfaction and complete graph closure.
- Absence of duplicate package-instance IDs and duplicate edges; package dependency cycles are allowed only in complete output from an approved native resolver, while application and service composition cycles remain prohibited by their respective graph validators.
- Approved source-profile catalogue version and profile membership.
- Resolver name/version and source provenance structure.
- Artifact integrity metadata where available.
- Repository metadata identity/hash where required by the source profile.
- Base inventory identity, exact base package selections and architecture.
- Disposition, scope and installation decisions.

The validator must also reconcile each application's direct `package_dependencies` with the normalized package nodes: every direct selection must map to the correct package instance, version, source and resolver provenance; no direct declaration may disappear; and no package node may claim a descriptor requester that did not declare it.

A deliberate re-resolution is a separate operation. It produces a new candidate and a new lock; it does not mutate the meaning of an already validated lock.

### 10.2 Determinism and canonical ordering

The normalized representation is deterministic:

- `packages` are sorted by `id` in ascending bytewise lexical order.
- `dependency_edges` are sorted by `from`, then `to`, then `constraint`, each in ascending bytewise lexical order.
- `source_profiles` are sorted by profile identifier and contain no duplicates.
- `requested_by` is sorted by `app_id` and contains no duplicates.
- Package IDs are unique; edge tuples are unique.
- JSON serialization uses UTF-8, sorted object keys, the repository's existing two-space indentation and one trailing newline.
- Volatile timestamps, temporary paths, credentials, environment-specific cache paths and nondeterministic resolver output order are excluded from the canonical lock content.

Resolution repeatability and lock stability remain distinct. The same requirements, target, resolver version, source profile and repository metadata should produce the same normalized result. Once exact selections are locked, offline validation must not change them or query live registries.

### 10.3 Lock comparison and tamper detection

Lock comparison treats `package_resolution` as one authoritative semantic section and reports a package-resolution change when any of its policy version, source profiles, base inventory identity, package records or dependency edges differ. It must not compare only package names or versions while ignoring provenance, disposition, integrity or target binding.

Validation must reject a modified package record, edge, source profile, resolver identity, integrity value, base inventory identity or install decision when the mutation breaks the contract. Reordering records into a non-canonical representation is also invalid; a canonical lock must not silently normalize tampered input during validation.

### 10.4 Legacy-lock compatibility and migration

Three cases are distinct:

1. **Lock v1:** is unsupported. Validation and lock comparison reject it; it is not a migration input. Product lock artifacts must be generated directly as current lock v2 from current source manifests. No v1-to-v2 conversion path is provided.
2. **Pre-extension lock v2 without `package_resolution`:** remains readable as a legacy composition lock only when all application `package_dependencies` are absent or empty. It is not package-resolution-complete and cannot be used as evidence that external package dependencies were resolved.
3. **Pre-extension lock v2 containing non-empty `package_dependencies` but no `package_resolution`:** may be inspected as migration input, but must be rejected for package-resolution-complete validation/build eligibility with an explicit package-resolution migration-required diagnostic. The direct records cannot be promoted into a complete transitive graph because they contain no authoritative transitive closure.

Every newly generated package-resolution-complete lock uses `lock_version: 2` and includes `package_resolution`, including an empty package list and edge list when the selected composition has no external package dependencies. Migration regenerates the normalized graph from current approved descriptors, target runtime, source profiles and trusted inventory; it must not fabricate transitive dependencies or provenance from legacy direct selections.

Comparison of a legacy v2 lock against a new package-resolution-complete candidate must report the required package-resolution migration. It must not treat a missing section as equivalent to an empty resolved graph.

### 10.5 Failure behaviour

Any incomplete, ambiguous, inconsistent or unverifiable package-resolution record fails closed. The resolver must not write a package-resolution-complete lock when any required package, edge, source, resolver, target, integrity or base-inventory evidence is unresolved.

## 11. Application source package files — explicit boundary

M4.2.3 resolves package requirements declared in the selected Marketplace App Descriptors and other explicit composition inputs.

The descriptor may identify application-local project/lock files (for example, `python_project_file` or `node_lockfile`). However, M4.2.3 does not acquire a rolling application branch or inspect its working tree to read those files. Doing so would create a second source-acquisition operation that could observe a different branch commit from the later image build.

Therefore:

- M4.2.3 must not pretend that it has resolved package declarations it has not inspected.
- Application-local dependency files are consumed only after the requested application branch is acquired by the M4.2.4 build process.
- M4.2.4 must capture the exact acquired source revision and the dependency-file identity/hash used during the build.
- The image build must use the application's declared lockfile/frozen-install behaviour where available; it must not silently perform an unconstrained upgrade.
- M4.2.4/M4.2.5 must record and verify the resulting installed package inventory against the acquired source and build inputs.
- If the application source contains package requirements that are not represented in the M4.2.3 descriptor/composition resolution, the build must report that distinction rather than claiming the M4.2.3 lock covers them.

This boundary preserves rolling-branch acquisition. It also identifies a required M4.2.4/M4.2.5 integration: source-local dependency files and the packages actually installed from them must be captured as build provenance and verified.

If the platform later requires every source-local package to be resolved before image construction, that requires a separately approved source-snapshot handoff. It must not be implemented by silently pinning rolling branches or independently checking out branches in M4.2.3.

## 12. Security and operational requirements

- Use subprocess argument arrays; never interpolate descriptor values into shell commands.
- Validate package identities, constraints, source profiles and target values before invoking an adapter.
- Do not execute publisher-provided hooks or arbitrary build commands during metadata resolution.
- Disable package lifecycle scripts during Node metadata resolution where supported.
- Do not install Python distributions or Node packages merely to discover metadata.
- Python source distributions that require executing an untrusted build backend for metadata must fail closed unless a separately approved, isolated build-metadata policy is implemented.
- Use disposable workspaces and target-specific environments.
- Apply execution timeouts, bounded output, concurrency limits and resource limits.
- Use protected credentials and redact secrets from all output.
- Restrict network access to approved package sources and required metadata endpoints.
- Verify downloaded artifact hashes/signatures where the ecosystem and source provide them.
- Cache only with keys that include ecosystem, target, resolver version, source profile/snapshot and request identity. A cache hit must not weaken integrity validation.
- Unsupported or partially implemented adapters fail closed.
