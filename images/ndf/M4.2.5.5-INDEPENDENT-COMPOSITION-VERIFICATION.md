# M4.2.5.5 — Independent Application and Service Composition Verification

**Status:** Started — design baseline recorded 2026-11-14.
**Parent work package:** M4.2.5 — Image Verification.
**Implementation branch:** `feat/m4.2.5-image-verification`.
**Predecessor:** M4.2.5.4 — Independent Source Verification (accepted).
**Scope:** Independently validate the actual Bench application set and the selected capability, independent-service and external-requirement composition against generated lock-v2.

## 1. Objective

Prove that the final Frappe product image contains exactly the Bench applications authorized by the generated lock-v2, and that the independent services and external requirements declared by the selected product composition remain separate from the Bench application inventory.

The verifier must not treat the resolver's successful lock validation, build metadata or an earlier build-stage report as proof of final image composition. It must independently inspect the source manifest/descriptor records and final runtime image, compare them with the exact generated lock-v2, and fail closed on missing, unexpected, duplicated, cross-category or tampered composition.

## 2. Existing contracts and observations

M4.2.3 already defines the composition model and must remain authoritative:

- `lock-v2.applications`: Bench-installable Frappe applications, including Frappe itself.
- `lock-v2.capabilities`: explicit optional-capability selections, represented by manifest path, required flag and selected flag.
- `lock-v2.services`: independently deployed container-service descriptors.
- `lock-v2.external_requirements`: externally managed service/provider requirements.
- `lock-v2.manifests`: source manifest identities and exact SHA-256 checksums.
- Canonical service descriptors: `images/ndf/descriptors/services/<service-id>.json`.

A service descriptor records `service_id`, `service_kind`, `artifact` or `provider`, `depends_on`, and related runtime/build metadata. Container service artifacts use digest-pinned OCI image references. External requirements carry provider identity and requirement information.

The current `validate_image.py` already compares application names across lock-v2, build metadata and build inventory, checks repository/ref identity, and compares runtime `apps/` directories and `sites/apps.txt` with the build metadata application list. M4.2.5.5 must preserve and strengthen these checks rather than create a second app resolver. The material gap is independent verification of capability selections, service/external inventories, descriptor bytes and the category boundary between Bench apps and independent artifacts.

**Manifest-version caveat:** the current resolver records explicit capability selections in `lock-v2.capabilities` for composition-manifest v2 (`manifest_version: "2.0.0"`). Legacy v1 manifests do not produce those lock selection records; a `capabilities` property present in a v1 file must not be interpreted as a selected capability. The independent verifier must treat the lock's explicit selection records as authoritative, verify their v2 source declarations, and fail closed on contradictory or unsupported version/selection combinations. It must not silently migrate v1 manifests or invent selection semantics in this package.

## 3. Authority and trust boundary

| Input | Authority / use |
|---|---|
| Generated lock-v2 exact bytes | Expected application, capability, container-service and external-requirement composition; its SHA-256 is the report's primary composition identity |
| Product and included manifest files | Source declarations for selected capabilities and composition; verify each loaded manifest against the checksum recorded in lock-v2 |
| Service descriptor files | Source of truth for service identity, kind, artifact/provider data and dependency declarations; verify exact bytes against `descriptor_sha256` |
| Build metadata and build inventory | Cross-check evidence only; neither may expand or redefine lock composition |
| Final runtime image | Actual Bench application directories and `sites/apps.txt`; independent observed application set |
| Existing source-provenance verification | M4.2.5.4 source trust result; not a substitute for composition inspection |

The verifier must not import the resolver's `compose_applications`, `compose_services` or lock-validation conclusions as its own evidence. It may reuse JSON Schema validation and low-level canonical serialization helpers only where doing so does not import resolver decisions.

## 4. Required verification

### 4.1 Exact Bench application composition

- Validate lock-v2 structure and exact-byte SHA-256.
- Require unique application names and valid application records.
- Independently derive the expected Bench application names from the lock and validate their source-manifest declarations/checksums.
- Compare the exact set with build metadata, `apps.json`, captured build inventory, final runtime `apps/` directories and `sites/apps.txt`.
- Reject missing, unexpected, duplicate or cross-category names.
- Preserve the existing distinction between requested refs, resolver-time refs and actual acquired source revisions already verified by M4.2.5.4.

### 4.2 Capability selection

- Validate every lock capability record: canonical manifest path, unique path, boolean `required` and `selected` values, and required capabilities selected.
- Reconcile capability records with the root product manifest's capability declarations and the exact loaded-manifest inventory.
- Verify manifest file SHA-256 values against `lock-v2.manifests`.
- Reject an unselected optional capability contributing applications, services or external requirements.
- Reject a selected capability whose manifest is missing, unlisted or checksum-mismatched.

### 4.3 Independent service and external-requirement composition

- Validate unique `service_id` values across both service categories.
- Re-read every referenced canonical service descriptor and verify its exact SHA-256 against the lock record.
- Verify descriptor identity, `service_kind`, artifact/provider fields and dependency declarations against the lock record.
- Require container services to carry a valid immutable OCI image reference with a SHA-256 digest; reject mutable tags.
- Require external requirements to carry provider identity and a non-empty requirement; reject container artifact fields on external records and provider fields on container records.
- Independently verify transitive dependency closure, category membership and topological resolution order; reject missing dependencies, cycles, duplicate IDs and container/external category substitution.

### 4.4 Bench/service separation

- Prove that only `lock-v2.applications` enter the Bench install input and runtime app inventory.
- Reject service IDs or external-requirement IDs in `apps.json`, build metadata applications, build inventory applications, runtime app directories or `sites/apps.txt`.
- Reject any application identity that collides with a service or external-requirement identity.
- Do not claim that this package builds or deploys independent service images. Service deployment and candidate orchestration remain outside M4.2.5.5.

### 4.5 Independent report

Emit a versioned `ndf-image-composition-verification-v1` report containing:

- verifier name/version and report schema version;
- lock-v2 SHA-256;
- manifest and service-descriptor path/checksum inventory;
- expected and observed Bench application names;
- capability selections and their validation results;
- container-service and external-requirement inventories;
- dependency-closure/order results;
- category-separation checks; and
- overall `passed` or `failed` status.

The report must bind to the exact lock-v2 bytes. Missing, malformed, ambiguous, unsupported, inconsistent or unverified inputs fail closed. It must not claim that separate service images were built or runtime-tested.

## 5. Acceptance checklist

| ID | Acceptance requirement |
|---|---|
| C5.1 | Exact lock-v2 application composition independently validated |
| C5.2 | Runtime app directories and `sites/apps.txt` exactly match the expected Bench app set |
| C5.3 | Manifest identities and checksums verified against lock-v2 |
| C5.4 | Required and optional capability selections independently verified |
| C5.5 | Container-service descriptors and immutable artifact image references verified |
| C5.6 | External-requirement descriptors and provider contracts verified |
| C5.7 | Service dependency closure, category membership and resolution order independently verified |
| C5.8 | Bench app/service/external identity separation enforced |
| C5.9 | Missing, unexpected, duplicate, cross-category and tampered composition rejected by negative fixtures |
| C5.10 | Versioned report validates against schema and binds to exact lock-v2 bytes |
| C5.11 | Focused tests and full NDF regression pass |
| C5.12 | Required real product Buildx evidence proves final-image composition inspection and report export |

## 6. Required positive and negative fixtures

Positive coverage:
1. Product with no optional capabilities, services or external requirements.
2. Product with one selected optional capability contributing Bench apps.
3. Product with an unselected optional capability that contributes nothing to the resolved composition.
4. Selected capability with one container service and a transitive service dependency.
5. Selected capability with one external requirement.
6. A valid composition where service and Bench application inventories are disjoint.

Negative coverage:
1. Missing or unexpected runtime Bench app; duplicate app names; `apps.txt` mismatch.
2. Service or external requirement leaked into `apps.json`, build inventory or runtime app directories.
3. App/service/external identity collision.
4. Missing, duplicate or unexpected capability selection; required capability marked unselected.
5. Manifest or service descriptor bytes changed without matching lock checksum.
6. Container service with mutable image tag or missing digest.
7. External requirement with missing provider or invalid service kind.
8. Missing, cyclic, duplicated or cross-category service dependencies.
9. Build metadata/inventory attempting to add or remove an application relative to lock-v2.
10. Missing, malformed, stale or lock-mismatched composition report.

## 7. Scope boundaries

Included: independent validation of application, capability, container-service and external-requirement composition; final runtime Bench application inspection; descriptor and manifest checksum verification; category separation; report schema; positive/adversarial tests; final-image inspection integration.

Excluded:
- Reimplementing manifest resolution or package resolution.
- Building or deploying independent service images.
- Changing the M4.2.3 composition/descriptor contracts without a separately justified amendment.
- Final verification-evidence/image-digest binding (M4.2.5.6).
- Candidate publication gating (M4.2.5.7).
- Product Deployment Descriptor generation (M4.2.6).

## 8. Implementation sequence

1. Inspect the lock-v2, selected manifest graph, service descriptor catalogue and current image inspection data contract.
2. Finalize the report schema and independent verifier interface.
3. Implement manifest/capability/service descriptor integrity checks without importing resolver conclusions.
4. Implement final-image app-set inspection and category-separation checks.
5. Add positive and adversarial fixtures for each acceptance dimension.
6. Integrate report extraction/export into `validate_image.py` and the manual product Buildx workflow.
7. Run focused tests, full NDF regression, `compileall` and `git diff --check`.
8. Run one representative product Buildx build when the new final-image inspection path is ready; expand to additional products only if the fixtures or composition variation justify it.
9. Record exact acceptance evidence before proceeding to M4.2.5.6.

## 9. CI execution policy

Product image Buildx runs are manual-only through `workflow_dispatch`. Do not restore push or pull-request triggers for the product build matrix. During routine commits, use focused tests and the local NDF regression suite. Run the NDF validation workflow when a remote CI signal is useful. Run a selected product Buildx image only when a real final-image acceptance condition requires it; use the all-products matrix only when broad product coverage is explicitly justified.
