## 1. Approved storage decision

The platform owner approved repository-tracked evidence in the NDF repository.

Canonical repository location:

```text
images/ndf/inventories/
└── debian-trixie-amd64/
    └── <runtime-platform-manifest-digest-without-sha256-prefix>/
        ├── inventory-manifest.json
        ├── builder/
        │   └── dpkg-inventory.tsv
        └── runtime/
            └── dpkg-inventory.tsv
```

The directory is keyed by the runtime platform-specific OCI manifest digest. The manifest records both builder and runtime identities and binds each inventory to its own exact platform-specific image digest. A changed builder or runtime digest requires a new capture and evidence directory; an existing capture must never be relabelled for a different digest.

Repository tracking is selected because it is reviewable, versioned, directly consumable by the resolver, and independent of GitHub Actions artifact-retention windows or new external storage infrastructure.

## 2. Authoritative producer and scope

`images/ndf/scripts/inspect_target_runtime.sh` remains the single authoritative producer. A.4 extends this producer; it does not introduce a parallel inventory producer. It delegates the dpkg capture operation to `images/ndf/scripts/capture_dpkg_inventory.sh`, which writes raw output to a temporary file, requires `docker run`/`dpkg-query` and deterministic sorting to succeed, validates the TSV record shape, and atomically replaces the destination only after all checks pass.

The producer continues to capture separate inventories from the exact selected images:

- `builder/dpkg-inventory.tsv`
- `runtime/dpkg-inventory.tsv`

Each TSV is deterministic, sorted under `LC_ALL=C`, and contains the native dpkg package identity, exact installed version and architecture. The structured manifest binds each TSV to its image identity and checksum.

This A.4 handoff covers the Debian native package database (`dpkg`) only. It does not claim that a dpkg inventory proves Python distribution or Node package presence. Python and Node base-package classification remains unsupported until ecosystem-native inventory evidence is separately specified and accepted.

## 3. Evidence manifest

The producer emits `inventory-manifest.json` with this versioned shape (illustrative values are placeholders):

```json
{
  "schema_version": "1.0.0",
  "producer": {
    "name": "images/ndf/scripts/inspect_target_runtime.sh",
    "version": "1"
  },
  "package_database": {
    "name": "dpkg",
    "format": "dpkg-query-tsv"
  },
  "inventories": {
    "builder": {
      "image": {
        "reference": "frappe/build@sha256:<platform-manifest-digest>",
        "index_digest": "sha256:<index-digest>",
        "manifest_digest": "sha256:<platform-manifest-digest>",
        "platform": "linux/amd64"
      },
      "package_database_version": "<exact-dpkg-version>",
      "file": "builder/dpkg-inventory.tsv",
      "sha256": "<64-lowercase-hex>",
      "package_count": 408
    },
    "runtime": {
      "image": {
        "reference": "frappe/base@sha256:<platform-manifest-digest>",
        "index_digest": "sha256:<index-digest>",
        "manifest_digest": "sha256:<platform-manifest-digest>",
        "platform": "linux/amd64"
      },
      "package_database_version": "<exact-dpkg-version>",
      "file": "runtime/dpkg-inventory.tsv",
      "sha256": "<64-lowercase-hex>",
      "package_count": 286
    }
  }
}
```

Requirements:

- The manifest schema version is independent of the composition lock version.
- Image references must be digest-pinned and the reference digest must equal `manifest_digest`.
- Both image records must identify the same OCI platform as the candidate target; builder and runtime digests remain independently bound.
- `sha256` is the SHA-256 of the exact TSV bytes committed to the repository.
- `package_count` is the number of valid package records, not an unverified summary value.
- Paths are normalized repository-relative POSIX paths, contained within the evidence directory, and cannot escape it.
- The validator recomputes checksums and package counts; it does not trust manifest declarations alone.
- The package database name, format and exact version are explicit.
- The manifest contains no timestamps, temporary paths, registry credentials, source URLs or other volatile/environment-sensitive data.
- The existing raw inspection bundle is not copied wholesale. In particular, runtime metadata and APT source files are not required for this package-presence handoff and must not be committed as a side effect.

## 4. Stage-aware inventory semantics

Builder and runtime inventories are separate evidence sets and must not be merged.

For native OS package records:

- `scope: "build"` is checked against the builder inventory.
- `scope: "runtime"` is checked against the runtime inventory.

The selected inventory must match the corresponding image's platform-specific digest and platform. An exact package name/version/architecture match is required. A package found only in the other stage does not satisfy the dependency.

The current accepted RT-01 comparison is evidence only for its exact digests: 286 runtime entries are also present in the builder at identical versions; the builder has 122 additional entries. This observed subset relationship is not a permanent assumption and must be recomputed for every new image digest.

The lock's existing `base_inventory` field must be refined into a stage-aware reference containing both inventory identities (builder and runtime), while retaining the single top-level `target_runtime` as the target authority. The exact lock field shape is defined in §10.0.6 of `M4.2.3-A-PACKAGE-RESOLUTION-CONTRACT.md`; A.5 fixtures must prove the representation and its validation. This document does not create a second lock or duplicate target identity.

## 5. Resolver and lock requirements

- A base OS package must resolve against the inventory selected by its normalized `scope`.
- The package identity must match native dpkg identity, exact version and architecture.
- A base package is recorded with `install: false`.
- A missing package, version mismatch, architecture mismatch, wrong stage, digest mismatch, invalid path, malformed TSV or checksum mismatch fails closed.
- The lock records a stable repository-relative evidence reference and the manifest/TSV checksums needed to retrieve and verify the evidence offline.
- Lock validation must not fetch live registries or regenerate inventory evidence.
- A changed inventory checksum or image digest is a package-resolution semantic change and must be visible in lock comparison.

The A.4 implementation must reconcile the exact lock representation with the accepted A.3 `package_resolution` structure before changing resolver behavior. No separate package lock is introduced.

## 6. M4.2.4 and M4.2.5 handoff

M4.2.4 consumes the accepted lock and its repository-tracked inventory evidence when constructing the candidate image. It must preserve the selected digest-pinned builder/runtime base images and capture actual build inputs and installed package results.

M4.2.5 verifies the resulting image against:

- The digest-bound base inventory selected for each stage.
- The build inventory and exact application/Frappe revisions acquired during the build.
- The package selections and installation decisions in the lock.
- The actual installed native package inventory in the produced image.

M4.2.4/M4.2.5 must use the same immutable evidence references carried by the lock. They must not independently infer base package presence from mutable tags or a fresh, unrelated inventory capture.

This handoff does not change rolling application branch acquisition semantics.

## 7. Sanitization and repository admission

Before any evidence is committed:

1. Inspect both TSVs and the generated manifest.
2. Confirm they contain only package identity, exact version and architecture, plus approved image/database provenance.
3. Reject credentials, credential-bearing URLs, private repository endpoints, temporary paths and unrelated raw runtime metadata.
4. Recompute SHA-256 values after sanitization; the manifest must describe the exact committed bytes.
5. Run the inventory validator against the repository-relative evidence directory.

Only the manifest and the two sanitized TSV inventories are admitted by this A.4 layout. The full local inspection directory remains local evidence unless a later, separately approved requirement calls for additional artifacts.

The accepted RT-01 capture can be finalized without pulling mutable upstream tags again by running the existing producer in evidence-finalization mode:

```bash
bash images/ndf/scripts/inspect_target_runtime.sh \
  --finalize-existing \
  --output-dir /path/to/rt01-amd64-20261110-verified
```

This mode reads the already captured immutable image references, platform metadata, dpkg TSVs and dpkg version from the existing runtime metadata. It does not contact Docker or resolve mutable tags again. It writes the structured manifest and refreshes the root checksum list. The final committed evidence must still be reviewed and sanitized before copying the two TSVs and manifest into the canonical repository layout.

## 11. Inventory capture failure-path hardening — 13 November 2026

The previous producer piped `dpkg-query` directly into `sort`. Because the container shell did not enable pipeline failure propagation, a failed query could theoretically leave partial output while `sort` returned success.

The producer now calls `scripts/capture_dpkg_inventory.sh`. The helper:

- Executes `dpkg-query` without a downstream pipeline.
- Captures output in a temporary file and checks the Docker command's exit status.
- Rejects empty or malformed TSV output.
- Sorts under `LC_ALL=C` into a second temporary file.
- Atomically publishes the final TSV only after all steps succeed.
- Removes temporary files on success or failure and preserves any existing destination if capture fails.

Two regression tests cover successful sorted publication and a simulated Docker/dpkg-query failure after partial output. The failure test also verifies that an existing inventory remains unchanged and temporary files are cleaned up.

The implementation is committed to the feature branch. The user-run focused helper tests passed (**2 passed in 0.07s**) and the full NDF suite passed (**215 passed in 7.54s**). No new Docker image build or upstream image pull was required for these tests.
